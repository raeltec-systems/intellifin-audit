# Story 21.3 consumer contract

The skills catalogue contains deliberate Admin installations, not arbitrary retrieved instructions. `application::skills::SkillsStore` separates Admin `catalog/assignment_options/status_history/install/set_status` from audit `selection_impact/discover/select/current_use`. Admin alone grants neither audit scope nor source access. Every browser-bound port requires its captured exact session; mutations additionally enforce actor, Origin and CSRF at HTTP admission.

HTTP surface: `GET /api/skills/organisations/{organisation_id}` reads `CatalogSnapshot`; `POST .../install` and `POST .../status` accept `InstallSkill` and `ChangeSkillStatus`, returning `CatalogReceipt`. Scoped `GET /api/engagements/{engagement_id}/tasks/{task_id}/skills` returns `Discovery`; `POST .../skills/select` accepts `SelectSkill`; `GET .../skills/selections/{selection_id}` performs current-use inspection. Scoped routes require `organisation_id` and `client_id` query fields. Selection responses use `SelectionView` (`selection` plus fresh `current`), never an execution result.

`Manifest` schema 1 records stable technique `id/version`, purpose, source reference/revision/license, inputs/outputs, exact method version IDs, conjunctive declared needs and inert text/script resources. `SkillVersion.id` is the immutable catalogue identity; manifest `id/version` is unique within the organisation. The infrastructure hashes the domain's versioned length-framed canonical UTF-8 encoding, and separately hashes every exact resource content. No trim, Unicode normalization, fetching, extraction, script launch or model call occurs. Installation metadata/structural validation do not establish independent content certification.

`SelectSkill` carries a durable logical key, exact catalogue version ID, reason, and expected catalogue/selection revisions, current method binding ID and Task execution epoch. Selection reads `TaskBasis.current`, never current assignments or `candidate_version_ids`. The immutable `Selection` retains actual `selector_id`, accepted `authority_actor_id` separately, exact version/digest, selected time/revision/reason, catalogue revision, entire current methodology `Binding`, current Task execution epoch and dependency fingerprint. The binding retains requirement field sources, historical template source IDs, neutral provenance and original producing epoch. Optional techniques cannot erase methodology or turn `suitable_skills` advice into obligatory invocation.

A `SelectionView` is the immutable historical selection plus fresh `Inspection`. Exact retry returns that original receipt even after disable/recall, alongside blocked current eligibility. A new expected-basis conflict changes nothing. Catalogue status changes, policy/authority changes and selection serialize on organisation advisory 205 then engagement/Task fences. Selection finishes staged/deferred writes before the final joint current method, viewer/session, accepted-actor and server-time fence; crossing a deadline rolls back the selection. A policy writer cannot overtake a staged selection holding organisation advisory 205, and logout cannot overtake its exact session row held FOR SHARE. Those contenders serialize: selection-first preserves the receipt, while later policy/session changes block fresh use/retry as appropriate; restriction-first refuses selection. These locks do not make a returned receipt a cached grant. Disable and terminal recall remain usable at capacity, do not alter consumed operations or receipts, and expose affected selections under current audit access.

`permissions::inspect_capability` performs a bounded projection over the same accepted/current structural, account, source and rule predicates as exact evaluation. Whole six-field tuple alternatives retain recipient/classification correlations; every hard and delegated layer intersects. Empty standing coverage is not denial. Missing acceptance/unreadable state/query exhaustion is unavailable; observed hard denial/revocation is forbidden. Explicitly naming another account is forbidden against the Task's single accepted account even if other needs fit or the projection budget has already depleted; full authority integrity and source checks retain precedence. Conclusive accepted/current account restrictions are assessed before bounded projection. `NeedInspection.blocking_bound` carries only the redacted accepted/current flag, policy kind and optional delegation depth; no policy subject, rule values or credentials cross this port. The inspector never searches other accounts or substitutes the viewer's member policy. Every required need must survive. Some compatible possibilities still need exact operation details, trusted material and current admission/decision/consumption.

The default API has no qualified operation or analysis adapter for skill use. Pure applicable techniques are selectable without operation acceptance. Otherwise compatible unqualified needs remain unavailable; proven hard denials remain forbidden. `SkillsRepository::with_qualification_source` is explicit server-only synthetic loopback configuration matching the owned gateway's exact source/ledger/endpoint-digest/contract binding. It is neither a browser flag nor a production registry. No selection creates an operation, decision, claim, wakeup or execution outcome.

`current_use` is a standalone fresh read transaction returning `SelectionView`, not an invocation capability or externally exposed transaction-local gate. It also checks Task controls. Future invocation must compose/recheck current technique eligibility within its own actual effect-admission/consumption boundary and pass real operations through existing gates. A returned inspection/receipt/fingerprint is never a bearer or cached grant. `observed_at` is server time; per-need `refresh_at` is an advisory deadline only, and revocation can invalidate earlier. Replacing the method/Task execution basis requires explicit reselection.

Limits: 128 installed versions and 2 MiB stored installation commands per organisation; 128 selections and 1 MiB stored receipt JSON per Task. Each selection includes the full binding, so large bindings lower practical history count. Schema 9 is an additive suffix; published migrations/catalogues 1–8 are byte-identical. Manifest limits: 32 inputs/outputs, 16 conjunctive needs, 32 exact method versions, 16 resources; each resource 32 KiB, all resources 128 KiB, canonical manifest 200,000 bytes. Per-need policy projection bounds 256 regions and 65,536 comparisons; each immutable scoped inspection shares 1,048,576 comparisons across all needs. Identical needs and version projections are memoized only within that Task/authority/time observation; historical selection method/epoch fences still run individually. Exhausted needs return unavailable with metadata/history retained. Direct exact-version selection/current-use has a fresh budget and assesses only that version. Status restriction and exact replay bypass admission capacity. Public revisions/epochs are canonical decimal strings; timestamps are bounded integer UTC seconds.

Skill JSON reads use a dedicated 8 MiB bound; ordinary JSON reads stay 4 MiB. Current inspection reasons are capped at 256 UTF-8 bytes. The conservative serialized envelope proof includes current status provenance at 2,000 four-byte Unicode scalars for every version, all redacted blocking bounds, 128 candidates plus 128 selection inspections, 16 needs per inspection, resource digests, and full stored command/receipt budgets with wrapper/numeric-string margins. It measures discovery 7,467,743 bytes, catalog 3,685,956 bytes, assignment page 144,773 bytes, history page 419,101 bytes and impact page 66,288 bytes. Assignment proof deliberately overcounts 50 clients plus 50 engagements although only one kind appears in an actual page. Delegation depth is zero-based 0..7 for at most 8 ancestors.

The repaired interfaces are bounded independently: `CatalogSnapshot` contains organisation, revision and versions only. Every `SkillVersion.status_event` records immutable event ID, actor ID, server time, event revision, status and exact optional reason (installation has no status-change reason). Admin `assignment_options` returns at most 50 clients or engagements, with `next_after`; engagement pages require one explicit client. `status_history` returns at most 50 events newest-first with `next_before_revision`. The Admin routes are `GET .../assignments?kind=client|engagement&client_id?&after?` and `GET .../versions/{version_id}/history?before_revision?`. Their failures or sizes cannot hide catalogue restriction controls, including when the separate Methodology catalogue fails.

`GET /api/engagements/{engagement_id}/skills/impacts` accepts the usual organisation/client scope plus optional `version_id`, `after_task_id` and `after_revision`. Audit `selection_impact` reads only the explicitly selected, currently authorised organisation/client/engagement. Text cursors and their SQL predicates, row/aggregate ordering and supporting indexes explicitly use byte/ASCII `COLLATE "C"`, matching the browser validation regardless of database locale. An optional version ID filters one visible version; omitting it locates selections whose current version is disabled/recalled. Pages contain at most 50 narrow historical selection references, exact version/digest/method binding/epoch/catalogue revision, selector/time, current status/revision and usable technique labels. Cursor is `(task_id, revision)`; there is no cross-engagement total. ConversationWorkspace opens the exact affected Task from this engagement-level list. Admin configuration and status receipts stay count-only and grant no audit access.

Skills draft custody is memory-only and exact actor/session/organisation/scope/Task owned. It retains unsent installation/edit/status/selection text and original expected basis through transient session verification failures and App unmount. Private content stays hidden until the same owner is freshly authorised. A retained Settings subtree also waits for its own new catalogue authorization after reactivation; an organisation page or failed Methodology read cannot authorize a cached skill editor. Intentional cancellation retains the actual hidden DOM separately from its disclosure eligibility. Denial, identity/session replacement, logout, cancellation and success discard it. Recovery never submits automatically. Custody is bounded to 16 audiences/8 MiB including submitted uncertain commands; admission checks the prospective total before mutation, preserves all existing recovery and rejects new custody with an actionable capacity message before transmission. State transitions must likewise retain the current editor when new custody refuses; empty entries are removed. Pause/Stop and existing exact receipt recovery remain available. This skills-specific repair does not fix or claim the separately deferred Story 21.2 methodology unsent-draft issue.
