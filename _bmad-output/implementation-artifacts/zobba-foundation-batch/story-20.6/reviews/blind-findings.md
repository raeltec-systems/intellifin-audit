- **B01 — Keep uncertain commands across a failed access refresh.** In `zobba/web/src/MembershipWorkspace.tsx:298-301`, any failed refresh changes the view to `unavailable`; the conditional rendering at lines 376-382 then unmounts `OrganisationEditor`/`InvitationAcceptance`, destroying the only copy of the uncertain command held by `useMembershipMutation` at lines 27-52. After an invitation POST commits but its response is lost, a subsequent failed periodic refresh or **Refresh access** permanently removes **Retry exact request**, even though the user stayed on the page. An acceptance has the same problem, and an issued invitation's secret cannot be recovered from storage. Preserve the account/session-bound recovery record outside the disposable view and hide it until access is verified. The isolated Chromium reproduction in `/tmp/zobba-review-20-6/blind-browser-evidence.mjs` observed one submitted command followed by zero retry buttons after recovery.

- **B02 — Treat same-actor session rotation as an audience change.** `zobba/web/src/MembershipWorkspace.tsx:274-277` clears private state only when the actor ID changes, and the editor keys at lines 381-382 likewise omit the session identity. If another tab signs the same person in again, a refresh replaces `session.csrf_token` while retaining the original invitation draft, private link and uncertain action; `useMembershipMutation` then submits retained work with the new session. This misses the specification's replaced-session/no-old-draft case. Bind protected state and component generations to both actor and exact session, or require explicit recovery before rebinding an uncertain command. Isolated Chromium confirmed a pre-rotation email draft remained visible and was POSTed using the replacement CSRF token.

- **B03 — Capture and scrub invitation fragments on same-document navigation.** `zobba/web/src/MembershipWorkspace.tsx:10-12` reads the secret only once at module initialization, and the listeners installed at lines 304-317 do not handle `hashchange`. Starting on `/invitation`, navigating to a second `/invitation#invitation=...` link is a same-document navigation: the new secret remains in the address bar/history and the form continues to display and accept the first invitation. Handle each incoming fragment by immediately scrubbing it, cancelling the previous preview, and resetting the secret-bound acceptance state. Isolated Chromium showed the second fragment still present and only the first secret ever sent for preview.

- **B04 — Preserve an unchanged assignment's expiry during an ordinary membership Save.** `zobba/migrations/0005_membership_administration.sql:185-187` first disables every assignment and then unconditionally sets `expires_at=NULL` for every selected assignment. The projection at line 99 omits assignment expiry, so an Admin editing only a role cannot see that this also converts every still-valid temporary assignment into permanent access. An assignment due to expire tomorrow therefore survives indefinitely after a role-only Save. Carry assignment validity through the command, or retain the existing expiry for unchanged assignments and make renewal a separate explicit change; cover future, rather than only already-expired, assignments.

- **B05 — Align membership-expiry validation with the browser's supported range.** `zobba/crates/application/src/membership.rs:158` accepts every positive `i64`, and the SQL update stores it, while `zobba/web/src/membership.ts:44-46` rejects values above `253402300799`. A valid authenticated Save with `expires_at=253402300800` therefore succeeds but makes the entire containing membership page fail parsing and appear as a connection interruption on subsequent reads. Use the same bounded timestamp contract in the application, database and generated API, and check the boundary through Save followed by snapshot parsing.

- **B06 — Provide a way to renew an expired membership and show its effective status.** `zobba/web/src/MembershipWorkspace.tsx:107-113` offers only an Active checkbox and a read-only expiry label; line 180 always resubmits the original expiry. For an existing expired member, checking Active and saving reports success while access remains expired, and the list at line 172 labels the member “Active” solely from the stored Boolean. Admin cannot repair this state through the delivered administration UI, and a new invitation is intentionally refused for any existing member. Add explicit expiry extension/clearing controls and an expired status that reflects the same time predicate used by authorization.

- **B07 — Preserve administration access for valid schema-4 memberships with over 100 assignments.** `zobba/migrations/0005_membership_administration.sql:97-101` raises `membership_capacity` for the whole snapshot when any of the first 51 members has 101 assignments. Schema 4 allows that state; migration 5 neither migrates it nor provides a separately paged assignment read. Thus upgrading a valid existing organisation can make its entire first membership page unusable, even when the oversized member is only the look-ahead row, leaving no UI route to narrow or deactivate it. Supply bounded assignment pagination or an explicit repair projection for legacy rows, and test a populated 4→5 upgrade with 101 assignments.

- **B08 — Handle malformed optional recipient-claim types without rejecting ordinary sign-in.** The new email-scope request in `zobba/crates/infrastructure/src/oidc.rs:331-335` feeds the typed `CoreIdToken` decoding at lines 375-381; the `None` fallback at lines 468-472 is reached only after that decoding succeeds. A signed token with `email:123` or `email_verified:"true"` is rejected by the locked `openidconnect` standard-claim deserializer before the code can withhold recipient proof. This contradicts the documented ordinary-sign-in fallback for invalid email claims. Verify the signed identity while treating malformed optional recipient evidence as absent, preserving strict checks on required identity/signature claims. The local dependency reproduction `/tmp/zobba-review-20-6/blind-optional-claims.rs` confirmed both malformed cases fail deserialization; the new fixture tests cover only a syntactically invalid string address.

- **B09 — Move keyboard focus to a useful destination when a successful Save closes its form.** `zobba/web/src/MembershipWorkspace.tsx:161` unmounts the focused editor after success, while the restoration logic at lines 321-325 only handles an element that remains connected and supplies no fallback. After creating an invitation or saving a member, focus falls to `BODY`; the next Tab starts again at the page navigation instead of the new private link or saved member. Set a deliberate focus target for each completed action and exercise keyboard-only completion. Isolated Chromium confirmed `document.activeElement.tagName === 'BODY'` after invitation creation.

- **B10 — Distinguish unavailable invitation previews from recipient refusals.** The catch at `zobba/web/src/MembershipWorkspace.tsx:215-218` converts every preview failure, including HTTP 429/503, an aborted eight-second request and malformed responses, into `preview.kind='refused'`. Lines 228-229 then tell a correctly signed-in recipient the invitation is unavailable to their verified account and may be expired/revoked. An ordinary transient outage is therefore presented as an authority problem, with fresh sign-in suggested even though it cannot help. Add an unavailable/retry state and reserve the recipient-refusal copy for an actual authorization refusal; include unavailable and timeout browser cases.

- **B11 — Bound organisation-list work by the actor's memberships rather than all tenants.** `zobba/migrations/0005_membership_administration.sql:89-90` starts from all organisations and invokes the volatile `membership_admin(actor,o.id)` helper once per candidate before satisfying `LIMIT 51`. For an ordinary user with no Admin role, or an Admin of only one late-sorting organisation, the request scans the tenant catalogue despite returning an empty or one-row page. As tenants grow, unrelated organisations determine this endpoint's latency and can exhaust the four-request/six-second membership lane. Start from an indexed actor membership lookup, join eligible organisations, and verify the query plan for an actor with sparse/no Admin memberships.

- **B12 — Publish the membership vocabulary and bounds in the generated contract.** `zobba/crates/api/src/membership.rs:241-268` exposes roles, keys, versions, recipient addresses and secrets mostly as unrestricted strings; the response declarations at lines 182-236 similarly omit role/status/kind enums and the 50-row page bounds. Consequently generated clients accept values such as `roles:["owner"]`, noncanonical versions or invalid identifiers even though the owned validators reject them, and the web client must manually replace generated role/status types in `web/src/membership.ts:5-15`. Add shared schema vocabulary, identifier/version patterns, email/secret limits and bounded-page annotations so the generated OpenAPI/types describe the actual accepted contract, including invalid-request examples.
