## Remaining finding

**R1 — Expiry can cross between fence selection and authority renewal.** The implementation evaluates expiry at multiple separate wall-clock instants within one Save:

1. `zobba/migrations/0005_membership_administration.sql:153` selects an assignment for expiry fencing only when its finite deadline has already passed. For an active retained scope with `renew:true` and a future deadline, with unchanged roles/membership, none of the other predicates selects that scope.
2. After `membership_fence` returns, `:239` evaluates `clock_timestamp()` again. If the deadline passed between those evaluations, `renew:true` now clears the deadline to NULL. The scope becomes usable indefinitely, but its old Task epoch, admitted claim and delegated authority were not fenced.

This is a permitted input: `zobba/crates/infrastructure/tests/membership/legacy_upgrade.rs:285–296` explicitly sends `renew:true` for a still-future grant, and the API contract accepts it. The newly added test expires the grant **before** Save starts, so it cannot catch expiry **inside** Save. A scheduling delay, or time spent processing other affected scopes inside `membership_fence`, is sufficient; no concurrent membership edit or version mismatch is required. After the Save commits, current-scope checks see the restored assignment, and `TaskRepository::consume` (`zobba/crates/infrastructure/src/task.rs:593–609`) can still see the unchanged old basis and admitted claim.

There is the same split for organisation membership: `:229` sets `narrow` using the old membership expiry before `membership_fence` runs. When an active finite membership is explicitly extended or made unlimited, `narrow` is false if its old expiry is still future (and roles are unchanged). If that deadline passes before `:231` writes the extension, the membership is restored without fencing all of its scopes. The new expiry need only be NULL or later than the old deadline; ordinary unchanged-expiry saves do not cause this analogue.

**Evidence and limits:** `final-blind-clock-predicate.sql` runs only a `BEGIN READ ONLY` / SELECT / ROLLBACK in the maintenance `postgres` database. Using the same expiry comparisons with a controlled 1.2-second gap, PostgreSQL returned `{"selected_for_expiry_fence":false,"renew_true_clears_expiry":true}` (`final-blind-clock-predicate.txt`). This demonstrates the predicate split; I did not mutate fixtures or claim an end-to-end durable-claim reproduction. The source ordering above establishes the unfenced update path. The lead should add a guarded integration regression that forces expiry between classification and write while an old Task claim/delegation exists.

**Recommended minimal repair:** Conservatively fence an explicitly renewed existing assignment with a finite expiry, even when that expiry is still future at fence selection. Likewise, set the all-scopes fence when an existing finite organisation membership is explicitly widened (new expiry is NULL or later than the previous expiry), as well as under the current narrowing/revoked/expired conditions. This keeps existing entrypoint signatures and fresh post-wait authority checks. Retained `renew:false` assignments and unchanged membership expiry remain ordinary edits; unrelated scopes remain unaffected by a scope-specific renewal. An explicit attempt to renew a future finite grant may pause that scope's old execution even when the deadline itself is preserved: document and test that conservative behaviour. Do not substitute `statement_timestamp()` for fresh checks, since it predates lock waits.
