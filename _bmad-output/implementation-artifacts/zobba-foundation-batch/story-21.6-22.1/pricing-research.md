# Story 22.1 qualification: public model, compatibility, and pricing research

Research completed 3 October 2026 UTC. This is evidence for an **unapproved proposal**, not an approval, entitlement check, paid qualification, or production profile registration. Only public documentation HTTPS GETs were performed; TLS verification stayed enabled through the existing proxy/CA configuration. No model API, token-counting API, credential value, secret file, Cargo command, browser, or repository mutation was used.

## Decision

**The accepted-budget identifiers are real, documented API model IDs, but neither fits this adapter's current non-reasoning qualification. A defensible total below USD 1 is not established by the 16 KiB body cap and published rates alone. Instead, recommend an explicitly approved USD 20 API-token envelope before taxes for the compatible candidates, using their full documented context capacities as the conservative input allowance.**

For a separately approved qualification of the existing text/tool adapter, the documented compatible candidates are **`gpt-4.1-2025-04-14` and `claude-sonnet-4-6`**. The parent requested candidate research after the reasoning incompatibility was found. This recommendation authorizes no substitution or call. It qualifies only those candidates if the owner later approves them and the complete cost/entitlement prerequisites are met.

## What is and is not bounded

The limit of three attempts per provider, one concurrent request, no retries, and a durable one-shot approval bounds potentially billable attempts only if the complete dispatch stack observes it. Count errors, timeouts, and interrupted or unknown responses as full reserved attempts. A local 60-second timeout is not a provider billing limit or proof that generation stopped.

**Output is documentable.** OpenAI's [token-counting guide](https://developers.openai.com/api/docs/guides/token-counting) says `max_output_tokens` limits all generated tokens, including non-visible tokens; visible text and `reasoning_tokens` alone are insufficient. Anthropic's [Messages reference](https://platform.claude.com/docs/en/api/messages/create) calls `max_tokens` an absolute generated-token maximum; its [thinking guide](https://platform.claude.com/docs/en/build-with-claude/thinking) says it is strict and includes current-turn thinking. Thus the intended 1,024 cap can bound all generated tokens when the actual endpoint accepts and applies that request, not just visible text. This does not cure unsupported reasoning shapes.

**Input remains unproven.** A 16,384-byte serialized JSON body is neither a provider-certified 4,096-token nor a 16,384-token input bound. Complete billing inputs include request formatting, message boundaries, tool schema serialization and history. No retrieved official source supplies a universal byte-to-total-billed-token upper bound for these complete bodies.

- OpenAI's counting guide describes `POST /v1/responses/input_tokens` as returning the **exact** count the model will receive, including formatting tokens, tools and schemas. Local text tokenizers alone do not account for all that structure. No count request was made, and pricing/authorization for an added endpoint would need review.
- Anthropic's [token-counting guide](https://platform.claude.com/docs/en/build-with-claude/token-counting) says token counting is free, supports structured messages and tools, but the count is an **estimate** and actual message input can differ by a “small amount.” It does not publish a numeric worst-case error allowance. It also says system-optimization tokens may appear in counts without being billed. This caveat does not erase separately priced tool-system overhead.
- Anthropic's [tool-use pricing](https://platform.claude.com/docs/en/about-claude/pricing#tool-use-pricing) specifies Sonnet 4.6 tool-system overhead of **497 tokens for auto/none**, or **589 for any/tool**, when tools are supplied. This is in addition to tool definitions and tool exchange content. With no tools, `none` adds zero. For the current tool-proposal and continuation phases, include the applicable overhead in each complete input count. Avoid adding it twice if a verified full count already includes it. Opus 5.5's documented auto/none tool overhead is 286; that does not solve its capability mismatch.
- The continuation includes a provider-generated call ID. A cost proof must cover every allowed substitution (or count the eventual complete continuation before sending), rather than only the placeholder preview.

The full context limits give far looser input allowances whose costs exceed USD 1. They do support a larger, reviewable USD 20 proposal without assuming a byte-to-token ratio or adding token-count API calls; see the recommended calculation below.

## Conditional arithmetic, not a current spend proof

For the compatible candidate pair, under verified Standard/global prices, no paid hosted tools, no cache writes, and 3 × 1,024 generated tokens at each provider:

`C_max = (2 × sum(OpenAI billed input tokens) + 3 × sum(Anthropic billed input tokens)) / 1,000,000 + USD 0.070656`

For example, **if independently established** complete billed input were at most 32,768 tokens for every request, the six-request ceiling would be **USD 0.562176**. This is a useful proposed admission threshold, **not** a bound derived from the existing body-byte limit. The unknown input bound must not be replaced by that example number in the approval.

Published Standard prices also require account/request evidence. At the read-only inspection, the builder omitted service-tier and inference-geography controls. Anthropic's Messages reference says omitted `inference_geo` inherits the workspace default and `service_tier` can select priority capacity. OpenAI publishes different Fast rates (GPT-4.1 $3.50/$14). Explicit Standard transport settings below remove this default-tier ambiguity. Reconcile any negotiated tariffs separately.

## Conservative full-context envelope — recommended proposal

Use the published maximum context/input capacity for **every** attempt, including failed or unknown attempts, plus the full 1,024-token output reservation. Do not subtract output space from the input allowance; that deliberately over-reserves. Complete input includes formatting, tool-system overhead, schema and portable continuation history, so do not add those again on top of a full context allowance. The model rejects input beyond its supported context: OpenAI's Responses reference specifies a 400 error with the default disabled truncation; Anthropic's thinking/context documentation specifies validation errors when input plus `max_tokens` exceeds context on Claude 4.5 and later.

| Provider/profile | Input allowance per attempt | Highest applicable Standard input/output tariff used | Three-attempt reservation |
| --- | ---: | --- | ---: |
| OpenAI `gpt-4.1-2025-04-14` | 1,047,576 tokens, the documented context capacity | $2 / $8 per MTok | `3 × (1,047,576 × 2 + 1,024 × 8) / 1,000,000` = **$6.310032** |
| Anthropic `claude-sonnet-4-6` | 1,048,576 tokens, conservatively rounding the documented 1M **up** to cover either decimal or binary interpretation | $3 / $15 per MTok, multiplied by **1.1** to include the published US-only geography premium even if global is actually used | `3 × (1,048,576 × 3 + 1,024 × 15) × 1.1 / 1,000,000` = **$10.4315904** |
| Combined | All six permitted attempts | Standard, no paid hosted tools or explicit cache writes | **$16.7416224** |

**Recommend USD 20 as the proposed maximum authorization for API-token usage before taxes.** This leaves about $3.25 above the full-context reservation. It preserves the smaller 16 KiB reviewed-body limit; it does not permit larger payloads, extra requests, retries, tools, subscriptions, deposits or model substitution. It is a conservative modeled usage envelope, not a promise about the providers' invoice or an account-wide spending limit. No token-count API or strict dashboard hard-limit claim is required for this calculation.

**Long-context pricing was checked explicitly.** OpenAI's model page gives one GPT-4.1 Standard token rate for its full 1,047,576-token window; its current Standard pricing row has no separate long-context premium. The >272K doubling applies to models with corresponding long-context rates, including Sol, and must not be imposed on GPT-4.1 by analogy. Anthropic's pricing page states: **“Claude 4.6 and later models and Claude Mythos Preview include the full 1M token context window at standard pricing. (A 900k-token request is billed at the same per-token rate as a 9k-token request.)”** Hence older Sonnet long-context premiums do not apply to Sonnet 4.6. The Anthropic 1.1× geography multiplier is already reserved above. OpenAI's published 10% regional-processing uplift applies to models released on/after 5 March 2026; GPT-4.1's 14 April 2025 snapshot predates that rule, and the proposed global `api.openai.com` endpoint is not a FedRAMP endpoint.

**Expected usage is much smaller, but unmeasured.** For planning only, 4,096 complete input tokens per request and the full 1,024 output cap would cost $0.132096 at global Standard rates, or $0.1403904 with the Anthropic US premium. A rough $0.10–$0.20 pre-tax expectation is reasonable for short synthetic probes, but no actual token count or invoice supports it yet. This illustration is not derived from the 16 KiB limit and is not the authorization ceiling.

**Taxes are explicitly excluded from this USD 20 API-token proposal.** [OpenAI Services Agreement §6.3](https://openai.com/policies/services-agreement/) says “Fees are exclusive of taxes,” charged according to applicable law and account billing details. [Anthropic Commercial Terms §H.2](https://www.anthropic.com/legal/commercial-terms) says fees do not include taxes, duties or assessments unless the applicable invoice specifies otherwise. Account jurisdiction, exemptions, exchange/payment fees and negotiated terms were not inspected. If the owner requires an all-in invoice ceiling, that account-specific evidence must be incorporated before approval; do not describe this pre-tax calculation as an invoice guarantee.

## Exact Standard transport settings and response evidence

- **OpenAI Responses request:** `"service_tier": "default"`. The [Responses create reference](https://developers.openai.com/api/reference/resources/responses/methods/create) says: **“If set to ‘default’, then the request will be processed with the standard pricing and performance for the selected model.”** Omission defaults to `auto`, which inherits project settings. The reference also says setting the parameter makes the response body include the service tier **actually used**, which can differ from the requested value. Record the response's `service_tier`; the expected Standard value is `default`. A different/missing value prevents claiming observed Standard processing and should stop further qualification sends while preserving the charge reservation.
- **Anthropic Messages request:** `"service_tier": "standard_only"`. The [service-tier guide](https://platform.claude.com/docs/en/api/service-tiers) says: **“Only use standard tier capacity, useful if you don't want to use your Priority Tier capacity.”** Default `auto` can consume Priority capacity. The guide says the response **`usage.service_tier`** reports the assigned tier; the [Messages reference](https://platform.claude.com/docs/en/api/messages/create) includes the `standard` response value. Record and expect `standard`; a different/missing value prevents claiming observed Standard processing and should stop further qualification sends while preserving the reservation.

These are documented fixed transport parameters, not account-setting requests. The parent may incorporate them and appropriate existing-wire verification before presenting the manifest. The calculation above depends on those explicit settings (or equivalent proven Standard processing). With OpenAI Fast instead, the full-context combined total including Anthropic US would be **$21.4741464**, so an `auto` assumption is not enough for the proposed USD 20 envelope.

## Required owner/account evidence before any paid qualification

1. Explicit approval of the compatible candidate IDs, or deferral until the accepted-budget IDs' reasoning support exists. Do not silently replace approved models. Record the requested and actual returned model versions.
2. Nonproduction OpenAI project and Anthropic workspace bindings mapped to the intended keys, with exact model/endpoint entitlement. Public model availability is insufficient. Keys belong in secure environment settings; no secret values in the evidence.
3. A dated tariff record for the applicable service tier, geography, cache behavior and account terms, with a reservation calculation for **all** potentially billable attempts and applicable fees.
4. Review the **USD 20 pre-tax full-context reservation**, exact native request bodies with the Standard service-tier fields, maximum six attempts, and the original synthetic-only payload/output limits. This path needs no extra count API. If the owner instead insists on USD 1, provider-supported smaller complete-input bounds covering every initial body and allowed continuation substitution remain necessary; Anthropic token-count estimates alone publish no numeric worst-case error bound.
5. Do not represent a dashboard budget as enforcement of this envelope. [OpenAI now documents hard limits](https://developers.openai.com/api/docs/guides/spend-limits), but explicitly says enforcement is not instantaneous and recorded spend can exceed the configured amount; it gives no numeric overshoot maximum. Anthropic's [rate/spend-limit documentation](https://platform.claude.com/docs/en/api/rate-limits) documents rejecting requests at a user-set spend limit, but the reviewed material does not establish an in-flight overshoot allowance for a strict combined USD 1 bound. Merely setting the two displayed limits to sum to USD 1 is insufficient. Such an account-wide hard-limit guarantee is unnecessary for the larger documented per-attempt reservation proposed here.

The remaining decision is approval of the compatible profiles and the **larger pre-tax envelope**, with Standard-tier native requests made concrete and locally verified first. It is not a missing-model finding and does not require asking for nonexistent strict account enforcement. No approval request should claim a strict USD 1 guarantee or an all-in invoice guarantee.
