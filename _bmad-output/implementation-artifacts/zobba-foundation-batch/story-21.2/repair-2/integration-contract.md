# Story 21.2 consumer contract — implementation handoff

This records implemented source contracts for later 21.3/21.4 consumers; those consumers are not implemented here. Final gate results are recorded separately.

- `application::methodology::MethodologyStore::task_basis` is the current scoped audit inspection boundary. Admin configuration snapshots are a separate boundary and grant no client-work access. Every HTTP read is exact-session fenced; every mutation additionally checks captured actor, Origin and CSRF.
- `TaskBasis.current` is an immutable exact binding, not the current catalogue. Its `resolution` carries resolved context, status, exact `version_ids`, stable requirement IDs, `mandatory` standing, each field's source version IDs, exact template ID/version/content, issues and reason. Its separate `candidate_version_ids` retains the eligible immutable pool, including Missing/Outside policies, for later context discovery. Requirements inherited as mandatory cannot be removed by a narrower assignment. `None` inherits; explicit empty optional values clear their field. Missing or ambiguous criteria do not claim satisfaction and should block only dependent conclusions.
- Availability is an integer UTC timestamp; applicability is a separate inclusive business date interval plus optional area. Default context comes from unconditional scoped assignments. Explicit Create context wins and participates in exact retry meaning. Attributed Guide commands can explicitly replace full context at the same safe boundary; omission leaves it unchanged. Exact retry and conversation echo include Guide context. Initially resolved context is retained through subsequent default changes; newly resolved previously missing context is frozen when a change is applied. Same-rank conflicts and straddled periods are explicit issues, never resolved by latest Save.
- A Task binding's `execution_epoch` is its database-assigned effective-from epoch. Resolve recorded work by the greatest binding epoch not after its immutable producing epoch. `infrastructure::methodology::binding_at_execution_epoch` is the owned resolver. Existing operation inspection and cursor-paginated attempt history expose `execution_epoch` and `methodology_binding_id`; they retain original association after Task controls, rebinding and recall. Binding `context_command_id` retains the exact Guide command that supplied context, including after pending state clears and later active Saves. This reveals no receipt capability. Historical pre-methodology work maps to the labelled neutral epoch-zero binding. Do not infer method association from timestamps or current catalogue state.
- New-only Saves preserve existing bindings and generate retained-work notices. Active changes and Guide context resolution start with the Task's pinned candidate pool and add only explicit due active changes; intervening new-only versions never leak into that set. Recursive successor ancestry retires superseded assignments. A scheduled active Save persists a coordinator wakeup and becomes due without another Save, including for Tasks created between Save and activation and stopped Tasks continued before the cutoff. Continue uses the same bounded enrollment function as creation; it does not retroactively adopt missed activations or new-only Saves. Resolution and acknowledgement use the same captured cutoff, leaving later events pending with their durable wakeup.
- Pending due changes fence unused claims and new operation admission/dispatch. Consumed `current()` and receipt-only `observe()` retain original-basis rights. The owned coordinator reconciles consumed inert/external facts before applying and advancing the method binding plus Task epoch atomically. Pause and Stop persist. Both inert claim consumption and external operation dispatch finish staged/deferred database work before their final current-use cutoff check; crossing a due cutoff rolls back new consumption and receipt capability together. Recall is an overlay preventing affected new use; it does not rewrite old bindings or consumed outcomes and remains usable at configuration capacity.
- Saved versions, assignment/source/diff/impact records and receipts are immutable. Revision is organisation-wide. Exact actor/scope/key/meaning replay returns the same receipt; changed meaning conflicts. Undo is a new attributed successor. Template `(id, version)` content is immutable within an organisation. Historical template content resolves through separately scoped, available immutable sources even after a successor removes the predecessor from requirement candidates. Its exact source is the earliest scoped available declaration; source recall follows the content and cannot be bypassed by an identical redeclaration. Historical template lookup does not import predecessor criteria or defaults. `resolution.version_ids` names selected assignment candidates, not the exhaustive content dependency set: future consumers must also retain per-field sources and every `templates[*].source_version_id`, which can be absent from both selected and pinned candidate IDs. Imported sources remain proposals until ordinary Admin Save. The editor follows explicit `supersedes` ancestry for Edit, Undo and revision recovery; matching assignment or date fields never establishes lineage.
- `resolution.neutral_source_version_ids` identifies neutral contributors (up to 128 saved sources plus the builtin starter). Join it to each requirement field's `field_sources` and template `source_version_id`. Empty/default-only overrides cannot relabel inherited neutral criteria. Mixed neutral/adopted content retains ordinary completeness rules and carries qualified reason/UI wording; it does not claim that all criteria are adopted.
- Public revisions and epochs are canonical decimal strings. Availability, binding and Save timestamps are bounded JSON integer UTC seconds (0..253402300799). Stable IDs use the existing bounded ASCII contract. Text/labels count Unicode scalar values, including accepted U+FEFF; template prose preserves exact multiline layout. Limits: 100 requirements, 32 values per field, 32 templates/sections, 200-scalar labels, 2,000-scalar text, 200,000 definition bytes, 128 saved versions and 512 KiB saved commands per organisation; Task binding history reserves at most 1 MiB. Complete bounded binding history is inspectable; operation/attempt lists retain their existing honest cursors.
- Schema 8 adds only new storage plus optional command context. Migration/catalogue prefix 1–7 is unchanged. New methodology tables have forced RLS and owner-mediated functions; runtime has no direct new table grant. Configuration and Task admission share organisation advisory 205 then ordered engagement/Task locks, followed by exact-session and current-authority checks.

Future assessment/review consumers must use the exact Task/operation binding and stable requirement IDs. Impact/notices provide change facts, not automatic draft recomputation, acceptance, sign-off or issued-history rewriting. No evaluation/model claims are made by this story.

Capacity admission is deliberately conservative: every pending future binding reserves 4,096 bytes plus 16 times the organisation's aggregate saved configuration bytes, including a pending Guide when accepting an active Save. This can refuse configuration/context changes before actual history reaches its 1 MiB storage ceiling. Exact replay, recall, original receipt recovery and ordinary context-free guidance remain available. A real near-capacity neutral-history regression proves atomic Guide refusal with no coordinator retry trap.

Concrete reservation limit: above 65,280 aggregate saved-configuration bytes, one pending binding reserves more than 1 MiB even with no prior binding history; existing history and queued changes lower this threshold. The 512 KiB saved-command/catalogue ceiling is separate and does not promise active-rebinding capacity.

P16 changes no wire/domain/storage contract. Consumer inspection panels must relinquish request ownership before intentionally aborting a read, retain hidden same-owner DOM through authority/projection revalidation and tab-away, and preserve exact-owner/session withdrawal. A genuinely current failed read or deadline still withdraws stale basis content. The browser regression verifies the same marked inner disclosure, its open state and restored focus; retaining only an outer panel is insufficient.
