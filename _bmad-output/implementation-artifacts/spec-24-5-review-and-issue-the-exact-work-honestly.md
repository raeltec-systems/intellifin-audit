## Intent

**Problem:** After 24.4 every work-product version is a checked, immutable draft, but nothing records who checked it. Every shelf row, API response and export says "Draft — not reviewed" (`REVIEW_STATE`, `domain/src/work_product.rs:74`; `ExportView::review`, `export.rs:218`). There is no way to submit a version for team review, to approve the exact version and its support, to self-review honestly when the firm allows solo practice, to return work for changes, or to issue it to named recipients, and nothing stops a person who prepared the work from "independently" reviewing it. The method's review rules are free text (`Requirement.review_rules`, `methodology.rs:170`), so the platform cannot know whether solo review is allowed.

**Approach:** People review and issue; the agent never does. A person who submits a version accepts responsibility for it (agent-prepared content included) and becomes its preparer. Trusted code builds a **review package** that binds the exact version and a **manifest** of everything it rests on (records, effective dispositions, exception statuses, summaries, quoted originals, method binding). An eligible assigned Audit manager outside the version's contributor set **reviews and approves** it (team), or, only where the bound method permits solo practice, the preparer **self-reviews and approves** it, always labelled "Self-reviewed by <name>; no independent review." **Issue** is a separate action that binds the approved package, recipients and the exact export bytes; issued records never change, and a correction is a linked successor issue with a reason and the changed claims. Every state is derived on read from immutable records; the database rechecks authority (in the person's own session), independence, manifest agreement and staleness, so a worker connection can never sign off. The agent sees review state and a reviewer's notes in its context and addresses them natively by drafting successor versions.

## Boundaries & Constraints

**Always:**
- **Review mode is typed method configuration (owner decision 2 pending).** `Requirement` gains optional `review_mode: independent_review | solo_permitted` (absent = inherit; omitted from serialised documents when absent so old methodology versions and bindings keep their bytes). Merge: a mandatory inherited `independent_review` is kept against a narrower `solo_permitted` (the method cannot be relaxed); otherwise the narrower value replaces it. A binding's **effective mode** is `solo_permitted` only when at least one resolved requirement says `solo_permitted` and none says `independent_review`; otherwise (including neutral bindings and every binding recorded before 0025) `independent_review`. Admin sets it through the existing ordinary methodology Save (no approval ceremony); document proposals (22.6) never propose it. Shown in Task methodology, the agent's method outline and the review panel.
- **Authority.** Prepare and submit: a currently assigned Auditor or Audit manager. Review, approve, self-review and issue: a current `audit_manager` role plus a current assignment on the engagement (Admin alone never; an Auditor alone never). Every write runs under `task::lock` (organisation advisory 205, then engagement), `admission_fence` with the exact session, and the SQL guard (`knowledge_audit` + `audit_manager` + `evidence_session_locked` on `zobba.session_hash`, set only for the write). A replayed request key is answered only after the same fence; a revoked person's replay is 403.
- **Contributors** (pure `domain::review::contributors`, recomputed in SQL): for version v, every person who (1) authored a human block present in v, (2) authored any human version of v's lineage (v and all predecessors), (3) confirmed an agent change of their blocks in the lineage (24.4 `change_request.requested_by`), or (4) accepted responsibility by submitting or self-reviewing any package of a version in the lineage. Each with its closed contribution kinds (`edited_block`, `authored_version`, `requested_change`, `accepted_responsibility`). The agent is listed as "Zobba (agent)" and is never an independent reviewer. Guide direction and review notes are not contributions (owner decision 3 pending).
- **Review package** (new `work_product_reviews`, immutable): Task, product, version ID + version digest, binding ID, effective review mode of that binding, `mode team|solo`, submitter, session-bound key (idempotent per actor), contributors with kinds (≤64), manifest lines + digest, labels (frozen display names), database time. Submission requires: the version is the product's head under the per-product lock (`work_product:` advisory key shared with version writers); the version is of rule `statement_figures_v2` (frozen snapshot); `missing_required` is empty; every claim and platform block is current (24.4 currency); the version's binding is the Task's current binding; no undecided package for that version; the version has no approval; the submitter's withheld set is empty.
- **Manifest** (rule `review_manifest_v1`): C-sorted lines `kind|id|digest[|extra]` for the version, its binding and template source version, every assertion's record (outcome adds `head|<chain head>` and `disposition|<newest disposition ID or none>`; exception adds its derived status and newest exception-disposition `seq`), every coverage/exceptions block's record, every quoted original's digest. Digest = SHA-256 of the lines joined by `\n`, computed identically in Rust and SQL (like `work_product_exception_digest`). The guard rebuilds the lines from rows and refuses any other set.
- **Decisions** (new `work_product_review_decisions`, one per package, immutable): `approved` (team), `self_approved` (solo), `changes_requested{notes 1–16: {block_id?, text 1–2,000 bytes}}`. Each records the decider, key, its own manifest (rebuilt now) and frozen labels. `approved` needs: package mode `team`; decider eligible (authority above) and not a contributor of the version now; decider ≠ submitter. `self_approved` needs: package mode `solo`; decider = submitter; the binding's effective mode `solo_permitted`. Both need: the package's version is still the head, every claim and platform block still current, the version's binding still the Task's current one, and the decider's withheld set empty. A manifest that differs from the package's only by non-material lines (a newer disposition or exception disposition with the same effective outcome/status) is allowed and shown ("since submission: …"); any material change refuses. `changes_requested` is allowed on any undecided package; it wakes the Task when it waits for direction (paused/stopped stay so), writes the Task's `observed` event in the same transaction (24.3a pattern), and its notes reach the agent.
- **Standing** (derived on read, never stored): `current` · `superseded{head}` (a newer version exists) · `support_changed{claims, platform}` · `method_changed{binding}`. An approval that is not `current` shows "This review no longer covers the current work: <reason>"; the approval row never changes.
- **Issue** (new `work_product_issues`, immutable, one per package): issuer (authority above), key, approved or self-approved package whose standing is `current`, issuer's withheld set empty, the binding defines review rules (no `missing_review_rules` issue, not neutral; owner decision 6 pending), recipients 1–20 `{name 1–200, organisation? 1–200}` recorded as attributed data (no delivery; owner decision 5 pending), formats 1–2 of `docx|xlsx`, `issued_on` = UTC date of the row's database time (the guard checks; a midnight race records nothing and answers a retryable 503), its own manifest, frozen labels, and its exports listed with digests. If the product has an earlier issue, the new issue must name `corrects` = the product's latest issue and a reason (1–2,000 bytes); `changed{added, removed, changed}` block IDs (changed = same block ID, different `authored_in_version`) are computed by trusted code and recomputed by the guard; one successor per issue under the per-product lock. The earlier issue is shown "Corrected by issue <ID> on <date>: <reason>"; its row and export bytes never change.
- **Exports (renderer `zobba-export-v3`).** Every new export renders the review facts known for its version at export time, frozen in the export row (`review_digest`, `review_id?`, `decision_id?`, `issue_id?`): "Draft — not reviewed" · "Submitted for team review by <name> on <date>; not yet reviewed." · "Returned for changes by <name> on <date>; not approved." · "Independently reviewed by <name> on <date> (version n). Prepared by <preparers>." · "Self-reviewed by <name> on <date>; no independent review." · "Issued on <date> by <name> to <recipients>. Zobba recorded this issue; it did not deliver the document." · correction lines · "This review no longer covers the current work: <reason>". Content-addressed object IDs include the review digest; same version, format, withheld set and review facts → identical bytes. Issued exports (withheld set empty) are rendered, stored, read back and recorded in the issue transaction; an object-store failure records nothing (503). v1/v2 exports stay as they are.
- **Read surfaces.** Shelf and version views replace the constant `Draft` with a closed `review_state` (`draft | ready_for_team_review | changes_requested | independently_reviewed | self_reviewed`), the standing, and `issue_state` (`not_issued | issued | corrected`), all read in one statement with the 24.4 shelf. GET `/…/work-products/{p}/reviews?cursor=` (exact count, C-ordered 50 page) and `/…/reviews/{r}` (version, manifest summary, contributors with names and kinds, decision, notes, issue, standing, since-submission differences). Values follow the viewer's withholding (24.4 B).
- **Writes** (Origin, CSRF, `X-Expected-Actor`, session-bound key, strict bodies): POST `/…/versions/{v}/reviews` `{key, mode: team|solo}` (solo records package + `self_approved` atomically); POST `/…/reviews/{r}/decisions` `{key, decision: approved|changes_requested, notes?}`; POST `/…/reviews/{r}/issues` `{key, recipients, formats, corrects?, reason?}`. Closed refusals: 403 `review_forbidden`; 409 `reviewer_is_contributor{kinds}`, `independent_review_required`, `package_stale{head?, refresh, platform}`, `method_changed`, `support_withheld`, `required_sections_missing`, `support_changed`, `version_unfrozen`, `package_open{review}`, `version_approved`, `already_decided`, `already_issued`, `review_rules_missing`, `correction_required{latest}`, `correction_stale{latest}`, `conflict`; 404 `not_found`.
- **Agent.** No new answer field. `products_text` gains one exact line per product (review state, standing, open package, latest issue) and a separate `work-product-review-notes` request message (24.3a pattern): the newest 8 open change requests with an exact count of the rest, each note marked by decision ID and block ID, the text inside the untrusted-content envelope as `person-input` attributed to the reviewer. `ASSESSMENT_CONSTRAINTS` gains: the agent cannot submit, review, approve or issue; it addresses review notes by drafting a successor (a person's block only at that person's request, 24.4); it says in its answer what the reviewer asked and what changed. Until Story 25.2 turns them into durable questions, a stale approval or issue is shown on read and in the agent's context, never only as a badge.
- **Migration 0025 `work_product_review_issue.sql`** (additive; 0001–0024 and catalogues v1–v24 byte-unchanged; `published.rs` pins 0024/v24): the three tables; `work_product_exports` gains the nullable review columns and renderer `zobba-export-v3`; definer function `work_product_review_mode(org,client,engagement,task,binding)` (scoped, like `work_product_template`); SQL helpers `work_product_contributors`, `work_product_manifest`; guards for every rule above (set-based, `enable_nestloop=off`, `coalesce(…, false)`, `IS DISTINCT FROM`); immutability (UPDATE/DELETE refused, also for the owner; TRUNCATE only under `zobba.disposable_fixture_reset=on` in `*_test`); forced RLS; runtime SELECT/INSERT; `SCHEMA_VERSION` 25; `schema-v25.catalog`; inventory lists, grants and function checks; smoke, health and browser runtime expect 25; the browser fixture reset deletes the new tables.

**Ask First:** Any new crate; a named reviewer or reviewer notifications (25.x); a firm-configured separate approver; delivering an issued package (email, connections, outbox); PDF; firm DOCX/XLSX template files; reopening a decided package; waivers; letting the agent change review notes or a person's blocks without their request; changing 24.4 claim rules; any live provider run.

**Never:** Admin-only or Auditor-only sign-off; a worker, the agent or a Guide message submitting, approving or issuing; self-review labelled or exported as independent, or "Self-reviewed" without "no independent review"; solo review where the bound method requires independence, through chat, reviewer absence or a changed label; approving or issuing a non-head version, changed support or a changed method binding; UPDATE/DELETE of a package, decision, issue or export; a mutable issued record; configuration edits creating or erasing review or issue facts; numeric confidence; counts from bounded lists; a model-written review state or label; an issued export rendered from anything but the exact version, package, decision and issue; live provider calls in tests; a compiled step pipeline.

**Acceptance Criteria:**
- Given any recorded decision or issue, when its manifest and contributors are rebuilt from the rows, then they equal the stored ones, and no approving person is a contributor of the version.
- Given a decided or issued package, when any later version, record, disposition, binding or membership change happens, then the package, decision, issue and export rows and bytes are unchanged and the change shows as standing or a since-submission difference.
- Given a worker connection, the agent, an Admin-only or Auditor-only person, when it inserts a package, decision or issue, then the database refuses it.
- Given the label "Self-reviewed", when it is shown anywhere (web, API, export), then "no independent review" is in the same sentence.

## Design Notes

People sign; trusted code checks what they sign. The package is the exact thing reviewed: one version plus the manifest of what its claims rest on. Approval and issue each record their own manifest, so "what was approved" and "what was issued" are facts, and the difference between them is visible, never silent.

```text
package wpr-…  version 2 (sha256 …)  mode team  submitted by Ebo (accepted responsibility)
contributors: Daniel [edited_block, authored_version] · Ebo [accepted_responsibility] · Zobba (agent)
decision: approved by Thandi · manifest = package manifest + 1 line (disposition|…; outcome unchanged)
issue wpi-… on 2026-10-22 to Northstar Audit Committee · docx sha256 … · xlsx sha256 …
```

Why the most conservative contributor rule: independence fails safe — over-inclusion only means someone else must review; under-inclusion lets a preparer sign as independent. Why method binding equality at approval and issue: "uncertain semantic changes are treated as potentially material" (design §3.3).

Lessons from the 24.1–24.4 reviews applied: model input never fails a cycle; every guard has its own one-column forgery and message; concurrency is proven with a held transaction and an observed wait, and the refusal names the head; NULL-safe SQL; authority rechecked on replay; withholding applied in web, API and exports alike; exact counts and C-ordered paging, no counts from bounded lists, no caps that make a record undecidable (bound reads, not history); person input enveloped and attributed; agent context lists everything it needs with exact counts; exports frozen and content-addressed, read back before recording; web parser errors name their rule; browser fixtures recorded from the real API; lease renewal in tests (`owned`/`renewing`), never a longer production lease.

Size: about 8,000 tokens, far above the 1,600 target (24.3 and 24.4 were also large). **[S] Split** (recommended): **24.5a** = review mode, packages, contributors, decisions, standing, v3 review lines, agent context, panel (migration 0025/v25; ACs 1, 2-review, 3-invalidation, 4); **24.5b** = issue, recipients, issued exports bound by hash, correction successors (migration 0026/v26; ACs 2-issue, 3-correction). Issue only reads immutable approvals, so 24.5a ships complete without it. **[K] Keep** as one story with one migration 0025.
