# Epic 2 Context: Author and approve a Procedure

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## 0. Owner-approved timing correction — 2026-09-04

Approval of a regression-gated successor records pending regression and its successor relationship without a speculative handover date. Actual activation after regression passes sets the authoritative boundary strictly after activation. The owner explicitly selected this behavior. This supersedes approval-time wording and invalidates prior downstream timing reviews: Story 2.8 and later Regression Run/scheduler contracts require revalidation. Execution and scheduler handover remain outside Epic 2.

## Goal

An Auditor picks one of four Procedure Templates, edits it into a Procedure expressed in audit vocabulary — period and scope, Population Source binding, Target Systems, Audit Instructions, Compliance Rule, Evidence Requirements, and Schedule — reads the platform-derived executable plan, and submits it for approval. An Audit Manager who did not author the version reviews a section-by-section diff and approves or rejects it. This epic delivers the Procedures, Procedure Builder, Procedure Detail, and Version review surfaces; the four Template contracts as data owned by the `procedures` module; the deterministic `PlanCompiler` (applicability predicates, boundary semantics, scope-widening checks); plan derivation as a queued worker job that may call a model; and the immutable Procedure Version state machine, including platform-authored drafts minted automatically when a referenced registration or platform configuration changes. It matters because nothing later in the product (Runs, Evidence, Results) can be trusted unless what was authored, reviewed, and approved is exactly what later executes — execution, Regression Runs, and Schedule handover themselves are later epics; this epic only authors and freezes what they will run against.

## Requirements & Constraints

- Four Procedure Templates exist as data owned by `procedures`: Terminated Users Retaining Access (hero, fully configurable), Segregation-of-Duties Conflicts, High-Value Transactions Without Required Approval, and Production Configuration Deviation. The latter three are configurable in period, Population Source, Target Systems, and Schedule at minimum; their Audit Instructions and Compliance Rule are editable but not required to be re-authored for acceptance.
- Period is an explicit date range on the version; a scheduled Run later derives its own period and records the derivation — the version never derives one itself.
- Population Source binding: manual upload is valid only for a `once` Schedule; daily/weekly/monthly require a versioned-file or read-only API binding. A binding must declare an expected record count (signed cover sheet or count endpoint) or authoring is blocked. A version can opt in to a zero-record Pass (else empty population is Inconclusive) and to permitting versioned duplicate primary keys (else a duplicate is a Gate failure).
- Target Systems are selected by name from what a PoC Administrator already registered (read-only credential, allowlisted origin/application identity). Kinds: web, desktop (agent-driven), API, versioned file (adapter-acquired). The version freezes, per system, its kind, allowed origins/application identity, credential reference, permitted read actions, registration digest, and per-attribute expected field labels/locator patterns.
- Audit Instructions are natural language, stored verbatim, per agent-driven Target System. On blur they are checked against the selected systems' allowlists for scope-widening (unregistered system, write verb, out-of-scope origin) and flagged inline before submission — this authoring-time flag is advisory only; execution-time denial (a later epic) is the enforced control, and anything that escapes the flag is denied at execution and logged as a security event.
- Compliance Rule conditions compile deterministically where possible (badge: Rule-Classified) or are retained as natural language (badge: Agent-Judged). Every condition carries a compiled applicability predicate, default `found = true`. Numeric comparisons need explicit boundary semantics (inclusive/exclusive); the P-3 USD 100,000 boundary is inclusive. A compiled condition meeting a value it does not name evaluates the record Unevaluated with a diagnostic naming the value — never a human-mapped guess. Record derivation order is fixed: Exception, then Unevaluated, then Compliant. A confidence threshold (default 0.80) is set once per version for Agent-Judged evaluations.
- Evidence Requirements: attribute value, Structural Snapshot, screenshot, source file excerpt, recording segment. Every attribute value must be grounded in a snapshot or file, never a screenshot/recording alone. Structural Snapshot and screenshot are always platform-captured for agent-driven systems (capture itself happens at execution, later epic). An attribute can instead be declared model-read, recorded as such rather than requiring deterministic grounding.
- Schedule is once/daily/weekly/monthly with a fixed UTC start time; activates on approval (or after a Regression Run when required). Period-derivation rule per frequency is recorded on the version but not executed here (daily → previous calendar day, weekly → previous Mon–Sun, monthly → previous calendar month, once → explicit period).
- Plan derivation never happens inside a web request — it is a queued `procedures` worker job, may call a model, and every re-derivation (successful or not) is recorded. The plan preview is read-only (Session Steps, ordered Plan Steps per Target System, Observations to capture, compiled/Agent-Judged conditions, credential references, limits, model identity when used). An underivable plan shows "Cannot derive: {reason}" and blocks Submit.
- Submission moves `DRAFT → SUBMITTED` only with no outstanding blocker and a derivable plan; it notifies every Audit Manager in the same transaction. The version's own author can never approve it. Approval freezes: compiled plan, Compliance Rule (compiled/uncompiled status + applicability predicates), Evidence Requirements, Target Systems + registration digests, Population Source binding, model/tool configuration, limits, Schedule; it records approver, time, and diff. Two concurrent approval attempts on the same version: the second fails an expected-revision precondition.
- Rejection requires a rationale, moves `SUBMITTED → REJECTED`, notifies the author; "Edit" returns it to `DRAFT`.
- Approving a version whose configuration tuple (model, prompt version, tool configuration, registration digests) differs from the prior Active version of the same Procedure records the pending successor relationship without `handover_at` and marks the version as requiring a Regression Run (executed in a later epic) before `ACTIVE`; otherwise it goes `APPROVED → ACTIVE` immediately. The activating command sets the authoritative boundary strictly after actual activation. A first version never needs a Regression Run.
- Approved/Active versions are truly immutable on their frozen fields — the only path to a new definition is "New version" (a Draft copy of the Active version). A `RegistrationChanged` event from `registrations` for a Target System or Population Source binding an Active version references mints a new platform-authored Draft automatically, in the same UnitOfWork; the prior version's Schedule keeps running until the new draft is itself approved. A platform-side model/prompt/tool configuration change follows the identical path. Every platform-authored Draft goes through the same `DRAFT → SUBMITTED → APPROVED | REJECTED` machine — no shortcut to Active.
- Out of scope for this epic: actually executing the plan, Regression Runs, and Schedule handover at a period boundary — those are later epics. This epic only authors and freezes what they will run against.
- NFR-11 (WCAG 2.1 AA, keyboard accessible) explicitly names the Procedure Builder. NFR-4 requires Rule-Classified evaluations to be reproducible from identical frozen inputs — enforced here by freezing compiler version and conditions at approval.

## Technical Decisions

- **Modules and layering (AD-1, AD-2):** `procedures` (Templates, Builder, versions, schedules) is the module of record; `registrations` owns Target System/Population Source registrations and publishes the change events `procedures` handles. `packages/domain` owns entities/state machines with no outward imports; `packages/application` holds commands/queries/plans and owned ports, importing only domain; `packages/infrastructure` implements those ports (Drizzle, pg-boss, model providers); `apps/web` is the composition root for the Builder UI, route handlers, and Version review. Application command handlers are the only mutation path — no module reads/writes another module's tables directly.
- **Registration digest (AD-2):** SHA-256 over RFC 8785 canonical JSON of exactly `{kind, allowed_origins | application_identity, credential_ref, permitted_actions, attribute_label_patterns, secondary_key}`, computed by one domain function owned by `registrations` (already implemented per Story 1.6's `packages/domain/src/registrations/target-system.ts` — reuse it, do not recompute).
- **Run kind distinction (AD-2, AD-19):** a `STANDARD` Run references only an `ACTIVE` version; a `REGRESSION` Run references the `APPROVED` version it gates — this epic only sets up the versions; Run execution is later.
- **PlanCompiler (AD-23):** owned by `procedures`; condition compilation and applicability derivation are deterministic domain functions with a compiler version frozen on the Procedure Version so identical inputs always compile identically. Builder invariants (manual-upload-needs-`once`, declared-count required, zero-record-Pass and versioned-duplicate as flags, explicit boundary semantics, default `found = true` applicability, Exception→Unevaluated→Compliant derivation order, scope-widening check against the registration allowlist) are domain validation rules, not UI-only checks.
- **Plan derivation as a worker job (AD-23, AD-3):** a `procedures` command executed as a queued worker job, never inside a web request; may call `ModelGateway` for derivation only (default model `claude-sonnet-5` via the Anthropic provider unless configured otherwise), with model identity and prompt version recorded on the version.
- **Versioning contract (Consistency Conventions table):** a Procedure Version freezes objective, scope, Population Source binding (with masking designation and declared-count mechanism), Target System registration digests (labels, secondary key), Audit Instructions, compiled plan and compiler version, derivation model/prompt version, conditions with applicability and compiled status, confidence threshold, zero-record-Pass and versioned-duplicate flags, compatibility declaration, Evidence Requirements, evaluator, schema/normalizer, execution prompt, model/tool configuration, limits, and Schedule.
- **State machine (verbatim, addendum §E):** Procedure Version `DRAFT → SUBMITTED → APPROVED | REJECTED`; `REJECTED → DRAFT` on edit; `APPROVED → ACTIVE` immediately or after the Regression Run; `ACTIVE → RETIRED` at the first period boundary after a successor is `ACTIVE`. Only `ACTIVE` versions run or schedule.
- **Human decisions (AD-7):** every transition records actor, time, prior state, decision, rationale, and aggregate revision; mutations (including approve/reject) require the expected revision — this is how "two Audit Managers act on the same Submitted version" resolves (second fails the precondition). Better Auth supplies identity/session only; application-owned roles authorize every command.
- **Notifications (AD-20):** version submission notifies every Audit Manager, approval/rejection notifies the author — created in the same transaction as the state change, in-app only for the PoC, delivered by a worker through one `NotificationSender` port with idempotent send keys.
- **Durable contracts (AD-14):** the compiled plan is a versioned executable contract (Zod schema + `schemaVersion`) consumed byte-for-byte by the worker at execution time — the worker never re-derives it.
- **Roles gating:** Auditor authors/submits; Audit Manager approves/rejects (never their own authored version); PoC Administrator cannot author Procedures at all ("PoC Administrator cannot author Procedures or start Runs."). The gating table lives in `packages/domain/src/identity/roles.ts` (established in Story 1.3) and must be extended there, not reinvented.
- **Stack pins relevant here:** Next.js 16.3.4, React 19.2.8, Drizzle 0.45.2/Kit 0.31.10, Zod 4.5.4, Vercel AI SDK 7.0.89 with Anthropic provider 4.0.47, pg-boss 12.29.0 for the plan-derivation job queue.
- Golden-dataset seeds, expected outcomes, and confirmation scripts referenced from each Template are versioned product data (AD-12/AD-19) used by later epics (Regression Runs) — Story 2.1 only needs to carry the reference, not exercise it.

## UX & Interaction Patterns

- **Procedures surface:** empty state's only action is "New procedure"; once Procedures exist, each renders as a card showing Active version, Schedule, next Run, and last outcome.
- **Builder invariants surfaced inline:** every section validates on blur (missing declared-count mechanism, upload paired with a non-`once` Schedule, scope-widening instruction, uncompiled condition without applicability) with warning-color inline messages; Submit stays disabled with the listed reason while any blocker or an underivable plan exists — never a tooltip-only explanation, and a disabled action's reason also appears in an "Unavailable actions" panel and as its accessible description.
- **Builder re-derivation:** any saved change queues a plan-derivation job; the plan preview shows "Re-deriving…" then "Re-derived {time}"; the plan preview itself has no edit controls — editing always happens back in the originating section.
- **Compliance Rule editor:** each condition row shows text, an evaluation-origin badge (Rule-Classified vs. Agent-Judged), the applicability predicate, a boundary-semantics selector for comparisons, and tolerance as a compiled numeric condition; the confidence threshold field is set once per version.
- **Version review:** shown as a section-by-section diff against the previous version (fully expanded when it's the first version); the author sees Approve disabled with the exact sentence "You cannot approve a version you authored."; Reject requires a rationale via a "routine with rationale" confirmation dialog.
- **Procedure Detail states:** Draft-only shows the versions list with a Draft badge and "Submit for approval" as primary, no Initiate Run; Submitted shows an approval-pending banner naming who can approve; Rejected shows the rationale inline next to "Edit"; a platform-authored Draft shows "Created by the platform after a {model / prompt / tool / registration} change; requires approval"; Retired shows "Retired {time}; superseded by v{x}." read-only; Active shows the Schedule with next Run time and an enabled Initiate Run.
- **Administration warning (Flow 0):** saving a Target System registration change that would ripple into Procedures warns "This change creates a platform-authored draft for {n} Procedures and requires approval." before the save commits.
- **Voice and tone:** sentence case; domain nouns (Run, Procedure Version, Compliance Rule, Target System, Population Source, Template, Schedule, Observation, etc.) capitalized as defined terms; every guard sentence names the object it protects; no status conveyed by color alone (badge = family + icon + word); disabled buttons always carry a stated reason.
- **Accessibility:** WCAG 2.1 AA and full keyboard access are required for the Builder specifically (NFR-11); tables use `<th scope>` with the first cell of every row a focusable link; confirmation dialogs trap focus and are never tooltip-only for a disabled action's reason.
- **Responsive floor:** below 900px the Builder and Version review show "Open on a desktop browser to author or approve." instead of degrading the flow.

## Cross-Story Dependencies

- Stories 2.2–2.6 all extend the same Draft Procedure Version created in Story 2.1 and all feed the plan compiled/re-derived in Story 2.6 — the Builder sections are independently editable but share one underlying version and one `PlanCompiler` pass.
- Story 2.6's plan preview is a precondition for Story 2.7's Submit: Submit is disabled whenever the plan is underivable, and Version review reuses the same read-only plan-preview component.
- Story 2.7's approval command is the trigger for Story 2.8's freezing and Regression-Run-requirement logic (comparing the configuration tuple against the prior Active version) — 2.8 cannot be implemented independently of how 2.7 stores the diff and approval decision; 2.8 adds activation-time `handover_at`.
- Story 2.8's platform-authored draft path depends on `registrations` (Story 1.6/1.7 work) publishing `RegistrationChanged`/digest changes that `procedures` consumes in the same UnitOfWork — this is a cross-module dependency, not just cross-story.
- This epic's output (an `ACTIVE` Procedure Version with a frozen compiled plan) is what Epic 3 (adapter-acquired Runs) and later epics (agent-driven Runs, Regression Runs, Schedule handover) execute against; none of that execution, including the FR-15 Regression Run, is implemented in Epic 2 — only the version-level "requires a Regression Run" flag is set here.
- Notification delivery (AD-20, `NotificationSender`) and the in-app Notifications surface are shared infrastructure also used by later epics (Escalations); Epic 2 is simply its first caller for version submission/approval/rejection.
