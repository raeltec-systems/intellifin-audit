# Epic 11 Context: Tenancy, scope and delegation

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Epic 11 makes every protected database row belong to an explicit tenant, client, engagement or user, and enforces that ownership inside PostgreSQL itself — not only in application code — before the product connects to any real (non-synthetic) account. It classifies every table, scopes it, forces row-level security with a permissive grant plus mandatory restrictive boundaries, makes ownership columns immutable except for one audited engagement-to-client binding transition, and moves background/maintenance work onto named, revocable, re-checked execution principals instead of one unrestricted worker identity. It also establishes the three user-facing roles (Auditor, Audit manager, Admin) as capability groups on top of tenant/client/engagement membership, plus invitation and removal commands with a transactional last-administrator rule. This is security-critical retrofit work on an already-large existing schema: nothing in any later epic is safe to build until this isolation is proven, and by owner decision it must run and pass before any personal account is ever connected.

## Requirements & Constraints

- Every protected record has an explicit owning tenant, with client/engagement/user associations wherever the record's meaning requires them; a tenant-wide or user-scoped record (a methodology pack, a preference) must be deliberately scoped, never reachable merely by omitting an identifier. The owner's own single-owner workspace is a tenant, enforced the same way as any other. An identifier supplied by a browser or a model is a selector only, never proof of access.
- Isolation is proven, not assumed: a negative cross-scope suite (one client's member cannot read, retrieve, be shown, or act on another client's rows, retrieval indexes, cached context, artifacts, background work or credentials) runs in CI before any personal account is connected and on every later release; a failing test blocks release. Positive tests are required too, per principal class and operation — a system that denies everything cannot pass.
- Retrieval filters by tenant, client and engagement before ranking, so client context can never cross engagements.
- A recorded grant (a Permissions Version, a delegation) never carries forward permissions already revoked: current grants, restrictions and approvals are rechecked before every dispatch and again on resume or retry.
- Background/scheduled work runs under an identifiable, bounded, approved execution principal, with the responsible human and authorizing decision recorded; it never borrows another user's credentials and never depends on an indefinitely live interactive session.
- The three tenant roles are capability groups, not job titles: Auditor (direct work, analyse/test, prepare/revise, submit for review, within assigned engagements); Audit manager (independent review/approval, return with notes, oversight, issue where permitted); Admin (users, model/provider config, connection policy, permission limits, and methodology pack/skill/template lifecycle as audited configuration). Engagement assignments (lead auditor, auditor, reviewer) are a separate, scoped layer, not tenant roles. Admin's methodology authority never substitutes for audit review/approval/issuance; a preparer can never satisfy required independent review of their own substantive work; a role change can never erase authorship/contributor history independence checks rely on. Reviews is visible only to someone with an assigned review responsibility and the matching capability.
- Invitations are administrator-created, bound to the intended recipient, tenant, permitted role assignments and any proposed engagement access; expiring, revocable, single-use; a forwarded link alone confers nothing, and both the invitation's validity and the inviter's current authority are rechecked at acceptance. The secret stays out of model context and ordinary logs. No open sign-up, no self-selected privileged role; first release is Create invitation / Copy invitation link only.
- Removal is three distinct actions — engagement, tenant, and a separate global account action — leaving other tenant memberships untouched on tenant removal. Revocation is enforced on subsequent requests AND on background dispatch/resume/retry; pending invitations and affected delegations are handled explicitly; a dispatched external action keeps its reconciliation path; authorship/approvals are preserved; reinstatement restores no old grant silently. The last active administrator can never be removed or demoted (transactional), and a pending invitation never counts as a replacement.

## Technical Decisions

**Table classification (Story 11.1).** Before any RLS policy is written, every table — existing and new — is put into exactly one of five classes, in a checked-in classification manifest (a source-controlled table, one row per database table). These are the exact class names used in the source docs: **tenant-owned** (e.g. methodology packs, skills, the Permissions Policy), **user-owned** (e.g. preferences, connections), **client/engagement-owned** (e.g. engagements, tasks, conversations, evidence, artifacts, memory, Runs and their children), **global authentication** (the Better Auth user/session/account/rate-limit rows), and **platform infrastructure** (the pg-boss schema, `schema_meta`, the worker heartbeat row). Each class gets its own policy shape; authentication and infrastructure tables are deliberately never given a tenant policy just to make a table count come out even. A build-time test fails whenever a real table has no classification row — the "unclassified-table test." Beside the classification manifest sits a second checked-in artifact, the **policy inventory**: for every protected table and command it supports, it documents the full combination of the one permissive grant policy plus the mandatory restrictive policies (tenant / client / engagement / owner boundaries), separately for three principal kinds — ordinary members, execution delegations, and maintenance principals. Story 11.1's second proof is "the inventory test"; the docs name it but do not specify further mechanics — not specified. Neither artifact's exact file path is given in the planning docs — not specified — but Story 11.1 establishes the `tenancy-v1` contract, so by the project's existing convention it is the story that authors `docs/contracts/tenancy-v1.md`.

**Scope columns (11.2).** A protected table carries `tenant_id NOT NULL`, plus `client_id`, `engagement_id` or `owner_user_id` where the record's meaning requires it. A child's foreign key to a protected parent is composite over scope — `(tenant_id, parent_id)` → `(tenant_id, id)`, or `(tenant_id, engagement_id, parent_id)` for an engagement child — so a permitted row can never reference another scope's object even through a valid id. Existing rows backfill to the owner's single-owner tenant, mapped per table.

**Roles and RLS (11.3–11.4).** Two database roles: the release migrator (owns every table, the only role running DDL/backfills) and the application runtime role (`NOSUPERUSER NOBYPASSRLS`, owns no table, used by web and worker). Every protected table gets `ENABLE` and `FORCE ROW LEVEL SECURITY`. A row is granted only when ≥1 applicable permissive policy passes AND every applicable restrictive policy passes; the permissive policy is scoped to the principal's own membership, and no additional permissive policy may bypass a restriction. Missing/invalid principal context yields zero rows, no writes. A **principal wrapper** sets `app.actor_id` / `app.tenant_id` via `SET LOCAL` inside the transaction, from a bounded membership query performed before the principal is trusted; only trusted infrastructure sets this, and model-generated SQL or sandbox code never reach the database directly. Column-level privileges are separate from RLS: a maintenance principal (e.g. the reconciliation principal) is granted `UPDATE` on specific named columns only.

**Ownership immutability (11.5).** `tenant_id` / `client_id` / `engagement_id` are held immutable by a migrator-installed `BEFORE UPDATE` trigger the runtime role cannot alter or disable. Exactly one ownership change is ever permitted — binding an unbound draft engagement to a client (`client_id IS NULL → client`) — through a dedicated, validated, audited command admitted only by a migrator-owned `SECURITY DEFINER` function (fixed safe `search_path`, `REVOKE EXECUTE FROM PUBLIC`, narrow `GRANT EXECUTE`) that checks membership and engagement state and writes the binding and its audit record together; never a route for relabelling existing client material.

**Delegation and service principals (11.6).** Background audit work runs under an `execution_delegation` row (delegating user, tenant, engagement, scope, approver, created/revoked timestamps); a job carries the delegation id, and the wrapper re-reads both the delegation and the delegating user's current membership at every claim and resume. Platform maintenance (credential revocation, timeouts, receipt reconciliation, sweeps) runs as named service principals with narrow, operation-specific RLS and column privileges — no general-purpose worker identity with unrestricted access.

**Migration sequence (11.2–11.7), strictly ordered:** (a) classify tables; (b) add/backfill scope columns to the owner's tenant; (c) create the two roles, rotate connection strings to the runtime role; (d) enable/force RLS with the policies; (e) route every `UnitOfWork` class and raw transaction site through the wrapper, refusing a scoped transaction with no principal; (f) drain workers, then re-validate jobs enqueued before migration against a delegation created for the owner at migration time; (g) move the supported-schema-range guard so an old build refuses to start against the newly scoped database; (h) reversible only up to the point RLS is forced.

**Historical chains and envelope v2 (11.8).** Historical event/evidence bytes are never rewritten, and `tenant_id` sits outside their existing hash, so old hashes can't authenticate a tenant assignment. The migration instead writes a separate, signed **ownership binding** per aggregate chain (aggregate id, tenant id, chain-head hash at migration time, event count, migration id), stored beside the existing chain heads. Every *new* chain segment uses **envelope v2**, putting `tenantId` (and `engagementId` where applicable) *inside* the hashed, canonicalised envelope; readers accept v1 (via its binding) and v2. A tenant's export contains only its own aggregates and verifies alone; reassigning an aggregate's tenant invalidates its binding signature, and a v2 event appended under the wrong tenant fails the chain check.

**Residual threat, stated rather than hidden.** RLS stops a forgotten filter, a wrong-scope query, or a legitimate principal reached by a mistaken code path. It does **not** contain a fully compromised trusted database client running arbitrary SQL as the runtime role — such a client can still read/write everything that role can reach, across every tenant. The code boundary (model/sandbox code never get a database connection), the runtime role's narrow privileges, and the audit chain are documented as mitigations, not full containment, and are revisited before any real data is adopted.

**Where new code lives:** the scope model is domain code (`packages/domain/src/identity/scope.ts`, with `requireScope` / `resolvePrincipal`); the transaction wrapper, database roles and RLS policies are infrastructure. Contract names: `tenancy-v1` (new), `audit-event-envelope-v2` (extends the existing envelope).

## Cross-Story Dependencies

- 11.1 → 11.8 is a strict pipeline: each migration step depends on the one before it. Stories 11.9–11.11 build on the tenancy/delegation that pipeline establishes; 11.11's revocation of background work explicitly reuses 11.6's delegation mechanism.
- Epic 10 (Disposition and rename) renames application packages, environment flags and identifiers; that rename must land first, in the same delivery slice, before this epic writes any new modules.
- This epic delivers storage, commands and enforcement only — no new screens. Identity plumbing and stored role values already exist; the Users-and-roles, invitations and Remove-access screens that exercise 11.9–11.11 are built in Epic 18 (the Zobba shell/workspace/Reviews/Settings epic), story 18.11, with the invitation-creation screen specifically in story 18.12. Until then, 11.9–11.11 are proven behind the product's existing screens.
- This epic is a hard prerequisite for every later epic: Epic 12 (Engagement/Agent Task/agent loop), Epic 13 (Agent Permissions/connectors) and Epic 19 (promotion/recurring checks) all dispatch background work through the delegation and principal wrapper established here. By owner decision, no personal account may be connected until this epic's isolation suite (two tenants, two clients, two engagements, two users) passes; that suite reruns on every release afterward as a standing assurance obligation owned by Epic 9.
