## Intent

**Problem:** Everything before this reads ONE record per Work Item. P-4 reads four configuration
parameters off ONE page in ONE Work Item, and its declared count is extracted by the AGENT
rather than published by the system. Both are shapes the platform has never executed, and both
are places a plausible-looking Run could conclude over an incomplete read.

**Approach:** One Observation per baseline parameter, each grounded in the same page's Structural
Snapshot with the PARAMETER NAME as its identity attribute. The Gate reconciles the
agent-extracted declared count against the Observations registered, exactly as it reconciles a
published one. No adapter is in the loop.

## Boundaries & Constraints

**Always:** Four Observations for the four parameters — `max_manual_approval_amount`,
`mfa_required_for_admin`, `session_timeout_minutes`, `production_debug_mode` — under the ONE Work
Item, each grounded in the page's Structural Snapshot, each with the parameter name as its
identity attribute (FR-20, AD-18, §C). The signed snapshot identifier and the expected parameter
count are both AGENT-EXTRACTED, and the Gate reconciles that count EXACTLY against the
Observations registered — "the same as any other declared count" is the acceptance text, and it
means the existing `declared-count` machinery, not a second reconciliation written for the agent
path. `run_observation` is unique on `(work_item_id, population_record_key)`, so the four
parameters must have four DISTINCT record keys — the parameter name is the key, which is also
what makes the identity attribute the parameter name rather than an account id.

**Never:** Never accept a partial read. A parameter absent from the page, or present but
unreadable at its locator, yields `INCONCLUSIVE` — never a silent Compliant. Never let the
agent-extracted count be trusted as a fact about the platform: it is a value read from a page,
so it is untrusted content that is RECONCILED against what was registered, and a disagreement is
a Gate failure rather than a correction to either side.

**Scope:** P-4, the Production Configuration Deviation Procedure, against the synthetic
ProdConsole Northstar system. Adding ProdConsole's page and its golden expectations to
`fixtures/northstar/` is part of this story if they are not already there; the declared count
and every digest are GENERATED by `uv run fixtures/northstar/generate.py`, never typed beside
the rows they count.

## I/O & Edge-Case Matrix

| Input | Expected |
|---|---|
| The page carries all four parameters | Four grounded Observations, one Work Item, count reconciles, Run concludes on the rule |
| The page carries three | `declared-count` reconciliation fails → `INCONCLUSIVE` |
| A parameter is present but its locator resolves to nothing | `grounding: null` → `required-evidence` FAILS → `INCONCLUSIVE` |
| The agent-extracted count says 4, five Observations are registered | Reconciliation fails. The disagreement is the finding, not the smaller number |
| The signed snapshot identifier is absent | Recorded as a failing check; the Run cannot claim the page was the published one |
| Two parameters share a name | The unique index makes it one Observation; the count then disagrees, which is correct |
| A parameter's value contradicts its locator on re-read | `snapshotCorroboration` writes `contradictory`; `canBeCompliant` is already false |

## Design Notes

**Why the parameter name is both the record key and the identity.** The unique index on
`(work_item_id, population_record_key)` is what makes a redelivery idempotent and what makes a
duplicate key ONE Observation. For P-4 the "record" is a parameter, so the parameter name is the
key, and the identity attribute — the grounded value holding the matching key as the Target
System displays it — is the parameter's label on the page. That also means a page listing a
parameter twice collapses to one Observation and then fails the count, which is the correct
direction: the finding is the disagreement, not a quietly smaller number.

**Why the agent-extracted count is reconciled and not trusted.** It is a value read off a page
the platform did not write, so AD-9 applies: it is untrusted content. §H already treats a
declared count as a claim to be reconciled rather than a fact, which is exactly the right
treatment here; nothing needed to change to make that true.
