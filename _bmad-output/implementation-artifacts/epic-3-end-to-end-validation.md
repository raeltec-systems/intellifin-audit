## What this is

Epic 3's acceptance is not "the tests pass". It is that a Run, driven by the real worker
against the real synthetic systems and a real database, reaches each terminal outcome the
product can produce, for the reason the outcome rules say it should.

## The bar, corrected

The epic brief assumed eight demonstrable outcomes. **Six are demonstrable in this epic and
two are not**, and the two are named rather than quietly counted.

| # | Outcome | How it is produced | Status |
|---|---|---|---|
| 1 | Inconclusive, segregation-of-duties | The full golden population, real worker | **Proven** |
| 2 | Inconclusive, high-value approvals | The full golden population, real worker | **Proven** |
| 3 | Pass | The clean source with no seeded failure, real worker | **Proven** |
| 4 | Control Failure | The clean source carrying one true conflict, real worker | **Proven** |
| 5 | Run Failed | A Session Step failing after bounded retries | **Proven** (integration); the worker also proves the acquisition form |
| 6 | Canceled | Story 3.10 | **Proven** |
| 7 | Pending Confirmation | Needs an Agent-Judged evaluation | **Not reachable in Epic 3** |
| 8 | Completed to Inconclusive | Needs a human rejection of an evaluation | **Not reachable in Epic 3** |

Rows 7 and 8 are implemented, sit in the addendum's order, and are tested with constructed
state in the domain and against PostgreSQL. Epic 3 produces only rule-origin evaluations, so
nothing is ever pending and no human rejects anything. Epic 4 makes row 7 reachable; Epic 6
makes row 8 reachable.

## Why the golden populations cannot produce Pass or Control Failure

This is the correction, and it is not a limitation of the scoping — it is the golden datasets
working as designed.

**The segregation-of-duties source lists one account twice.** Verified: thirteen rows, one
duplicated identifier. The Gate counts duplicate source primary keys over EVERY parsed row,
deliberately, because "a duplicate inclusion happened to filter out is still two Source rows
claiming one identity". So that check fails on every Run over this source, at any scope, and
a failed Gate row is Inconclusive.

**The high-value source has one transaction with no processed time.** The frozen inclusion
rule therefore cannot place it in or out of the Period — for any period, because the value is
absent rather than out of range — and an indeterminate row stays unaccounted. So the
inclusion reconciliation fails on every Run over this source.

**Scoping cannot escape either.** The inclusion rule is a conjunction of predicates and its
text comparison is equality only, so the narrowest honest scope is a single record. That is
enough for a Pass case in principle, but it does not remove a duplicate or an indeterminate
row from the SOURCE, and those two checks read the source.

A golden dataset that seeds every failure mode at once is exactly what it should be. It just
cannot also be the dataset that demonstrates success.

## The clean source

One additional synthetic system, built to the same rules as every other fixture:

- Its population has distinct primary keys and no missing dates, so no file-level or
  inclusion-level Gate row fails and the per-record verdicts decide the outcome.
- Its expectations are declared BY HAND in `fixtures/northstar/expectations/`, so nothing
  validates a Result against the implementation that produced it.
- Its declared count and cover-sheet digest are GENERATED by `fixtures/northstar/generate.py`
  and recomputed independently in TypeScript. A number typed beside the rows it counts is
  wrong the first time somebody edits the dataset.
- Every value is invented, and the synthetic marker walk starts at the fixture root and
  subtracts an allowlist, so the new folder is covered without being added to a list.

Two Procedures over it: one whose records are all compliant, giving **Pass**; one carrying a
single true conflict, giving **Control Failure**. Both through the real worker.

## What "proven" means here

For each demonstrable outcome: the real worker process, the real synthetic service over the
network, a real PostgreSQL, and a real object store. The assertion reads what the Run
actually stored — the sealed Result, its outcome, the row that decided it, the Gate rows and
the per-record verdicts — and compares it with the expectation file read off disk.

Not a hand-built harness that calls the pipeline directly. Twelve of the high-value cases
were reachable only that way until Story 3.9's repair, and that is precisely the gap this
plan exists to close.

## What closed it — 6 September 2026

The clean source is **CoreDirectory**: `fixtures/northstar/datasets/coredirectory-accounts.json`,
served at `/coredirectory/accounts` and published as two versioned files with signed cover
sheets. It seeds nothing. Its roles expand through the SAME `rolematrix.json` the golden P-2
Run freezes — a second copy would be a second source of truth for one expansion — and it
carries the existing generation timestamp (`2026-09-01T00:00:00Z`), effective period
(`2026-08-01`..`2026-08-31`) and generation (`2026-09-01.1`), because two generation dates in
one fixture set is two answers to "when was this true".

Two populations, differing by ONE role on ONE account:

| Population | Records | The one difference | Outcome |
|---|---|---|---|
| `coredirectory-accounts-compliant` | CD-3001..CD-3004 | CD-3003 holds `VENDOR_MAINTAINER` | **Pass** |
| `coredirectory-accounts-conflict` | CD-3101..CD-3104 | CD-3103 holds `VENDOR_MAINTAINER` **and** `VENDOR_APPROVER` | **Control Failure** |

Everything else about the two Runs is identical, so the difference in outcome is attributable
to the rule and to nothing else. CD-3001 and CD-3003 are deliberate near misses — one
permission short of a prohibited pair each — so a rule that flagged a MEMBER of the conflict
vocabulary rather than a PAIR fails the Pass case.

### The assertion that matters

Both browser cases assert the failing §H set is **EMPTY**, and assert it against the
expectation file's own `gate_expectation.failed_checks`. A Pass produced by weakening a check
is not a Pass. Proven by mutation: adding one undeclared role to the compliant population puts
`unnamed-value` on the Gate and the Pass case fails with `INCONCLUSIVE`; removing
`VENDOR_APPROVER` from CD-3103 makes the Control Failure case fail with `COMPLIANT` where it
requires `EXCEPTION`; binding each Procedure to the other population fails both.

### Still not reachable, and still named

Rows 7 and 8 are unchanged. Nothing here makes an Agent-Judged evaluation pending, and
nothing here rejects one.
