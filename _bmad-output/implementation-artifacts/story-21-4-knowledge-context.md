## Decision

**The proposed narrow authority contract is sufficient for canonical 21.4's “explicit promotion across permitted scopes,” provided it delivers real positive promotion/reuse paths and the concrete safeguards below. No unresolved product-authority question prevents that implementation.** The words “permitted scopes” do not require inventing universal client publishers, firm knowledge editors, another role, or every possible scope-to-scope transition.

Canonical 21.4 scopes promotion without defining new governance (`epics.md:427–449`). The adopted design explicitly permits authorized same-client cross-engagement work (`Zobba-Product-and-Architecture-Design.md:64`), requires explicit eligibility/current access/period applicability for reuse (`:278`), distinguishes personal preferences, firm method, client facts and engagement knowledge (`:282`), and prohibits client-to-firm laundering (`:278`). Admin configuration and engagement assignment already provide the necessary authority boundaries (`:185–191`, `:251–257`). SPEC CAP-24 and its constraints preserve those boundaries (`SPEC.md:58–60`, `:83`).

### Freeze these supported operations

1. **Own harmless preference → assigned engagement.** The owner explicitly publishes an exact revision of a small typed, non-content-bearing setting to an engagement where they currently have audit authority. Record owner, value/revision, destination, time and publication identity. An authorized destination reader may see the released value without gaining access to private conversation or other personal records. The publication is an optional setting, never a method or required control. Do not make the recipient satisfy owner-only personal-record ACLs: that would make the promised release unusable. Preserve the private origin reference without disclosing its private content. This narrow value-release rule applies only to allowlisted presentation settings, never arbitrary prose labelled “preference.”
2. **Engagement-derived knowledge → explicit same-client reuse.** Record the exact knowledge revision and named destination engagement/Task as a scoped reuse authorization. Require current origin and destination audit authority plus current access to every evidential/message dependency. A client eligibility tag alone is insufficient: an actual later Task in the named destination must retrieve the eligible result with its original source, period, author and status. It does not automatically select every future engagement or disclose to all client users. Each human reader and accountable Task consumer independently qualifies; the requesting collaborator cannot lend their access to a Task owner.
3. **Firm context → existing saved Admin configuration.** Use the applicable immutable 21.2 configuration/binding with configuration provenance. Do not copy its text into a writable generic knowledge record and thereby create a second configuration authority. Admin's configuration access never supplies client-evidence access. Arbitrary firm publication, including client-derived “lessons,” is outside this supported transition set.

Keep the Task's one engagement tuple unchanged. Reuse eligibility, source access and execution/disclosure authority are three checks. Existing `OperationStore::accept_authority` is the sole widening path (`zobba/crates/application/src/operation.rs:54`); its implementation requires the accountable actor (`infrastructure/src/operation.rs:623–641`). Current permission evaluation compares current and accepted Task scope/actor/identity (`domain/src/permissions.rs:415–443`). Therefore a reuse receipt is **not** a ready-made operation grant. Define the exact destination-Task knowledge selection and source manifest now; if a subsequent operation needs wider accepted bounds, it must use the existing accountable acceptance path. Never swap the Task's scope to make a foreign-origin lookup pass. Model invocation remains a later consumer, not a proof claimed here.

## Required implementation behavior

These are implementation commitments, not requests for broader policy:

- **Make promotion operational.** Persist exact revision, named destination, author and dependency links; expose an explicit action and prove later-Task retrieval in the destination. Prove origin-only, destination-only, different-client, withdrawn-source and replaced-session denials. A type enum or permission-error-only implementation does not deliver promotion.
- **Define useful mutation authority.** An assigned Auditor/Audit manager can contribute attributable corrections and exclusions within their authorized engagement, preserving the previous author/version and visible conflicts. Owner-only personal mutations and withdrawal of one's own publications are supported. A destination exclusion need not erase the shared origin globally. Expose eligible correction/update/forget in What Zobba is using; “forget” removes future usable context, not originals or audit history. This satisfies eligibility without giving Admin/manager a new global power to erase others' knowledge.
- **Give publication Undo exact semantics.** Use withdrawal of the selected publication with dependent-context invalidation. Undo of an inferred personal revision withdraws that revision and its still-active publications; show the affected destinations. A newly edited personal preference does not silently overwrite an already-published engagement value. Retain historical receipts; ordinary author departure does not itself erase engagement-shared sources. No additional approval is necessary.
- **Implement source correction separately from new uploads and assertion correction.** Use an explicit same-origin registered-evidence predecessor/replacement declaration, expected revision, exact retries and transitive invalidation. Existing evidence originals have no logical correction identity (`migrations/0006_evidence.sql:3–31`); a matching name or asserted source version cannot infer replacement. Inaccessible dependencies must exclude revealing text/provenance before ranking, not leave a readable claim beside a broken citation.
- **Complete real automatic recording and the inferred-preference case.** Typed records and manual preference Save alone do not prove “record automatically” or canonical AC2. Use the minimum concrete producers below. Preserve source/status limitations; do not claim semantic understanding.

General firm/client publisher roles, all-client global defaults from ordinary auditors, manager/Admin global erasure, generic free-text personal declassification and autonomous cross-engagement discovery are optional expansions. They are not prerequisites to this bounded canonical contract. Do not report them as delivered.

Binary/unsupported formats remain acquired evidence with an explicit extraction limitation; no invented text extractor is necessary. A manually supplied `inferred=true` flag or an uncalled future model hook fails that proof. The inferred presentation setting can also be the narrow personal-to-engagement release example, provided the owner explicitly selects the destination and it remains optional.

## Integration rules

These are routine engineering choices supporting the canonical story. Start only after the producer handoff is verified. Keep authority in existing owners and do not claim model interpretation.

- **Direction standing:** Accepted Guide projection preserves exact author, command, target Task/cycle, time and scope once. A Task-local instruction does not silently become standing engagement-wide instruction merely because another Task can retrieve the historical decision. Inspection must distinguish original target and reusable context from current Task direction. Do not infer an unrelated later Guide supersedes all previous direction. Live direction changes still use Task admission, not a knowledge table writer.
- **Supported excerpts:** Accept an exact registered evidence identity and bounded byte range; derive excerpt bytes server-side through existing verified original download/object ports. No arbitrary submitted prose becomes verified merely by attaching a citation. Record digest, immutable storage/acquisition version, byte boundaries and certainty “source says this,” not truth. Keep assertions distinct and allow them to link support without certifying their interpretation.
- **Lock order:** Preserve organisation advisory205 before engagement/Task fences. For same-organisation reuse spanning two engagements, acquire all required source/destination rows in deterministic order under that organisation fence. Cross-engagement reuse must not invert the existing lock order or hold database locks across object-store I/O.
- **I/O custody:** Object reads occur outside database transactions. Reauthorize source/session and validate exact registered identity plus current correction/dependency state at the knowledge write/disclosure boundary after I/O. Immutable bytes do not imply current source permission. Never hold a transaction across object-store I/O or expose acquisition credentials.
- **Encoding:** Use bounded UTF-8 decoding only, no PDF/Office parser process before qualified analysis. Byte offsets refer to original bytes. Preserve leading BOM/U+FEFF, CRLF and emoji; refuse invalid/non-boundary ranges instead of silently normalizing. Browser rendering must not strip BOM or count UTF-16 positions as byte offsets.
- **Period:** Preserve explicit versus unknown applicability. A later Task with unknown business period cannot silently treat a period-limited fact as current. Report meaningful omissions separately; scope/source access must filter before counts, ranking and display. Empty retrieval is not absence.
- **Preference inference:** A truthful deterministic learner can observe repeated explicit Expand/Reduce choices on Task inspection and learn only `task_inspection_layout`, with event/rule provenance, owner-private standing, inspect and Undo. Do not infer response verbosity or audit judgments from those clicks. Apply the layout preference only where the viewport supports it. Manual preference Save alone is not evidence of the canonical inferred-preference criterion.
- **No repeated override:** Undo or explicit preference correction must prevent identical past observations from immediately recreating the inferred preference. Track the consumed observation horizon and current owner choice; newly attributable changes remain inspectable. A preference never changes Permissions, review requirements or evidence standing.
- **Publication:** Exact own typed harmless preference release can expose that value to a currently assigned engagement without exposing private source conversation/events. Named same-client destination reuse retains every source ACL and requires current origin and destination authority. General arbitrary firm-wide publication is not required to implement permitted-scope promotion; existing Admin configuration supplies firm context without an audit-source bypass.
- **Correction:** Evidence is immutable acquisition identity. Same filename, digest or asserted source version does not supersede a source. Explicit same-original-scope source-correction declaration links registered old/replacement IDs with actor/reason/version/retry, invalidates bounded transitive dependencies and preserves both originals. Knowledge assertion correction is separate. Undo creates a fresh attributable event and does not automatically resurrect unchecked claims.
- **Producer ownership:** Methodology bindings and skill selections remain their owners' projections. “What Zobba is using” composes these with knowledge; it cannot replace current-use checks or imply agent invocation. Filter and revalidate each fragment's actual source authority, not only the knowledge record's broader eligibility label.
- **Automatic acquisition capture:** The canonical design calls for automatic supported observations, not only a manual knowledge editor. At verified supported plain-UTF-8 acquisition, commit an exact bounded excerpt and actor-source assertions (distinct standing), or a durable capture obligation with a real implemented consumer. Deduplicate by registered original/version/range. Unsupported/binary formats retain an explicit extraction limitation. Capture failure/capacity cannot silently lose a registered original or imply that retrieval is complete. Record a meaningful capture/omission state; do not ship a permanently unconsumed hook as completed automation. Decide and document legacy-original/Guide capture coverage during implementation, preserving all originals and accepted commands.
