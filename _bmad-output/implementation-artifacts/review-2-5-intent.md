# Story 2.5 intent alignment

This is a descriptive review of the supplied frozen-after-approval block and `C:/Users/opc/AppData/Local/Temp/intellifin-story25-review.diff`. No code was changed and no builds or tests were run. Test descriptions below identify assertions in the diff, not independently verified execution results.

## 1. Defensible readings of the intent

1. **Draft-authoring contract.** Evidence requirements and the Schedule become editable Builder data, owned by a Procedure Version. Grounding is a declaration validated when authoring, not proof that evidence already exists. The Schedule records a frequency, UTC time of day and derivation rule. The explicit prohibitions exclude capture, scheduling execution, period calculation and approval.
2. **End-to-end Auditor experience.** “Editable,” “stated reason,” “survive reload” and “inline on both sections” describe visible Builder behavior as well as a correct command and database representation. On this reading, browser interaction, refreshed cross-section state and rendered refusals are part of the expected outcome.
3. **Per-attribute versus per-system capture semantics.** “Per declared attribute” permits an author-created list of named attributes. “For agent-driven Target Systems” can mean either a version-wide capture policy whenever any selected system is agent-driven, or capture metadata specific to each attribute's source system. The frozen block does not define an attribute-to-system association.
4. **Pairing-only versus broader completeness.** The matrix explicitly makes manual-upload plus a recurring frequency saveable but blocked. The phrase “every other frequency requires a versioned-file or read-only-API binding” can additionally be read as requiring a blocker for a recurring Schedule with no binding. That is a broader completeness reading than detecting the explicit mismatched pair alone.
5. **Fixed UTC start.** A fixed UTC time of day is a defensible reading of “start time.” An absolute start timestamp is also linguistically possible in isolation; the frozen block does not specify a date or an initial occurrence anchor. The diff chooses time of day.

## 2. Reading implemented by the diff

The diff implements the Draft-authoring reading through the Builder, command, domain and persistence layers, with substantial coverage of the Auditor-experience reading. It stores a freely authored, version-owned attribute list and a nullable Schedule with `HH:MM` UTC time. It maps the four frequencies to recorded derivation identifiers, without adding execution or period derivation.

`EvidenceScheduleForm.tsx` supplies the two editors. The evidence validator rejects screenshot/recording-only grounding with the attribute name, accepts explicit model-read, and enforces bounded shapes. `updateEvidenceDraft` authorizes before validation, locks the version, guards the whole-row token, refuses stale/non-Draft edits, detects unchanged values and atomically writes a lifecycle event. The repository and generation-11 migration persist the typed fields; the row token includes them.

Capture metadata uses the version-wide interpretation: any current agent-driven target forces Structural Snapshot, screenshot and `platformCaptured` for every requirement. Target selection updates these fields in the same guarded write. No requirement contains a target-system identifier. Initial P-1 values and migration backfill derive platform capture from Template defaults, whereas later saves derive it from selected targets.

The completeness helper implements the explicit pairing reading: manual-upload plus non-once produces `upload-frequency-mismatch`; a missing binding or Schedule produces no evidence blocker. Population Source and Schedule render the mismatch while allowing saves. Empty evidence lists and unset Schedules remain representable.
