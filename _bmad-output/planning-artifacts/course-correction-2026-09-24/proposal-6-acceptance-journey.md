# Proposal 6 of 7 — The first end-to-end acceptance journey

Status: draft for owner review on 2026-09-25; awaiting a / e / s. Builds on the approved Proposals 1–5 (PRD revision 4, spine revision 5, EXPERIENCE.md and DESIGN.md revision 2, the Zobba design pack, the epic plan with its four gated slices). It specifies the one journey the first acceptance must complete: starting conditions, fixture data, expected observations, required decisions and observable evidence at each stage. **The scenario is acceptance data, never harness behaviour** ("Do not hard-code the scenario into the harness."). No implementation is authorised; the harness, fixtures and truth file named here are built by the stories Proposal 5 assigns, and this document is what they are checked against.

Standing constraints carried verbatim: "Initial connector testing will use my personal Google, Microsoft and other authorised accounts—not employer systems or company information."; "Personal-account testing must not be represented as proof that every organisational integration works."; "Credentials must remain outside model-visible content, and instructions embedded in documents, emails or external pages must not be allowed to change permissions."; "Preserve historical evidence, signed content and identifiers that existing records depend on."

## 1. Scenario (acceptance data)

Lumina Assurance (the tenant) audits Northstar Bank plc (the client). Engagement: **Q3 2026 ITGC**, period **1 July – 30 September 2026**, control **AC-07 — Leaver access removal**: *"Access of leavers is removed from the directory and from each in-scope application within five working days of the exit date."* Names follow the pack's reference screens (Daniel Okonjo, Ama Mensah, Nomsa Dlamini, Chipo Zulu, Peter Lungu, Bwalya Kunda). In-scope "systems" are represented by file extracts in the designated Drive folder — the directory and two applications, AccessGate and LoanCore — because the first acceptance uses Google connectors and no target-system browser session (Proposal 5 §6; the task-path browser connector is deferred).

The journey follows EXPERIENCE.md revision 2's Flows A–L in order (§3). The fixture is small enough to check by hand and large enough to carry every case the requirements name.

## 5. What the harness requires (the acceptance record)

- **Per record, per condition**: the 23 leavers × (directory, AccessGate, LoanCore) compared with `expected.json`; the swap case (two records' results exchanged) fails; an aggregate count alone never passes.
- **Signals and limitations independently checkable**: the post-exit login signal present as pending and absent from exceptions; the LoanCore limitation present with its source citation; the contractors' absence explained; each read from the stored claims, not from the rendered prose.
- **Statuses separate**: execution, input quality, assessment and review read from their own records on every Run and task.
- **Decisions bound**: every confirmation's bound details equal the details on the decision surface; a changed detail invalidates; no duplicate confirmation.
- **Provenance and containment**: no credential, invitation secret, OAuth token or provider identity in any artifact, snapshot, log, audit payload or model request (the catalogue-driven scan over every persistence subject); the embedded instruction changed nothing.
- **Personal-account labelling**: every connector result in the report carries "personal account · designated resources" and the enterprise requirements are documented separately, never claimed.
- **Sentences**: every fixed sentence the harness looks for is read from EXPERIENCE.md revision 2 on disk; agent explanations are checked for required facts, prohibited claims and links, never one phrasing.
- **Every computed check is required** (`report.required` equals the set the harness computes; a unit test proves it by mutation).
- **The conversational envelope** (3d §3, provisional bounds to be set in the Slice 1 story and recorded here when set): first visible reply, tool-call latency per connector, wait resumption time after an answer, scheduled-run start delay after its boundary.

## 7. Negative and adversarial cases carried from the existing acceptance discipline

The catalogue-driven credential scan (2026-09-08), the "check the FIRST failure" rule, the per-record truth comparison, the required-check mutation test, the hostile-fake connector conformance and the injection evaluation set are reused as they are. The acceptance additionally asserts: a message that looks like a command ("approve this") grants nothing; a suggested reply submits only its text; the Stop control shows Stop requested before Stopped by you; leaving and returning mid-task restores the conversation, the selected artifact and the pending decision; switching to the Kafue Mining engagement (a second, empty engagement seeded for the purpose) carries no attachment, selected resource or unsent draft across.

## 8. What the first acceptance does not prove (kept visible)

Task-path browser execution; spreadsheet production and PDF export; Gmail sending beyond refusal; organisational (enterprise) integrations; regression execution; model replacement; retention operations; investigation as a separate task from a recurring run; Microsoft connectors. Each is deferred per Proposal 5 §6 and reported as "not demonstrated" in the acceptance record rather than omitted.

## 9. Deliverables this proposal creates (built by their stories, not now)

`tests/fixtures/acceptance/northstar-q3-2026/` (the generator, the sheets and Docs as CSV and text, `expected.json`, the cover notes, the truth for both scheduled runs); `scripts/verify-acceptance-journey.mjs` with `tests/unit/acceptance-journey.test.ts` (required-check mutation, sentence pinning, swap case); the acceptance workflow that refuses to start unless the candidate revision's Slice 0–3 gates are green and `/sign-in` serves the hydration marker; the acceptance record (secret-scanned report, screenshots per stage, labelled real versus injected).

## Why

Direction §H ("the first connector demonstration should show the agent finding a document, preserving the original, analysing a working copy, producing an output, using email or calendar context and completing an explicitly authorised collaboration action… prove that prohibited source changes are refused and connection failures are reported honestly"); Proposal 1 §2.3's first acceptance case; Proposal 5's slices and §6 boundary; the pack's scenario names; the existing acceptance discipline (per-record truth, required checks, sentences pinned to the contract). No implementation is authorised.
