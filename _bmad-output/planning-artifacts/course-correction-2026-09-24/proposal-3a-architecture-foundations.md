## C1 — Tenancy and scope enforcement

**(1) Requirements:** FR-53, FR-54, FR-83, FR-84; supports FR-80 (retrieval scope) and FR-65. Extends AD-8, AD-11 (tenant isolation leaves the Deferred list) and AD-22 (chain ownership binding, below). No contract is superseded; every new contract in 3b–3c inherits this one.

**(2) Approach**

- *Introduced:* `tenant`, `tenant_membership` (user × tenant × role), `client`, `engagement_membership` (user × engagement × role), `execution_delegation`. The scope model lives in `packages/domain/src/identity/scope.ts`; the application owns `requireScope` / `resolvePrincipal`; infrastructure owns the transaction wrapper, roles and policies.
- *Table classification first.* Before any policy is written, every existing and new table is classified as one of: **tenant-owned** (methodology packs, skills, mandate policy), **user-owned** (preferences, connections), **client/engagement-owned** (engagements, tasks, conversations, evidence, artifacts, memory, Runs and their children), **global authentication** (Better Auth user/session/account/rate-limit rows), or **platform infrastructure** (pg-boss schema, `schema_meta`, worker heartbeat). Each class gets its own policy shape; authentication and infrastructure tables are not given a tenant policy to satisfy a table count. The classification is a checked-in table and a test fails when a table is unclassified.
- *Columns:* every protected table carries `tenant_id NOT NULL`, and `client_id` / `engagement_id` / `owner_user_id` where the record's meaning requires them (FR-53). **Scope-consistent references:** foreign keys are composite where a child references a protected parent — `(tenant_id, parent_id)` referencing `(tenant_id, id)`, and `(tenant_id, engagement_id, parent_id)` for engagement children — so a permitted row cannot reference another tenant's or client's protected object even through a valid id.
- *Runtime roles and policies.* Two database roles: the **release migrator** (table owner; the only role that runs DDL and backfills) and the **application runtime** role, `NOSUPERUSER NOBYPASSRLS`, not the owner of any table, used by web and worker. Every protected table has `ENABLE ROW LEVEL SECURITY` **and** `FORCE ROW LEVEL SECURITY`. Each protected table and supported command has an explicitly scoped **permissive grant policy**, together with the mandatory **restrictive policies** for its applicable boundaries (tenant, client, engagement, owner). PostgreSQL grants a row only when at least one applicable permissive policy passes AND every applicable restrictive policy passes; the permissive policy is scoped to the principal's membership, so it never grants beyond it, and no additional permissive policy may bypass the mandatory restrictions. `USING` governs which existing rows a `SELECT`, `UPDATE` or `DELETE` may target; `WITH CHECK` governs the row an `INSERT` or `UPDATE` proposes. The policy inventory (checked in beside the classification table) documents the complete combination for ordinary users, execution delegations and maintenance principals. Missing or invalid principal context denies access: zero rows and no writes.
- *Scope immutability, separate from row eligibility.* `USING` and `WITH CHECK` decide eligibility; neither proves an ownership column stayed unchanged. Ownership columns (`tenant_id`, `client_id`, `engagement_id`) are held immutable by a `BEFORE UPDATE` trigger on every protected table that compares `OLD` and `NEW` and raises on any change; the migrator installs it and the runtime role cannot alter or disable it. Engagement-owned children carry `tenant_id` and `engagement_id` and reach the client through the engagement; client-bound material (snapshots, client-scoped connections, client memory) carries `client_id` directly and can exist only once the engagement is bound. The one permitted ownership change is therefore the **initial binding** of an unbound draft engagement (`client_id IS NULL → client`) on the engagement row itself: a separate, validated and audited command, admitted by a `SECURITY DEFINER` function owned by the migrator that accepts only that transition and only for a client the actor is a member of. Ordinary updates cannot reassign protected records across scopes, and the binding is not a route for relabelling existing client material, evidence history or active tasks. Owning a resource personally does not override a client restriction attached to that resource.
- *Column restrictions for maintenance principals.* RLS controls rows; column privileges are a separate mechanism. The reconciliation principal is granted `UPDATE (receipt_state, receipt_recorded_at, receipt_reference)` on `task_step` at the column level and no `UPDATE` privilege on any other column or table; its restrictive policy limits which rows. Neither mechanism is described as doing the other's job.
- *Principal context.* The wrapper sets `app.actor_id` and `app.tenant_id` with `SET LOCAL` inside the transaction, from the authenticated session's membership, and every scoped read or write runs inside such a transaction. The membership check itself is a bounded query (FR-53's "authorisation may itself require bounded membership or resource-metadata queries") performed under the wrapper before the principal is trusted for the rest of the transaction.
  - *Boundary statement.* Only trusted infrastructure establishes database principal context. Model-generated SQL and sandbox code never execute against the application database or obtain its runtime connection. Untrusted inputs cannot supply SQL that changes principal settings. RLS addresses: a repository or handler that forgets a filter; a query written against the wrong scope; a compromised or mistaken application code path that runs ordinary queries with a legitimate principal. RLS does **not** contain a fully compromised trusted database client that can execute arbitrary SQL with the runtime role's privileges: such a client can read and write every row the runtime role can reach, across tenants. The code boundaries (no model or sandbox access to the database), the runtime role's limited privileges and the audit chain are **mitigating controls** that reduce the likelihood and the undetected window of that compromise; they are not a guarantee of containment. The residual threat is stated here explicitly, is accepted for the synthetic-data phase, and is one of the isolation gates real-data adoption must re-assess (PRD §7).
- *Background execution (FR-84).* Audit work executes under an identifiable, bounded delegation: `execution_delegation` (delegating user, tenant, engagement, scope, approver, created-at, revoked-at); a job carries the delegation id and the wrapper opens its transactions as that principal, re-reading the delegation and the delegating user's current membership at each claim and resume (FR-83). Platform maintenance — credential revocation, timeout handling, receipt reconciliation, sweeps — uses explicitly defined **service principals** with narrow, operation-specific authority expressed as their own RLS policies (for example: the reconciliation principal may update `task_step.receipt_state` and nothing else). There is no general-purpose worker identity with unrestricted tenant access. Consequence: when a user disconnects an account or loses membership, revocation and the recording of an already-dispatched operation's eventual outcome remain possible without restoring that user's permission to start new work.
- *Retrieval, caches, summaries.* There is no index today. Any index introduced in 3c stores `tenant_id`, `client_id` and `engagement_id` in each row under the same RLS boundary and filters by scope before ranking. Caches and summaries (FR-87) are stored records with the same scope, never process-wide state.
- *Migration plan (security work, not mechanical).* (a) classify tables; (b) add columns, backfilled to the owner's single-owner tenant (decision 3), with the mapping written down per table; (c) create the roles and rotate the web and worker connection strings to the runtime role; (d) enable and force RLS with the policies; (e) route the six `UnitOfWork` classes and the raw `db.transaction(` sites through the wrapper, refusing to open a scoped transaction without a principal; (f) queued and in-flight work: drain workers before the migration (AD-15), and jobs enqueued before it are re-validated against a delegation created for the owner at migration time; (g) `SUPPORTED_SCHEMA_MIN/MAX` moves so an old build refuses to start against the scoped database; (h) recovery: the migration is reversible only before RLS is forced (the expand step), and the release runbook says so.
- *Historical ownership binding (AD-22).* Historical event and evidence bytes remain unchanged; `tenant_id` sits outside their hashed envelope, so those hashes do not authenticate the tenant assignment. The migration therefore writes an **ownership binding** per aggregate chain: `(aggregate_id, tenant_id, chain head hash at migration, event count, migration id)`, canonical-JSON, signed with the AD-22 `ManifestSigner` key, versioned, and stored beside `audit_event_heads`. **New chain segments** use envelope version 2, which puts `tenantId` (and `engagementId` where applicable) **inside** the hashed, canonicalised envelope; AD-14 upcasters read v1 and v2. Chains stay per aggregate (the current `audit_event_heads` model); the aggregate-to-tenant binding is what makes them tenant-partitioned, so an export contains only the requesting tenant's aggregates and their bindings and verifies without any other tenant's rows. Verification detects an attempted reassignment: changing an aggregate's `tenant_id` invalidates its binding signature, and a v2 event appended under a different tenant fails the chain check.

**(3) Failure and verification**

- Run against the **deployed runtime role**, not a convenient test role: a fixture asserts the role is `NOSUPERUSER NOBYPASSRLS` and owns no table.
- **Positive tests first**: for each principal class (ordinary member, execution delegation, each maintenance principal) and each intended operation, an authorised principal performs it and the row is read or written. A system that denies everything must not pass the isolation acceptance suite.
- Two synthetic tenants, two clients in one tenant, two engagements of one client, two users with private records. Every read, write, retrieval, export, background claim and connection use is attempted across each boundary through the real repositories AND through raw SQL under the wrapper; each must return nothing or refuse. Negative **writes**: cross-scope insert, update that changes `tenant_id` / `engagement_id`, delete of another scope's row, and an insert whose composite foreign key points at another scope's parent — each refused. **Ownership immutability**: an actor who is a member of both client A and client B updates an existing protected record of A to name B and is refused by the trigger, through the repository and through raw SQL; the initial binding of an unbound draft engagement to a client the actor belongs to succeeds and is audited; a second binding, a binding to a client the actor is not a member of, and a binding attempted by a plain `UPDATE` rather than the command are each refused. **Column privileges**: the reconciliation principal updates `receipt_state` on a row its policy permits and succeeds; it updates any other column of that row, or any column of another table, and is refused by the privilege check.
- Context tests: missing principal (zero rows, no writes), rollback (the setting does not leak), connection-pool reuse (a second transaction on the same connection with no principal sees nothing), concurrent requests with different principals on one pool, and a query outside the wrapper.
- Unauthorised selectors are rejected before protected content is returned or an effect is performed; the test asserts the refusal and that no protected row was read into the response.
- Delegation and service principals: revoked delegation, removed membership and downgraded grant each stop a queued and a resumed job before dispatch with a recorded reason; the reconciliation principal cannot read conversation content or write artifacts.
- History: the existing chain-verification tests stay; a **tampered-ownership** test reassigns an historical aggregate's `tenant_id` and asserts the binding fails; a tenant export verifies with the other tenant's rows absent.
- Runs before any personal account is connected (decision 3) and on every release.

**Changes to existing safeguards:** chain, evidence and Run tables gain `tenant_id`; historical canonicalisation is unchanged; ownership is authenticated by the signed binding and by envelope v2 going forward. The migrator and runtime become different database roles. The "web never reads object storage" rule is unchanged.

## C2 — Engagement and Agent Task aggregates

**(1) Requirements:** FR-52, FR-55, FR-56, FR-57, FR-59, FR-87, FR-88. Extends AD-3, AD-16, AD-17 and `durable-escalation-v1`, `run-pause-v1`, `run-request-token-v1`. Leaves `executable-plan-v1`, `run-result-v1`, `run-level-gate-v1` intact for the recurring-check path.

**(2) Approach**

- *Introduced:* `engagement` (draft-capable: every field but tenant and creator nullable at creation; FR-52), `conversation` (engagement-scoped; messages reuse the immutable-metadata + encrypted-content split of `run_conversation_message` with a new owner key), `agent_task` (owner, engagement, conversation, mandate version reference and digest, state machine `QUEUED → RUNNING → WAITING → PAUSED → COMPLETED | CANCELED | FAILED`, revision, lease, budget with reserved and consumed counters), `task_step` (the step ledger; see dispatch semantics below), `task_wait` (kinds `clarify`, `confirm-action`, `reconcile`, plus the existing closed-option kinds), `task_interaction_command` (receipts, the `run_interaction_command` transitions).
- *One-time work is fully capable.* Agent Tasks can produce evidence-linked assessments, candidate findings, limitations and reviewable artifacts without becoming recurring checks. They use the shared evidence-validation and review safeguards through the artifact and task contracts defined in 3b–3c. Promotion is optional. What a task never writes is the **existing Run-path tables** (`run_result`, `run_gate_check`, `run_exception`); a task's assessments are artifacts with their own review state (3b) and their own gate-style checks (3c).
- *Draft engagement and client binding.* A draft engagement may have no client. Before any client material enters its context (a snapshot, a connection scoped to a client location, a client memory item), the engagement must be bound to the client scope; the binding is a typed command. A missing client never means unrestricted client access: with no client bound, only tenant-wide and the user's own resources are reachable.
- *Reused, keyed by task:* the claim/lease/revision guard (`guarded`), the controller lease (`run_control_lease` shape), the one-open-wait invariant and deadline job (`run_wait` mechanics, pg-boss singleton `wait:<id>`) **applied per task** — an open wait freezes its own task, never the engagement's other tasks or conversations — the receipt ledger and "first use of a request key decides", the audit chain, the live channel (`openRunTimelineStream` generalised to any chained aggregate), pause and cancel boundaries.
- *Not relaxed:* `audit_run.version_id` stays `NOT NULL`.
- *Dispatch and reconciliation semantics (FR-66, FR-88).* Every external-effect step has a durable **operation identity** (task, step, bound material details, digest), one or more **attempt identities**, and a **dispatch claim** (worker, lease epoch, claimed-at) written and committed **before** dispatch. The dispatch happens outside any database transaction. Outcomes are recorded per attempt as one of: `not-dispatched`, `possibly-dispatched` (claim written, no result), `accepted` (provider acknowledged, effect pending), `confirmed`, `unresolved`. A replacement worker that finds a `possibly-dispatched` attempt may not start a new attempt while the earlier one may still complete: it first waits out the attempt's declared completion window and runs the connector's reconciliation (C4); A **positive lookup** that identifies the original operation records its actual state: if the effect completed, completion is recorded without performing it again; if it is still pending, that same operation continues to be observed or reconciled. A **negative lookup** permits a new attempt only where the connector can establish that the original operation was not applied and cannot subsequently complete (`lookup-establishes-absence`); otherwise the outcome remains `unresolved`. Reissuing the same operation under a valid provider-supported idempotency guarantee is a **separate** recovery mechanism: it retains the original bound operation details, respects the provider's key scope, lifetime and payload rules, and is refused when any of those no longer hold. Expiry of a local completion window, lease or timeout is not itself proof that an external effect did not occur or cannot still occur. An `unresolved` attempt puts the task into a `reconcile` wait — a distinct decision, not a `confirm-action` prompt that invites sending the same message again. Its options: **keep observing**; **mark done manually**, which records an attributable human resolution with its supporting reference and never manufactures a provider-confirmed receipt (the ledger shows `resolved-by-human`, never `confirmed`); **retry**, which a human request does not by itself make safe — where duplication remains possible the uncertainty is retained and shown, and the retry is not presented as guaranteed duplicate-free; **abandon**. A **late receipt** for an earlier attempt is recorded against that attempt through a narrow reconciliation path run by the reconciliation service principal; a stale worker holding an expired lease can write that receipt and nothing else.
- *Interruption and stop.* Pause and cancellation prevent further dispatch at the supported boundaries and request interruption of in-flight work where the connector supports it. The UI shows "stop requested" until the worker records cessation; an action already performed is never described as undone.
- *Ownership:* domain owns the task state machine, wait rules and receipt-state transitions; application owns the commands and the step-ledger writer; infrastructure owns storage and the queue. Execution is worker-only under a delegation (C1).

**(3) Failure and verification**

- Races: two claimants on one task; stale-revision resume refused; lease expiry **before** dispatch (claim not written → the replacement dispatches once) and **after** dispatch (claim written → the replacement waits, reconciles, and never dispatches twice while the first may complete).
- Crash points at the three FR-88 moments; late responses after cancellation and after revocation land on the original attempt; concurrent reconciliation by two workers produces one recorded outcome.
- Reconciliation outcomes, each asserting that no second external effect is produced: a completed action found by positive lookup (completion recorded, nothing sent); an accepted-but-pending action (observation continues, nothing sent); an inconclusive negative lookup from a `lookup-positive` connector (stays `unresolved`, `reconcile` wait opened); a late completion arriving after the local completion window (recorded on the original attempt, a retry already refused or still pending is not dispatched); manual resolution (ledger `resolved-by-human`, no `confirmed` receipt); a human retry where duplication remains possible (uncertainty shown, not labelled duplicate-free).
- A stop during an in-flight effect: the effect completes, the receipt is recorded, the task ends `CANCELED` with the action visible.
- Per-task wait isolation: an open wait on task A leaves task B and the conversation usable.
- Draft engagement: a client-scoped read with no client bound is refused; binding a client then permits it.
- SSE gap/duplicate property for task streams.

**Changes to existing safeguards:** AD-7's "free text from humans is never passed to the model" and AD-16's "no model conversation state is persisted across a wait" are replaced (3d). The one-open-wait rule keeps its meaning at task scope.

## C3 — Mandate and the authorisation gate

**(1) Requirements:** FR-3, FR-60, FR-61, FR-62, FR-83. Supersedes `tool-action-v1`'s scope source and action vocabulary; keeps its gate shape. Amends AD-4 and AD-9 (3d).

**(2) Approach**

- *Stored definitions.* `mandate_policy` (administrator ceiling per tenant: allowed connectors, effect classes, confirmation defaults, budgets) and `engagement_mandate` (the auditor's grant for an engagement: connections named, source locations, output locations, effect classes enabled within the ceiling, confirmation choices). Both are **versioned canonical documents** stored in full; the digest identifies a version and is frozen on the task as the reference to the frozen authority. A digest alone never describes permissions.
- *Effective authority per operation* = task's frozen authority ∩ current administrator ceiling ∩ current membership and grants ∩ current execution delegation ∩ current engagement and resource restrictions ∩ applicable connection restrictions (scopes granted, state). A change can remove one permission while adding another: frozen {A, B} and current {B, C} yields {B}; neither the old A nor the new C is available until the auditor re-freezes. The proposed operation is evaluated against the resulting intersection; an unrelated narrowing never refuses an otherwise permitted operation. Confirmation requirements combine conservatively (any layer requiring confirmation requires it); budgets account for consumed and reserved amounts.
- *Gate outcomes.* `authorizeToolCall(effectiveAuthority, call)` in `packages/domain/src/mandate/` — pure, ordered, first decisive rule wins, closed vocabulary — returns one of **allowed**, **needs-clarification** (a required parameter or target cannot be resolved), **needs-confirmation** (permitted, confirm-required), **denied** (with a closed reason). Order: connection or internal capability permitted → operation declared → effect class enabled → resource inside the permitted location class for that effect → parameters valid against the declared schema → budget → confirmation. Called at the port call site in application (`performToolCall`), never in an adapter. A `denied` outcome is `security.action-denied`, terminal for that step, never retried and never re-attempted through another tool; a later, explicitly authorised Mandate amendment can support a **new, linked** attempt. A `needs-confirmation` outcome is not a security event.
- *Internal tools* (search context, run analysis, revise artifact, propose memory, request decision, promote check) pass the same gate without a connection: their descriptor declares `connection: none` and the connection rule is skipped, not faked.
- *Capability summary to the model.* The model never sees the Mandate documents. It receives a safe capability summary derived from the effective authority — usable tools, resources it may address, relevant limits and which operations will ask for confirmation — so it can plan without probing; enforcement stays in the application.
- *Resource boundary (FR-3).* Locations are identified by **canonical account and resource identity** per connector (a Drive file or folder id and its drive; a mailbox account and label id; a calendar id; for browser and HTTP targets an origin plus path after redirect resolution), never by display path alone; containment is evaluated on the canonical identity (parent chain for files, account for mail, origin for web). Aliases, shortcuts and moved files resolve to their canonical target before the check; overlapping source and output locations resolve **source-wins**; a browser redirect is re-checked at the destination. A connector or browser operation whose actual write target cannot be safely established does not execute that write.
- *Source protection is absolute.* Original received evidence, preserved snapshots and audited operational source records cannot be made writable through Mandate changes or a second-person approval. Where the auditor needs an editable version, the platform creates a distinct authorised **output copy** (a working artifact) in an output location. Closing an artifact does not remove source protection. Legitimately editable working artifacts remain versioned outputs; preserving a snapshot of one (for evidence) does not convert its future revisions into prohibited source mutation. The sandbox mounts sources read-only and has no connector access; a browser write hits the same location rule.
- *Ownership:* domain (authority computation, gate), application (call-site enforcement, receipts, capability summary), infrastructure (storage).

**(3) Failure and verification**

- Unit: a killing test per gate rule; a table over (effect class × location class × operation × outcome); the intersection test with frozen {A, B} / current {B, C}; confirmation combination; budget with reserved amounts.
- Resource tests: source write refused via connector, script and browser; alias and shortcut resolved to a protected canonical target and refused; moved file; overlapping locations resolve source-wins; redirect to a protected destination refused; an unresolvable write target does not execute.
- Mutation harness (the `verify-*-mutations.mjs` pattern) on the location rule, the intersection, the source-wins rule and the denied-never-retried rule.
- Integration: a grant revoked between dispatch and resume; a connection scope reduced at the provider (simulated) — each refuses that operation only, and an unrelated permitted operation still runs.

**Changes to existing safeguards:** `PERMITTED_READ_ACTIONS` and the write-verb ban stay for Target System registrations on the Run path; connectors use effect classes, and the canonical-resource rule carries the source-protection guarantee. The earlier draft's second-person reclassification exception is **withdrawn**.

## C4 — Connector framework, connections, credential broker, model-data policy

**(1) Requirements:** FR-63, FR-64, FR-65, FR-66, FR-67, FR-68, FR-89. Extends `credential-containment-v1`, `agent-workspace-v1` (the browser becomes one connector), `workspace-capability-v1` (tokens are capabilities) and AD-4/AD-10.

**(2) Approach**

- *Connector framework (introduced).* `ConnectorDescriptor` (id, version, operations: name, effect class, parameter schema, confirmation default, idempotency capability with its guarantee, key scope, expiry and payload binding; reconciliation capability `none | lookup-positive | lookup-establishes-absence`; location types; result validation rules), a `ConnectorPort` in application implemented per provider in infrastructure, and a shared conformance suite. Internal tools implement the same descriptor and go through the same gate and ledger (FR-64) under a common invocation model.
- *Connector results are two things.* **Invocation outcome:** `not-dispatched | accepted-pending | confirmed | denied | failed-before-effect | unknown-after-dispatch`. **Returned-data quality:** `complete | partial | empty-under-contract | unknown`. A timeout after dispatch is `unknown-after-dispatch`, never `unreachable`; an outage before dispatch is `failed-before-effect` with reason `unreachable`. Exact names are settled in the contract; the distinctions are mandatory.
- *Verification of claimed effects.* An adapter's success is not trusted on its own shape: operations declare provider references (event id, message id, file id), operation-specific validation (the returned object matches the bound material details), and read-back where the provider supports it. Action status shown to people is derived from the step ledger; generated narrative references those receipts. This reduces overstatement; it is not claimed to make overstatement impossible.
- *Connections (introduced).* `connection` (tenant, owner user, connector, canonical account identity, scopes granted, state `active | disabled | revoked`, timestamps) and `connection_secret` (encrypted refresh and access tokens, AES-256-GCM under a new `CONNECTION_SECRET_KEY`, AAD-bound to tenant, connection id, provider and account identity, and secret and key version; key rotation re-wraps under the new version inside the broker; recovery never exposes plaintext outside the named components). **Disconnect ordering:** disable is written and audited in one transaction; the gate reads connection state inside the same transaction as its dispatch claim, so dispatch not yet authorised is refused after local disable; a refresh completing after disable, or a cached credential, cannot reactivate a disabled connection (the broker checks state before writing any token); already-dispatched operations are interrupted where supported and otherwise reconciled truthfully — their effects may still complete, and disconnect does not undo them. Provider-side revocation is a separate state (`revoked`) reached by a maintenance job under a service principal; local disable and provider revocation stay distinct because providers propagate revocation with delay.
- *OAuth transaction and credential broker (the narrow components FR-63 asks for).*
  - `connection_attempt`: single-use, bound to the initiating user and session, tenant, connector, requested scopes, exact registered redirect URI, `state`, PKCE (S256) challenge, created-at and expiry.
  - Attempt creation (the named **authentication-initiation handler** in web): generates `state` and the PKCE verifier, derives the S256 challenge, **immediately seals** the verifier for the broker with a public-key envelope (libsodium sealed box or an equivalent vetted HPKE library — no custom scheme) and discards its plaintext reference. Only the challenge goes into the authorisation URL; the verifier is never returned to the browser. *Trust-boundary choice, deliberate and narrow.* PKCE requires the client to generate the verifier and send its derived challenge; it does not prescribe which server-side component of our application generates it. We accept transient verifier generation in the authenticated web handler rather than requiring a broker round trip solely for URL construction. The named initiation handler may transiently process the verifier and the named callback handler may transiently process the authorisation code; neither value is exposed to the model, ordinary application logs or persistent plaintext storage. Provider access tokens, refresh tokens, client secrets and broker decryption keys remain outside the web process. These two exceptions grant no general-purpose secret access to any other web handler.
  - Callback route (`apps/web/app/api/connections/[connector]/callback/route.ts`, the one named web component): validates `state` against the attempt **and** the current session (same user, tenant, attempt not expired or used), applies the provider's defined mix-up defence (next bullet), seals the authorisation code for the broker, marks the attempt `code-received`, redacts the code from logs and traces, and enqueues a bounded, prioritised exchange job. A duplicate callback for a used or expired attempt is refused; the route never holds a client secret or a token.
  - Mix-up defence: every supported provider has a defined one, recorded in its `ConnectorDescriptor`. Where the provider returns the `iss` response parameter (RFC 9207), the callback validates it against the attempt's provider. Where it does not, the attempt uses a **distinct, issuer-bound redirect URI per provider** and the callback validates that the response arrived at the URI registered for the attempt's provider (the alternative the OAuth security guidance, RFC 9700, documents). The defence is never silently omitted; a provider offering neither is not supported.
  - Broker (`packages/infrastructure/src/connections/connection-broker.ts`, worker-only; new rule `no-connection-broker-in-web`): unseals verifier and code with its private key (held only by the worker), re-validates the attempt and the initiating user's **current** authority, exchanges the code with the provider using PKCE, validates the token response and granted scopes against the request, encrypts the secrets, activates the connection, and audits. *Exchange recovery.* The broker persists a **token-exchange attempt** (`exchange_attempt`: attempt id, state `not-dispatched | failed-before-dispatch | dispatched-outcome-unknown | redeemed | abandoned`, dispatched-at) and commits it **before** the token request is sent. An authorisation code is single-use: a response lost after possible dispatch must not revert the attempt to an unconsumed-code state and must not trigger generic automatic redemption retries, because the provider may already have consumed the code and may revoke tokens issued from it on reuse. Recovery is per state: `failed-before-dispatch` (the request provably never left — local validation failure, connection refused before the request was written) may be retried within the code's lifetime; `dispatched-outcome-unknown` uses a documented provider-supported recovery mechanism where the adapter declares one, and otherwise leaves the connection inactive and requests a new authorisation flow. A token result that was received and encrypted locally but whose activation did not commit may be used to finish the **original** activation after rechecking the initiating user's current authority. An unknown or missing token result is never represented as an active connection. An expired queued code likewise produces a reconnect request, never a fabricated active connection. *Refresh recovery.* Refresh is serialised per connection (a row lock) and refused for a disabled connection. Serialisation stops concurrent callers; it does not resolve a response lost after token rotation, and blind reuse of the previous refresh token is not a universal answer because rotation can invalidate it. Each adapter records its provider's rotation and recovery behaviour (reuse grace window, recovery call, or reconnect required); a lost refresh response moves the connection to `refresh-unresolved` and follows that recorded behaviour, ending in `active` only on a verified token or in a reconnect request. Disconnect during exchange: the attempt is abandoned and any received token is revoked, not stored.
  - `connector-credentials.ts`: resolves a connection into a `ResolvedCredential` bound to the **already-approved destination and operation** (the closure authorises only requests matching that binding; a general `authorize(headers)` is not a resource boundary), wrapped by `guardedCredentials` so every artifact freeze and model request is scanned.
- *Disclosure policy (FR-89).* `disclosure_policy` per tenant, optionally narrowed (never widened) per engagement. A decision combines the item's content type, sensitivity, and source and scope restrictions with the approved provider deployment, endpoint or account, and configuration. Derived summaries, extracts and redactions inherit their inputs' restrictions unless an authorised transformation explicitly records a different classification; combining allowed and restricted material never downgrades the restricted material. The policy is applied before every outbound model request, including resumed context and fallback; any future embedding, indexing or model-observability service sits inside the same boundary. An unknown classification or an unapproved destination blocks the request and does not silently select another provider; the raw source is preserved unchanged and the permitted derived representation is recorded with provenance.
- *Ownership:* domain (descriptor and result types, policy evaluation), application (ports, conformance suite, gate call site, attempt creation), infrastructure (adapters, broker, secret storage, callback route), worker (all runtime connector I/O and the broker), web (callback route and the connections settings UI, which reads state and never secrets).

**(3) Failure and verification**

- Conformance suite per adapter: refusal, partial data, failure before effect, timeout after dispatch (must be `unknown-after-dispatch`), a plausible-looking but unverifiable success (fails validation without a provider reference), an accepted-but-not-completed operation, idempotent retry per declared capability, and the empty-versus-unreachable distinction. The hostile fake adapter proves specified malformed and contradictory responses are rejected; it is not claimed to prove an arbitrary adapter cannot lie.
- Reconciliation: a positive lookup of a completed effect records completion and sends nothing; a positive lookup of a pending effect continues observation; a negative lookup from a `lookup-positive` connector leaves the outcome unknown; only `lookup-establishes-absence` permits a new attempt; idempotent reissue is tested as its own path and is refused on key-scope, lifetime or payload mismatch rather than treated as fresh dispatch.
- OAuth: swapped `state`, wrong user, wrong tenant, replayed callback, expired attempt, expired queued code, disconnect before activation, concurrent refresh. **Exchange recovery**: a failure before token-request dispatch (state `failed-before-dispatch`, retry permitted and succeeds) versus a response lost after successful redemption (state `dispatched-outcome-unknown`, the code is never resent, the fake provider's second redemption would fail and revoke, the connection stays inactive and a reconnect is requested — or the declared provider recovery completes it); a locally encrypted token result whose activation did not commit finishes the original activation after the authority recheck; duplicate queued exchange jobs (the second reads the attempt state and sends nothing). **Refresh recovery**: a refresh response lost after rotation follows the adapter's recorded behaviour and never blindly reuses the old token; the connection ends `active` only on a verified token. **Mix-up defence**: for a provider with `iss`, a response carrying another issuer is refused; for a provider without it, a response arriving at another provider's issuer-bound redirect URI is refused. Runtime tests in addition to config typing and boundary plants.
- Disconnect: dispatch after local disable refused; a refresh completing after disable does not reactivate; an already-dispatched operation's late receipt is recorded and shown; provider revocation failure leaves the connection disabled.
- Disclosure: a restricted item blocks the provider and the fallback (adapter never called); a derived summary of restricted material inherits the restriction; an unknown classification blocks.
- Personal-account acceptance (FR-68) on designated resources; enterprise requirements documented separately, not claimed.

**Changes to existing safeguards:** `CREDENTIAL_TOKENS` stays for Run-path registrations; connections are a second, per-user credential source with the same containment shape. Worker-only secrets gain `CONNECTION_SECRET_KEY`, the broker private key and the OAuth client secrets. The credential scan remains supplementary.
