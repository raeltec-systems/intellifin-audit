# Proposal 3b of 7 — Architecture: sources, evidence, working material, artifacts, controlled execution environment

Status: draft for owner review on 2026-09-24; awaiting a / e / s. Builds on the approved 3a baseline (D-3a-1..4) and carries its dependencies forward: scoped tables with composite scope keys and envelope v2 (C1); absolute source protection with output copies (C3); invocation outcome versus data quality on every acquisition (C4); delegation for background work (C1). Nothing here reopens a settled 3a decision.

Baseline facts checked on `main` `c18ad36`: every stored byte is Run-owned immutable Evidence (`run_evidence.run_id NOT NULL`, five closed kinds, idempotency key `evidence-v1:<runId>:<kind>:<scope>`); the reserve → `putIfAbsent` → read-back → size/SHA-256 → `REGISTERED` sequence is one implementation (`freezeArtifact`) behind the credential guard; the object store never overwrites and the post-Run integrity sweep re-verifies; worker-signed read grants keep the web out of object storage (`no-evidence-store-in-web`). There is no source-identity metadata (provider, external id, revision or etag, modified time, query), no working copy, no derivation or lineage record, no artifact versioning outside `procedure_version`, no document-processing path beyond `sheet`, `json` and `web_tree`, and no code-execution runtime of any kind (`@solarisdk/sandbox` is named in the spine and installed nowhere).

Owner decisions this proposal asks for:

| Decision | Proposed choice |
|---|---|
| D-3b-1 | Sealing has three units: each registration is immutable on its own; an Agent Task seals a task evidence package at its terminal state (the `SealPackage` shape, owner-namespaced); an artifact version's **approval** freezes the exact evidence and artifact versions it cites. No seal waits for a Run. |
| D-3b-2 | The execution environment is a separate sandbox process with kernel-level isolation (a container or microVM per execution in deployment). A same-host `local` mode exists for development and is recorded on every execution record as the weaker guarantee, exactly as `run_workspace.mode` does for the browser. |
| D-3b-3 | FR-90's initial formats are `.docx` and `.xlsx`, produced from pack templates inside the sandbox; PDF is an export of a produced document, not an authored format. Fidelity tests are named in C7. |
| D-3b-4 | Working material is retained with its task under the engagement's retention policy and is never promoted to evidence in place; a derived output is registered as a **new** immutable object with a derivation record. |

Each change states: (1) requirement mapping and the contracts it supersedes or extends; (2) implementation approach — reused, generalised, introduced — with ownership of state, authorisation, credentials and execution; (3) failure and verification approach; and, explicitly, any change to an existing safeguard.

## C5 — Source snapshots: evidence generalised past the Run

**(1) Requirements:** FR-69, FR-67, FR-72 (input status), FR-3 (source-side); extends `evidence-package-v1`, `population-acquisition-v1`, `capture-grounding-absence-v1`, AD-5, AD-18. Leaves the Run-path kinds, keys and object layout untouched: an artifact frozen by an earlier build still resolves to the same object.

**(2) Approach**

- *Owner-namespaced reservation (generalised).* The idempotency key becomes `evidence-v2:<ownerKind>:<ownerId>:<kind>:<scope>` with `ownerKind ∈ {run, task, artifact-version}`; the `evidence-v1` prefix and the Run object layout stay for Run owners. `evidenceIdFor` and `evidenceObjectKeys` gain the owner; the object layout for new owners is `<tenant>/<ownerKind>/<ownerId>/<kind>/<scope>`. Same `freezeArtifact`, same guard, same `putIfAbsent`, same read-back and digest rule, same "never demoted".
- *New kinds (closed, extended by name):* `source-snapshot`, `extraction-record`, `derived-output`, `generated-document`, `execution-log`. `REQUIRED_EVIDENCE_KINDS` stops being keyed by Template: a Task declares what it requires per step (3c), a Run keeps the Template table until compiler-2 replaces it.
- *Source identity (introduced, FR-69).* `source_snapshot` (scoped per C1) carries: connector and canonical account identity (3a C3's canonical resource identity), `external_id`, `path_at_acquisition`, `revision` (etag, revision id or version number, as the provider names it), `modified_at`, `owner_at_source` where available, the connection id used, the acquiring principal or delegation, the acquisition instant, the **request that produced it** (operation, sanitised parameters digest, `task_step` id), the representation acquired (media type, export format when the provider converted it, e.g. Google Docs → `.docx`), and a `limitations` list from a closed vocabulary (`converted-representation`, `metadata-unavailable:<field>`, `partial-download`, `provider-truncated`). No value is invented: an unavailable field is absent and named in `limitations`, never defaulted.
- *Snapshot versions.* A source is identified by (connector, canonical account, external id); each acquisition registers a new `source_snapshot` with `supersedes` pointing at the previous snapshot of the same source in the same engagement when the provider revision or the digest differs. An existing snapshot is never replaced; a re-acquisition with identical bytes and revision reconciles to the existing row (the `putIfAbsent` rule, one layer up).
- *Query and paginated extraction (FR-69).* `extraction-record` freezes, beside the bytes, the request parameters, page boundaries or cursors, the provider's count or continuation facts, and the completeness or consistency evidence it offered — a version-consistent listing token, a total count, or nothing. The two-axis result from 3a C4 lands here: invocation outcome AND data quality (`complete | partial | empty-under-contract | unknown`). "Bytes saved" never implies `complete`; `complete` requires a positive fact from the provider or an exhaustive walk the record can show.
- *Sealing (D-3b-1).* Registration is the per-artifact immutability point. A Task seals its evidence package at its terminal state through the existing `SealPackage`, owner-namespaced, so an abandoned reservation is named rather than dropped. Artifact-version approval freezes the version's cited set (C7). The deferred "terminal without a package" trigger is written for `agent_task` as it is for `audit_run`.
- *Read access.* Evidence read grants generalise from `(actor, run, evidence, locator)` to `(actor, owner, evidence, locator)`; worker-signed, bounded, revocable, consumed on the web server; the web still never reads object storage. The integrity sweep walks every owner kind.
- *Retention (FR-81, second half).* Registered evidence and artifact versions are retained under the engagement's retention policy and never by the execution environment's lifetime. Deletion is a scoped administrative command with its own audit event; the object store keeps its no-overwrite rule and a deleted object's digest stays in the chain.
- *Ownership:* domain (kinds, keys, limitations vocabulary, snapshot supersession rule), application (`freezeArtifact`, seal, grant issuance), infrastructure (store, repositories, sweep). Acquisition is worker-only through connectors (3a C4) under a delegation (3a C1).

**(3) Failure and verification**

- Every new owner kind through the same reserve/upload/verify/register tests as the Run path, plus a redelivery test per owner (same key, same object, no second row).
- Identity: a Drive file re-acquired after an edit produces a second snapshot with `supersedes`; re-acquired unchanged reconciles; a converted representation records `converted-representation` and the export format; a provider that omits `modified_at` yields a snapshot naming `metadata-unavailable:modified_at` and no default.
- Extraction: a paginated listing interrupted at page 3 registers `partial` with the pages it has; a provider offering no consistency evidence registers `unknown`, never `complete`; an empty result under contract is `empty-under-contract` and distinguishable from a refused or unreachable source.
- Task seal: a task ending with an open reservation seals `INCOMPLETE` naming it; a terminal task with no package fails to commit.
- Grants: a grant issued for owner A cannot read owner B's object; expired and revoked grants refused; the web bundle still fails `no-evidence-store-in-web`.
- Retention: deleting a registered artifact needs the administrative command, writes its event and leaves the digest in the chain; the sweep reports a deleted object as `deleted-by-policy`, not `object-missing` (a store that cannot be read is not proof of tampering — unchanged).

**Changes to existing safeguards:** reservation keys gain an owner; kinds are extended by name; `REQUIRED_EVIDENCE_KINDS` is per-Template only on the Run path. No relaxation of registration, immutability, read-back or the integrity sweep.

## C6 — Working material, derived outputs and provenance classes

**(1) Requirements:** FR-70, FR-71, FR-72; extends AD-14 (the "transformation" provenance node it names and nothing implements), `structural-snapshot-v1` (bytes in, verdict out), AD-6.

**(2) Approach**

- *Four provenance classes, one column, closed:* `acquired` (a source snapshot), `received` (material sent to the engagement: an email attachment, an upload), `derived` (an output of a recorded method over registered inputs), `generated` (narrative or structure the agent wrote). Every evidence row and every artifact-claim citation carries one. A `generated` item can never be cited as support for a factual claim (C7); it can prompt a question.
- *Working material (introduced, D-3b-4).* `working_material` (scoped; task, name, media type, current revision) with `working_material_revision` (object key, digest, size, produced-by step, created-at). Revisions are append-only objects — the store's no-overwrite rule holds — but the material is **mutable in meaning**: a later revision supersedes an earlier one and nothing about a revision is evidence. Working copies are made from registered snapshot bytes by a recorded copy step; a working copy therefore always names the snapshot it came from. Retention follows the task and the engagement policy; the disposable execution environment holds only a mount of these objects.
- *Derived outputs (introduced).* Registering a derived output is one transaction that writes the `derived-output` evidence row (through `freezeArtifact`, so the credential guard and read-back apply) and its `derivation` record: `inputs[]` (evidence ids and digests, working-material revisions), `method` (kind `script | query | tool`, the code or query object's digest, the tool descriptor and version, the parameters' canonical digest), `environment` (execution record id from C8, image digest, limits), `validation` (kind, what was checked, outcome; from a closed list — `row-count-reconciled`, `checksum-matched`, `schema-conformed`, `sample-reviewed:<n>`, `none`), and the producing principal. An output whose validation is `none` registers with `validation: none` visible and cannot support a factual claim until a validation record is added (a new derivation record, never an edit).
- *Lineage.* `evidence_derivation` is the lineage table (output → inputs); it is walked upward to show an assertion's basis and downward to flag what a superseded snapshot affects (C7's dependency flagging reads it).
- *Corroboration for derived outputs.* The re-read rule generalises: a claim grounded in a derived output is corroborated against the registered output bytes at a locator (C8's substrates), and the output is corroborated against its inputs by re-running the recorded method **only** in the sandbox, as a separate, recorded validation execution — never inside a registration transaction (bytes in, verdict out stays the registration rule).
- *Input status (FR-72).* Every derived output and every artifact claim carries the input status the Gate vocabulary already has — `complete | partial | stale | out-of-period | unavailable` per input — computed from the snapshots' extraction records, `modified_at` and the engagement period, and written down rather than inferred at read time; the assessment an input constrains inherits the worst status of its inputs.

**(3) Failure and verification**

- A working-material revision cannot be cited as evidence (the citation validator refuses the class); promoting it means registering a derived output with a derivation record that names the revision as an input.
- Derivation: an output registered with an input digest that no registered evidence carries is refused; parameters that differ from the recorded canonical digest produce a different derivation, never an edit; `validation: none` blocks factual support and is shown.
- Provenance: a `generated` row cited as support for a factual claim is refused at claim validation and at approval.
- Re-execution validation: the recorded method re-run over the recorded inputs in a fresh sandbox reproduces the output digest, or records `non-reproducible` with the two digests; the result is a new validation record.
- Input status propagation: a `partial` extraction as an input yields an output and a claim marked `partial`; a snapshot with `modified_at` after the period end marks `out-of-period`.
- Lineage: superseding a snapshot lists every derived output and claim downstream of it.

**Changes to existing safeguards:** none relaxed. The "bytes in, verdict out" corroboration rule now applies to derived outputs, with method re-execution kept outside registration.

## C7 — Artifacts: versions, claims, dependencies, approval, produced files

**(1) Requirements:** FR-73, FR-74, FR-75, FR-76, FR-90, Trust Seam rule five; generalises `procedure_version`'s lifecycle mechanics (frozen fields, author ≠ approver, platform-authored drafts on dependency change) and `evaluation-review-sealing-v1`'s "original preserved, decision appended". Amends AD-2's entity list (3d).

**(2) Approach**

- *Aggregates (introduced).* `artifact` (scoped; engagement, type from the loaded pack, current version pointer, retired-at) and `artifact_version` (immutable once written: content object key and digest, structured content document for claim anchoring, author record — human, agent-under-delegation, or both with the human responsible named —, `supersedes`, review state, created-at). Review states are `draft → reviewed → approved → issued`, with the pack declaring which states a type requires and who may move each (FR-76); the platform enforces only the transitions and the independence rule (approver ≠ author where the pack requires it, the `authorApprovingOwnVersion` check generalised).
- *Frozen after approval.* `approved` and `issued` versions gain generation-14-style frozen-field triggers: content, claims, citations and author record cannot be updated; a correction is a new version. `draft` and `reviewed` versions can be replaced only by a new version too — history is never rewritten, a draft is simply cheap to supersede.
- *Claims (introduced, FR-74).* `artifact_claim` anchors a span of the structured content to a **claim class** from a closed vocabulary: `factual`, `assumption`, `hypothesis`, `inference`, `limitation`, `unverified`, `instruction`, `decision`, `recommendation`, `plan`. A `factual` claim must cite one or more `evidence_citation` rows (evidence id, locator, provenance class ∈ {acquired, received, derived}) and carries a support status `supported | unsupported | contradicted` computed by corroboration (C6) — never by the model. The other classes are labelled and shown as what they are; `instruction`, `decision`, `recommendation` and `plan` keep their author and are refused as citations for control operation. Neither a citation nor a label establishes that a conclusion is verified: `supported` means the cited bytes at the locator say what the claim says, no more.
- *Dependencies and reconsideration (FR-75).* `artifact_dependency` (version → cited evidence, cited artifact versions, approvals relied on). Superseding a version, superseding a snapshot (C5) or registering a new derivation (C6) flags every dependent version `needs-reconsideration` with the reason; the flag is cleared only by a new version or a recorded "reviewed, unchanged" decision. An approval belongs to exactly one version and never carries forward. The platform-authored-draft mechanism (`mint-platform-draft`) is what raises the flag: reused, not copied.
- *Approval freezes the cited set (D-3b-1).* Approving a version seals `(version, cited evidence digests, cited artifact version digests)` as a package; a later change to any of them cannot alter what was approved, only flag it.
- *Produced files (FR-90, D-3b-3).* A version may carry a **rendering**: a `.docx` or `.xlsx` produced in the sandbox (C8) from an approved pack template and the version's structured content, validated by a round trip (re-opened and parsed; required structure present; embedded content preserved or reported), stored through `freezeArtifact` as kind `generated-document`, provenance `generated`. Unsupported template features are reported on the version (`rendering_limitations`, closed list) and never silently dropped. A rendering reaches a connected output location only through a `write-output` connector operation under the Mandate (3a C3) with the confirmation the Mandate requires; the platform keeps its own copy as the record. PDF is an export of a rendering. The formats named for the delivery phase are exactly these two; adding one is an epic decision.
- *Types and templates from the pack (FR-76).* The platform ships no artifact type as a constant; the example pack supplies plan, procedure, request list, working paper, finding and report types with their required states. The Procedure Version stays a special artifact type on the Run path until compiler-2 (3c).
- *Ownership:* domain (states, claim classes, citation rule, dependency propagation), application (commands, approval, rendering job), infrastructure (storage), worker (rendering in the sandbox), web (review surfaces; never renders a file itself).

**(3) Failure and verification**

- Lifecycle: an author approving their own version refused where the pack requires independence; approving a version with an `unsupported` factual claim refused unless the pack's type permits approval with limitations, in which case the claim is shown as unsupported on the approved version; updating an approved version's content refused by the trigger through the repository and raw SQL.
- Claims: a `factual` claim with no citation fails validation; a citation of a `generated` row refused; a citation whose locator does not resolve in the cited bytes is `unsupported`; corroboration that reads a different value is `contradicted`; a `recommendation` cited as control evidence refused.
- Reconsideration: superseding a snapshot flags every dependent approved version; the approval on the old version is unchanged; a new version starts `draft` with no approval; the flag survives an unrelated re-read.
- Rendering fidelity tests, named: template heading and numbering structure preserved; tables with merged cells preserved or reported; embedded images preserved; tracked changes and comments in a template reported as unsupported; formulas in an `.xlsx` template preserved and recalculated values reported as such; a document with an unsupported feature carries the limitation and still validates; a rendering that fails the round trip is not stored as a version rendering.
- Output location: a rendering saved to a source location refused (3a C3); saved to an output location only with the required confirmation and a receipt; the platform copy's digest equals the uploaded object's read-back where the provider offers one, else the receipt records `read-back-unavailable`.

**Changes to existing safeguards:** the version lifecycle, independence rule and frozen-field triggers are generalised, not weakened. The Run path's `run_result` and Result review are untouched.

## C8 — Controlled execution environment and document processing

**(1) Requirements:** FR-81, FR-82, FR-70 (execution of methods), FR-62 (independent enforcement per layer); extends `agent-workspace-v1` (the weaker-guarantee rule and `mode`), `credential-containment-v1`, `structural-snapshot-v1` (new substrates), AD-11. New boundary rule `no-code-execution-in-web`.

**(2) Approach**

- *`CodeExecution` port (introduced), worker-only.* `execute({ task, step, program: { language, source digest, entrypoint }, inputs: mounts[], parameters, limits, network: 'none' | { allowlist } })` → `{ exitStatus, outputs[], stdout/stderr (bounded, scanned), usage, executionRecordId }`. Application owns the call site and the step ledger entry; infrastructure owns the sandbox adapter; the web cannot import it (dependency-cruiser rule, planted in both spellings like the four existing rules).
- *Isolation (D-3b-2).* Each execution runs in a fresh sandbox: separate process with kernel-level isolation (a container or microVM in deployment), no host credentials, no environment variables beyond the declared parameters, no access to the application database or the object store credentials, its own filesystem, and **network denied by default**. A network exception is a Mandate-declared allowlist enforced by the sandbox's network namespace, not by the code, and each connection attempt is recorded. The sandbox never holds a connector credential: data leaves and enters only through mounts and collected outputs; a step that needs a connector performs it outside the sandbox and mounts the result. `execution_record.mode` records `isolated` or `local`, and the weaker guarantee is written wherever an execution is shown, exactly as `run_workspace.mode` does.
- *Inputs and outputs.* Inputs are read-only mounts of registered snapshot bytes and working-material revisions, named by evidence id or revision id and digest-checked at mount. Outputs are collected from a declared output directory, each registered as working material or, when the step says so, as a derived output with its derivation record (C6). The execution record (`execution_record`: program digest, image digest, parameters digest, limits, resource usage, exit status, started and ended at, mode, network attempts) is itself frozen as evidence kind `execution-log`, so a method's run is inspectable after the sandbox is gone.
- *Limits.* CPU time, wall time, memory, disk and output size are Mandate budgets reserved before execution (the FR-56 budget rule) and enforced by the sandbox; exceeding one ends the execution with a closed diagnostic and the partial outputs are kept as working material, never registered as derived.
- *Disposable.* Nothing durable lives in the sandbox. Required evidence, artifacts and task state are written by the worker from collected outputs; the sandbox is destroyed after collection and a lost sandbox is a failed step, not lost evidence.
- *Document processing (FR-82).* Extraction is a set of platform-provided programs run through the same port on the registered source bytes: PDF (text with page and bounding-box locators, and page images for visual inspection), Office (`.docx` paragraphs and tables with structural locators; `.xlsx` cells), CSV (the existing `sheet` parser), email MIME (headers, parts, attachments each registered as `received` snapshots with their own digest), images and scanned pages (OCR producing text with confidence and a locator per line, plus the page image). Each produces an `extraction-record` with source locators and a `content_status` per region from a closed list (`extracted`, `unsupported`, `missing`, `uncertain:<reason>`). Structured output is never proof of accuracy: a claim grounded in an extraction is corroborated against the **preserved source representation** — the PDF page image or the original bytes — at the locator, which is why page images are kept beside text.
- *New substrates for `structural-snapshot-v1`:* `pdf` (`$.pages[<n>].blocks[<i>]`), `doc` (`$.body[<i>]` for paragraphs, `$.tables[<t>].rows[<r>].cells[<c>]`), `mail` (`$.headers.<name>`, `$.parts[<i>]`), `image` (`$.lines[<i>]` over OCR output, corroborated against the image by a human-reviewed check where OCR confidence is below the pack's threshold), plus the existing `sheet`, `json`, `web_tree`. One grammar, the existing parsing rules (no leading zeros, no separators in names), and an unimplemented substrate stays an explicit `corroboration-unsupported`.
- *Retrieval versus full examination.* The model may ask for targeted retrieval over extraction records or a full read; the tool result states what was searched (which snapshots, which regions, which query) and what was not, and absence is never inferred from an incomplete search — the `search-completeness` reading, applied to documents. Visual inspection sends page images to the model only under the disclosure policy (3a C4).
- *Ownership:* domain (execution record shape, locator grammars, content status vocabulary), application (port, call site, extraction programs' descriptors), infrastructure (sandbox adapter, extraction program images), worker (all execution).

**(3) Failure and verification**

- Isolation negatives, run against the deployed sandbox mode: read of a host path, read of an environment variable, outbound connection with `network: none`, outbound connection outside an allowlist, write to a mounted input, database connection attempt, object-store credential lookup — each refused and recorded; the same suite under `local` mode records which guarantees do not hold rather than passing vacuously.
- Limits: CPU, wall, memory, disk and output-size exhaustion each end the execution with the named diagnostic and keep partial outputs as working material only.
- Inputs: a mount whose digest does not match its registered evidence is refused before the program starts; an output claiming an input the step did not mount is refused at derivation.
- Disposability: the sandbox destroyed mid-execution fails the step; evidence registered before the failure is unchanged; a retry is a new execution record.
- Document processing per format: a text PDF, a scanned PDF (OCR with low-confidence lines marked `uncertain`), a `.docx` with tables and tracked changes (tracked changes reported), an `.xlsx` with formulas, a multipart email with two attachments (three `received` snapshots), a corrupt file (`unsupported`, no partial claim of success); for each, a claim at a locator corroborated against the preserved representation and a deliberately wrong claim reported `contradicted`.
- Retrieval honesty: a search over two of three snapshots reports the third as not searched; an absence claim over an incomplete search is refused at claim validation.
- Boundary: `no-code-execution-in-web` planted in `src` and `dist` spellings; the web bundle contains no sandbox adapter.

**Changes to existing safeguards:** the browser workspace's weaker-guarantee rule extends to code execution. `credential-containment-v1` gains the sandbox as a place a credential must have nowhere to land (no mounts carry one; stdout/stderr are guard-scanned before storage). Nothing else relaxed.

## Dependencies carried into 3c–3d

- 3c (agent loop, memory, skills, promotion): tool results as data with the two-axis result and input status (C5, C6); `derived-output` registration as the only route from analysis to citable support (C6); claim classes and citation validation the model must produce into but never adjudicate (C7); the `CodeExecution` port as one tool behind the Mandate gate and budgets (C8); compiler-2 promotes an approved **method artifact** (C7) whose recorded derivations (C6) become the frozen steps of a recurring check; retention and deletion commands for memory follow C5's administrative-command shape.
- 3d (spine and contracts): AD-5, AD-6, AD-14, AD-18 amendments; `evidence-package-v2` (owner namespace, kinds, limitations vocabulary), `derivation-v1`, `artifact-version-v1` (states, claim classes, citation rule, dependency flag), `code-execution-v1` (port, execution record, isolation modes, limits), `document-extraction-v1` (formats, content status, substrates and locator grammars), and the four D-3b decisions; the classification of every new table under C1's policy inventory.
