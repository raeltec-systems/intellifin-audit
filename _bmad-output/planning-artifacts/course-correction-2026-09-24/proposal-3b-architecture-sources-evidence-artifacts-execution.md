# Proposal 3b of 7 — Architecture: sources, evidence, working material, artifacts, controlled execution environment

Status: APPROVED by the owner on 2026-09-24 in full, with D-3b-1..4 approved including the revised isolation requirement (a concrete, tested sandbox profile; network-disabled analysis for the first delivery; synthetic-only local development with no automatic fallback). The approval accepts the architecture; it is not evidence that isolation, document fidelity, analytical validation or recovery works. No implementation is authorised. Carried into implementation acceptance: the positive, negative and failure-recovery tests as obligations, and in particular that an incomplete population cannot produce unsupported population-wide assurance; ordinary new-period data does not invalidate unrelated historical conclusions; approval binds the actual reviewed deliverable; incomplete or late evidence stays honestly represented without rewriting sealed history; the sandbox backend and deployed profile are selected, documented and tested before acceptance. Operating rule: the harness creates and maintains this metadata through its operations; the auditor sees material limitations, decisions and review needs and is never required to populate provenance fields or approve every intermediate calculation; review is organised around the working paper, artifact or decision, with claim-level records underneath.
History: revised on 2026-09-24 after the owner's eight edit groups (D-3b-1..4 taken as below); awaiting owner approval. Builds on the approved 3a baseline (D-3a-1..4) and carries its dependencies forward: scoped tables with composite scope keys and envelope v2 (C1); absolute source protection with output copies (C3); invocation outcome versus data quality on every acquisition (C4); delegation for background work (C1). Nothing here reopens a settled 3a decision. The metadata and checks below are produced by the harness and surfaced when relevant; they are not a series of forms the auditor completes before analysis can begin.

Baseline facts checked on `main` `c18ad36`: every stored byte is Run-owned immutable Evidence (`run_evidence.run_id NOT NULL`, five closed kinds, idempotency key `evidence-v1:<runId>:<kind>:<scope>`); the reserve → `putIfAbsent` → read-back → size/SHA-256 → `REGISTERED` sequence is one implementation (`freezeArtifact`) behind the credential guard; the object store never overwrites and the post-Run integrity sweep re-verifies; worker-signed read grants keep the web out of object storage (`no-evidence-store-in-web`). There is no source-identity metadata (provider, external id, revision or etag, modified time, query), no working copy, no derivation or lineage record, no artifact versioning outside `procedure_version`, no document-processing path beyond `sheet`, `json` and `web_tree`, and no code-execution runtime of any kind (`@solarisdk/sandbox` is named in the spine and installed nowhere).

## C5 — Source snapshots: evidence generalised past the Run

**(1) Requirements:** FR-69, FR-67, FR-72 (input status), FR-3 (source-side); extends `evidence-package-v1`, `population-acquisition-v1`, `capture-grounding-absence-v1`, AD-5, AD-18. Leaves the Run-path kinds, keys and object layout untouched: an artifact frozen by an earlier build still resolves to the same object.

**(2) Approach**

- *Owner-namespaced reservation (generalised).* The idempotency key becomes `evidence-v2:<ownerKind>:<ownerId>:<kind>:<scope>` with `ownerKind ∈ {run, task, artifact-version}`; the `evidence-v1` prefix and the Run object layout stay for Run owners. `evidenceIdFor` and `evidenceObjectKeys` gain the owner; the object layout for new owners is `<tenant>/<ownerKind>/<ownerId>/<kind>/<scope>`. Same `freezeArtifact`, same guard, same `putIfAbsent`, same read-back and digest rule, same "never demoted".
- *New kinds (closed, extended by name):* `source-snapshot`, `extraction-record`, `derived-output`, `generated-document`, `execution-log`. `REQUIRED_EVIDENCE_KINDS` stops being keyed by Template: a Task declares what it requires per step (3c), a Run keeps the Template table until compiler-2 replaces it.
- *Source identity (introduced, FR-69).* `source_snapshot` (scoped per C1) carries: connector and canonical account identity (3a C3's canonical resource identity), `external_id`, `path_at_acquisition`, `revision` (etag, revision id or version number, as the provider names it), `modified_at`, `owner_at_source` where available, the connection id used, the acquiring principal or delegation, the acquisition instant, the **request that produced it** (operation, sanitised parameters digest, `task_step` id), the representation acquired (media type, export format when the provider converted it, e.g. Google Docs → `.docx`), and a `limitations` list from a closed vocabulary (`converted-representation`, `metadata-unavailable:<field>`, `partial-download`, `provider-truncated`). No value is invented: an unavailable field is absent and named in `limitations`, never defaulted.
- *Content identity and acquisition identity are two things.* A snapshot's **content** is identified by its digest and media type; an **acquisition** is identified by its own record: request, principal or delegation, connection, instant, returned version metadata and limitations. A new authorised acquisition records its own acquisition row even when the bytes match an earlier snapshot, so the fact that a later check really re-read the source is never lost. A **retry of the same logical acquisition** (same task step, same request key) is idempotent and reconciles to the first attempt's record; a **later independent acquisition** is a new observation, never a retry of the old one. Byte storage may be reused within an authorised deduplication boundary (one tenant, one store), but provenance, access control and retention obligations stay independently represented on each acquisition; a matching digest grants no access across scopes and every grant names an acquisition, not a digest.
- *Source evolution.* A source is identified by (connector, canonical account, external id). A later acquisition with a different revision or digest records its **relationship** to the earlier one from a closed list — `subsequent-observation` (the ordinary case: newer material exists), `correction` (the provider or the client says the earlier content was wrong), `explicit-replacement` (a superseded document by declaration), `unknown` — with the basis for that classification. A new version does not by itself establish that the earlier one was wrong. Historical analyses stay bound to the exact snapshot and acquisition records they used; the ordinary arrival of next month's data never flags a prior approved report. What creates an attributable **impact record** and the reconsideration workflow (C7) is a change that affects an existing conclusion's basis: a `correction`, an invalidated extraction, altered applicable criteria, or a newly established coverage limitation. "Newer material exists" is a notification, and it is shown as something different from "the approved conclusion's basis is invalid".
- *Query and paginated extraction (FR-69).* `extraction-record` freezes, beside the bytes, the request parameters, page boundaries or cursors, the provider's count or continuation facts, and the completeness or consistency evidence it offered — a version-consistent listing token, a total count, or nothing. The two-axis result from 3a C4 lands here: invocation outcome AND data quality (`complete | partial | empty-under-contract | unknown`). "Bytes saved" never implies `complete`; `complete` requires a positive fact from the provider or an exhaustive walk the record can show. **Traversal coverage and point-in-time consistency are separate facts**: retrieving every page establishes coverage of the traversal; it establishes that all pages describe one consistent source state only when the provider supplied a version-consistent token or the record can show one, and otherwise `consistency: unknown` is written beside `coverage: complete`.
- *Sealing (D-3b-1).* Registration is the per-artifact immutability point. A terminal Task **always records a package manifest**, even when the package is empty, incomplete or holds only failed acquisition attempts: package completeness, execution outcome and audit assessment are three separate facts and none is derived from another. A storage outage or an abandoned reservation is named in the manifest, never smoothed into a complete package; a purely conversational task terminates with an empty manifest and manufactures no evidence. Late external receipts and later validations are appended as **linked supplements** with their own provenance and never rewrite a sealed manifest. Artifact-version approval binds the version's cited set (C7). The deferred "terminal without a package" trigger is written for `agent_task` as it is for `audit_run`.
- *Read access.* Evidence read grants generalise from `(actor, run, evidence, locator)` to `(actor, owner, evidence, locator)`; worker-signed, bounded, revocable, consumed on the web server; the web still never reads object storage. The integrity sweep walks every owner kind.
- *Retention (FR-81, second half).* Registered evidence and artifact versions are retained under the engagement's retention policy and never by the execution environment's lifetime. Deletion is not an unrestricted administrative bypass: it requires the applicable **retention decision**, a check for **preservation holds** on the engagement, client or item, and a check for **retained dependencies** (a derivation, claim or approved version that names the item refuses the deletion or records the loss explicitly). Authorised deletion records what was removed and why, preserves the permitted metadata and the digest, and updates the item's **evidence-availability** status and every dependent export's and reproduction's status. A retained digest proves what was there; it does not make deleted evidence inspectable or reproducible, and no surface says otherwise.
- *Ownership:* domain (kinds, keys, limitations vocabulary, snapshot supersession rule), application (`freezeArtifact`, seal, grant issuance), infrastructure (store, repositories, sweep). Acquisition is worker-only through connectors (3a C4) under a delegation (3a C1).

**(3) Failure and verification**

- Every new owner kind through the same reserve/upload/verify/register tests as the Run path, plus a redelivery test per owner (same key, same object, no second row).
- Identity: a Drive file re-acquired after an edit produces a second snapshot related as `subsequent-observation`; re-acquired **unchanged on a later date** produces a new acquisition record over the same content with the later date, principal and connection; a retry of the original acquisition (same step, same request key) reconciles to one record; identical bytes acquired from two different sources produce two snapshots with two acquisitions and no cross-scope grant; a normal next-period extract flags no prior approved report; a `correction` to records underlying an approved finding creates an impact record and flags that finding; a converted representation records `converted-representation` and the export format; a provider that omits `modified_at` yields a snapshot naming `metadata-unavailable:modified_at` and no default.
- Extraction: a paginated listing interrupted at page 3 registers `partial` with the pages it has; a provider offering no consistency evidence registers `coverage: complete, consistency: unknown` after a full walk, never a bare `complete`; an empty result under contract is `empty-under-contract` and distinguishable from a refused or unreachable source.
- Task seal: a task ending with an open reservation records `INCOMPLETE` naming it; a task interrupted by a storage outage records the outage against the reservation and never a complete package; a conversational task with no evidence records an empty manifest and terminates; a late receipt arriving after the manifest is appended as a supplement and the manifest's digest is unchanged; a terminal task with no manifest fails to commit.
- Grants: a grant issued for owner A cannot read owner B's object; expired and revoked grants refused; the web bundle still fails `no-evidence-store-in-web`.
- Retention: deletion under a preservation hold is refused; deletion of an item a derivation or an approved version depends on is refused, or, under an explicit override, records the dependency loss on the dependent; an authorised deletion writes its event, keeps digest and metadata, marks availability `deleted-by-policy`, and a tenant export names the deleted item as deleted rather than omitting it; the sweep reports `deleted-by-policy`, not `object-missing`.

**Changes to existing safeguards:** reservation keys gain an owner; kinds are extended by name; `REQUIRED_EVIDENCE_KINDS` is per-Template only on the Run path. No relaxation of registration, immutability, read-back or the integrity sweep.

## C6 — Working material, derived outputs and provenance classes

**(1) Requirements:** FR-70, FR-71, FR-72; extends AD-14 (the "transformation" provenance node it names and nothing implements), `structural-snapshot-v1` (bytes in, verdict out), AD-6.

**(2) Approach**

- *Four provenance classes, one column, closed:* `acquired` (a source snapshot), `received` (material sent to the engagement: an email attachment, an upload), `derived` (an output of a recorded method over registered inputs), `generated` (narrative or structure the agent wrote). Every evidence row and every citation carries one. Generated narrative is never independent evidence of the facts it narrates; what a generated item CAN support is bounded by its provenance: a generated workbook's analytical content is supported through its registered derivations (C6), and a preserved prior report establishes what that report stated or which version was issued, not that its assertions were true. Acquiring or uploading a generated summary does not remove its known provenance limitations. A citation chain must lead to the actual supporting records; a chain that circulates between generated artifacts without reaching an `acquired`, `received` or `derived` record with its own basis is refused as circular.
- *Working material (introduced, D-3b-4).* `working_material` (scoped; task, name, media type, current revision) with `working_material_revision` (object key, digest, size, produced-by step, created-at). Revisions are append-only objects — the store's no-overwrite rule holds — but the material is **mutable in meaning**: a later revision supersedes an earlier one and nothing about a revision is evidence. Working copies are made from registered snapshot bytes by a recorded copy step; a working copy therefore always names the snapshot it came from. Retention follows the task and the engagement policy; the disposable execution environment holds only a mount of these objects.
- *Derived outputs (introduced).* Registering a derived output follows the recoverable storage protocol and then commits its metadata atomically: reserve the logical output; upload and verify its bytes through `freezeArtifact` (credential guard, `putIfAbsent`, read-back, digest); then, in one database transaction, register the verified object reference together with its `derivation` record. Object storage never participates in the database transaction; recovery reconciles the `reserved`, `uploaded`, `verified` and `registered` states, and an object whose derivation metadata is missing or uncommitted cannot become support for anything. The derivation record holds: `inputs[]` (evidence ids and digests, and the working-material revisions used, each **explicitly retained** and traced for as long as the derivation is — a retained dependency is not thereby evidence, it is a retained dependency); `method` — the **actual** code, query or tool invocation retained as an object (digests verify retained material; they do not reconstruct missing material), its parameters in canonical form, and the required dependency versions (image digest, library versions, calculation engine); `environment` (execution record id from C8); the producing principal; and the validation records below.
- *Four kinds of check, four records.* **Integrity** checks establish that preserved bytes match their recorded identity. **Reproducibility** checks establish whether the recorded method reproduces its specified result. **Analytical validation** checks relevant properties of the method and the output (a join key's uniqueness, a reconciliation to a control total, agreement with the system of record on a sample, a population count against an independent declaration). **Audit assessment** determines what the evidence supports under the applicable criteria. These are separate records with separate outcomes; passing one does not satisfy another. A script can reproducibly perform the wrong join, and a workbook can keep every row while assigning results to the wrong people, so no validation label is by itself the condition for factual support. A validation record names the validator (person, or program and version), the checks performed, expected and observed results, coverage, limitations and the claim or output it relates to. The **required** checks depend on the method and the claim class and are declared by the methodology pack; the platform enforces that the declared checks exist with a passing or explicitly accepted outcome before a claim can be `supported`, and treats no single label as sufficient. Internal consistency never establishes agreement with the system of record; that is an analytical validation the pack must ask for where it matters.
- *Reproducibility, stated precisely.* Each derivation declares what reproduction means: **byte identity** of the output, or **equality under a declared semantic comparator** (row-set equality ignoring order, numeric equality within a stated tolerance, schema-and-values equality) with the comparator and tolerances recorded. Material differences are never silently normalised. Model-assisted steps retain their actual inputs, outputs, prompt and model identity and promise no identical future output; their reproducibility record says so. Re-execution runs when the applicable validation plan requires it, in the sandbox as a separate recorded execution (C8), and never automatically because somebody read a citation.
- *Lineage.* `evidence_derivation` is the lineage table (output → inputs); it is walked upward to show an assertion's basis and downward to flag what a superseded snapshot affects (C7's dependency flagging reads it).
- *Corroboration for derived outputs.* Locator corroboration generalises: a claim grounded in a derived output is corroborated against the registered output bytes at a locator (C8's substrates), which is an integrity-and-reading check and nothing more. Re-running the method is the reproducibility check above; it is never performed inside a registration transaction (bytes in, verdict out stays the registration rule).
- *Input quality assessment (FR-72, independent dimensions).* Each relevant input carries a **versioned quality assessment** with independent dimensions: **availability and acquisition** (acquired, partial, unavailable), **freshness or "data as at"** (the instant or period the data represents), **completeness and coverage** (traversal coverage and, separately, point-in-time consistency, from the extraction record), **period relevance** (whether the content falls in the engagement period), and **provenance and validation** (class and the checks that exist). Every dimension admits `unknown` / `not-established`. Each assessment records its basis, the applicable rule, the observation time and the assessor or validating program. Outputs and claims bind the assessment **versions** in force when they were produced; a later assessment is a new version and creates an impact record only where C5's rules say so. Provider modification time is acquisition metadata, not the business period the data represents: a January-generated report can describe December transactions, and a recently modified file can hold stale figures. Period relevance and freshness are established from source content, extraction parameters, source semantics and the pack's approved rules; where these are insufficient the dimension stays `unknown`, never a guess from `modified_at`.
- *Dependency-specific propagation.* A limitation constrains the claims and assessments that depend on the affected input, through the lineage table; it never invalidates every conclusion in the engagement. Supported record-level exceptions stay visible when population-wide assurance is inconclusive. An unrelated limitation leaves an unrelated claim untouched.

**(3) Failure and verification**

- A working-material revision cannot be cited as evidence (the citation validator refuses the class); promoting it means registering a derived output with a derivation record that names the revision as an input.
- Derivation: an output registered with an input digest that no registered evidence carries is refused; parameters that differ from the recorded canonical form produce a different derivation, never an edit; a derivation whose method object is missing (digest only) is refused; a crash between upload and metadata commit leaves an `uploaded` object that recovery reconciles and that no claim can cite until registered.
- Validation kinds: a repeatable-but-wrong method (a join on the wrong key that reproduces byte-for-byte) passes reproducibility and fails the pack's required analytical validation, so its claims stay `unsupported`; a checksum-only validation offered for a control conclusion is refused because integrity alone never satisfies a required analytical check; a required check with an explicitly accepted failure is shown as accepted-with-limitation, never as passed; a semantic comparator with a tolerance reports a difference outside it as `non-reproducible` with both values.
- Provenance: a `generated` narrative cited as support for the facts it narrates is refused; a generated workbook's figures cited through their derivation are accepted; a preserved prior report cited for "what the report stated" is accepted and cited for "the assertion is true" is refused; a circular chain (report A cites summary B cites report A) is refused at claim validation.
- Re-execution: the recorded method re-run over the recorded inputs in a fresh sandbox reproduces the output under the declared comparator, or records `non-reproducible` with both results and the comparator; a model-assisted step's re-execution records a new output and never claims identity; re-execution is not triggered by reading a citation.
- Input quality: current-but-partial data (fresh, `coverage: partial`) constrains only the population claims; complete-but-out-of-period data (`coverage: complete`, `period-relevance: outside`) constrains the period claims and not the completeness ones; a report produced after period end whose content is in-period is `period-relevance: inside` despite its `modified_at`; a source with no basis for freshness is `freshness: unknown` and no default is written; an independently supported record-level exception inside an incomplete population stays `supported` while the population claim is constrained.
- Lineage: superseding a snapshot lists every derived output and claim downstream of it.

**Changes to existing safeguards:** none relaxed. The "bytes in, verdict out" corroboration rule now applies to derived outputs, with method re-execution kept outside registration.

## C7 — Artifacts: versions, claims, dependencies, approval, produced files

**(1) Requirements:** FR-73, FR-74, FR-75, FR-76, FR-90, Trust Seam rule five; generalises `procedure_version`'s lifecycle mechanics (frozen fields, author ≠ approver, platform-authored drafts on dependency change) and `evaluation-review-sealing-v1`'s "original preserved, decision appended". Amends AD-2's entity list (3d).

**(2) Approach**

- *Aggregates (introduced).* `artifact` (scoped; engagement, type from the loaded pack, current version pointer, retired-at) and `artifact_version` (content object key and digest, structured content document for claim anchoring, author record, `supersedes`, created-at). **Content, claims, citations and authorship are immutable per version** from the moment the version is written, whatever its review state. Review, approval, issue and reconsideration are separate **lifecycle records** (`artifact_version_decision`: version, kind, actor, basis, instant, revision it was taken against), and the current state of a version is projected from those records; nothing rewrites what an earlier version contained or what was originally approved. The pack declares which states a type requires and who may move each (FR-76); the platform enforces only the transitions and the independence rule. The author record names the **responsible human** and every human contributor beside any agent or delegation identity; independence checks (approver ≠ author where the pack requires it, the `authorApprovingOwnVersion` check generalised) are evaluated over the responsible human and the human contributors, never over the service identity alone. Packs configure review requirements within the platform's mandatory approval and authority rules and cannot remove them.
- *Revision-bound decisions.* Every review, approval and issue decision names the version **and the revision** of the projection it was taken against (the content digest, the claim-set digest, the citation-set digest and, for a deliverable, the rendering digest). A version whose content is immutable cannot change between review and finalisation; what can change is which rendering or which supplement is attached, so the decision binds those too, and a decision taken against a stale revision is refused (the existing revision-guard shape).
- *Claims (introduced, FR-74).* `artifact_claim` anchors a span of the structured content to a **claim class** from a closed vocabulary: `factual`, `assumption`, `hypothesis`, `inference`, `limitation`, `unverified`, `instruction`, `decision`, `recommendation`, `plan`. A `factual` claim must cite one or more `evidence_citation` rows (evidence id, locator, provenance class ∈ {acquired, received, derived} under C6's provenance rules) and carries a **support status** owned by the platform: `supported`, `unsupported`, `contradicted`, `pending-review`, `not-machine-checkable`. The platform owns every transition and enforces its required basis. Exact field, identity, arithmetic and other explicitly supported checks are corroborated **deterministically** against the cited bytes and the required validation records, and only those checks can move a claim to `supported` or `contradicted` without a person. **Semantic interpretation, visual interpretation and professional judgement** may be proposed by the model with evidence, rationale and uncertainty; such a claim enters `pending-review` (or `not-machine-checkable` where no deterministic check applies) and moves to `supported` only through the human review the pack requires, with the reviewer recorded. A model cannot make its own assertion authoritative by returning `supported`; an unsupported parser or an unresolved visual interpretation is `not-machine-checkable` or `pending-review`, never `contradicted`. The other classes are labelled and shown as what they are; `instruction`, `decision`, `recommendation` and `plan` keep their author and are refused as citations for control operation. Neither a citation nor a label establishes that a conclusion is verified: `supported` means the required basis exists and the cited material says what the claim says, no more.
- *Dependencies and reconsideration (FR-75).* `artifact_dependency` (version → cited evidence and acquisition records, cited artifact versions, assessment versions, approvals relied on). An **impact record** (C5) — a `correction`, an invalidated extraction, altered criteria, a newly established coverage limitation, or the supersession of a cited artifact version — flags every dependent version `needs-reconsideration` with the reason, through the platform-authored-draft mechanism (`mint-platform-draft`, reused). A `subsequent-observation` produces a **notification** that newer material exists and no flag. The flag is cleared only by a new version or a recorded "reviewed, unchanged" decision. An approval belongs to exactly one version and never carries forward.
- *Approval binds the deliverable (D-3b-1, D-3b-3).* Approving a version binds, by digest, the exact artifact content and claim set, the cited evidence and artifact versions, the validation records and input-quality assessment versions relied on, the applicable template and methodology-pack version, and — where a deliverable is being approved — the **specific rendering presented** for approval. A later rendering generated from the same structured content is not approved by that approval; the release contract (3d) states how an additional format is validated and associated with an approved version, as a new revision-bound decision. A methodology may permit approval of a report that carries explicit limitations or unresolved matters; it may not turn an `unsupported` or `pending-review` factual claim into a verified one, nor suppress a limitation the pack requires.
- *Produced files (FR-90, D-3b-3).* A version may carry a **rendering**: a `.docx` or `.xlsx` produced in the sandbox (C8) from an approved pack template and the version's structured content, stored through `freezeArtifact` as kind `generated-document`, provenance `generated`. Round-trip parsing is one validation layer; acceptance also checks the material content against the artifact's structured content and claims (every table, figure, cited value and required limitation present and equal), relevant spreadsheet calculations (C8's calculation rules), embedded-content preservation (images, evidence screenshots, attachments) and the rendered appearance of representative documents against reference renderings. A **supported-template-feature matrix** is maintained per pack template; a feature outside it is either a harmless limitation recorded on the version (`rendering_limitations`, closed list: a lost style, a dropped comment) or a **blocking defect** — a missing evidence image, an incorrect or stale formula result, an omitted required limitation, an altered or lost material table — which prevents approval and issue of that rendering. A rendering reaches a connected output location only through a `write-output` connector operation under the Mandate (3a C3) with the required confirmation; the platform keeps its own copy as the record. PDF is an export of an approved rendering, validated and bound the same way. The authored formats for the delivery phase are exactly these two; adding one is an epic decision.
- *Issuance is its own event.* Saving a draft or an approved rendering to an output folder is not issuance. Issuance is a separate authorised lifecycle record naming the exact version, rendering and recipient or location; external delivery claims are bounded by the connector receipt (a saved file is `confirmed` saved, not read; a sent report is `accepted` by the mail provider, not received).
- *Types and templates from the pack (FR-76).* The platform ships no artifact type as a constant; the example pack supplies plan, procedure, request list, working paper, finding and report types with their required states. The Procedure Version stays a special artifact type on the Run path until compiler-2 (3c).
- *Ownership:* domain (states, claim classes, citation rule, dependency propagation), application (commands, approval, rendering job), infrastructure (storage), worker (rendering in the sandbox), web (review surfaces; never renders a file itself).

**(3) Failure and verification**

- Lifecycle: the responsible human of an agent-authored version attempting a prohibited self-approval refused, and so is a human contributor listed on the author record; a decision taken against a stale revision (content, claim set, citations or rendering changed since the reviewer loaded it) refused; a concurrent edit during approval produces a new version and the approval lands on the old one only, revision-checked; updating any version's content refused by the trigger through the repository and raw SQL; approving a version with an `unsupported` factual claim refused unless the pack permits approval with limitations, in which case the claim stays `unsupported` on the approved version and is shown.
- Claims: a `factual` claim with no citation fails validation; a citation of a `generated` narrative for the facts it narrates refused; a locator that does not resolve is `unsupported`; a deterministic check reading a different value is `contradicted`; a model-proposed semantic interpretation enters `pending-review` and becomes `supported` only with a recorded reviewer; a claim over an unsupported parser is `not-machine-checkable` and never `contradicted`; a model returning `supported` in its output moves nothing; a `recommendation` cited as control evidence refused; a circular citation chain refused.
- Reconsideration: a `correction` impact record flags every dependent approved version and the old approval is unchanged; a `subsequent-observation` notifies and flags nothing; a new version starts `draft` with no approval; the flag survives an unrelated re-read.
- Rendering fidelity tests, named: template heading and numbering preserved; a table with merged cells preserved or reported; an embedded evidence screenshot present in the rendered output (its absence is blocking); tracked changes and comments in a template reported as unsupported; an `.xlsx` formula recalculated by the recorded engine with a stale cached value detected (blocking); an unsupported formula reported by name; a material table lost or altered detected against the structured content (blocking); a structurally valid document whose visible output omits a required limitation detected (blocking); a document with a harmless limitation carries it and still validates; a rendering that fails any blocking check is not attachable to an approval.
- Output location and issuance: a rendering saved to a source location refused (3a C3); saved to an output location only with the required confirmation and a receipt; the platform copy's digest equals the uploaded object's read-back where the provider offers one, else the receipt records `read-back-unavailable`; a draft export to an output folder does not create an issue record, and an issuance without an approved, bound rendering is refused; a changed rendering after review requires a new revision-bound decision before issue.

**Changes to existing safeguards:** the version lifecycle, independence rule and frozen-field triggers are generalised, not weakened. The Run path's `run_result` and Result review are untouched.

## C8 — Controlled execution environment and document processing

**(1) Requirements:** FR-81, FR-82, FR-70 (execution of methods), FR-62 (independent enforcement per layer); extends `agent-workspace-v1` (the weaker-guarantee rule and `mode`), `credential-containment-v1`, `structural-snapshot-v1` (new substrates), AD-11. New boundary rule `no-code-execution-in-web`.

**(2) Approach**

- *`CodeExecution` port (introduced), worker-only.* `execute({ task, step, program: { language, source digest, entrypoint }, inputs: mounts[], parameters, limits, network: 'none' | { allowlist } })` → `{ exitStatus, outputs[], stdout/stderr (bounded, scanned), usage, executionRecordId }`. Application owns the call site and the step ledger entry; infrastructure owns the sandbox adapter; the web cannot import it (dependency-cruiser rule, planted in both spellings like the four existing rules).
- *Isolation (D-3b-2, amended).* Before the implementation is accepted, a **concrete sandbox backend and enforced security profile** are selected and documented: the backend (a sandboxed-container runtime such as gVisor, or a microVM), its runtime and image versions, and the profile (dropped capabilities, no privileged mode, read-only root, seccomp and no-new-privileges, user namespace, mount allowlist, resource limits, network disabled). The execution record stores backend, version and profile identifier, not only `isolated`. The **boundary** is stated: untrusted execution is separated from the application database, the credential broker, object-storage credentials, host services (including any cloud metadata endpoint) and every other workspace; a backend satisfies the design only when its actual configuration and the negative tests below establish those protections. `local` mode is explicitly enabled development behaviour (`CODE_EXECUTION_MODE=local`, non-production, manually staged synthetic fixtures), recorded on every execution record, never an automatic fallback when isolation is unavailable, and it cannot satisfy personal-account connector acceptance. A sandbox never replaces the surrounding controls — the Mandate gate, disclosure policy, the external-effect ledger and connector authorisation still apply to everything that enters or leaves it.
- *Network.* Analysis execution is **network-disabled in the first delivery**; dependencies are available through approved, versioned images. A later network exception needs its own enforceable egress contract (3d, a later epic) and a domain allowlist is never a route around connector authorisation, disclosure policy or the external-effect ledger. The sandbox never holds a connector credential: a step that needs a connector performs it outside the sandbox and mounts the result. No credential is injected by design; because source files themselves may contain sensitive strings, unexpected sensitive content found in inputs or outputs is handled under the established restriction and quarantine policy, and the credential scan stays supplementary.
- *Trust boundaries at the edges.* The **trusted supervisor** (the worker-side adapter) supplies execution identity, the mounted-input manifest, enforced limits, timings and the observed termination state; these are the execution record. Program stdout, stderr and any program-written manifest are **untrusted output**, retained as bounded, guard-scanned objects and never treated as an execution receipt. Output collection admits only declared output locations and rejects path escape, symbolic and hard links, special files, oversized output and undeclared locations; the collector never follows an untrusted path into host storage or another workspace. Collected objects inherit the scope and disclosure restrictions of the inputs. Source documents, templates and parsers are untrusted inputs: macros, external links, remote resources and other active content do not execute because a document is opened or rendered, and the extraction and rendering programs run under the same profile.
- *Inputs and outputs.* Inputs are read-only mounts of registered snapshot bytes and working-material revisions, named by evidence id or revision id and digest-checked at mount. Outputs are collected from a declared output directory, each registered as working material or, when the step says so, as a derived output with its derivation record (C6). The execution record (`execution_record`: program object and digest, backend, image and profile identifiers, parameters digest, limits, supervisor-observed resource usage and termination state, started and ended at, mode) is itself frozen as evidence kind `execution-log`, so a method's run is inspectable after the sandbox is gone.
- *Limits.* CPU time, wall time, memory, disk and output size are Mandate budgets reserved before execution (the FR-56 budget rule) and enforced by the sandbox; exceeding one ends the execution with a closed diagnostic and the partial outputs are kept as working material, never registered as derived.
- *Disposable.* Nothing durable lives in the sandbox. Required evidence, artifacts and task state are written by the worker from collected outputs; the sandbox is destroyed after collection and a lost sandbox is a failed step, not lost evidence.
- *Document processing (FR-82).* Extraction is a set of platform-provided programs run through the same port on the registered source bytes: PDF (text with page and bounding-box locators, and page images for visual inspection), Office (`.docx` paragraphs and tables with structural locators; `.xlsx` cells), CSV (the existing `sheet` parser), email MIME (headers, parts, attachments each registered as `received` snapshots with their own digest), images and scanned pages (OCR producing text with confidence and a locator per line, plus the page image). Each produces an `extraction-record` with source locators and a `content_status` per region from a closed list (`extracted`, `unsupported`, `missing`, `uncertain:<reason>`). Each extracted region is bound to the **source digest, the extraction or renderer program version and a stable source location**: PDF and image regions carry the page and the region geometry needed for visual inspection; Office regions retain the package part, sheet, cell, paragraph, table or embedded-object identity needed to resolve the cited material. Structured output is never proof of accuracy: a claim grounded in an extraction is corroborated against the **preserved source representation** — the PDF page image or the original bytes — at that location, which is why page images are kept beside text. OCR confidence records the recogniser's uncertainty and does not establish transcription correctness; high confidence never bypasses the pack's verification requirement for a transcribed value, and an unresolved transcription is `not-machine-checkable`, never `contradicted`.
- *Spreadsheets.* An extraction distinguishes **formula text**, the **stored cached value**, and a **value recalculated** by the selected calculation engine, and records the engine and version, external dependencies, the calculation outcome and any unsupported function. Opening and saving a workbook is not a recalculation; a stale cached value is never described as freshly calculated. A received source is never recalculated or refreshed in place: recalculation produces a separate derived representation with its own derivation record.
- *New substrates for `structural-snapshot-v1`:* `pdf` (`$.pages[<n>].blocks[<i>]`), `doc` (`$.body[<i>]` for paragraphs, `$.tables[<t>].rows[<r>].cells[<c>]`), `mail` (`$.headers.<name>`, `$.parts[<i>]`), `image` (`$.lines[<i>]` over OCR output, each line bound to its region geometry on the preserved image; corroboration of a transcribed value against the image is a human-reviewed check where the pack requires it, whatever the confidence), plus the existing `sheet`, `json`, `web_tree`. One grammar, the existing parsing rules (no leading zeros, no separators in names), and an unimplemented substrate stays an explicit `corroboration-unsupported`.
- *Retrieval versus full examination.* The model may ask for targeted retrieval over extraction records or a full read; the tool result states what was searched (which snapshots, which regions, which query) and what was not, and absence is never inferred from an incomplete search — the `search-completeness` reading, applied to documents. Visual inspection sends page images to the model only under the disclosure policy (3a C4).
- *Ownership:* domain (execution record shape, locator grammars, content status vocabulary), application (port, call site, extraction programs' descriptors), infrastructure (sandbox adapter, extraction program images), worker (all execution).

**(3) Failure and verification**

- Isolation negatives, run against the **deployed backend and profile** (the profile identifier asserted first): read of a host path, read of an environment variable, outbound connection of any kind, write to a mounted input, database connection attempt, object-store credential lookup, cloud metadata endpoint access, an escape attempt through configuration or mounts (privileged flag, host mount, capability request) — each refused and recorded; a run whose isolation is unavailable fails rather than falling back to `local`; the same suite under `local` mode records which guarantees do not hold rather than passing vacuously.
- Limits: CPU, wall, memory, disk and output-size exhaustion each end the execution with the named diagnostic and keep partial outputs as working material only; a program that prints a success line and exits non-zero is recorded as failed from the supervisor's observation, and a program-written manifest claiming outputs that were not collected is ignored; an output containing a symlink to a host path, a special file, an oversized file or a path outside the declared output directory is rejected at collection.
- Inputs: a mount whose digest does not match its registered evidence is refused before the program starts; an output claiming an input the step did not mount is refused at derivation.
- Disposability: the sandbox destroyed mid-execution fails the step; evidence registered before the failure is unchanged; a retry is a new execution record.
- Document processing per format: a text PDF; a scanned PDF (OCR lines with region geometry, a deliberately misrecognised value that a human check catches and that high confidence does not wave through); a `.docx` with tables and tracked changes (tracked changes reported, an embedded screenshot extracted with its identity); an `.xlsx` with formulas (formula text, cached value and recalculated value all recorded; a stale cache detected; an unsupported function named); a multipart email with two attachments (three `received` snapshots); a document with a macro or external link (not executed, reported); a corrupt file (`unsupported`, no partial claim of success); for each, a claim at a locator corroborated against the preserved representation and a deliberately wrong claim reported `contradicted`.
- Retrieval honesty: a search over two of three snapshots reports the third as not searched; an absence claim over an incomplete search is refused at claim validation.
- Boundary: `no-code-execution-in-web` planted in `src` and `dist` spellings; the web bundle contains no sandbox adapter.

**Changes to existing safeguards:** the browser workspace's weaker-guarantee rule extends to code execution. `credential-containment-v1` gains the sandbox as a place a credential must have nowhere to land (no mounts carry one; stdout/stderr are guard-scanned before storage). Nothing else relaxed.

## Dependencies carried into 3c–3d

- 3c (agent loop, memory, skills, promotion): tool results as data with the two-axis result and the independent input-quality dimensions (C5, C6); `derived-output` registration with its validation records as the only route from analysis to citable support (C6); claim classes and platform-owned support-status transitions the model proposes into but never adjudicates, with `pending-review` and `not-machine-checkable` (C7); the `CodeExecution` port as one tool behind the Mandate gate and budgets, network-disabled (C8). **Promotion does not promote an exploratory execution trace verbatim.** Compiler-2 constructs a reviewed, versioned execution definition from the selected method artifact and the relevant derivations; it explicitly distinguishes fixed criteria and validated steps from period parameters, expected new inputs, exploratory branches, failed attempts and one-off collaboration actions. Historical acquisition ids provide lineage and are not the source bindings for future periods: the recurring definition states how new authorised inputs are acquired and validated each period. Promotion never automatically schedules every action performed during investigation (the demonstration's calendar invitation is one-off collaboration, not a step of the check). Retention and deletion commands for memory follow C5's shape (retention decision, holds, dependencies).
- 3d (spine and contracts): AD-5, AD-6, AD-14, AD-18 amendments; `evidence-package-v2` (owner namespace, kinds, limitations vocabulary), `acquisition-v1` (content versus acquisition identity, source-evolution relationships, impact records versus notifications), `derivation-v1` (retained method objects, the four check kinds, validation records, reproducibility comparators), `input-quality-v1` (the independent dimensions, versions, dependency-specific propagation), `artifact-version-v1` (immutable content, lifecycle records, claim classes, support-status transitions, revision-bound decisions, approval binding, issuance), `code-execution-v1` (backend and profile, supervisor-versus-program trust, output collection, `local` mode conditions, network-disabled first delivery and the later egress contract), `document-extraction-v1` (region binding, OCR rules, spreadsheet calculation rules, substrates and locator grammars), `rendering-v1` (feature matrix, blocking defects, additional-format association), `retention-v1` (decisions, holds, dependencies, availability status), and the four D-3b decisions; the classification of every new table under C1's policy inventory.
