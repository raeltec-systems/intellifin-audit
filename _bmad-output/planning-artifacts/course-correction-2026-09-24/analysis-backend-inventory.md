# Backend inventory vs. the 2026-09-24 course correction

Baseline: `main` at `c18ad36`. Source: `direction-2026-09-24.md`, `AGENTS.md`. Produced by a read-only analysis agent on 2026-09-24; persisted by the correct-course session.
Scope: `packages/domain`, `packages/application`, `packages/infrastructure`, `apps/worker`, `apps/northstar`, `scripts`. `apps/web` is inventoried separately in `analysis-web-ux.md`.

## Summary

1. The audit chain (canonical JSON + sha256 + hash-linked events) is provider-neutral, small, and exactly the foundation the direction asks to preserve. RETAIN as-is.
2. Identity/roles/gating is a closed permission table keyed to a fixed 3-role, 24-action vocabulary. The mechanism (default-deny, DB-backed role, audited denial) is right; the table is IntelliFin's own org model and must become firm-configurable. EXTEND.
3. Templates (P-1..P-4) are literal TypeScript constants, not data a firm authors. This is the single largest conflict with direction §E/H and must be REPLACEd by an authorable methodology/skill layer that still compiles to something enforceable.
4. The deterministic Compliance Rule compiler, executable-plan compiler, Run-level Gate (§H), and outcome table (§E.1) are a real, working "durable execution + truthful conclusion" engine. The mechanism is exactly what §D asks for ("verifiable outcomes", "method and results preserved") — but it is wired one-to-one to the closed Template/condition vocabulary. EXTEND: keep the gate/evidence/outcome shape, generalise the inputs it grounds against.
5. Evidence integrity (S3 store, sealed packages, integrity sweep, credential containment, read grants) is provider-neutral, already object-store-based, and matches direction §C's "preserved source snapshot → working copy → linked outputs" almost exactly. RETAIN/EXTEND (extend to non-browser document sources: Drive/Gmail/etc. rather than only Target Systems).
6. Durable execution (pg-boss queues, workspace provisioning, run control lease, waits, escalations, deferred pause, notifications) is a solid durable-agent-loop substrate that the direction explicitly wants ("multi-step work... interruptions, resumption, durable background execution"). RETAIN/EXTEND — generalise beyond one worker-driven Run of one Template to arbitrary conversational tasks.
7. The model gateway already sits behind the Vercel AI SDK (`@ai-sdk/anthropic` + `@ai-sdk/openai`, a shared `LanguageModel` interface), so provider replaceability partially exists today. EXTEND: today's two gateways (plan-derivation, agent-evaluation) are single-purpose, narrow-tool-catalogue callers, not a general orchestration runtime.
8. Solari/Playwright browser execution is a genuine "sandboxed tool execution" seam (workspace, egress allowlist, credential containment, capture suppression) worth keeping and generalising past browser-only tools to file/email/calendar connectors.
9. The whole authoring stack (form-driven Builder sections, plan-derivation queue tied to Draft saves, guided preparation/section review, version lifecycle/approval gates tied to a fixed section vocabulary) is the form-driven Procedure Builder the direction says to stop expanding. Most of this is REPLACE/RETIRE as the primary path, though the approval/version-lineage mechanism (immutable versions, dual-control approval, platform-authored drafts on config change) should survive as a generic "artifact versioning + approval" service.
10. Conversational surfaces already exist (`run-conversation*`, encrypted messages, receipt ledger, command intake, workspace preview) but are scoped narrowly to "chat about one Run, issue Pause/Resume/Stop/Answer commands against one frozen plan" — not "converse to accomplish arbitrary audit work with real tools." EXTEND: the receipt/idempotency/encryption/audit-linkage pattern is exactly right and should become the chassis for the general agent conversation.

Counts (approximate, backend-only, non-test lines): domain ≈17.3k, application ≈23.6k, infrastructure ≈24.3k, worker ≈1.2k, northstar ≈2.4k, scripts ≈3.7k. 61 migration generations (`packages/infrastructure/drizzle/0001..0061`), 66 Drizzle tables in `packages/infrastructure/src/db/schema.ts`.

## Hard-coded methodology (fights §E/§H "firms supply their own methodology")

1. `packages/domain/src/procedures/templates.ts` — the four Templates (P-1 Employee Terminations, P-2 SoD, P-3 Payment Approval, P-4 Config Review) are literal build constants with fixed sections, fixed default Target Systems, fixed control statements, fixed per-Template coverage rule (`TEMPLATE_COVERAGE_RULES`), and a fixed `PROCEDURE_TEMPLATE_IDS = ['P-1','P-2','P-3','P-4']` tuple pinned by a unit test against the PRD addendum's own §C prose.
2. `packages/domain/src/procedures/target-draft.ts` — scope-widening detector hard-codes the internal-caps compound-name heuristic with LoanCore/PayrollVault/LedgerDesk as the worked examples (mechanism is generic; comment/tests reference these names).
3. `packages/application/src/runs/agent-prodconsole.ts` + `prodconsole-labels.ts` — a P-4/ProdConsole-specific producer with a hard-coded label contract (`Parameter`/`Value`/`Snapshot identifier`/`Expected parameter count`/`Snapshot taken at`) that only makes sense for the one synthetic Northstar config page.
4. `packages/domain/src/procedures/compliance-draft.ts`, `plan-compiler.ts` — P-1's C1/C2/disablement-window 24-hour rule, P-2's RoleMatrix permission-pair policy, and P-3's permissive found-or-proven-absent rule are named and special-cased in comments and in some branch logic (e.g. `disablementWindowCondition`, `RolePrivilegePolicy`) rather than being purely data-driven per-firm rule authoring.
5. `packages/domain/src/runs/{evaluation,result,execution,population,observation,gate}.ts` and `packages/application/src/runs/{execute-agent-work-item,execute-adapter-steps,rule-evaluation,register-observations,execution-ports,execute-agent-steps,agent-tool-planner,agent-observation,run-gate,record-review}.ts` — all reference the four Template ids or the coverage-rule split (`must-appear` vs `found-or-proven-absent`) directly, because the Run pipeline branches on which of the four fixed Templates produced the frozen plan it is executing.
6. `packages/infrastructure/src/db/schema.ts`, `procedure-list.ts`, `run-conversation-repository.ts`, `run-detail-repository.ts`, `adapter-execution-repository.ts` — read/reference the fixed Template id union at the storage/query layer (e.g. as a CHECK-constrained or type-narrowed column), not just in comments.
7. `apps/worker/src/{main,startup}.ts` — startup wiring names P-1/P-4 execution paths (agent vs. adapter classification) explicitly in comments describing which Template shape exercises which stage.
8. `apps/northstar/*` and `fixtures/northstar/*` — an entire synthetic-system fixture catalogue (LoanCore, AccessGate, ApproveNow, CoreDirectory, ProdConsole, PeopleHub, ConfigRegistry, RoleMatrix) built to exercise exactly the four fixed Templates; golden expectation files (`p-1-live-acceptance.json`, `p-2-sod-conflicts.json`, etc.) encode per-record "correct" outcomes for that fixed dataset.
9. `scripts/seed-northstar.mts`, `scripts/verify-deployed-loancore.mjs` — operational scripts that only make sense for the four-Template/Northstar demonstration workload.

## Provider seams

- **Anthropic** — `@ai-sdk/anthropic`'s `createAnthropic`, used identically in both model gateways: `packages/infrastructure/src/procedures/model-gateway.ts` (plan derivation) and `packages/infrastructure/src/runs/agent-model-gateway.ts` (agent evaluation / tool planning). Selected via `AgentModelProvider`/`ModelIdentity` config, not hard-imported per call site.
- **OpenAI** — `@ai-sdk/openai`'s `createOpenAI`, same two gateway files (plan derivation and agent execution), plus a separate, narrower OpenAI Responses-API adapter for writing assistance: `packages/infrastructure/src/procedures/authoring-model.ts` (`AUTHORING_OPENAI_API_KEY`, model `gpt-5.6-terra`, `store:false`).
- **Seam location (both gateways)**: an abstract `SdkModelGateway` / `AgentModelGateway` implementation wraps a Vercel AI SDK `LanguageModel` behind an application-owned port (`ModelGateway`, `AgentModelGateway` in `packages/application/src/procedures/plan-ports.ts` and `packages/application/src/runs/agent-ports.ts`). Swapping or adding a provider means adding a `createX(...)` call and wiring `AgentModelProvider`/`ModelIdentity` configuration — the port contract (frozen prompt version, strict-shape parsing, no provider text retained, `finishReason==='stop'` required) does not change per provider. This is a real, already-working seam for §D's "orchestrate replaceable reasoning models," though today it serves exactly two narrow call shapes (compile-a-plan, propose-a-tool-action) rather than a general agentic loop.
- **Solari** (`@solarisdk/browser`) — managed remote browser provider, isolated to `packages/infrastructure/src/runs/browser-execution.ts` behind the application-owned `BrowserExecution` port. The same file also implements a `local` mode (bare `chromium.launch()` via `playwright-core`) selected by `WorkspaceMode` at runtime — so a provider-vs-local seam already exists for the one tool category (browser) IntelliFin currently automates. No equivalent seam yet exists for the direction's other target integrations (Drive/OneDrive/SharePoint, Gmail/Outlook, Calendars, Todoist/Planner, GitHub) — those would each need their own connector port + adapter pair following this same "port in `application`, provider SDK only in `infrastructure`, AD-1 boundary-checked" pattern.
- **Conversation content encryption** — not a model provider, but a provider-neutral seam worth noting: `ConversationContentCipher` (`packages/infrastructure/src/runs/conversation-content.ts`) is AES-256-GCM with its own dedicated key, independent of any model or connector provider, so message content never needs to touch a third-party SDK to be protected at rest.
