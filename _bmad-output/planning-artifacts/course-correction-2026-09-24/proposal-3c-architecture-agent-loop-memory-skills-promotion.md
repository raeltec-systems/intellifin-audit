# Proposal 3c of 7 — Architecture: the agent loop, context and memory, skills and methodology packs, promotion to recurring checks

Status: revised on 2026-09-24 after the owner's nine edit groups (D-3c-1..4 taken as below); awaiting owner approval. Builds on the approved 3a (D-3a-1..4) and 3b (D-3b-1..4) baselines and carries their dependencies forward without reopening them: the Mandate gate with four outcomes and the capability summary (3a C3); two-axis connector results, disclosure policy at every outbound request and the `reconcile` wait (3a C2, C4); the independent input-quality dimensions, derivation and validation records, platform-owned claim support status with `pending-review` and `not-machine-checkable`, and the network-disabled `CodeExecution` port (3b C5–C8); promotion that never promotes an exploratory trace verbatim (3b, dependencies).

Baseline facts checked on `main` `c18ad36`: the model layer sends a JSON envelope through the AI SDK's `generateText` with **no native tool calling**, one platform-built opaque tool per turn, and the model may author no parameter (`agent-execution-v1` invariants 1–3, `parameterNames: []`); a turn is bound to a Work Item's registered snapshot (`validate_agent_turn`); every request and response is credential-scanned and retrieved content travels in an `untrusted` field; provider, model and prompt version are recorded per turn and rejected output is never retained; the tool cap is 128; tokens are reserved before paid I/O. There is no memory store, no retrieval index, no skill or pack representation (Templates are build constants), and no promotion path other than hand-authoring a Procedure Version in the Builder. The Procedure Version lifecycle (`DRAFT → SUBMITTED → APPROVED → ACTIVE → RETIRED`, author ≠ approver, frozen fields, `regressionRequirement`, `handoverAt`, `mint-platform-draft`) is intact and is what promotion reuses.

Owner decisions this proposal asks for:

| Decision | Proposed choice |
|---|---|
| D-3c-1 | **Taken.** Native tool-calling through the application-owned execution boundary: the SDK transports requests and responses and never executes a tool, advances an autonomous multi-step loop or performs a provider-hosted action; every proposed call has a durable identity bound to its descriptor version, effective parameters and originating turn before execution; completed calls survive restart without re-execution; platform-owned fields are excluded from the model-authored schema and injected from trusted state, and a conflicting explicit target is refused rather than silently rebound; provider-required continuation items are retained under the conversation's controls and provider switches rebuild from portable state at a safe boundary. Supersedes `agent-execution-v1`'s "the model authors no parameter". |
| D-3c-2 | **Taken.** Scope-owned memory: an explicit instruction from a user with authority over the scope is that user's recorded confirmation; an agent-inferred item is a proposal until the scope owner confirms; firm and client scopes need their owner. Memory lifecycle status is separate from factual verification status; methodology memory and engagement memory reference the authoritative pack and decision records and never amend or replace them; precedence is the approved configuration under mandatory authority boundaries, not a hard-coded hierarchy. |
| D-3c-3 | **Taken.** Versioned skills and methodology packs as tenant data, under mandatory platform safeguards a pack cannot remove (evidence integrity, scope enforcement, required quality limitations, truthful outcomes, mandatory approvals), with an explicit admission boundary for skills and a usable starting experience before any firm-specific pack exists. |
| D-3c-4 | **Taken, wording revised.** An approved recurring definition is a Procedure Version compiled by compiler-2, so `audit_run.version_id` stays non-null and the existing lifecycle applies. The definition **freezes the audit method** — objectives, source and population rules, criteria, validations, permitted capabilities and decision boundaries — and execution cannot invent tests or change those elements. Within an explicitly declared, versioned and approved step, **bounded model-assisted execution** is permitted (navigating an authorised interface, locating the specified document, extracting a field for later corroboration) with its instructions, tools, inputs, limits and output contract frozen. Open-ended investigation is a separate Agent Task that never mutates the frozen definition or a sealed result, and that may create linked evidence, an impact record and a proposal for correction or rerun. |

Each change states: (1) requirement mapping and the contracts it supersedes or extends; (2) implementation approach — reused, generalised, introduced — with ownership of state, authorisation, credentials and execution; (3) failure and verification approach; and, explicitly, any change to an existing safeguard.

## C9 — The agent loop: one turn, one tool boundary, durable in between

**(1) Requirements:** FR-56, FR-57, FR-58, FR-59, FR-61, FR-62, FR-88, FR-89, UJ-1..UJ-5. Supersedes `agent-execution-v1` (the P-1/P-4 closed loop) as the conversational path's contract; keeps its invariants 4–8 and 12–16 by name (gate before port, closed request shape, credential scan of request and response, untrusted retrieved field, refusal audited without text, boundary checkpoints). Extends AD-16 and AD-7 as 3a C2 already announced. `agent-execution-v1` stays in force for compiler-1 Runs until compiler-2 replaces them.

**(2) Approach**

- *Invocation model (introduced, replaces the JSON envelope).* `ModelInvocation` in application: messages (system, developer, conversation, tool results), tool schemas derived from the capability summary (3a C3), and the provider, model and prompt version to use. Implemented in infrastructure over the AI SDK's tool-calling API, so providers are swapped by configuration and the model sees exactly the tools its effective authority allows. **The SDK transports model requests and responses and nothing else**: it never executes a tool, never advances an autonomous multi-step loop (`maxSteps` stays 1, tool `execute` handlers are absent) and never performs a provider-hosted action outside IntelliFin's authorisation, budget, dispatch and receipt mechanisms. Provider identity, model, prompt version, token usage and finish reason are recorded on every turn (`task_turn`), rejected or malformed output is classified and never retained, and the credential guard scans the outbound request and the inbound response. The disclosure policy (3a C4) is applied to the assembled context before every call, including a resumed one.
- *Response contract.* A response may contain text, zero, one or several tool calls, or a wait request; each accepted turn and each proposed call has a **durable identity** (`task_tool_call`: turn, ordinal, descriptor version, effective parameters, state), written before execution. Calls execute **serially** in the first implementation; each call passes its own schema validation, gate and lifecycle boundary. Partially streamed arguments are never dispatched: a call is bound only when its arguments are complete and validated. A call that follows a `needs-confirmation` or `needs-clarification` call in the same response is held until that wait closes; nothing continues past a wait on an assumed outcome. A completed call and its result survive restart and are never executed again: on resume the executor replays recorded results into context, and a regenerated model response cannot make an already-performed external action a new authorised operation, because the operation identity (3a C2) already holds its outcome.
- *Provider continuity.* Provider adapters may retain the provider-bound continuation items their supported API requires (a reasoning item that must accompany a tool result, a response id) under the same scope, encryption, retention and disclosure controls as the conversation; they are neither authority nor audit evidence. A provider change rebuilds context from portable, authorised work state (the ledger, the conversation, artifacts, waits) at a safe boundary; provider-specific state is never forwarded to another provider and a switch never replays a completed external effect. Supported provider capabilities — tool calling, structured parameters, images, continuation, cancellation — are tested per adapter, and "configuration-only replacement" applies only where the required capabilities and the disclosure policy are satisfied.
- *The turn cycle (the executor, worker-only under a delegation).*
  1. **Assemble** context from durable state only: the task's objective and plan, the step ledger tail, the conversation window, retrieved memory and artifact excerpts (C10), the loaded skills (C11), the capability summary. Nothing in process memory survives a restart, so assembly reads the same rows a restart would.
  2. **Reserve** the turn's budget (tokens, steps, time) against the task's Mandate budget before paid I/O (the existing reservation rule).
  3. **Call** the model. The response is handled under the response contract above: text is a message to the auditor; each tool call is bound with a durable identity; a wait request (a question, a confirmation, a reconciliation) opens a wait.
  4. **Validate** a tool call: parameters against the descriptor's schema, from which platform-owned scope and authority fields are **excluded** and injected from trusted state; a model-selected resource id remains a selector subject to validation, and a conflicting explicit target (another account, recipient, record or resource than the one the task is bound to) is refused with a reason rather than silently rebound; safe defaults may be supplied for absent optional fields, which supplies context and never changes the meaning of the proposed action; the effective operation is fully bound before any confirmation and a material change after confirmation invalidates it; then the Mandate gate (`allowed | needs-clarification | needs-confirmation | denied`). `needs-clarification` and `needs-confirmation` open the corresponding `task_wait`; `denied` is `security.action-denied`, terminal for **that operation** (never for the task or the engagement), and the model is told the closed reason and nothing else. An ordinary schema mistake receives bounded correction feedback (at most the descriptor's declared retry count); a permission denial is never presented as a schema repair and is never re-attempted through another tool.
  5. **Dispatch** through the port (connector, `CodeExecution`, or an internal tool) with the step ledger written first (3a C2's dispatch claim for external effects).
  6. **Return the result as data**: the two-axis outcome, the returned payload marked `untrusted` with its provenance and input-quality assessment (3b C6), and the receipt. Tool results are never rendered as the platform's prose and never carry authority.
  7. **Boundary**: the lifecycle boundary runs after every tool result and every model answer — pause, cancel, revoked delegation, exhausted budget, lost lease — before the next step is taken (the existing `lifecycleBoundary` rule, now with no call site that can forget it because the executor has one loop).
- *Self-review, scoped to material audit content.* Material findings, conclusions and substantive artifact changes pass through the applicable self-review and validation checkpoint before they are presented as reviewed analytical output: the executor runs a review turn against the artifact's claims and their support status (3b C7) and the input-quality assessments (3b C6), and the model must label every claim class it produced. Routine progress messages, questions and minor edits do not require a second model call; a material revision invalidates the relevant prior checks. Self-review records what was examined and the issues found; it is not human approval and cannot promote its own unsupported interpretation to verified status. Tentative drafts and progress are shown with their actual status: unchecked model text is never streamed as a verified finding and quietly corrected by a later hidden review. Where validation or review cannot complete (budget, provider failure), the useful draft is preserved and presented with the limitation; important signals are never suppressed and no check is implied to have passed. A candidate finding may hold a `supported` condition beside an unresolved cause: the claim-level distinctions are kept rather than the whole draft withheld.
- *Investigation within the Mandate (UJ-3).* The model may plan and pursue adjacent investigation using the same loop; what bounds it is the effective authority (3a C3), the budget, and the requirement that material investigative steps land on the ledger as steps with their own results. Nothing about investigation is a separate mode: an investigation is more tool calls under the same gate.
- *Waits and resumption (FR-57, FR-88).* A question, a confirmation and a reconciliation are durable `task_wait` rows with deadlines (3a C2). The auditor's free-text answer is a conversation message: it informs the next turn and never executes anything; where an exact bound decision is needed (a closed option, a confirmation bound to material details) the existing receipt mechanism records it. On resume — after an answer, an interruption, a worker restart or a pause — the executor re-derives effective authority (FR-83), re-reads the delegation, re-assembles context from durable state and re-briefs the model with the ledger tail and the answer. **Conversation state IS persisted** (the encrypted conversation and the turn records), replacing AD-16's "no model conversation state across a wait" with "no authority is ever carried in conversation state": the model resumes with memory of what happened and none of its permissions come from that memory.
- *Instruction provenance and prompt injection.* Five categories enter the model's context and none grants authority by appearing there: **platform controls** establish non-negotiable boundaries (the capability summary, the claim rules); **authenticated user requests** direct work within those boundaries; **approved skills, methodology and active preferences** guide behaviour within their applicable scope; **retrieved evidence and external messages** are source content, labelled with provenance; **proposed memory and unapproved packs or skills** are inspectable content and not active behavioural rules. The Mandate constrains capability and authority; it does not by itself establish that every permitted operation is relevant, correctly reasoned or faithful to the auditor's intent. The runtime therefore keeps instruction provenance visible in context, binds material actions to the task and the applicable decisions, applies disclosure restrictions, and enforces the approved evidence, validation and review requirements — so content that induces a permitted-but-inappropriate action (omitting an exception, proposing misleading memory, altering a draft, including material in an output) meets those checks rather than only the gate. **Prompt injection remains a residual risk** that requires behavioural evaluation as well as permission tests; the product does not claim that labelling content or enforcing tool permissions eliminates it.
- *Model replaceability.* The invocation model carries no provider-specific field outside the adapter's retained continuation items; prompt versions are immutable text identified by version; a pinned model configuration on a recurring check records what was approved and is not a promise of identical output (FR-51). Switching providers for a task is a configuration change under the disclosure policy and the provider-continuity rule above.
- *Ownership:* domain (turn and wait state machines, claim labelling rules), application (executor, invocation model, tool validation, gate call site, context assembly), infrastructure (AI SDK adapters, storage, queues), worker (all execution). The web renders conversation, timeline and waits; it composes no model (`no-agent-model-in-web` unchanged).

**(3) Failure and verification**

- The loop's one call site: a mutation harness proves that removing the gate call, the schema validation, the budget reservation or the boundary check fails a named test each.
- Response contract: a response with two tool calls executes them serially with two gate decisions and two boundary checks; a streamed call interrupted mid-arguments is never dispatched and the turn is recorded incomplete; a call following a confirmation wait in the same response is held until the wait closes; a restart after a completed tool result replays the result and dispatches nothing; a regenerated response proposing the same completed external action is refused by the operation identity.
- Parameter binding: a platform-owned field is absent from the offered schema and injected; a model-supplied conflicting target (another recipient, another record) is refused, not rebound; an absent optional field receives a safe default recorded as such; a confirmed operation whose arguments then change is re-confirmed or refused; a schema mistake gets bounded correction feedback and a permission denial gets none and is not retried through another tool.
- Provider continuity: a provider-bound continuation item is stored encrypted under the conversation's scope and retention, never forwarded to another provider; switching providers mid-task rebuilds context at a boundary with no duplicate external effect and no lost decision; each adapter passes the capability tests (tool calling, structured parameters, images, continuation, cancellation) before it is selectable.
- Injection, inspected on the resulting work and not only at the gate: content requesting an out-of-scope action is `denied` or `needs-confirmation` and the ledger shows the attempt; content attempting to suppress an exception through permitted tools (a draft revision that drops a supported claim) is caught by the self-review and claim checks and the exception stays visible; source text pretending to be a user confirmation does not close a wait (confirmations come only through the receipt mechanism); malicious content proposing a memory item lands `proposed` and never `active`; these are behavioural evaluations run on every prompt version, and their pass rate is reported, not claimed as elimination.
- Resumption: kill the worker mid-tool-call, after a tool result and during a wait; each resumes from durable state with authority re-derived; a revoked delegation during the wait stops the task with a recorded reason; the resumed model sees the same ledger tail a fresh worker reads.
- Self-review: a same-model review missing an arithmetic error that the deterministic check catches (the deterministic check governs); a candidate finding with a `supported` condition and an unresolved cause is shown with both statuses; budget exhaustion before review presents the draft with the limitation and no implied pass; a material claim changed after its review invalidates the review and is re-checked; a routine question triggers no review turn.
- Provider swap: the same task replayed against a second provider adapter produces a valid turn record with the new identity and no code change outside configuration; a restricted item under the disclosure policy blocks both the primary and the fallback provider.
- Budget: a turn that would exceed the reserved budget is refused before the call; a mid-task exhaustion ends the task at the boundary with partial work preserved as working material and artifacts.

**Changes to existing safeguards:** `agent-execution-v1`'s "model authors no parameter" is superseded for the conversational path (D-3c-1); AD-16's no-persisted-conversation rule becomes no-authority-in-conversation; AD-7's "free text from humans is never passed to the model" is replaced by "free text is model input and never authority". Gate-before-port, credential scanning, untrusted labelling, closed diagnostics and boundary checkpoints are unchanged.

## C10 — Context assembly, retrieval and governed memory

**(1) Requirements:** FR-79, FR-80, FR-87, FR-89 (context under policy), UJ-4. Introduces the memory aggregate the spine defers; extends 3a C1 (scoped index rows) and 3b C5 (retention).

**(2) Approach**

- *Durable records are the source of truth; the working context is bounded, not minimal.* The runtime maintains a **working context** for the current task holding the conversation and tool-call history the task needs, selected source material, unresolved questions, prior decisions and current artifact versions, plus the engagement summary (a derived record, FR-87), the loaded skills and pack instructions, and the capability summary. It is reconstructed from durable records on restart and **compacted** only when necessary; a compaction records its inputs, the range it covers and its limitations, preserves links back to the authoritative records, and must not convert a hypothesis into a fact, discard an unresolved quality limitation or replace an approval record with a summary of one. Summaries and indexes are derived context with their own provenance and never replace evidence, decisions or approvals; creating one changes nothing about the records it summarises.
- *Retrieval (introduced), one access path among several.* An index over memory items, artifact versions, extraction records and conversation messages, each row carrying `tenant_id`, `client_id`, `engagement_id` and the item's classification under the same RLS boundary (3a C1). Retrieval **filters by each item's actual applicable scope before ranking** — user preferences, tenant-wide methodology, client knowledge, engagement-private material — with engagement isolation as the default; results carry provenance, effective dates, the sources and versions covered, indexing freshness, truncation and material exclusions. An incomplete or stale index never supports a claim that relevant evidence does not exist. Indexed retrieval is not the only way to inspect authorised material: the agent can enumerate sources, read a specific document in full, continue through longer material and use visual inspection (3b C8), and the auditor can say "read the full document" inside the conversation. Explicitly authorised use of a prior engagement's report happens through a governed reference and access grant, not by promoting it into firm-wide memory. Summaries, cached context and provider continuation items are re-evaluated when their underlying access or disclosure permissions change: a stale summary cannot preserve access that was revoked, and revoked content is absent from a resumed context. For methodology and policy, "current" means applicable to the work and period examined; where the period spans a policy change, every applicable version is returned with its effective range, and a mismatch is flagged rather than the newest preferred. Embeddings, if any, are computed only by a provider the disclosure policy approves for that content and stored in scoped rows.
- *Memory (introduced).* `memory_item` with the six scopes — `user-preference`, `firm-methodology`, `client-knowledge`, `engagement-facts-and-decisions`, `conversation-and-execution-state`, `confirmed-lessons` — each item carrying owner, scope keys, provenance (who, where, which message, evidence or approval it came from), effective dates, version and `supersedes`, and status `proposed | active | superseded | rejected`. Scope ownership: a user owns their preferences; the engagement lead owns engagement facts and decisions; a firm or department owner owns methodology; the client-knowledge owner is the tenant's designated role; confirmed lessons need the owner of the scope they apply to. `conversation-and-execution-state` is not written by proposals at all: it IS the conversation, ledger and task rows, read through the same store for retrieval and never promoted by being stored.
- *Lifecycle status is not verification status.* An active memory item carries a separate **verification status**: `user-reported`, `source-supported` (with the evidence or record it points to), `disputed`, `awaiting-verification`. An explicit retention instruction is recorded without a second prompt, and its content keeps its source, qualifications and verification status; when a material audit conclusion depends on that information, the agent follows the applicable evidence and review requirements (3b C7) rather than treating the memory as established. Recording "the client's fiscal year ends in March" establishes that an authorised user asked us to remember that statement.
- *Authoritative records stay singular.* `firm-methodology` memory references the applicable approved pack version and its source records and cannot amend them: an instruction that changes methodology starts the pack-change workflow (C11). `engagement-facts-and-decisions` memory summarises or locates decisions; the authoritative decision is its attributable application record, and ordinary authorised engagement updates need no separate memory-approval ceremony. Scope owners may delegate defined maintenance rights (a team member may maintain engagement facts) so the engagement lead does not approve every routine factual update.
- *Writing memory (D-3c-2).* An **explicit instruction** ("remember that I prefer…", "record that the client's fiscal year ends in March") from a user with authority over that scope is recorded as an `active` item with that message as its confirmation; the agent does not ask again. An **agent-inferred** preference, correction or lesson (UJ-4's "retain this correction") is written `proposed` with source, scope and reason and shown as a proposal; it becomes `active` only on the scope owner's confirmation, and a pending proposal is never fed to the model as an instruction (it may be shown to the model as a pending proposal, labelled). Promotion across scopes (an engagement lesson to firm methodology, a client fact to a cross-engagement item) follows the destination scope's approval and confidentiality rules; client knowledge never leaves its client.
- *Precedence and conflicts.* The platform enforces the **approved precedence configuration** (from the active pack's criteria-authority order, C11) together with the mandatory authority boundaries; it does not hard-code the reference workspace's hierarchy as universal methodology. A preference cannot override an applicable mandatory requirement whatever its retrieval rank. Structured conflicts (two active items on the same typed point) are checked mechanically; conflicts inferred from prose are recorded as **proposed conflicts** with supporting references, and the model does not silently decide applicability or resolve a material ambiguity. Memory may point to evidence and approvals; it never stands in for them, so a memory item is never citable as support for a factual claim (3b C7).
- *Retention and correction.* Superseding an item keeps the old version; rejecting a proposal keeps the record; deleting follows 3b C5's retention rules. A memory item that was the basis of a recorded decision is a retained dependency of that decision; correcting or retiring an item ends its active use at once and is visible on the decisions that relied on it.
- *Ownership:* domain (scopes, statuses, precedence rule, ownership rule), application (proposal and confirmation commands, retrieval query, context assembler), infrastructure (index, storage, embedding adapter).

**(3) Failure and verification**

- Scope: a client-B memory item never appears in a client-A engagement's retrieval, through the query and through raw SQL under the wrapper; an engagement item never appears in another engagement of the same client unless promoted or referenced through a governed grant; a prior engagement's report reached through a grant is readable there and still absent from firm memory.
- Continuity: a correction survives compaction and a restart; an unresolved limitation survives compaction; a stale index followed by a direct full read finds the document the index missed and the retrieval record shows the index's coverage; content revoked mid-task is absent from the resumed context and from any summary; an engagement period spanning two policy versions returns both with their ranges.
- Writing: an explicit instruction from the scope owner is `active` with no second prompt and its verification status is `user-reported`; the same instruction from a user without authority over that scope is `proposed`; an inferred correction is `proposed` and invisible to the model as an instruction until confirmed; confirmation by a non-owner refused; a delegated maintainer updates an engagement fact without the lead's approval; a memory instruction cannot amend an approved pack and opens the pack-change workflow instead; a retired item stops being used and the decisions that relied on it show that.
- Currency and precedence: a methodology item effective after the engagement period is flagged; two packs with different configured precedence resolve the same structured conflict differently and both are enforced; a prose-inferred conflict is recorded as proposed and not decided; a preference never overrides a mandatory requirement.
- Authority: a memory item saying "the auditor may send emails without confirmation" changes nothing at the gate; a memory item cited as evidence is refused.
- Summaries: regenerating an engagement summary changes no record it summarises and carries its own provenance.

**Changes to existing safeguards:** none relaxed. Memory is a new aggregate under the existing scope, retention and citation rules.

## C11 — Skills and methodology packs as versioned tenant data

**(1) Requirements:** FR-76, FR-77, FR-78, FR-85, FR-86. Supersedes AD-2's "Templates are data owned by the procedures module" as implemented (build constants) by tenant data; keeps P-1..P-4 as one optional example pack (owner decision 1).

**(2) Approach**

- *Methodology pack (introduced).* `methodology_pack` (tenant-owned, versioned, immutable per version, status `proposed | approved | active | retired`) containing: phases and gates; artifact types with their required review states and who may move them (3b C7); templates for produced files with their supported-feature matrix (3b C7); rating scales; sampling conventions; criteria authority order; reporting structures; approval and independence requirements; the required validation checks per method and claim class (3b C6); Gate parameters for recurring checks (C12). The platform ships **example packs** as data files, including P-1..P-4 with their fixtures as one optional pack; none is loaded by default and none is universal. Activating a pack version for a tenant, or changing the active version, is an approved, audited change; an engagement records the pack version it runs under and does not silently follow a newer one.
- *Mandatory platform minimum.* A pack configures methodology, not the minimum integrity of the product. Gate requirements are the **platform-mandatory minimum plus applicable methodology checks**: packs may select supported methods, add checks and configure permitted parameters, and cannot remove evidence integrity, scope enforcement, required quality limitations, truthful outcome states or mandatory approval protections. Before acceptance, every existing Gate rule is classified `platform-mandatory`, `methodology-configurable` or `legacy-template-specific` in a checked-in table with a test, and the safeguards are preserved when the checks generalise (C12).
- *Starting without a pack.* A new authorised workspace can converse, inspect permitted files, perform exploratory analysis and prepare provisional outputs with no firm methodology configured. Formal methodology-dependent outputs, ratings, approvals and recurring-check promotion name the configuration still required, and missing configuration blocks the affected action, not all useful work. The product offers explicit starter-pack selection or conversational pack preparation (FR-86); it never silently loads P-1..P-4 and never invents a firm's methodology.
- *Skills (introduced).* `skill` (tenant-owned or shipped example, versioned, immutable per version): identifier, purpose, applicable context (engagement types, phases, artifact types), required capabilities (which tool operations and effect classes it expects to use), expected outputs (artifact types, claim classes), and the instruction text. A skill describes approach. An external document does not become an active skill because it resembles a skill file: loading as behavioural instructions requires registration under the tenant and the applicable approval, and a proposed or unapproved skill is inspectable content only (C9's instruction categories). An approved skill is loaded into the model's context as labelled instructions and can request nothing the Mandate does not grant: required capabilities are matched against the capability summary and an unmet one is reported to the auditor, never satisfied by widening authority.
- *Discovery and loading (FR-85).* The executor selects skills from the auditor's explicit choice or from the task's objective, phase and context through retrieval (C10), shows which were loaded, and records skill and pack versions on the task (`task_skill_use`). Loading a skill cannot grant permissions, bypass a required decision, or alter an approved recurring-check definition — it is context, and the gate does not read context.
- *Pack proposal (FR-86).* Methodology documents, templates and conversational instructions can be turned into a **proposed** pack version by the agent (a `generated` artifact with its sources cited); the pack owner reviews and approves it through the artifact lifecycle (3b C7). Configuring a methodology requires no change to the core application: packs are data validated against a versioned pack schema, and a pack that fails validation is refused with the reason.
- *Compiler-1 Templates.* `templates.ts` becomes the source of the example pack's data files. The constants and every compatibility resource compiler-1 versions depend on (the Template contracts, `PLAN_LOOKUP_COLUMNS`, the coverage rules, `REQUIRED_EVIDENCE_KINDS`) are **retained for as long as any ACTIVE compiler-1 version exists**; removing Templates from the new primary path must not strand a frozen version. Existing ACTIVE compiler-1 versions keep executing unchanged (the standing rule that frozen bytes are never edited).
- *Ownership:* domain (pack and skill schemas, validation), application (activation command, discovery, loading), infrastructure (storage, retrieval), web (pack and skill administration surfaces).

**(3) Failure and verification**

- Authority and admission: a skill declaring a required capability the Mandate lacks is loaded with the gap reported and the operation is still `denied` at the gate; a skill instruction "approve the finding" produces no approval; a document shaped like a skill file found in a source folder is not loaded as instructions and is shown as content; an unapproved registered skill is not loaded.
- Bootstrap: a new workspace with no pack converses, reads permitted files, runs exploratory analysis and produces a provisional working paper; promotion and a rating are blocked naming the missing configuration; no pack is loaded without an explicit selection.
- Mandatory minimum: a pack that omits or disables a `platform-mandatory` Gate rule is refused by name; a pack that adds a check and reconfigures a `methodology-configurable` one validates; every existing rule appears in the classification table.
- Versions: a task records the exact skill and pack versions; publishing a new pack version changes no running task and no active recurring check; activating it is an audited command and the engagement's recorded version is unchanged until re-bound.
- Packs as data: the example pack validates; a pack with an undefined artifact state or a validation check the platform does not implement is refused by name; a firm pack differing from the example in every configurable field runs an engagement end to end with no code change; a compiler-1 ACTIVE version executes unchanged after the Templates leave the primary path.
- Proposal: a pack proposed from uploaded methodology documents cites them and is `proposed` until the owner approves; the agent cannot approve it.

**Changes to existing safeguards:** Templates cease to be constants; the frozen-bytes rule for existing Procedure Versions is unchanged.

## C12 — Promotion, compiler-2 and recurring execution

**(1) Requirements:** FR-51, FR-13..FR-18 (as applied to promoted checks), FR-72, FR-84, UJ-6, PRD §8.1's thin recurring proof. Extends `executable-plan-v1` (compiler-2 beside compiler-1), `run-level-gate-v1` (pack-parameterised checks), `run-result-v1`, the Procedure Version lifecycle and AD-23.

**(2) Approach**

- *The method artifact.* Promotion starts from an artifact that satisfies the **validated `promotable-method` schema** (a semantic capability declared by the artifact type, whatever the pack names the type): the selected approach, the criteria, the analytical steps with their retained code or queries (3b C6), the expected inputs described as **acquisition rules** (connector, canonical location, selection and period rules, required quality dimensions), the period parameters and other future-period rules, the validation checks required, the outcome vocabulary and review responsibility. The agent constructs it from the task's ledger and derivations by **selection**, keeping fixed criteria, validated steps and the future-period rules, and excluding historical literal values, exploratory branches, failed attempts and one-off collaboration actions (3b's carried rule); the auditor edits and approves the artifact like any other (3b C7).
- *Compiler-2 (introduced, beside compiler-1).* Compiles an approved method artifact into a frozen executable plan over a **closed step vocabulary**: `acquire-source` (an acquisition rule), `execute-method` (a retained program with bound parameters and an input manifest), `assist` (a **bounded model-assisted step**: frozen instructions, the tools it may use, its inputs, limits and an output contract naming which outputs are deterministically corroborated extracted values and which are model-proposed judgements entering `pending-review`), `validate` (a required check), `evaluate` (deterministic criteria over derived outputs, reusing the compiler-1 condition grammar where it applies), `assess-quality` (the input-quality dimensions to establish at that point), `report`. No `send`, `create` or `investigate` step exists; notification policy is a separate, later contract and the vocabulary is versioned so it can carry one without contradiction. Compilation is **deterministic over a validated specification**: identical inputs compile identically; unsupported or ambiguous semantics produce an explicit unresolved issue that blocks submission, never silently executable code; the compiler version is frozen on the version. The compiler emits a **reviewable mapping** from the method artifact to the executable definition (criteria, matching logic, parameter rules, required validations, each traced to its source passage). A model may check the compilation (the existing `equivalentExecutablePlan` shape); its disagreement is not a veto, but a material discrepancy it names is an unresolved issue that must be resolved before activation. Approval binds the selected method **and** the compiled definition being authorised; where the pack lets one review satisfy both, one decision is recorded against both digests, and separate approvals exist only where the methodology requires them.
- *A promoted check is a Procedure Version (D-3c-4).* `procedure_version` gains `compiler = 2` rows whose frozen inputs are the method artifact version, the compiled definition and mapping, the pack and skill versions, the acquisition rules, the retained code objects and digests, parameters, validation requirements, every `assist` step's frozen contract, the pinned model and tool configuration (recorded, not a promise), the schedule and the review responsibility. The existing lifecycle applies: `DRAFT → SUBMITTED → APPROVED → ACTIVE`, approver ≠ author, frozen fields after approval, `regressionRequirement` on a changed configuration, activated succession and calendar handover, platform-authored drafts on a bound change (`mint-platform-draft`). Reusing these commands is not evidence they work with compiler-2: each is exercised with a `compiler = 2` version in the acceptance suite. `audit_run.version_id` stays non-null and every scheduled run is a Run.
- *Recurring execution.* A scheduled Run executes under an `execution_delegation` created at activation for the responsible human (3a C1, FR-84), re-checked at each claim and before each dispatch. The executor runs the compiled plan step by step; the **frozen method** — objectives, source and population rules, criteria, validations, permitted capabilities and decision boundaries — cannot be changed or extended by execution, and no step may invent a test. Model turns occur only inside declared `assist` steps under their frozen contract; their deterministically corroborated extracted values and their model-proposed judgements keep the distinct statuses 3b approved. Quality and prerequisite checks (`assess-quality`, `validate`) constrain the dependent steps and the assessment at the point they are established, not only at a final step: a failed required validation prevents the dependent evaluation from producing a final pass. Then the Run-level Gate — the platform-mandatory rows plus the pack's configured checks, over the same closed diagnostic mechanism — and the §E.1 outcome table.
- *Expected inputs, access failures, material changes (FR-51), classified by identity and meaning.* New source contents inside the approved population, period and source rules are ordinary inputs. An expired or revoked connection blocks the affected acquisition, records a truthful access failure, opens a recovery request to the responsible human and constrains the affected assessment; **reconnection** must establish restoration of the approved account, canonical resources and authority (the connection's canonical account identity and the resources' canonical ids, 3a C3), never merely a matching display name, and then needs no re-approval. A path or name change that preserves the approved canonical resource and its containment is recorded as a metadata change; a move that changes the authorised boundary or the acquisition's meaning is a material change. A changed matching rule, criterion, methodology applicability or execution behaviour is a material change: the check is not executed against it, a platform-authored draft is minted and goes through approval. Publishing a new pack version creates no automatic change to a pinned check; rebinding the check is a separate reviewed change.
- *Coverage limitations and statuses (UJ-6, FR-72).* A scheduled run with a missing, partial, stale or out-of-period input constrains the affected assessment immediately through the quality dimensions and the Gate; supported record-level exceptions remain visible; execution status, input and coverage status, audit assessment and review or issue status are four separate facts on the Result. "Pass / Exception / Inconclusive / Failed-to-run" is the summary vocabulary over them.
- *Adjacent investigation during a scheduled run.* A signal found during a run (an unexpected account, a pattern) is recorded as a `signal` on the Result. It may start an investigative Agent Task **automatically only within an existing approved delegation and an explicit budget**; otherwise it creates a proposal or a decision request. Investigation never mutates the frozen definition or a sealed result — historical bytes are preserved — and it never suppresses what it learns: where it establishes that a result's basis was incomplete or wrong, it creates linked evidence, an impact record and a proposal for correction or rerun under 3b's reconsideration mechanisms.
- *Thin recurring proof (PRD §8.1) and the minimum recurring safety it must include.* The first scheduled proof includes: durable run identity and period ownership, duplicate-delivery suppression, interruption recovery, authority checks before each dispatch, verification that the pinned definition is the one executing, required input checks, and truthful result states — plus promotion of the leaver-access method, second-person approval, activation, one scheduled rerun under a delegation, and one rerun with a deliberately incomplete input reported Inconclusive with the exception still visible. Advanced succession and configuration-change workflows (missed starts, handover under succession, regression runs, drift detection, notification policies) are later epics (Proposal 5) **only if every unsupported transition is explicitly blocked**: a version whose configuration requires a regression gate cannot activate because regression execution is deferred; it stays `APPROVED` pending regression, as the lifecycle already says.
- *Ownership:* domain (compiler-2, step vocabulary, Gate parameterisation, outcome table), application (promotion command, scheduled execution, recovery requests), infrastructure (scheduler as a pg-boss schedule under the existing queue discipline), worker (execution).

**(3) Failure and verification**

- Selection, not transcript: promoting a task whose ledger holds a calendar invitation, two failed attempts and an exploratory branch yields a method artifact containing none of them and containing the period rule and acquisition rules; the compiled plan has no `send` step; a method artifact naming a historical acquisition id instead of an acquisition rule is refused; a differently named pack type that satisfies the `promotable-method` schema promotes.
- Compilation: an ambiguous criterion produces an unresolved issue that blocks submission; a model-named material discrepancy blocks activation until resolved; the mapping traces every criterion and validation to its source passage; one review satisfies both decisions where the pack allows and two are required where it does not.
- Bounded assistance: an approved `assist` step navigates and extracts a field, the value is corroborated deterministically and a semantic judgement lands `pending-review`; an `assist` step attempting a tool outside its contract is `denied`; an execution attempting to alter a criterion is refused; an incomplete required validation prevents a final pass.
- Lifecycle with compiler-2: the author cannot approve; frozen fields refuse updates; a changed acquisition rule requires regression and the version cannot activate while regression is deferred; succession and handover behave as the existing tests require with a `compiler = 2` version; duplicate schedule delivery produces one Run; a restart mid-run resumes the same Run; revocation between two steps stops the next dispatch with a reason.
- Determinism: compiling the same method artifact twice yields identical bytes; a model disagreeing with the compilation is recorded and the compiler's bytes are stored.
- Scheduled run: executes under the delegation; a revoked delegation stops it before acquisition with a reason; no model turn occurs outside a declared `assist` step; a quality failure established at `assess-quality` constrains the dependent evaluation immediately.
- FR-51 cases: new-period data runs normally; an expired connection yields an access failure, a recovery request and a constrained assessment, and re-connecting the same account runs the next period without re-approval; a folder renamed with its canonical id and containment preserved is a metadata change and the check runs; a move that changes the authorised boundary mints a platform-authored draft and the check does not run against it; reconnecting a different account with the same display name is refused as restoration; a new pack version changes nothing until re-approved.
- Coverage: the deliberately incomplete input yields `coverage: partial`, an Inconclusive assessment, a visible supported exception and `execution: completed`; the four statuses are asserted separately.
- Investigation: a signal during a run creates a separate task only under an existing delegation and budget, else a proposal; the Run's sealed result digest is unchanged by anything that task does; an investigation establishing that the result's basis was wrong produces linked evidence, an impact record and a rerun proposal, and the historical result stands with the flag.

**Changes to existing safeguards:** compiler-1 and its Runs are unchanged; the Gate's twenty rows become the example pack's check set and other packs declare their own under the same mechanism; `RUN_STOP_STATES`, outcome ordering and Result sealing are unchanged.

## How the pieces work together in one conversational task

The scenario is the approved first acceptance case (owner decision 2). It is acceptance data; every mechanism below is generic and none of it names the scenario.

1. **Context discovery (UJ-1; C9, C10, C11).** The auditor opens a draft engagement and writes: "Test leaver access for Q3 using the material in the shared folder." **Fixture setup, stated:** the acceptance environment has the synthetic client created, the engagement bound to it and the example pack selected before any client-scoped material is reached; personal ownership of the connected account does not erase the material's client restriction, and a missing client or pack would block the affected action rather than being silently resolved. The executor assembles context; the task's Mandate names the auditor's Drive connection and the client's folder as a source location (3a C3). Retrieval finds the pack's "control testing" and "population analysis" skills by phase and objective; both are loaded and recorded. The model proposes `drive.list` on the folder: schema-valid, `allowed`, dispatched; the result comes back as data with `coverage: complete, consistency: unknown`. It reads the control description and the period from two documents (each acquisition a `source_snapshot` with its extraction record) and answers with what it found, one assumption (the period end date is inferred from a file name), and what it still needs (which system exports are authoritative). The plan artifact it proposes is a `draft` version with claim classes labelled: the control wording is `factual` and cited; the period is `assumption`.
2. **Question and resumption (UJ-1, FR-57; C9).** "Which of the two directory extracts is authoritative?" opens a `clarify` wait with a deadline. The auditor is away for a day; the worker restarts twice. On the answer, the executor re-derives authority, re-reads the delegation, rebuilds context from the ledger and the encrypted conversation, and continues with the answer as a message. Nothing about the model's earlier reasoning granted anything.
3. **Analysis (UJ-2; C9, 3b C6, C8).** The leaver list, directory extract and application user list are acquired as snapshots with their quality assessments (the application list's export is `coverage: partial` because the provider truncated it, recorded from the extraction record, not guessed; and the fully downloaded, fully traversed directory extract turns out to hold only accounts created during the period, which the population-completeness validation the pack requires reports as a **business-population** limitation — technical acquisition completeness is not population completeness). Working copies are made by a recorded copy step. The model proposes `code.execute` with a script it wrote; the platform validates the call, reserves the sandbox budget, mounts the three snapshots read-only, runs it network-disabled, collects the output, and registers it as a `derived-output` with its derivation record and a `validation: none`. The pack requires a row-count reconciliation and a sample agreement to the directory for this method; the executor runs the reconciliation as a validation execution and asks the model to propose the sample check, which lands `pending-review`. The three field-level observations ("account X was active on date Y") are `factual`, cite the derived output at three locators and are `supported` by the deterministic checks; the finding "three leavers retained access after their exit date" depends on the sample agreement still `pending-review` and is presented as a candidate finding awaiting its required validation, not as supported; the population claim is constrained by both the `partial` coverage and the business-population limitation and says so.
4. **Signals and investigation within the Mandate (UJ-3; C9).** The output shows one login after an exit date. The model investigates: it proposes reading the application's audit-log export in the same folder (`allowed`, inside the source location) and finds the login. It records the steps on the ledger and labels the result a `signal` with an `inference` about cause, not a `factual` finding about the control. It also notices the partial population and proposes asking the client for the full export (UJ-5), which is a `draft` request-list update, not a send.
5. **Self-review and the working paper (C9, 3b C7).** The review turn checks every claim: the three retained-access items are `supported`; the population conclusion carries the coverage limitation; the login is a signal `pending-review`. The working paper version is written with these labels and cites the snapshots, the derived output and the extraction records.
6. **Correction and memory (UJ-4; C9, C10, 3b C7).** The auditor says: "The third leaver was a contractor whose access ended on contract end, not exit date; that one is not an exception." This is a **challenge**, not an overwrite: the original deterministic evaluation is preserved; the agent records the challenge, checks the applicable criteria and the contract evidence in the folder (a further acquisition), and resolves the affected classification through the approved correction path — a new working-paper version (the old one unchanged), an impact record on the finding version that depended on it, and the plan's dependent conclusion flagged `needs-reconsideration`; if no contract evidence is found, the classification stays `disputed` with the auditor's judgement recorded as a `decision`. The model proposes a `client-knowledge` memory item scoped to what was established — "this contractor's access ended at contract end, per the auditor, source: this message, verification: user-reported" — as `proposed`, and not the client-wide rule "contractors retain access until contract end"; the auditor confirms it and it becomes `active` for that client only, still `user-reported`. The auditor also says "always show me the exception list before the narrative"; that is an explicit `user-preference` instruction from its owner and is `active` at once.
7. **Correspondence and one external action (UJ-5; 3a C4, C9).** The Mandate names the auditor's Gmail connection and a designated label as a source. The model reads the evidence thread (`gmail.search` with the platform-fixed label scope; the result says which messages were searched), updates the request record as a `draft` artifact version, and proposes `calendar.create-event` for a walkthrough with the designated test recipient. The gate answers `needs-confirmation`; the material details (recipient, time, title) are shown; the auditor confirms; the receipt records `confirmed` with the provider's event id and read-back. The narrative says "an invitation was created", not "the walkthrough is scheduled with the client".
8. **Promotion (UJ-6; C12).** The auditor asks to run this monthly. The agent constructs the method artifact by selection: the acquisition rules (the folder, the three export names as location rules, the period rule), the script and its parameters, the required validations, the criteria, the outcome vocabulary. The calendar invitation, the audit-log investigation and the failed first script are not in it. The auditor edits and approves the artifact; compiler-2 compiles it; the Procedure Version is submitted; a second person approves it; it activates with a delegation for the auditor.
9. **Scheduled run and honest inconclusiveness (UJ-6; C12).** The first scheduled Run acquires the next period's exports under the acquisition rules, executes the retained script, runs every validation the approved method requires (the fixture supplies complete exports and the sample agreement is presented for the human review the pack requires before the final assessment), evaluates, assesses quality and seals a Pass or Exception. The second, with the application export deliberately truncated, records `coverage: partial`, an Inconclusive assessment, the supported exceptions still visible, `execution: completed`, and no change to the definition. A signal during the run starts nothing inside the Run; it is recorded and can be picked up as a new task.

At no point did the auditor fill a provenance field, approve an intermediate calculation or confirm a routine read; the reviews they gave were the ones the pack requires. The metadata was produced by the harness's operations; what the auditor saw were the assumption, the question, the coverage limitation, the confirmation for the one external action, the correction's consequences, the memory proposal and the approvals.
