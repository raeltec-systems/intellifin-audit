# Zobba: accepted brownfield course correction

## 0. Decision and scope

The owner stated: **“Revision 3 is the design I want us to build from”** and requested consolidation of active documents, dependency-led implementation planning/stories, updated Pair screens and a completed operating budget. This is a **major brownfield course correction**. The existing repository, completed work and lessons remain useful; the accepted Rust/fresh-schema architecture replaces incompatible implementation assumptions. Product discovery is not restarted.

That instruction authorizes the planning updates recorded here. It does not authorize production deployment, destructive data migration, supplier purchases or treating proposed commercial terms as agreed. New story descriptions are the implementation handoff, not claims of completed development.

## 1. Trigger and impact

The earlier active set mixes a procedure/compiler-based PoC with September's conversation-led direction and preservation of the TypeScript/Node backend, old schema and compiler paths. Revision 3 resolves those conflicts: engagement conversation coordinates continuing Tasks; Zobba owns a clean Rust engine and fresh schema; real managed computers, standing Permissions, methodology/skills/knowledge, audit evaluation and truthful review form the complete experience.

The trigger is the owner's accepted product/architecture direction, not a defect in one story. Historical Epic1–19 completion/status remains evidence for that implementation only. Unfinished legacy scope is superseded for the new build where incompatible; it is not relabelled complete or carried forward as a constraint.

## 3. Chosen path

Use **direct document adjustment and a replacement dependency-led backlog**, with targeted architectural rebuilding. Broad rollback would discard useful evidence/review/recovery work without providing the new engine. Keeping all old stories and wrapping a second engine around them would preserve constraints the owner explicitly removed. Reducing the first-complete milestone to file-only chat would contradict the accepted product.

This is substantial implementation work; the plan sequences independently reviewable stories and names qualification risks without inventing a delivery date. Early computer/access qualification and durable-operation proofs run as soon as their dependencies exist. The first batch is a foundation, not a claim of product completion. Component reuse, test adaptation and old-runtime retirement are explicit work items.

## 4. Handoff and verification

- Product/architecture/UX owners reconcile active contracts and preserve prior versions and identifiers.
- `bmad-spec` re-derives the canonical capability contract and records coherence/preservation checks through the append-only memlog tool.
- `bmad-create-epics-and-stories` derives the backlog; `bmad-sprint-planning` checks implementability and generates/validates the standard tracking file.
- `bmad-build` later executes explicit new story IDs using the active companions. Commercial gates qualify launch commitments; they do not reopen the accepted architecture.
- The handoff includes the build sequence, bounded first batch, story dependencies/coverage, reference-screen evidence and reproducible budget. No second broad design report is required.
