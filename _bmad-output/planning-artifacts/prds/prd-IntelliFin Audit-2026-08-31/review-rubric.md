# PRD Quality Review — IntelliFin Audit (revision 2)

Reviewed: `prd.md` (revision 2, updated 2026-09-01) and `addendum.md` (revision 2) against `.claude/skills/bmad-prd/assets/prd-validation-checklist.md`. Stakes: exploratory PoC, chain-top (feeds UX → architecture → epics), multi-role B2B with meaningful UX.

## Overall verdict

This is a strong, thesis-driven PRD: the Vision (§1) is specific enough that it could not be swapped into another product, the object chain Control → Procedure → Run → Agent Workspace → Evidence → Review carries through every FR, and the counter-metrics (SM-C1–C4) show the authors know how the thesis could be faked. What is at risk is downstream precision rather than direction: two scope gaps (no notification path for Escalations during unattended Runs; an unstated second execution mode for API/file Sources and API-form Target Systems inherited from revision 1) will force architecture and UX to invent product decisions, and a cluster of glossary drift (`Audit Trail`, `Source`, `Pending Confirmation` vs the `System Outcome` definition, Step/Work Item relation, `Solari`) will leak into the domain model if not fixed before the architecture spine is revised. No finding is critical; the PRD is usable for downstream work once the two high findings are resolved.

## Decision-readiness — adequate

Decisions are stated as decisions, not considerations: the Auditor names Target Systems (FR-7, §6 "the agent does not choose scope"), one Agent executes sequentially (FR-20, §6), no human override of Rule-Classified results (FR-41, §7), and the Audit Manager cannot approve their own Procedure Version (FR-2, FR-13). The maturity table (§8.2) makes the given-up territory explicit rather than hiding it. Open Questions (§11) are genuinely open — OQ-1 (model/provider and confidence threshold) and OQ-3 (which desktop application and platform) have no answer smuggled into the next sentence, and each has an owner and a revisit trigger.

Two things hold this back from strong. First, the PRD contains zero `[NOTE FOR PM]` callouts, yet it has real tensions that a decision-maker should see flagged: the §4.5 description names **Solari** as the workspace/sandbox provider while NFR-15, FR-26, FR-27 and the "Workspace provider dependency" risk (§10) all insist on provider neutrality — the cost of that neutrality (copying session recordings into IntelliFin storage, FR-27 second consequence) is a real trade-off that is currently stated only as a risk mitigation. Second, §0 states that "The architecture spine dated 2026-09-01 and the UX handoff dated 2026-09-01 … must be revised against this document before build" — a significant re-work decision presented as a footnote rather than a decision with a cost.

### Findings
- **medium** No `[NOTE FOR PM]` at real tensions (§4.5 description, §10 "Workspace provider dependency", §0 revision note, FR-4 assumption) — The rubric expects tensions to be visible to the reader who will decide them. Solari-vs-neutrality and the rev-1 artifact re-work are the two that most need one. *Fix:* add `[NOTE FOR PM]` at §4.5 (Solari as a named dependency vs NFR-15 neutrality and the recording-copy cost of FR-27), at §0 (re-derivation cost of architecture/UX), and at FR-4 (see Strategic coherence finding on SM-8).
- **low** OQ-1 bundles two decisions with different owners and timing — "Which model and provider should power plan derivation (FR-12) and Agent-Judged classification (FR-35), and what confidence threshold applies?" The threshold is a product decision (`[ASSUMPTION]` FR-35) that gates SM-4; the provider choice is engineering. *Fix:* split into OQ-1a (provider/model) and OQ-1b (Agent-Judged confidence threshold and who sets it per Procedure Version).

## Substance over theater — strong

The Vision (§1) is earned: "Missing, stale, incomplete, contradictory, or inaccessible evidence must never yield a Pass" and the Control-vs-Procedure distinction drive FR-9, FR-30, FR-31 and SM-5 directly. Three roles, two named protagonists (Daniel, Maya) — each role changes a rule somewhere (FR-2, FR-13, FR-40). No differentiation section exists, and none is missed; §8.2 does that work honestly. NFRs mostly carry product-specific bounds (NFR-6 30 min / 50 records / two Target Systems; NFR-8 three retries; NFR-9 five minutes). §2.1 naming the non-users is a good, cheap honesty move.

Residual furniture is minor: NFR-10 (daily backup, RPO 24h / RTO 8h) and NFR-11 (WCAG 2.1 AA) read like boilerplate for an exploratory PoC, though both at least carry numbers. The second clause of NFR-6 ("for file and API Sources with up to 10,000 records, 95% of Runs complete within five minutes") is revision-1 residue that now describes an execution path the PRD no longer defines — see Strategic coherence.

### Findings
- **low** NFR-10 and NFR-11 are borderline furniture for an exploratory PoC (§5) — Neither is tied to a Success Metric, a risk, or a journey. *Fix:* either drop NFR-10 into §8.3 Deferred, or state why a PoC needs backup/recovery targets; keep NFR-11 only if the SM-1 authoring subject or PoC acceptance depends on it.

## Strategic coherence — strong

There is a thesis and the PRD bets on it: "an Auditor can create an executable Procedure without a developer coding it for them" (§4.2) plus trustworthy-in-both-directions execution (§1). Prioritization follows: one fully configurable hero Procedure, three Templates, the hero journey walked end-to-end in UJ-1–UJ-6. Success Metrics validate the thesis rather than activity — SM-1 (zero procedure-specific code), SM-5 (100% seeded bad Evidence → non-Pass), SM-7 (independent reproduction) — and each lists the FRs it validates. Counter-metrics are unusually good: SM-C3 "a demo that needs a developer per Procedure does not prove the thesis" and SM-C4 "No silent judgment" name the exact ways this PoC could cheat. Scope kind is a problem-solving/capability proof and the scope logic (§8.1) matches.

One coherence crack: the execution model. §4.5 and FR-19 define a single execution path — the Audit Agent "opens the Population Source … signs in to each Target System" inside an Agent Workspace — and the Glossary defines Target System as "an approved application, web surface, or desktop application". But addendum §A.1 lists Population Sources acquired via "Read-only API" (PeopleHub, AccessGate, LedgerFlow), §A.2 lists nothing for AccessGate/RoleMatrix yet §C P-2 names "AccessGate role detail; RoleMatrix as reference file" as Target Systems, and NFR-6 sets a separate performance bound for "file and API Sources". The PRD never says whether the Agent calls APIs from the workspace, whether a non-workspace pipeline path exists, or how a versioned reference file is a "Target System" the Agent "signs in to". SM-8 (generalization through "the same Builder, Runner, Workspace, Timeline …") depends on the answer.

### Findings
- **high** Second execution mode implied but undefined (NFR-6 second clause; addendum §A.1 "Read-only API" rows; §C P-2 "AccessGate role detail; RoleMatrix as reference file" as Target Systems; Glossary *Target System*) — Architecture cannot tell whether API/file acquisition runs inside the Agent Workspace via the same Step/Work Item/Observation model (FR-19, FR-20) or through a distinct connector path carried over from revision 1. This decides whether SM-8 is measuring one execution engine or two. *Fix:* state in §4.5 (or a new FR) that in the PoC every Population Source and Target System — including API and versioned-file forms — is accessed by the Audit Agent from within the Agent Workspace as Steps, and widen the *Target System* glossary entry accordingly; or, if a non-workspace path is intended, define it as its own FR and make NFR-6's second clause reference it. Either way, reconcile §A.2 so every Target System named in §C appears in the table.
- **medium** FR-4 `[ASSUMPTION]` weakens SM-8 — FR-4 says the three non-hero Templates' "Audit Instructions and Compliance Rule [are] editable but not required to be re-authored for PoC acceptance", so their instructions are effectively pre-authored by the build team. SM-8 then proves the engine generalizes, but not that *an Auditor* can author a second Procedure without a developer — which is the thesis (SM-C3). *Fix:* either add a `[NOTE FOR PM]` stating that generalization of the *engine* is what SM-8 proves and Auditor authoring is proven only for the hero, or require at least one non-hero Template to be re-authored by the SM-1 Auditor.

## Done-ness clarity — adequate

Every FR carries a "Consequences (testable)" block and most consequences are genuinely verifiable: FR-3 (denied and logged), FR-13 (freezes named artefacts, records diff), FR-18 ("No file, session, cookie, or credential persists"), FR-30 with addendum §H as a normative table, FR-35 (Pending Confirmation until confirmed), FR-40 (blocked states enumerated). Addendum §E state models give engineers the enumerations they will need. This is above the usual bar.

Where it thins: the builder's derived plan (FR-12) has no correctness loop — the Auditor "can read" it and it is "readable … without inspecting code", but nothing says what happens when the plan is wrong. Is the plan editable, re-derived from edited instructions, or rejected at approval? UJ-1 says "in language he can check", which implies a check-and-fix cycle the FRs don't provide. FR-8's second consequence ("an instruction referencing an unregistered system, a write action, or an out-of-scope origin is flagged at authoring") requires natural-language analysis but names no detection test or seeded case. Several bounds are adjectives or missing: FR-38 "stable fingerprint across Runs of compatible Procedure Versions" ("compatible" undefined); FR-45 "reflects the latest state without a page reload" (no latency bound — NFR-7 covers Live View only); FR-35 "a confidence signal" (no scale; OQ-1 defers the threshold but not the signal's form); FR-25 Escalation timeout "four hours for scheduled Runs" (manual Runs unspecified).

### Findings
- **medium** FR-12 has no plan-correction path (FR-12, UJ-1) — Downstream UX needs to know whether the Auditor edits the plan, edits inputs and re-derives, or only approves/rejects. Without it, story creation will invent one. *Fix:* add a consequence: "The Auditor cannot edit the plan directly; changing any structured field or Audit Instruction re-derives the plan, and the re-derivation is recorded. A plan that cannot be derived blocks submission with the reason shown."
- **medium** FR-8 scope-widening detection is untestable as written (FR-8 second consequence) — "flagged at authoring" for natural-language instructions has no acceptance mechanism. *Fix:* add a golden set of instructions to addendum §D (one unregistered system, one write verb, one out-of-scope origin) and a consequence "100% of seeded scope-widening instructions are flagged before submission; any that escape are denied at execution (FR-3) and recorded as a security event."
- **low** "compatible Procedure Versions" undefined (FR-38) — Cross-Run fingerprints are the one cross-Run feature kept in scope (§8.3), so the compatibility rule matters. *Fix:* define compatibility (e.g. same Procedure, same matching key, same Compliance Rule digest) in addendum §B.
- **low** FR-45 dashboard freshness has no bound — *Fix:* extend NFR-7 to the Runs dashboard, or state a bound in FR-45.
- **low** FR-25 Escalation timeout only bounded for scheduled Runs — *Fix:* state the manual-Run behaviour (same four hours, or waits while any Auditor session is open).
- **low** FR-35 "confidence signal" has no form (FR-35) — *Fix:* name the representation (e.g. a value in [0,1] plus the rationale) so the FR-35 `[ASSUMPTION]` threshold has something to compare against.

## Scope honesty — adequate

The Non-Goals section (§7) does real work — "free-form conversational procedure authoring", "Parallel Work Item execution", "Human override of Rule-Classified results" each pre-empts an inference a reader would otherwise make — and `[NON-GOAL for PoC]` callouts sit where the omission would be silently assumed (FR-7 agent-discovered scope; FR-20 parallel execution). Thirteen inline `[ASSUMPTION]` tags are indexed in §12 and roundtrip cleanly. The revision note in §0 is honest about superseding rev-1 downstream artefacts. Open-items density (13 assumptions + 6 Open Questions, 0 `[NOTE FOR PM]`) is reasonable for an exploratory PoC.

The gap is one silent omission at the heart of the delegation thesis. §2.2 lists the job "step in when it needs me, and otherwise leave it to finish", and UJ-4 shows a scheduled Run at 06:00 with "No one is signed in". FR-25 says an unanswered Escalation "times out to Inconclusive" after four hours, and FR-45 shows Awaiting Auditor on a dashboard — but no FR notifies anyone. As written, any Escalation raised during an unattended Run becomes Inconclusive unless an Auditor happens to open the dashboard. That may be an acceptable PoC scope choice, but it is neither an FR nor a Non-Goal, and UX will have to decide it.

### Findings
- **high** Escalation notification for unattended Runs is neither specified nor declared a Non-Goal (FR-25, FR-16, FR-45, UJ-4, §2.2 "step in when it needs me") — UX and architecture both need to know whether a notification channel (email, in-app, other) is in PoC scope; the Escalation timeout `[ASSUMPTION]` (four hours) only makes sense if someone can learn about the Escalation within it. *Fix:* either add an FR ("The system notifies the initiating Auditor and every Audit Manager when a Run enters Awaiting Auditor, via at least one configurable channel; the notification records delivery on the Audit Trail") or add `[NON-GOAL for PoC]` notification under FR-25 with a `[NOTE FOR PM]` acknowledging that unattended Escalations will usually time out to Inconclusive in the PoC.
- **low** Pause timeout vs Escalation timeout are unreconciled (FR-23 30 min; FR-25 four hours) — Both hold a workspace open; the 30-minute pause limit is presumably about workspace cost, which the four-hour Awaiting Auditor state ignores. *Fix:* state whether the workspace is preserved for the full Escalation timeout and why the two limits differ.

## Downstream usability — adequate

Glossary is present and most of the revision-2 nouns (Audit Agent, Agent Workspace, Work Item, Observation, Agent-Judged classification, Escalation, Execution Timeline, Replay, Schedule, Target System, Population Source, Compliance Rule, Procedure Version, Step) are defined once and used consistently across UJs, FRs and SMs. IDs are contiguous and unique (FR-1–47, NFR-1–15, SM-1–11, SM-C1–4, UJ-1–6); cross-references resolve (FR-34→FR-41; SM "Validates" lists; addendum §A/§C/§E/§F/§H/§I). Every UJ has a named protagonist. Addendum §I maps rev-1 IDs, which downstream artefacts derived from rev-1 will need.

The drift that matters is the set of nouns the architecture spine must model but the Glossary does not define, plus one internal contradiction: the *System Outcome* glossary entry says "Pass or Control Failure", but FR-35 says "the Result's outcome is Pending Confirmation" and addendum §E's Normative Outcome Rules list Pending Confirmation as a System Outcome. The Step/Work Item relation is also not stated: Step's examples ("open file, sign in") are Run-level, while Work Item is per-record-per-Target System with "its own … Timeline segment" (FR-20) — so some Steps belong to no Work Item, which FR-26's "Steps, Work Items" listing leaves implicit.

### Findings
- **medium** *System Outcome* definition contradicts FR-35/FR-37/addendum §E (Glossary; FR-35; FR-37; §E table) — Glossary: "Deterministic control conclusion of Pass or Control Failure"; FR-35/§E add Pending Confirmation. Architecture will model one enumeration; the PRD gives two. *Fix:* revise the glossary entry to "Pass, Control Failure, or Pending Confirmation (while any Agent-Judged classification is unconfirmed)" and add Inconclusive/Run Failed/Canceled explicitly as Run states that are *not* System Outcomes.
- **medium** *Audit Trail* is used as a defined noun but is not in the Glossary (FR-41, FR-42, NFR-3, NFR-14, SM-9, addendum §F) — It is distinct from the Execution Timeline (FR-26 is per-Run execution; FR-42 is system-wide events) and architecture must know they are separate stores. *Fix:* add a Glossary entry and state its relation to the Execution Timeline (Timeline events are also Audit Trail events, or not).
- **medium** Step ↔ Work Item relation undefined (Glossary *Step*, *Work Item*; FR-19; FR-20; FR-26) — Population acquisition and sign-in Steps precede any Work Item. *Fix:* in the *Work Item* or *Step* entry, state "Steps that acquire the population or sign in to a Target System belong to the Run; Steps that locate, inspect, and capture belong to exactly one Work Item."
- **medium** `Solari` named without definition and against the neutrality rule (§4.5 description; addendum §J; NFR-15) — A vendor appears once in the FR body and once in the addendum; everywhere else the PRD says "workspace provider". *Fix:* add a Glossary entry *Workspace Provider* ("the service supplying the Agent Workspace's browser/desktop sandbox and session recording; Solari in the PoC") and use the generic term in §4.5.
- **low** `Source` (bare) leaks from revision 1 (§2.1 "synthetic Sources"; FR-2 "Source configuration"; FR-29 "Later Source or Target System changes"; FR-38 "Source contract"; NFR-6 "file and API Sources"; §8.3 "Design-partner Sources") — The Glossary defines only *Population Source*. *Fix:* replace with *Population Source* where that is meant, or add *Source* as an explicit alias.
- **low** `Timeline` short form (FR-20, FR-26, FR-27, NFR-1, NFR-3, NFR-14, SM-2, SM-6) — *Fix:* add "(Timeline)" to the *Execution Timeline* glossary entry as a declared short form, as *Audit Procedure (Procedure)* already does.
- **low** `Unevaluated`, `human-classified`, `Inconclusive`, `Pending Confirmation`, `executable plan` have no Glossary entries — All are used across multiple FRs (FR-9, FR-35, FR-36, FR-37, SM-4) and are enumerated only in addendum §E or nowhere. `Run Failed` gets an entry; `Inconclusive` does not. *Fix:* add entries, or add a Glossary line "Classification origins and Run/outcome states are enumerated in addendum §E."
- **low** `Auditor Review` is performed by the Audit Manager (Glossary; §2.1; FR-40) — Defined, but the name invites misreading. *Fix:* consider *Manager Review* or add "(performed by the Audit Manager)" to the entry.

## Shape fit — strong

Chain-top, multi-stakeholder B2B with a genuinely UX-heavy core (Procedure Builder, Live View, Replay), so UJs with named protagonists are load-bearing and the PRD provides them; six journeys for three roles is proportionate, not theatre. The compliance flavour is handled by addendum §G (standards basis) without pretending certification. Revision 2 is effectively brownfield relative to its own rev-1 downstream artefacts, and §0 plus addendum §I handle that honestly. The only shape residue is the rev-1 data-pipeline model surfacing in NFR-6's second clause and addendum §A/§C (see Strategic coherence); resolving that finding removes it.
