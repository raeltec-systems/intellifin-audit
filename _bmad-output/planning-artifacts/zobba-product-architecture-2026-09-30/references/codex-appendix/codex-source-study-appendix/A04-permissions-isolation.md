# 04 — Permissions and isolation (Codex @ 8ffd91e42aa001b7e897bea812b02f89264f9fa0)

## Summary (10 lines)
1. Codex enforces restrictions in three distinct layers: Rust types only structure policy data; the OS (bubblewrap+seccomp, Seatbelt, Windows restricted tokens/WFP/MXC) is the only thing that actually confines a child process; application policy (approval policy, execpolicy rules, patch safety, requirements) decides *whether* and *how* a child is sandboxed.
2. `execpolicy` is a Starlark-dialect prefix-rule language (`prefix_rule`, `network_rule`, `host_executable`); decisions are literal-token prefix matches, strictest-of-matches wins (`forbidden > prompt > allow`), with an exact-first-token tier that pre-empts basename fallback and heuristics.
3. An execpolicy `allow` is not "skip the prompt": when every parsed segment matches an explicit allow rule the command runs **unsandboxed** (`bypass_sandbox: true`); only denied-read policies stop that.
4. Escalation is a two-attempt loop (sandboxed → retry unsandboxed) driven by a *heuristic* denial classifier over the child's own output; under `untrusted`/granular modes a prior approval is reused for the unsandboxed retry without a second prompt [INFERENCE].
5. Linux: default-allow seccomp *denylist* for network/ptrace/io_uring, `--ro-bind / /` plus writable binds, fresh user/pid/ipc/(net) namespaces, `--cap-drop ALL`, and a runtime check that no capabilities survived.
6. Managed egress is a real OS-forced proxy (Linux netns + TCP→UDS bridge; macOS Seatbelt loopback-port allow; Windows elevated WFP/MXC), but explicitly escalated commands bypass it.
7. Config layers override by precedence; admin constraints live separately in `requirements.toml`/MDM/cloud and are enforced by a `Constrained<T>` validator with fall-back-to-allowed values; requirements rules may only `prompt`/`forbid`.
8. Approvals persist three ways: in-memory session cache (never revoked), `$CODEX_HOME/rules/default.rules` appends (persisted, hot-added, not reloaded on edit), and per-turn/session permission grants (merge-only).
9. MCP servers and hooks are spawned with no OS sandbox; sub-agents inherit the parent turn's approval policy and permission profile.
10. For an audit harness: adopt the layering, fail-closed path resolution and `Constrained<T>` pattern; do not adopt "allow ⇒ unsandboxed", output-keyword escalation, client-supplied persisted amendments, or non-revocable grants.

## F1. execpolicy: the rule language and its evaluation
- **Problem.** Let users/admins pre-decide command classes (allow/prompt/forbid) independently of the model.
- **Code.** Starlark, `Dialect::Extended` with f-strings, standard globals plus three builtins [OBSERVED `execpolicy/src/parser.rs:L57-L79`, `L347-L472`]. `prefix_rule(pattern, decision?, match?, not_match?, justification?)`: decision defaults to `allow`; a first-token alternative list expands into one rule per head, keyed by that literal string in a `MultiMap` [OBSERVED `parser.rs:L357-L406`]. Matching is exact string equality per token, no globs/regex [OBSERVED `execpolicy/src/rule.rs:L22-L60`]. Evaluation tiers: (1) rules keyed by the literal `argv[0]`; (2) only if none matched and `resolve_host_executables`, basename fallback for an absolute path, restricted to `host_executable` paths when declared; (3) only if still nothing, a heuristics callback [OBSERVED `execpolicy/src/policy.rs:L305-L371`]. The result is `max` of matched decisions; empty matches panic by invariant [OBSERVED `policy.rs:L394-L411`]. `match`/`not_match` examples are validated at load against a policy holding only that rule [OBSERVED `parser.rs:L133-L152`]. `network_rule` compiles to allow/deny host lists, last rule wins per host, wildcards rejected [OBSERVED `policy.rs:L204-L223`, `rule.rs:L156-L212`]. Later `host_executable` for a name overwrites earlier [OBSERVED `parser.rs:L113-L115`]. No `load()` loader is installed [INFERENCE: `Evaluator::new` without a loader, `parser.rs:L68-L74`] and no evaluation step/memory limit is configured [OBSERVED absence, same lines].
- **Tests.** [TEST] `strictest_decision_wins_across_matches` `execpolicy/tests/basic.rs:L556-L593` — fails if max-severity aggregation or enum order changes; `host_executable_resolution_does_not_override_exact_match` `basic.rs:L928-L963` — fails if basename rules are consulted when an exact rule matched; `match_and_not_match_examples_are_enforced` `basic.rs:L511`; `host_executable_resolution_ignores_path_not_in_allowlist` `basic.rs:L862`.
- **Defaults/limits.** Core always enables host-executable resolution [OBSERVED `core/src/exec_policy.rs:L372-L374`]; README calls the language "preview" [DOC `execpolicy/README.md:L97`].
- **General vs local.** Prefix rules over argv are general; the heuristics fallback is tuned for developer shells.
- **Audit harness.** Would key rules on an allowlisted action vocabulary (typed tool actions), not free argv, and version/sign policy per tenant.
- **Recommendation: ADAPT IDENTIFIED CODE** — the crate is small (≈2.9k lines incl. tests, deps: starlark, multimap, shlex, serde) and self-contained, but the tier semantics must be changed (see F2).

## F2. How execpolicy composes with config layers, requirements and the sandbox
- **Problem.** Merge user, project, system and admin rules and turn the verdict into an approval requirement.
- **Code/state.** `ExecPolicyManager { policy: ArcSwap<Policy>, update_lock: Semaphore(1) }` owned by `SessionServices.exec_policy` [OBSERVED `core/src/exec_policy.rs:L276-L279`; `core/src/state/service.rs:L64`]. Loading walks layers low→high, reads `<layer>/rules/*.rules` (sorted, regular files only), skipping user/project when `--ignore-rules` [OBSERVED `exec_policy.rs:L662-L716`, `L1121-L1170`; `exec/src/cli.rs:L42-L44`], then overlays `requirements.exec_policy` [OBSERVED `L711-L715`]. A parse error in **any** rules file drops all non-requirements rules and continues with a warning [OBSERVED `L645-L660`]. Verdict mapping: `Forbidden`→reject; `Prompt`→ask unless approval policy forbids prompts; `Allow`→`Skip{bypass_sandbox}` where bypass is true iff every parsed segment matched an explicit allow rule [OBSERVED `L395-L462`]. Shell wrappers are decomposed only for plain word sequences (tree-sitter; no redirects/substitutions) [OBSERVED `shell-command/src/bash.rs:L29-L127`], and the wrapper is trusted only when the executable is the configured shell or lives in `/bin`/`/usr/bin`; for any other executable, the bare executable is evaluated as an extra command beside the parsed inner commands, so inner commands can only add restrictions ("inner commands can add restrictions, but cannot grant the executable trust") [OBSERVED `core/src/exec_policy/executable_identity.rs:L43-L46`, `L93-L102`].
- **Key semantics.**
  - An allow rule means unsandboxed execution [TEST `git_status_obeys_approval_policy_and_explicit_rules` `core/src/exec_policy_tests.rs:L1010-L1053` asserts `Skip{bypass_sandbox:true}` under a workspace-write profile; `absolute_path_exec_approval_requirement_matches_host_executable_rules` `L1056-L1080` asserts it under read-only]. Denied-read policies veto the bypass [OBSERVED `core/src/tools/sandboxing.rs:L239-L279`].
  - Requirements rules cannot be `allow` [OBSERVED `config/src/requirements_exec_policy.rs:L115-L124`; TEST `allow_decision_is_rejected` `core/src/config/config_loader_tests.rs:L4575`].
  - Because tier (1) pre-empts tier (2) for all layers alike, a user rule keyed on `/usr/bin/git` makes `/usr/bin/git push` `Allow` (and unsandboxed) even if requirements forbid `["git","push"]` [INFERENCE from `policy.rs:L311-L320` + `load_exec_policy` merge; mechanism pinned by the TEST above]. Admins can mitigate only by enumerating absolute paths as `any_of` first tokens; no requirements key disables user rules (not found: grep `ignore_user_and_project_exec_policy_rules` shows only the CLI flag and loader plumbing).
- **Tests.** [TEST] `malformed_custom_rules_preserve_requirements_exec_policy` `exec_policy_tests.rs:L369-L402` — fails if a broken user file also drops admin forbids; `ignores_rules_from_untrusted_project_layers` `L550`.
- **Defaults/limits.** 88 model-proposable prefixes are banned (`bash -lc`, `python`, `git`, `rm`, `sudo`, `env`…) [OBSERVED `exec_policy.rs:L57-L146`, `L958-L997`]; a one-shot migration strips such legacy allow lines guarded by `$CODEX_HOME/.sandbox_migration` [OBSERVED `execpolicy/src/sandbox_migration.rs:L16-L29`].
- **Audit harness.** Allow must never imply leaving the containment boundary; admin denies must be evaluated in a separate, non-overridable tier; parse failure should fail closed.
- **Recommendation: IMPLEMENT INDEPENDENTLY** — reuse the idea of tiered prefix rules, but make "admin deny" a first-class tier and decouple "no prompt" from "no sandbox".

## F3. Approval → sandbox → escalation loop (policy semantics)
- **Problem.** Run most commands without prompts inside a sandbox, escalating only when needed.
- **Code/state.** `ToolOrchestrator::run`: compute `ExecApprovalRequirement` (runtime-specific or default) → optionally prompt (`already_approved = true`) → first attempt with `SandboxType` from `SandboxManager::select_initial` → on `SandboxErr::Denied`, maybe prompt and retry [OBSERVED `core/src/tools/orchestrator.rs:L122-L233`, `L278-L317`, `L328-L500`]. `SandboxErr::Denied` is produced when a sandboxed command exits non-zero (not 2/126/127) and its stdout/stderr contains any of seven keywords ("permission denied", "sandbox", "operation not permitted"…) or exits 128+SIGSYS [OBSERVED `sandboxing/src/denial.rs:L13-L71`; `core/src/exec.rs:L827-L835`]. Retry without sandbox requires `wants_no_sandbox_approval` (true only for `untrusted` and `granular.sandbox_approval`), no denied reads, and either a new prompt or `should_bypass_approval(already_approved)` [OBSERVED `orchestrator.rs:L375-L448`; `tools/sandboxing.rs:L316-L338`].
- **Consequence.** Under `untrusted`, once a user approves a command for (sandboxed) execution, the command can print "permission denied" and exit 1 to obtain an unsandboxed rerun with no second prompt [INFERENCE from the lines above]. Under the default `on-request`, the shell retry is refused except for network approvals [OBSERVED `L375-L396`]; `apply_patch` overrides this and also offers the unsandboxed retry under `on-request` [OBSERVED `core/src/tools/runtimes/apply_patch.rs:L134-L141`]. Model requests for `require_escalated`/`with_additional_permissions` are rejected outright when prompts are disallowed (`never`, granular false) [OBSERVED `core/src/tools/handlers/unified_exec/exec_command.rs:L342-L352`].
- **Tests.** [TEST] `sandbox_denied_retry_uses_the_action_policy_and_reviewer` `core/src/session/tests/guardian_tests.rs:L921-L1034` — fails if a Skip-requirement denial retries without the "command failed; retry without sandbox?" prompt; it does **not** cover the already-approved branch (not found in `core/tests/suite/approvals.rs`; searched retry/escalat/untrusted names). Scenario table in `core/tests/suite/approvals.rs:L1031-L1111` pins `require_escalated` prompting/rejection.
- **Defaults.** Approval default `on-request` for trusted/unknown dirs, `untrusted` for explicitly untrusted; `untrusted` cannot be configured in config.toml [OBSERVED `core/src/config/mod.rs:L3731-L3758`]. Approvals may be routed to a model "auto_review" reviewer instead of the user [DOC `protocol/src/config_types.rs:L183-L202`].
- **Audit harness.** Escalation must be a separate, explicitly attributable decision with its own scope; never inferred from untrusted output; never reuse a sandboxed-run approval.
- **Recommendation: DO NOT ADOPT** — output-keyword-triggered escalation and approval reuse are unsafe for protected evidence.

## F4. Linux OS enforcement (codex-linux-sandbox + bubblewrap + seccomp)
- **Problem.** Confine filesystem, network and process reach of model commands.
- **Code/state.** The Codex binary re-execs itself as `codex-linux-sandbox` via an arg0 symlink placed in a per-process dir under `$CODEX_HOME/tmp/arg0` prepended to `PATH` [OBSERVED `arg0/src/lib.rs:L60-L101`, `L343-L440`; `sandboxing/src/manager.rs:L806-L812`]. Outer stage builds bwrap argv; inner stage (`--apply-seccomp-then-exec`) verifies descriptor mounts, **panics if any effective/permitted capability remains**, activates proxy routes, applies `no_new_privs`+seccomp, forks and reaps the command [OBSERVED `linux-sandbox/src/linux_run_main.rs:L160-L280`]. Full-disk-write profiles without managed proxy skip bwrap and get only seccomp [OBSERVED `L282-L293`]. Legacy Landlock is refused for filesystem-restricted policies because it "cannot isolate app-server sockets" [OBSERVED `L412-L419`].
- **Seccomp.** Default action `Allow`, matched rules `EPERM` — a denylist, x86_64/aarch64 only (`unimplemented!` otherwise) [OBSERVED `linux-sandbox/src/landlock.rs:L282-L293`]. - **Mounts.** `--ro-bind / /` (or tmpfs root for restricted reads), `--dev /dev`, writable `--bind`, protected subpaths re-applied `--ro-bind`, missing protected paths masked by binding `/dev/null` on the first missing component, writable-root symlinks rejected, app-server daemon socket dirs masked with `--perms 000 --tmpfs` [OBSERVED `linux-sandbox/src/bwrap.rs:L248-L415`, `L855-L887`, `L1434-L1500`]; `--unshare-user/-pid/-ipc`, `--unshare-net` unless full network, `--cap-drop ALL`, `--new-session`, `--die-with-parent` [OBSERVED `bwrap.rs:L355-L398`].

- **Recommendation: ADAPT IDENTIFIED CODE** — the bwrap argv builder and capability self-check are solid references; replace the seccomp denylist with an allowlist.
