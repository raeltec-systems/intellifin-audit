# Zobba product experience recommendation

Prepared for the product-and-architecture synthesis, 30 September 2026. This is design evidence and a recommended product contract; it is not an implementation plan.

## Recommended product

Zobba is the auditor's continuing working relationship with an audit agent: one conversation directs a real computer, analytical work and reviewable work products inside one engagement. The auditor supplies an objective, available material and judgement. Zobba owns the useful next action, investigates relevant leads within Permissions, produces supported work, and remains available for questions and redirection while it works. Work can continue after the tab closes and return when evidence, a schedule or a human decision makes further progress possible.

The product object is an **engagement task with an objective**, its conversation, work, decisions and results. It is not a compiled procedure, a chat answer or a virtual desktop session. The computer is an inspectable, controllable working resource belonging to that task; losing it does not lose the task. A task has one responsible auditor. Helpers contribute to the task rather than becoming a visible team the auditor must manage.

The complete experience spans engagement understanding, planning, evidence requests, walkthroughs, control design and operating effectiveness, population analysis, investigation, working papers, findings, reporting and follow-up. Methodology supplies the relevant distinctions; the product does not hard-code leaver access, one financial industry or one employer into its behaviour.

## Experience composition and information architecture

Retain the Pair identity and conversation/work relationship demonstrated by the design pack. Keep Graphite/Linen chrome, restrained Iris for Zobba presence and actionable references, semantic words for audit outcomes, supplied outlined marks, and the firm's own document typography. Do not put Zobba colours, interface diff marks or selection overlays into working-paper bodies or exports. The pack's existing artwork is useful design material, not evidence that any control currently works.

Use the pack's main navigation: **New task**, **Search**, **Scheduled checks**, **Engagements**, **Recent tasks**, **Connections**, **Settings**. Add **Reviews** for Audit managers. The Home/Continue surface includes an attention filter for all decisions, blockers and due work, with client, engagement, owner and next action. This gives all three roles one working environment without making every completed activity a notification. Engagements expose overview, active tasks, work products, evidence and continuing work; these are views within the engagement, not separate applications.

The task header always names the client, engagement, objective and responsible auditor. The default desktop layout is conversation beside the work, with one optional focused inspection surface rather than many permanent columns. The work surface can display the real computer, working data, a document, evidence, a change comparison or a result. “Computer” remains available while a machine is active even when a document is in front. “Working files” is the accessible file view of the same task; evidence originals remain distinct from editable copies.

A stable control strip shows current activity, open decisions, **Pause**, **Stop**, and, when relevant, **Take over**. The composer remains usable during execution. A short activity line explains the meaningful action and its subject; details expand into operations, sources and results. Progress counts appear only when measured. Long tool logs and provider internals are under **How it ran**.

Use explicit **Follow Zobba** for panel following. Automatic following begins when a user opens an active computer view. Selecting, pinning or editing another object suspends following until the auditor chooses it again. New outputs then appear as conversation links and a small new-work indicator. Replace the pack's implicit 30-second replacement rule: time elapsed is a poor proxy for whether someone has finished inspecting evidence. Preserve scroll, selection and return location across panels and reconnects.

Starting work requires no setup wizard. Inside an engagement, the scope is inherited. Outside one, Zobba can discuss a general question immediately, but before retrieving client sources it must resolve the client/engagement from the selected context or a contextual question. It must not silently combine clients or guess a client from similar filenames. Engagement creation can happen conversationally from a name and basic scope; the user does not fill execution/provenance fields.

## Core working journeys

### 1. Objective through useful work

“Review leaver access this quarter. The files are on SharePoint. Check the system, investigate anything unusual and prepare the working paper.”

1. Zobba locates authorised sources and applicable methodology, states a short useful approach, and starts. It asks only about ambiguity that changes the work, such as conflicting operative policies. Missing secondary evidence does not block independent analysis.
2. It establishes population scope and period, reads documents and embedded images, reconciles extracts with system information, and performs large comparisons in an analytical program. Working tables show exceptions, unmatched records, coverage and limitations rather than terminal output.
3. It opens the actual application beside the conversation when computer work is useful. Source/account/purpose are visible above the session. The auditor can watch, ask “What are you checking?”, inspect a saved capture or take over.
4. Useful leads may extend the working approach inside the objective. If a lead changes the agreed scope, operating purpose, external destination or spending limit, Zobba proposes that expansion and continues unaffected work. An exploratory plan can change; the changes and reasons remain inspectable.
5. Zobba drafts the working paper in the firm's template and reports what it established, supported exceptions, unresolved questions and limitations. A completed execution can still produce an inconclusive overall assessment and supported individual exceptions.

### 2. Question, correction and review

“Show me why this is an exception” opens the claim's source records and calculation, preserving the originating statement and a **Back to claim** path. Evidence is readable first: source, account/system, location, acquisition date, period and what it supports; identifiers and hashes stay in technical details. Supported locators include spreadsheet cells/rows, PDF page/region, document paragraphs/tables, email passages, system record fields and browser-capture elements.

An auditor can select a paragraph, table row, spreadsheet range or image region and ask a question. An explicitly requested edit to a draft saves a new draft directly, shows the change and offers Undo; it does not create an approval ceremony. The agent may improve draft analysis as new evidence arrives, but it calls out changed conclusions or limitations in the conversation and visible change summary. It never silently replaces approved or issued conclusions. Such work creates a proposed revision while preserving the exact approved/issued version.

Submitting for review fixes a version and its evidence/analysis dependencies. The reviewer reads the document in the same environment, asks Zobba questions, inspects source and method, and adds anchored notes. Review-time queries are read-only by default; new calculations are labelled review work, and edits belong in a proposed next draft. Review is a named human decision on an exact version, not a model self-check. **Return with notes**, **Mark reviewed**, **Approve**, and **Issue** express distinct decisions; firm policy may combine review and approval in one clearly named action when the same person is assigned both responsibilities. Issuance always records the exact rendering, destination and accountable issuer.

### 3. Evidence requests and follow-up

Zobba drafts an evidence request from a specific gap and maintains a standing request for the expected material. For an action requiring confirmation, the conversation contains one reviewable decision showing sender/account, recipients, content, attachments, destination and any calendar time/timezone. The adjacent draft can be edited. The action-specific button records the decision for those details; changes invalidate that decision. The product does not ask for every external action if a suitable standing grant already permits it.

Per-operation outcomes remain separate: sent, rejected before sending, partially completed, or uncertain after dispatch. Use “The send was submitted, but delivery is unconfirmed; I am checking Sent items” when the actual observation is only submission. Replace the pack's blanket “I sent…” uncertain-outcome phrase; it overstates success in an ambiguous dispatch failure. Failed confirmation is not evidence that nothing happened.

When expected evidence arrives, Zobba associates it with the request, checks source identity, period and completeness, and resumes eligible work. An unexpected file is candidate evidence, not a new instruction. New evidence that affects a conclusion opens a visible revision and its reason. Notifications identify what changed or needs a decision; they do not disclose sensitive evidence by default.

### 4. Ongoing assurance

“Run this each month and bring exceptions to me” creates a proposed recurring definition in the conversation. It contains objective/control, versioned method and analytical code, source mappings and completeness tests, expected population, criteria, period boundaries/timezone/calendar, output template, owner/reviewer, Permissions, budget and notification rules. This is a reviewed method, not a frozen click recording or a promise to reproduce stochastic exploration exactly.

Zobba explains assumptions introduced in promotion, especially period rules, completeness requirements and which judgement remains human. Audit-manager approval activates unattended assurance under firm policy. Eligibility depends on a reproducible method, understood inputs/limits and granted operations, not the pack's simple “uses an Available skill” condition. A demonstration of the method on the existing source snapshot is part of the reviewable evidence, not a new broad benchmarking programme.

Each period has its own result with exact inputs, method version and execution record, grouped under the check and linked to the originating task. Discussing a result continues that relationship without mixing separate periods into one enormous conversation. Results lead with the audit meaning, then Exceptions, Coverage, Evidence and How it ran. Material method/source/criteria/model-capability changes create a revision needing the applicable review; schedule time changes within authorised boundaries need not reapprove the analytical method. Missing evidence and access expiry yield waiting/didn't-run/inconclusive states as appropriate, never a passed check.

A **schedule**, a **standing evidence request**, and an **evidence-arrival trigger** are different objects sharing the continuing-task system. Late events are deduplicated; a task resumes only for the matched condition and current Permissions. The user can pause an individual check or all triggers for a task without deleting its history. Event storms are summarised, not converted into dozens of duplicate tasks.

## Controls and visible states

The state shown in the interface is a projection of accepted backend commands. UI controls do not wait for a model reply. “Received” means the command was durably accepted; “Applied” means the relevant work boundary has changed. Never show a false completed control transition because a local button changed appearance.

| Action | Product meaning | What the auditor sees |
|---|---|---|
| Watch | Observe the current session or work without changing control. | Live view with account, purpose, controller and connection state; saved evidence is clearly distinguished from the current screen. |
| Guide / ask | Send useful direction or ask about the same task while work continues. | Immediate durable acknowledgement. The agent answers from current work when possible. Direction is applied at a safe boundary; conflicting queued actions are held. The message identifies what is already done or dispatched. |
| Pause | Preserve the objective and work but stop starting further task work. | “Pausing” until affected interruptible work is cancelled/quiescent, then “Paused”. Already submitted effects can be checked; the UI names them. Resume continues from saved state. |
| Stop | Cancel the current pursuit of the objective and its dependent helpers. | “Stopping” then “Stopped; work so far saved”, with completed outputs and outstanding reconciliations. A later explicit Continue starts a new continuation of the same task, not silent automatic resumption. |
| Take over | Transfer exclusive input control of this computer to the person. | “Taking over” until the gateway confirms agent input is fenced, then “You control this computer”. Tasks using that computer wait. Independent analytical work may continue and is shown. |
| Hand back | Release the person's input control and ask Zobba to continue. | The gateway disables human inputs; Zobba observes the current application/file state, reconciles changes and resumes. It does not replay the old click queue. |
| Sign in | Enter credentials directly in a private application view. | “Sign in privately; Zobba cannot view this step.” Agent observation/input and recording of the credential view are disabled. An explicit Done/handback resumes observation after credential-entry surfaces are closed. |
| Reconnect | Restore viewing/control transport or source access. | Task state persists. A stale image is labelled with last-live time. Reconnecting never silently reissues an action or returns a human-controlled session to the agent. |

Private sign-in and human takeover use the same exclusive input foundation but are different user intents. Private sign-in must suppress model observation and capture, not simply hide a chat transcript. OAuth redirects on the user's device are preferable when the integration supports them. Passwords, MFA codes and recovery codes do not go through conversation or speech transcription. A machine without a suitable privacy route waits for authorised reconnection.

Computer states include **Starting**, **Zobba controls**, **Taking over**, **You control**, **Private sign-in**, **Handing back / Checking current state**, **Paused**, **Reconnecting**, **Suspended**, and **Unavailable**. They are separate from task execution, coverage, assessment, review and connection status. Only one input controller exists per computer. Other authorised collaborators may watch; a second person requests control. Loss of the controlling browser freezes input; it never silently grants control to another person or the agent.

Do not put every state dimension in the task header. Show the current activity or blocker there, the audit result and coverage together where the result is read, and human review on the artifact/result. The existing six-dimension status model is useful; add explicit computer ownership and resource state without collapsing them into “Running”.

## Permissions and operating purpose

Retain the name **Permissions** and the pack's readable **Can read / Can write / Asks first / Never / Scheduled checks / Connections / Administrator limits**, plus **Activity record**. One small summary is enough during normal work; the enforcement lives in the backend.

Attach purpose to actual account/system/resource capabilities:

| Purpose | Default experience |
|---|---|
| Inspect live operations | Read records and application views, export permitted source data, acquire evidence. Changes to audited operational records are excluded. Working copies remain editable. |
| Exercise a designated test system | Use named test accounts and test tenant, create labelled synthetic records, run specified workflows, capture outcomes and clean up authorised test data. Test authority does not transfer to an identically branded production system. |
| Coordinate audit work | Draft working papers, edit allowed audit documents, request evidence, send messages and arrange walkthroughs under granted destinations and confirmation rules. |

The account and environment label sit above the real computer and appear in a decision when consequential. Zobba cannot gain permission by reading a page that says “test”, loading a skill or receiving a model recommendation. A direct API, MCP tool and browser/desktop route enforce the same authority. A broad logged-in account is not a grant to automate every accessible operation.

A connection means reachability; task Permissions mean authorised use. Routine retrieval and calculations proceed. Ask only when the configured policy requires a new decision or when the task introduces a material new purpose/destination. Show who allowed an external action and its observed outcome in the Activity record. Human takeover remains attributable and does not turn the application's own controls into an agent permission bypass.

## Three roles and accountability

| Role | Responsibilities |
|---|---|
| Auditor | Direct assigned engagement tasks; use granted sources; prepare and correct drafts; answer questions; permit actions within delegated limits; submit work; inspect results. |
| Audit manager | Auditor capabilities plus assigned review, approval and issuance; scope engagement Permissions within Admin limits; own recurring definitions and review assignments. Reviewer/approver/issuer are engagement responsibilities assigned to people in this role, not extra product roles. |
| Admin | Configure users, integrations, model/processing policy, Permissions ceilings, methodology, skills, templates and retention. Admin authority by itself grants no audit review, approval or issuance. |

Remove “Methodology owner” as a fourth role from the pack; make methodology maintenance an Admin responsibility with named stewardship recorded in metadata. A person may hold Admin and an audit role, but each action uses its explicit authority; configuring the system does not confer authority to sign an audit conclusion. Self-review must never be represented as independent review.

Support individual auditors honestly: allow preparation, evidence work and export immediately. Recommend a declared sole-practitioner methodology that permits the accountable practitioner to issue work labelled **No independent review** if their professional requirements allow it. A firm requiring independent review cannot be bypassed by changing a title or combining roles. A sole-practitioner policy is a consequential product recommendation for the owner to settle; the rest of the role system does not need a fourth role.

## Memory, methodology, models and voice in the product

Keep engagement decisions, unresolved questions, source dependencies and accepted corrections across long conversations. A compacted context must not erase dissent, scope limits or which evidence supported a conclusion. “What are you using?” opens a readable current-context view: methodology version, selected skills, key decisions, relevant memories, sources and active model policy. It is inspection, not a pre-task form.

Personal presentation preferences may be learned within the user's scope and remain visible/editable. Client facts stay inside the client and cite their source; uncertain facts remain uncertain. A cross-engagement client fact is reused only with appropriate access and visible source. Organisation methodology and required review rules have a declared standing different from optional skill advice. Conversation can override “use a concise table”; it cannot quietly remove required independent review. Methodology import produces a draft of rules, phases, templates, scales and review responsibilities for Admin review, with unresolved interpretations highlighted.

Use an Admin-approved **model configuration** as the default task setting, visible in the composer. Let the auditor inspect the actual model/provider and select an allowed configuration or explicit model. Show capability and processing restrictions in plain language. The default may route visual, extraction and analysis work to appropriate permitted models while maintaining one accountable task. Provider/model changes are recorded per invocation; scheduled assurance follows a reviewed model-capability policy rather than depending forever on a marketing model name. The reference screenshots' model names are illustrative and are not a supported-model commitment.

Voice directs the same task: push-to-talk, visible listening indicator, live editable transcript and ordinary Send. Speech output is optional and stops immediately on user interruption without stopping the task. Pause/Stop/Take over remain direct accessible controls; voice can invoke the same intent but does not receive special authority. Confirmation of an exact consequential action remains on its readable decision surface, with accessible voice/switch support, so a vague “yes” outside that context cannot send a document. Never capture private sign-in audio as task context.

## Narrow screens and accessibility

On narrow screens, Conversation and Work become stable full-screen views with one-tap return to the prior claim or computer. A persistent compact strip retains Pause/Stop, controller state and an open-decision indicator. Questions open in a sheet that leaves the composer accessible; avoid stacking every limitation and decision permanently above it. This corrects the pack's potentially overfull “all decisions/limitations reachable without scrolling” wording while preserving access to them.

Computer takeover uses a dedicated full-screen surface with clear keyboard, pointer/touch controls and fit/zoom modes; a fixed, tested mapping prevents taps from reaching the wrong remote coordinates. Complex documents and data offer native responsive inspection even if remote application chrome is tiny. Narrow devices can direct tasks, review readable work and respond to decisions; they are not required to edit a dense desktop spreadsheet to complete every interaction.

Maintain keyboard navigation and focus return, real table semantics, 44px touch targets, reduced motion, sufficient contrast and visible text for all statuses. Screen-reader activity is announced by meaningful step, not token. Remote-computer limits are made clear; whenever available, structured document and table views provide an accessible alternative to pixels. Accessibility and real takeover correctness require implemented testing; mockups do not establish either.

## Consequential choices to carry to the owner, with recommendation

1. **Individual practice and independent review.** Recommend sole-practitioner issuance that states No independent review where the selected methodology permits it; require a different person for an independent-review attestation. This preserves individual use without misrepresenting assurance. No fourth role is needed.
2. **Supported computer/app promise.** Recommend fully supported managed browser and Linux document/analysis environment, with Windows application capability as an explicit paid profile when native Windows is required. Do not imply universal desktop compatibility. This affects customer suitability, licensing and compute cost; architecture should define the profile boundary now.
3. **Recurring authority and cost.** Recommend versioned assurance methods approved by an assigned Audit manager, per-check budgets and safe unattended grants. Schedule/event activation never grants new authority. The pricing/compute allowance must support genuine continued work; it should not depend on an always-open browser tab.

Ordinary choices resolved in this recommendation: explicit Follow Zobba replaces timer-based panel replacement; graphite primary actions; light default with later dark parity; supplied Pair SVGs; a neutral built-in working-paper template is available when a firm has none; visible provenance footer on by default and firm-configurable, while internal provenance is retained; no mandatory model picker interaction; no separate methodology-owner/approver product roles; no wizard before useful work.
