## Summary

1. The App Server is the one public boundary. The TUI has no `codex-core` dependency. TUI and exec use the app-server client, in-process (or remote for the TUI). External clients use stdio JSONL, WebSocket, WebSocket over a 0600 Unix socket, or a relay on chatgpt.com. [OBSERVED]
2. The wire format is JSON-RPC without the `jsonrpc` field, plus an optional W3C trace context. Rust types are the schema source. TS and JSON Schema are generated in test builds and pinned by three drift tests. [OBSERVED/TEST]
3. There is no version negotiation. `initialize` exchanges client info and capability flags. 90 methods or notifications are gated `#[experimental]`, and v1 is frozen legacy. [OBSERVED]
4. Approvals are server-to-client requests with `threadId/turnId/itemId`. Failures fail closed (deny). But any connection may answer, the answer carries no human identity, and approval events are not persisted. [OBSERVED]
5. Local transports have no sequence numbers and no replay. `thread/resume` returns a snapshot and re-sends pending approvals. Idle threads with no subscriber unload after 60 s. Only the chatgpt.com relay has seq/ack buffering. [OBSERVED]
6. Backpressure: a full queue blocks stdio. A slow WebSocket client is disconnected at 32 Ki queued messages. A request that meets a full inbound queue gets `-32001` (overloaded). The in-process transport silently drops most notifications. [OBSERVED/TEST]
7. Telemetry separates `log_only` data (email, tool arguments, 2 KiB output preview, the prompt if opted in) from `trace_safe` data (lengths only), and a test pins the split. The default release metrics exporter is Statsig (hosted). [OBSERVED/TEST]
8. Secret redaction uses four regexes on client-facing projections only. Approval prompts keep the raw command, and some warn logs print raw commands and unparseable rollout lines. [OBSERVED]
9. Strong test seams: a wiremock Responses server with `ev_*` SSE builders, a gated SSE stream, lifecycle-pausing hooks, virtual time, and about 1,350 insta snapshots. No property tests, fuzzing or published benchmark numbers were found. [OBSERVED/TEST]
10. Adopt one ordered owner per thread, fail-closed approvals, log/trace routing with a test, schema drift tests and rollout-trace. Reject the unattributed, unpersisted approvals and the lossy local delivery. [INFERENCE]

### F1. Wire format and schema source of truth

- **Problem.** Many clients (TUI, desktop, IDE, mobile, Python SDK) must share one fast-changing contract.
- **Code.** `rpc.rs` states the dialect: "We do not do true JSON-RPC 2.0, as we neither send nor expect the `jsonrpc: 2.0` field". `JSONRPCRequest` carries an optional `trace: W3cTraceContext` (`codex-rs/app-server-protocol/src/rpc.rs:L1-L2,L46-L55`). [OBSERVED] Methods are declared once in macros that generate the `ClientRequest`/`ServerRequest`/`ServerNotification` enums with wire names, and each request declares a **serialization scope** (`Global`, `Thread{thread_id}`, `ThreadPath`, …) that the server uses to queue conflicting requests (`codex-rs/app-server-protocol/src/protocol/common.rs:L140-L212,L498-L567`; `codex-rs/app-server/src/request_serialization.rs:L24-L51`). [OBSERVED] Counts: 170 client methods, 9 server-request methods and 84 notifications, from a grep of the macro blocks. [OBSERVED]
- **Schema generation.** In non-test builds `JsonSchema`/`TS` are no-op derive macros (`codex-rs/app-server-protocol/src/lib.rs:L64-L71`). Real `ts-rs`/`schemars` derivation happens only under `cfg(test)` (they are dev-dependencies in `Cargo.toml`). The release binary embeds zstd-compressed "precomputed exports" (`codex-rs/app-server-protocol/src/precomputed_exports.rs:L14-L18,L115-L123`) so that `codex app-server generate-ts|generate-json-schema` works without the generators (`codex-rs/cli/src/main.rs:L1392-L1407`). Regeneration is `just write-app-server-schema`: it runs the ignored test `write_schema_fixtures_from_env` and then regenerates the Python SDK types (`justfile:L176-L178`; `codex-rs/app-server-protocol/scripts/write_schema_fixtures.py:L36-L83`). [OBSERVED]
- **Tests.** [TEST] `typescript_schema_fixtures_match_generated` and `json_schema_fixtures_match_generated` (`codex-rs/app-server-protocol/src/schema_fixtures_tests.rs:L20,L40`) fail when a Rust type change is not reflected in the checked-in fixtures. `stable_precomputed_exports_match_schema_fixtures` (L47) fails when the embedded archive drifts from the fixtures. `precomputed_exports_are_written_to_disk` (`codex-rs/app-server-protocol/src/precomputed_exports_tests.rs:L13`) fails when runtime generation differs from the archive.
- **Limits.** The TS SDK is not generated, so drift is possible. AGENTS.md rules are only partly enforced: it says "Never use `skip_serializing_if = Option::is_none` for v2 payload fields" and "timestamps … integer Unix seconds", yet `CommandExecutionRequestApprovalParams` uses `skip_serializing_if` and `started_at_ms` is in milliseconds (`AGENTS.md:L277,L284` [DOC] vs `codex-rs/app-server-protocol/src/protocol/v2/item.rs:L1549-L1592` [OBSERVED]).
- **Audit harness.** The TypeScript analogue is a Zod/TS schema as the source, with generated JSON Schema, a CI fixture test, and a declared ordering scope per method.
- **Recommendation: ADOPT PATTERN.** Types as the source, a checked-in generated fixture and a drift test catch contract drift cheaply.

### F2. Handshake, capability negotiation, versioning

- **Code.** `initialize` takes `clientInfo{name,title,version}` and `capabilities{experimentalApi, requestAttestation, optOutNotificationMethods, extensions, explicitGatewayOauth}` (`codex-rs/app-server-protocol/src/protocol/v1.rs:L26-L70`). The response has `userAgent`, `codexHome` and the platform, and **no protocol version** (L72-L84). Requests before `initialize` get `"Not initialized"`. A second `initialize` gets `"Already initialized"`. An experimental method without opt-in gets `"<reason> requires experimentalApi capability"` (`codex-rs/app-server/src/message_processor.rs:L972-L980`; `codex-rs/app-server/src/request_processors/initialize_processor.rs:L71-L73`; `codex-rs/app-server-protocol/src/experimental_api.rs:L30-L32`). Experimental notifications are filtered per connection, and experimental fields are stripped from approval params (`codex-rs/app-server/src/transport.rs:L104-L128,L180-L204`). [OBSERVED] The code records its own open question: capability scope is per connection, which "can create odd cross-client behavior … on a shared thread" (`codex-rs/app-server/src/request_processors/initialize_processor.rs:L75-L80`). [OBSERVED]
- **Versioning.** "All active API development should happen in app-server v2. Do not add new API surface area to v1" (`AGENTS.md:L269`) [DOC]. v1 keeps only the handshake types, three deprecated methods and two legacy approval requests (`codex-rs/app-server-protocol/src/protocol/common.rs:L1449-L1464,L1819-L1830`) [OBSERVED]. Deprecations are announced at runtime through a `deprecationNotice` notification (`codex-rs/app-server-protocol/src/protocol/common.rs:L2004`) [OBSERVED], with tests such as `emits_deprecation_notice_for_legacy_feature_flag` (`codex-rs/core/tests/suite/deprecation_notice.rs:L16`) [TEST]. The only explicit version constant in this area is the relay's `REMOTE_CONTROL_PROTOCOL_VERSION = "3"` (`codex-rs/app-server-transport/src/transport/remote_control/websocket.rs:L69`) [OBSERVED].
- **Audit harness.** A multi-tenant API needs a real protocol version (or a dated API version) and server-side, per-tenant capability policy, not client-declared flags. `clientInfo.name` is self-declared, yet it changes behaviour (for example, resume payload redaction for named mobile clients, `codex-rs/app-server/src/request_processors/thread_resume_redaction.rs:L9-L15`) [OBSERVED].
- **Recommendation: ADAPT.** Take opt-in experimental gating (method and field level, enforced by the server). Add explicit version negotiation. Never key authorisation on self-declared client names.

### F3. How progress, tool results, approvals and outputs reach a client

- **Ownership.** For each loaded thread, the app-server spawns **one listener task**. It owns the ordered stream from `conversation.next_event()` and a `ThreadListenerCommand` channel (`codex-rs/app-server/src/request_processors/thread_lifecycle.rs:L214-L395`; `codex-rs/app-server/src/thread_state.rs:L59-L88`). For each event it: (1) updates `ThreadState.current_turn_history` (a `ThreadHistoryBuilder`, the same projector used to rebuild history from rollout files: `codex-rs/app-server/src/thread_state.rs:L197-L215`; `codex-rs/app-server-protocol/src/protocol/thread_history.rs:L360,L422`); (2) drops raw model events unless opted in (`codex-rs/app-server/src/request_processors/thread_lifecycle.rs:L326-L335`); (3) reads the current subscriber set; (4) calls `apply_bespoke_event_handling`. Stateless one-to-one projections (`ItemStarted/Completed`, deltas, exec begin/end) live in `item_event_to_server_notification` (`codex-rs/app-server-protocol/src/protocol/event_mapping.rs:L30-L466`). All outbound envelopes pass through **one** router task (`codex-rs/app-server/src/lib.rs:L912-L964`). [OBSERVED]
- **Message kinds.** Responses answer client requests. Notifications carry progress: `turn/started`, `item/started`, `item/agentMessage/delta`, `item/commandExecution/outputDelta`, `item/completed`, `turn/completed` and others (`codex-rs/app-server-protocol/src/protocol/common.rs:L1944-L1992`). Approvals are **server-initiated JSON-RPC requests**: `item/commandExecution/requestApproval`, `item/fileChange/requestApproval`, `item/permissions/requestApproval`, `item/tool/requestUserInput`, `mcpServer/elicitation/request`, and `item/tool/call`, which asks the *client* to execute a dynamic tool (`codex-rs/app-server-protocol/src/protocol/common.rs:L1761-L1818`). [OBSERVED]
- **Correlation.** `threadId` is a UUIDv7 (`codex-rs/protocol/src/thread_id.rs:L27-L31`). Approval params carry `threadId`, `turnId`, `itemId` (the model `call_id`), an optional `approvalId` for sub-command callbacks, and `startedAtMs` (`codex-rs/app-server-protocol/src/protocol/v2/item.rs:L1549-L1569`). Server request ids are sequential integers (`codex-rs/app-server/src/outgoing_message.rs:L326-L328`). Resolution emits `serverRequest/resolved {threadId, requestId}` **through the listener**, so it is ordered after the request (`codex-rs/app-server/src/thread_state.rs:L83-L88`; `codex-rs/app-server/src/bespoke_event_handling.rs:L1978-L1979`). Envelopes add `emittedAtMs`, not a sequence number (`codex-rs/app-server-protocol/src/protocol/common.rs:L2045-L2059`). [OBSERVED]
- **Ordering.** Per thread, events are serialized by the single listener and single router. There is no cross-thread order and no sequence field. The resume response and the replayed pending requests are ordered inside the listener (`codex-rs/app-server/src/request_processors/thread_lifecycle.rs:L806-L813`). [OBSERVED/INFERENCE]
- **Tests.** [TEST] `turn_interrupt_resolves_pending_command_approval_request` (`codex-rs/app-server/tests/suite/v2/turn_interrupt.rs:L221`) fails if an interrupt leaves an approval unresolved or does not emit `serverRequest/resolved` before `turn/completed` with status `Interrupted`. [TEST] `thread_start_jsonrpc_span_exports_server_span_and_parents_children` (`codex-rs/app-server/src/message_processor_tracing_tests.rs:L569`) fails if an inbound `traceparent` does not become the remote parent of the server span and its core children.
- **Recommendation: ADOPT PATTERN.** Use one ordered owner per conversation, requests for decisions and notifications for progress, and resolve requests on the same ordered path.

### F5. Reconnect, resume and subscriber lifecycle

- **Code.** Local transports keep **no per-client buffer and no sequence replay**. With no subscribers, notifications are simply not sent (`codex-rs/app-server/src/outgoing_message.rs:L199-L208`). Pending server requests stay in `request_id_to_callback`, keyed by request id and tagged with their thread (`codex-rs/app-server/src/outgoing_message.rs:L128-L157`). On `thread/resume` of a running thread, the listener sends the response (a history snapshot with paginated turns/items cursors) and then **replays pending approvals** to that connection (`codex-rs/app-server/src/request_processors/thread_lifecycle.rs:L806-L813`; `codex-rs/app-server/src/outgoing_message.rs:L446-L465`). Unloading needs *both* no subscribers *and* an inactive thread for `thread_unload_delay`, and it is skipped while the agent is running (`codex-rs/app-server/src/request_processors/thread_lifecycle.rs:L56-L63,L363-L373`). The default is 60 s (`codex-rs/core/src/config/mod.rs:L3916-L3917`). Item-anchored pagination (`thread/items/list` with `{"type":"item","itemId":…}`) lets a client catch up after a known item [DOC] (`codex-rs/app-server/README.md:L491-L505`). [OBSERVED]
- **The relay path does buffer.** The chatgpt.com remote-control WebSocket keeps unacked envelopes per `(client, stream)` and replays them on reconnect. Its cap is 128 outstanding, after which the writer stops pulling. Inbound `seq_id` duplicates are dropped (`codex-rs/app-server-transport/src/transport/remote_control/websocket.rs:L101-L137,L957-L1017`; `codex-rs/app-server-transport/src/transport/remote_control/client_tracker.rs:L133-L143`). Ping 10 s, pong timeout 60 s, backoff cap 30 s (`codex-rs/app-server-transport/src/transport/remote_control/websocket.rs:L72-L83`). [OBSERVED] [TEST] `incoming_message_timeout_does_not_advance_seq_id` (`codex-rs/app-server-transport/src/transport/remote_control/client_tracker.rs:L640`) fails if a failed delivery advances the dedup cursor.
- **Client side.** TUI reconnect uses backoff 0, 1, 2, 4, then 8 s under a shared 120 s deadline. Uncertain submissions are quarantined ("Nothing was retried"). Transport errors are never logged ("can contain endpoint credentials") (`codex-rs/tui/src/app/reconnect.rs:L1-L3,L48,L53-L54,L119`). [OBSERVED] [TEST] `thread_resume_replays_pending_command_execution_request_approval` (`codex-rs/app-server/tests/suite/v2/thread_resume.rs:L5461`) fails unless the replayed request equals the original and the turn completes after the answer. `websocket_disconnect_keeps_last_subscribed_thread_loaded_until_idle_timeout` (`codex-rs/app-server/tests/suite/v2/connection_handling_websocket.rs:L453`) fails if a disconnect unloads early or never unloads. `reconnect_exhaustion_and_unknown_initial_thread_stay_offline` (`codex-rs/tui/src/app/tests/active_reconnect_tests.rs:L609`) uses virtual time to assert exactly 120 s.
- **Audit harness.** A web client reconnecting after a network loss needs an exact cursor over a durable event log (Last-Event-ID). A snapshot alone does not prove nothing was missed.
- **Recommendation: ADAPT.** Take "replay pending decisions on resume" and "snapshot plus cursor pagination". Replace "no replay" with durable sequence replay.

### F6. Daemon lifecycle and restart recovery

- **Code/doc.** The daemon runs a detached, pidfile-backed app-server behind `CODEX_HOME/app-server-control/app-server-control.sock`. The socket is WebSocket over UDS, mode 0600, and its parent directory's ownership and permissions are checked (`codex-rs/app-server-transport/src/transport/unix_socket.rs:L30-L31,L49-L70`) [OBSERVED]. Lifecycle commands print one JSON object and are serialized per `CODEX_HOME` [DOC] (`codex-rs/app-server-daemon/README.md:L43-L46,L181-L183`). `shutdownGraceSeconds` is 60 by default (0–300) [DOC]. On a managed restart, `loaded-threads.json` records the loaded threads plus interrupted turns with output schema, service tier and environment (`codex-rs/app-server-transport/src/daemon_recovery.rs:L12-L30`; `codex-rs/app-server-transport/src/transport/mod.rs:L55-L62`). Recovery appends a `TurnAborted` to history and then starts **one** continuation turn with the prompt "Check the current state before repeating actions that may already have completed". It does this only if the permission profile and the local environment still match (`codex-rs/app-server/src/request_processors/daemon_continuation.rs:L1-L3,L75-L92,L102-L119`). [OBSERVED] [TEST] `managed_restart_resumes_loaded_threads_and_goal_without_client` (`codex-rs/app-server/tests/suite/v2/daemon_update_recovery.rs:L38`) and the parameterised `managed_shutdown_records_interrupted_turn` (L472), which covers completed, canceled, compacting, stricter-config and other outcomes.
- **Audit harness.** Automatic continuation that relies on the model to avoid repeated side effects is unacceptable for audit. An interrupted operation must be recorded as interrupted and then resumed or retried idempotently by explicit policy.
- **Recommendation: ADAPT.** Take "persist the interruption before exposing a new turn" and "refuse continuation if the policy got stricter". **DO NOT ADOPT** model-driven continuation.

### F7. Human decisions: fail-closed, but unattributed and not persisted

- **Code.** A malformed approval response, a client error or a dropped channel maps to `ReviewDecision::denied("approval request failed")` (`codex-rs/app-server/src/bespoke_event_handling.rs:L2025,L2035,L2042`). Headless exec rejects approvals (boundary table in §1.1). [OBSERVED] But `notify_client_response` accepts an answer from **any** connection, and the first answer wins. Only user-verification ceremonies are bound to one owning connection (`codex-rs/app-server/src/outgoing_message.rs:L467-L495,L561-L580`) [OBSERVED]. [TEST] `verification_is_delivered_to_one_owner_and_other_connections_cannot_resolve_it` (`codex-rs/app-server/src/user_verification_ownership_tests.rs:L30`) proves this ownership for verification only. `serverRequest/resolved` carries no decision and no actor (`codex-rs/app-server-protocol/src/protocol/v2/notification.rs:L74-L77`). The rollout policy classes `ExecApprovalRequest`, `ApplyPatchApprovalRequest`, `RequestPermissions`, `RequestUserInput` and `GuardianAssessment` as "Transient, non-durable events" (`codex-rs/rollout/src/policy.rs:L141-L204`). Only the resulting item persists, in paginated mode, as `ItemCompleted` with a status such as `Declined` (`codex-rs/rollout/src/policy.rs:L120-L121`) [OBSERVED/INFERENCE]. The `codex.tool_decision` telemetry log records decision and `source ∈ {User, Config, AutomatedReviewer}` with the *account* email (`codex-rs/otel/src/events/session_telemetry.rs:L1166-L1193`; `codex-rs/otel/src/events/shared.rs:L14-L31`). [OBSERVED]
- **General vs local.** On a single-user machine every connection is the same OS user (socket 0600), so any-connection answering is defensible. [INFERENCE]
- **Audit harness.** It needs per-request authorisation of the answering principal, the decision, the actor and the rationale in the immutable chain, and a durable record of the request itself.
- **Recommendation: ADOPT PATTERN** (fail-closed mapping). **DO NOT ADOPT** unattributed, first-connection-wins, non-persisted decisions.

### F8. Logs and telemetry

- **Two-target split.** `log_event!` writes to target `codex_otel.log_only` and includes `user.email` and `user.account_id`. `trace_event!` writes to `codex_otel.trace_safe` without identity (`codex-rs/otel/src/events/shared.rs:L14-L62`; `codex-rs/otel/src/targets.rs:L1-L11`). ### 1.11 Lessons for a conversation-plus-inspection web experience [INFERENCE]

1. Give each conversation one ordered owner. Stream items as `started → deltas → completed`, and make `completed` carry the full item so that deltas are disposable.
2. Use one projector for both the live and the persisted view (`ThreadHistoryBuilder`). Then the inspection pane and the chat cannot disagree. The launch-failure test (F11) asserts live item = persisted item = reconstructed item.
3. Put human decisions on the request/response channel with ids that point at the item, and replay pending decisions on reconnect. Unlike Codex, bind them to an authorised principal and persist them.
4. Treat the notification stream as lossy and the store as truth. Resume with a cursor (item anchor or sequence), not only a snapshot.
5. Codex's WebSocket listener **rejects any request with an `Origin` header** (`codex-rs/app-server-transport/src/transport/websocket.rs:L89-L104,L152`). [TEST] `websocket_transport_rejects_browser_origin_without_auth` (`codex-rs/app-server/tests/suite/v2/connection_handling_websocket.rs:L241`). It also refuses non-loopback binds without auth (L134-L142). So it is deliberately **not** a browser API. A web product needs its own authenticated gateway (session cookies, CSRF, tenancy) in front of any agent protocol.
6. Put `emittedAtMs` and a trace context on every message, and keep content in log-only sinks.
