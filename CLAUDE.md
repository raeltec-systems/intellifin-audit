# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

# Working rules

Repository guidelines, layout, and project policy live in `AGENTS.md`. Read that too.

## This is a living document

This file is the one shared place for decisions that affect how anyone — agent or developer — works with this codebase. When we hit a gotcha and agree on a workflow, record it here (see "Codebase decisions and gotchas" at the bottom) so a later agent does not re-decide it differently. Keep entries short: the decision, the reason, one line each. Update this file in the same commit as the work that produced the decision.

## Done means done

Not half done. Not done except for the part you decided to skip. And not a report about how it will be done.

Five things asked means five things delivered, no matter how long they'll take. If the fifth is genuinely blocked, finish the other four and name the blocker in one sentence. The specific blocker. Not "this needs more investigation."

## Act. Don't ask

Reversible and cheap? Do it, then tell me. Research, data pulls, analysis, drafts, refactors inside the scope I gave you, testing an API. A question costs me more than a re-run costs you.

Ask first only for: anything reaching an audience, anything we cannot undo, anything expensive.

Something is broken? Fix it. Reporting an issue you could have fixed turns your work into my to-do list.

## A question is a question

When I ask a question, answer it. Do not implement it.

"Should we use X?" is not "migrate everything to X." "What would it take to add Y?" is not "add Y."

When in doubt, assume it's a question. Answer first. Act when I say go.

## Speed and model routing

The model families named below describe Claude environments. Other agents use the
platform-specific adaptation in `AGENTS.md` after its managed context block; active
runtime instructions and available capabilities take precedence.

When running as a frontier-tier model (Fable, Opus, or their successors): optimize for wall-clock speed. Finish tasks quickly.

Route work to the cheapest model family that does it well. Never burn top-tier intelligence on routine work. The tiers, from cheapest to most capable — use whichever models from each tier are available:

- **Small/fast tier** (Haiku family): trivial mechanical work — file lookups, simple renames, formatting.
- **Mid tier** (Sonnet family): routine work — search, bulk edits, boilerplate, verification, running test suites.
- **Frontier tier** (Opus, Fable/Mythos family): hard reasoning that can run independently — architecture calls, tricky debugging, concurrency and correctness work. The top model (Fable) is costly; reserve it for work that actually needs it.

- Parallelize aggressively. Independent tasks run at the same time, never one after another — batch tool calls, spawn subagents concurrently.
- Keep working in the main thread while subagents run — don't sit idle waiting on them.
- Don't over-deliberate. Enough info to act = act. No long option surveys for decisions with an obvious default.
- Speed never trades away quality: same rigor, same verification, same "done means done". If parallelizing risks a worse result, slow down.
- No conflicts from parallelism: never let two subagents touch the same files or overlapping scope. Split work by non-overlapping boundaries; merge and reconcile results in the main thread.

## Short responses

It's been a long day and my brain is fried, talk to me like I'm 5.

Small words, short sentences, short paragraphs. If you have to use a big word, explain it right after. Only return what's actually necessary.

Just tell me what you did, did it work, what do I do now.

If I have to decide something: 2 options max, the context I need to pick fast, and which one you'd go with.

Keep paths and commands exact.

Always use ASD-STE100 Simplified Technical English when you talk to me.

# About this repository

## What it is

**IntelliFin Audit** is an audit-execution platform: an auditor defines an Audit Procedure once and delegates its repeated execution to an autonomous Audit Agent, whose work stays observable, replayable, evidence-backed, and subject to human review.

This repository is both a BMAD v6.11 planning workspace and, since Story 1.1, the application monorepo itself. Planning artifacts under `_bmad-output/` still lead the code: the product is specified before it is built. `AGENTS.md` holds the verified agent block; refresh it with `/bmad-project-context`.

Each planning-artifact folder is named `<type>-IntelliFin Audit-<date>/` — **the name contains a space**. Quote every path.

## The planning chain and its state

```
brief → PRD (+addendum) → UX handoff → architecture spine → epics/stories → sprint → build
```

Each stage carries a `.memlog.md` (append-only decision log) and, when reviewed, `review-*.md` / `recheck-*.md` files. Check a document's frontmatter `status` (`draft` or `final`) and `revision` before trusting it. A downstream artifact derived from an earlier revision is stale until re-derived; the PRD's §0 says which ones.

The PRD is the source of truth for product decisions. `prd.md` holds requirements (FR-n, NFR-n, SM-n); `addendum.md` holds normative detail (state models, Evidence Quality Gate rules, Template contracts, golden-dataset seeds, FR migration map). Read both.

## Commands

BMAD scripts run with `uv` and need Python 3.11+. Run them from the repository root.

```bash
# Resolve a skill's customization (what a skill reads on activation)
uv run _bmad/scripts/resolve_customization.py --skill .claude/skills/bmad-prd --key workflow

# Resolve the central config layers
uv run _bmad/scripts/resolve_config.py

# Append to a workspace memlog (never edit .memlog.md by hand)
uv run _bmad/scripts/memlog.py append --workspace "<artifact folder>" --type <decision|change|override|assumption|event> --text "<one line, reason included>"

# Run one skill's Python tests (tests declare their own deps via PEP 723 headers)
uv run --with pytest --with ruamel.yaml pytest .claude/skills/bmad-sprint-planning/scripts/tests/test_sprint_plan.py

# Run a single test
uv run --with pytest --with ruamel.yaml pytest ".claude/skills/bmad-review/scripts/tests/test_word_metrics.py::test_name"

# All skill tests
uv run --with pytest --with ruamel.yaml pytest .claude/skills/*/scripts/tests
```

## Working with BMAD skills

- Invoke skills by name (`/bmad-prd`, `/bmad-architecture`, `/bmad-review`, ...). Deprecated names (`bmad-create-prd`, `bmad-editorial-review`, ...) forward to the current skill.
- Skills spawn subagents for reviews and reconciliation. Each reviewer writes its full report to a file in the artifact folder and returns only a summary; the main thread never holds full review text.
- Every product decision made during a skill run is logged to the artifact's `.memlog.md` via the script above, in the same turn it is made.
- `_bmad/config.toml`, `_bmad/config.user.toml`, and `_bmad/_config/*` are installer-managed. Do not edit; override in `_bmad/custom/config.toml` instead.

## Codebase decisions and gotchas

- **Bash `cd` persists between calls.** Use absolute paths or `...`; a relative path after an earlier `cd` will miss.
- **Planning-artifact folders have a space in the name.** Always quote paths under `_bmad-output/`.
- **Memlog writes go through `memlog.py` only.** Hand edits break the append-only guarantee the resume logic depends on.
- **Reviews are files, not chat.** Reviewer subagents write `review-<slug>.md` / `recheck-<slug>.md` next to the artifact and return a summary; the parent reads the file only when drilling into a finding.
- **Revising an upstream artifact invalidates downstream ones.** After a PRD revision, the architecture spine and UX handoff must be re-derived; say so in the PRD §0 and in the PR.
- **`.claude/skills` and `.agents/skills` are copies, not symlinks.** A change to a skill must be made in both, or re-rendered by the installer.

### Monorepo (added with Story 1.1)

- **Node 24.20.0 and pnpm 11.25.0 are hard pins.** `.nvmrc` + `engine-strict=true`. Run `nvm use && corepack enable` before any `pnpm` command; Node 22 fails the install on purpose.
- **pnpm 11 blocks dependency build scripts.** The allowlist lives in `pnpm-workspace.yaml` under `allowBuilds:` (a name-to-boolean map). The pnpm 10 keys `pnpm.onlyBuiltDependencies` in `package.json` and `onlyBuiltDependencies:` in the workspace file are silently ignored.
- **Root pins `typescript@6.0.3`, packages pin `typescript@7.0.2`.** dependency-cruiser 18.2.0 cannot use the TypeScript 7 API; with 7 at the root it cruises zero modules and exits 0. Verified twice (2026-09-02): a first TS 7 test only looked green because pnpm had left the old 6.0.3 peer linked. `pnpm boundaries` now runs `scripts/check-boundaries.mjs`, which fails on a zero-module cruise. Drop the root pin only when dependency-cruiser supports TS 7.
- **Keep `node_modules` out of dependency-cruiser's `exclude`.** Excluded paths are not rule-checked, so excluding `node_modules`, a bare `dist/`, or a bare `\.d\.ts$` silently hides vendor imports whose entry point lives there and disables the AD-1 vendor rules. `doNotFollow` is the right knob; `exclude` is scoped to `^(apps|packages)/`.
- **Workspace packages export TypeScript source for types and `dist` for runtime.** Typecheck and Vitest work from a fresh clone with no build; anything that actually runs (`apps/worker`, Docker images) must run `pnpm build` first.
- **`pnpm db:migrate` runs `packages/infrastructure/src/db/migrate.ts` over postgres.js, not `drizzle-kit migrate`.** drizzle-kit connects with `pg`, which treats `sslmode=require` as `verify-full` and so rejects Railway's self-signed certificate with `SELF_SIGNED_CERT_IN_CHAIN`; its progress spinner also overwrites the driver's error, so the release log said only "Exit status 1". CI now runs the Railway `postgres-ssl:18` image with `sslmode=require` so this fails in CI, not in a release.
- **Migrations are release-only (AD-15).** Never call `drizzle-kit migrate` from app code or a startup path. `packages/infrastructure/drizzle/0001_worker_heartbeat.sql` also seeds `schema_meta.version = 1`; bump that with the next generation.
- **`packages/domain` and `packages/application` deliberately omit `types: ["node"]`.** Without the Node ambient types, `process.env` does not typecheck there at all — the AD-11 "no ambient env inward" rule is enforced by the compiler, not only by dependency-cruiser. Do not add `types: ["node"]` to either tsconfig to silence an error; move the code that needs the environment into a composition root or `packages/infrastructure/src/config.ts`.
- **dependency-cruiser rule patterns must not nest quantifiers.** It runs every `path` regex through a catastrophic-backtracking check and, on a hit, rejects the entire rule set — the cruise then exits non-zero with "Bailing out" and no rule is actually evaluated. Prefer several simple patterns in a `path` array over one clever combined regex.
- **Never `exclude` `node_modules` in `.dependency-cruiser.cjs`.** An excluded path is not rule-checked, so excluding it (or a bare `dist/` or `\.d\.ts$`) silently hides vendor imports whose entry point lives there and disables the AD-1 vendor rules. `doNotFollow` is the right knob; `exclude` stays scoped to `^(apps|packages)/`.
- **The supported schema range is a build constant, never an environment variable.** `SUPPORTED_SCHEMA_MIN`/`SUPPORTED_SCHEMA_MAX` in `packages/infrastructure/src/db/compat.ts`. As `SCHEMA_RANGE_MIN`/`SCHEMA_RANGE_MAX` it drifted: the Story 1.2 release migrated production to generation 2 while Railway still declared `1..1`, so web refused to start against a database its own release had just migrated, and the deploy failed its healthcheck. An image ships a fixed set of migrations, so only the image knows what it supports. **A new migration must raise `SUPPORTED_SCHEMA_MAX` in the same commit**; `db/schema-range.test.ts` reads the migrations and fails when the two disagree.
- **`.railway/railway.ts` declares the intended shape; it does not apply it.** Railway variables are live state, changed in the dashboard or through the connector. Anything that must not drift between them belongs in code, not in `env:`.
- **`.railway/railway.ts` is never compiled here.** `railway` is not a workspace dependency, so no typecheck, boundary check, or test touches that file. Its only validation is `railway config plan`.

### Audit events and telemetry (added with Story 1.2)

- **The audit hash input is `previous_hash_bytes || RFC 8785 canonical JSON`, hashed once with SHA-256.** The canonical envelope has exactly eleven keys (`actor`, `aggregateId`, `correlationId`, `eventId`, `eventType`, `occurredAt`, `outcome`, `payload`, `sequence`, `sessionId`, `source`) and deliberately excludes both hashes. Never feed a caller-shaped `JSON.stringify` to the hash; `canonicalizeAuditEvent` in `packages/domain/src/audit-event.ts` is the only canonicalizer. `tests/fixtures/audit-chain-golden.json` was produced independently with Python `rfc8785` + `hashlib`; re-verify against a non-TypeScript implementation if the envelope ever changes.
- **Sequences come from a locked `audit_event_heads` row, never from a sequence object.** The append does `INSERT ... ON CONFLICT DO NOTHING` then `SELECT ... FOR UPDATE`; PostgreSQL makes the conflicting insert wait for the in-flight transaction, so two first appends to one aggregate still get 1 then 2. Events with no natural aggregate chain under `platform`.
- **Do not add `pino` or `@sentry/node` to `serverExternalPackages` in `apps/web/next.config.ts`.** They are dependencies of `@intellifin/infrastructure`, not of `apps/web`. Under pnpm's isolated `node_modules` an externalized `require` from `.next/server` cannot resolve them. Next must keep bundling them through `transpilePackages`.
- **`drizzle-kit generate` needs `DATABASE_URL` set but never connects.** Any syntactically valid URL is enough to run the CI drift check locally.
- **Next's tracing root is a filesystem path, not a URL pathname.** Use `fileURLToPath(new URL('../../', import.meta.url))`; `.pathname` leaves `%20` and a leading slash before the Windows drive letter, which caused Turbopack's path-canonicalization failure in this workspace.

### Forms and controls (added with Story 1.5)

- **Every `<form>` names its `method`, and a control that mutates state never depends on JavaScript alone.** Three times now the same defect shipped: the sign-in form had no `method`, so a submission beating hydration would have put the password in the URL; the sign-out control was an `onClick` that fetched, so a click before hydration did nothing at all and looked like success; `UserForm` then repeated the sign-in mistake with a new user's initial password. A form with no method submits as a GET, and whatever was typed lands in history, the Referer header and every access log. `apps/web/src/form-method.test.ts` scans every `.tsx` and fails on a form without one. JavaScript may enhance a control; it may never be the only path.
- **A Server Action authorizes for itself.** It is a separate POST endpoint Next exposes by id, so reaching the page that renders it is not a precondition for invoking it. The page's `requireServerAction` protects the page; each action calls it again before reading input.
- **An object lookup keyed by request input needs `Object.hasOwn`.** `ACTION_RULES['constructor']` returned `Object.prototype.constructor` and threw where a denial belonged; `SECTION_LABELS['toString']` made a function into a breadcrumb label. A plain-object index is not a map.
- **Never assert a contract against a copy of itself.** Denial strings, ribbon copy and empty-state sentences are read from the UX artifacts on disk; badge treatments are checked against the stylesheet, not the module that lists them. A test comparing a file with itself proves only that the file agrees with itself.

### Identity and roles (added with Story 1.3)

- **The role never comes from Better Auth and is never cached.** Better Auth establishes identity and session only; the role lives in the application-owned `user_role` table and `DrizzleRoleRepository.findRole` reads it on every request. A role in a cookie, a JWT claim, or an in-memory map survives its own revocation, which AD-7 forbids. `GET /api/session` is the observable proof: delete the row and the next call reports `role: null` while the session row stays.
- **Route protection is default-deny with one explicit allowlist.** `apps/web/src/route-access.ts` is the only place a path becomes public (`/sign-in`, `/api/health`, `/api/auth/**`, Next static output, root files). `apps/web/middleware.ts` is the outer gate and can only see whether a session cookie exists; the real decision is `requireAction` in `apps/web/src/require-role.ts`, which resolves the session, reads the role, applies the domain policy, and audits the refusal. Adding a route family needs no change here — it is protected already.
- **The gating table lives in `packages/domain/src/identity/roles.ts` and nowhere else.** The five denial strings are copied character-for-character from EXPERIENCE.md "Roles and Action Gating"; every unspecified cell says `Your role does not permit this action.` `roles.test.ts` checks all 24 actions x 3 roles. FR-2's "cannot approve a version they authored" is scoped to `procedure.version.approve`; rejecting one's own version stays allowed.
- **An email address cannot be an audit `actor.id`.** `SAFE_ID_PATTERN` excludes `@`. A failed sign-in for an unknown address records `actor.id: 'unknown'` with `payload.subjectHash` = SHA-256 of the lower-cased address; a known address records that user's id. The address itself never enters the chain.
- **A sign-in that cannot be audited is undone.** `apps/web/src/sign-in-route.ts` appends `security.sign-in` before returning the cookie; if the append fails it deletes the session row and answers 503. Every failed attempt is rewritten to one 401 and one sentence, so an unknown address and a wrong password are indistinguishable; a 429 keeps its status and says so, because a rate limit tells nobody whether a user exists.
- **`instrumentation.ts` must stay edge-safe.** Adding `middleware.ts` made Next compile `instrumentation.ts` for the edge runtime as well. The Node-only work lives in `apps/web/src/boot.ts` behind a dynamic import inside the `NEXT_RUNTIME === 'nodejs'` branch; a top-level import of the infrastructure barrel there pulls postgres.js, Pino and `process.exit` into the edge bundle. Next 16 also warns that the `middleware` file convention is deprecated in favour of `proxy`; the spec names `middleware.ts`, so it stays until a story moves it.
- **`apps/web` uses extensionless relative imports.** Its tsconfig is `moduleResolution: bundler`; a `./telemetry.js` specifier typechecks but fails `next build` with "Module not found".
- **Users are created by `pnpm seed:identity` only.** Better Auth has `disableSignUp: true`, so the running application has no sign-up endpoint at all; `createSeedAuth` is the one instance that can create a user and only the operator script constructs it. The password comes from `SEED_PASSWORD` in the environment, never from an argument.
- **`next.config.ts` sets `agentRules: false`.** Without it `next dev` writes its own `AGENTS.md` and `CLAUDE.md` into `apps/web`; this repository already owns both names for the agent block and this decision log.
- **A production web build refuses a plain-http `BETTER_AUTH_URL`.** Better Auth marks the session cookie `Secure` only for an https origin, so `loadConfig` rejects http when `NODE_ENV` is production — which Next's standalone server sets for itself. `http://localhost` works under `pnpm dev` only; the CI smoke container passes a placeholder `https://` origin it never has to resolve.
- **Sign-in rate limiting is declared explicitly and stored in PostgreSQL.** Better Auth's default limiter is off outside production and counts in process memory; `/api/auth/**` is the only publicly allowlisted surface and the deployment can run more than one container, so `auth_rate_limit` (generation 3) holds the counters and the rules are stated in `identity/auth.ts`.
- **The middleware matcher is `/(.*)` and decides nothing.** A negative lookahead there is a second allowlist in another language that nothing tests, and it fails exactly as a slash-less prefix does — `(?!_next/image)` also skips `/_next/imagery`. `isPublicPath` is the only allowlist.
- **The root `package.json` links `@intellifin/domain` and `@intellifin/infrastructure` as devDependencies.** Without them `scripts/*.mts` cannot resolve the workspace packages under pnpm's isolated `node_modules`.

### Application shell and Ledger Signal tokens (added with Story 1.4)

- **The design system is built here, under the parent's names.** DESIGN.md inherits the IntelliFin Design System bundle, which lives in the Business Suite repository and is not in this one, so it restates every token value it needs. `apps/web/src/design/` therefore implements Sidebar, Button, StatusBadge, Banner, EnvironmentRibbon, EmptyState, Tabs and Icon locally under exactly those names, which keeps a later swap to the real bundle an import change rather than a rewrite.
- **`ux-designs/.../DESIGN.md` is the token source; `ux-designs/.../claude/DESIGN.md` is superseded.** The `claude/` copy is the pre-revision-2 prototype contract — four state families, no `info-solid`, two dialog weights, two breakpoints. Never read it as a contract. Between the two live spines, behaviour and copy follow EXPERIENCE.md and visual values follow DESIGN.md; both beat the prototype mockup.
- **Token values live in `apps/web/app/tokens.css` and nowhere else.** Names are mechanical: `colors.<k>` → `--color-<k>`, `typography.<role>.<prop>` → `--type-<role>-<kebab>`, `rounded.<k>` → `--rounded-<k>`, `spacing.<k>` → `--spacing-<k>`. `src/design/tokens.test.ts` parses DESIGN.md's frontmatter and this file and fails on any drift; it also fails if `globals.css` restates a documented hex instead of referencing the token.
- **The status vocabulary is data, not markup.** `src/design/status.ts` holds all nine DESIGN.md rows; `StatusBadge` takes only a family and a state and derives the word, treatment and icon, so a badge without an icon or with an unknown state cannot be written. `status.test.ts` reads the markdown table off disk, so a transcription error fails rather than looking plausible.
- **Hiding a nav item is presentation; it is never the control.** The sidebar removes Administration for non-administrators via `authorizeAction`, and `app/administration/page.tsx` independently calls `requireAction` — the first production caller of the audited authorization path. Adding a privileged surface means adding the server-side call, not only hiding the link.
- **Server components reach the session through `apps/web/src/server-session.ts`.** `require-role.ts` takes a `Request` and must stay free of `next/headers` so its unit tests run under plain Node; `server-session.ts` builds a `Request` from the incoming headers and delegates. One decision path, two entry points.
- **A disabled action is `aria-disabled`, not `disabled`.** A `disabled` element cannot be focused, so its accessible description is unreachable by keyboard — which turns the required reason into the tooltip-only explanation DESIGN.md forbids. `Button` refuses activation in its handler instead, and `UnavailableActions` renders the same sentence visibly, sharing one DOM node through `disabledReasonId`.
- **The focus ring is declared once, in `globals.css`, and components have no stylesheet to suppress it in.** It is `#0F766E` everywhere, and the rule sets outline and offset only — a `border-radius` there changes every control's corner shape on focus. Inside the navy sidebar the offset is 0 and a 4px white shadow sits BEHIND the outline, so white shows at 2-4px, outside the ring: with the default 2px offset the ring is drawn at 2-4px and a white band at 0-2px sits between element and ring, leaving the ring's outer edge against navy at 2.7:1. For the same contrast reason the active nav marker on that one dark surface is `--color-teal-500`, not `--color-teal`.
- **Playwright runs `next dev`, never a production build.** A production build sets `NODE_ENV=production`, where `loadConfig` refuses the plain-http `BETTER_AUTH_URL` the suite serves on. Run `pnpm build` first: the dev server and `pnpm seed:identity` both resolve workspace packages through their `dist` output.
- **`pnpm test:e2e` needs a migrated PostgreSQL 18 and the two seeded accounts.** `E2E_AUDITOR_EMAIL`, `E2E_ADMIN_EMAIL` and `E2E_PASSWORD` name them; CI's `e2e` job migrates, seeds and installs Chromium before running. A WCAG 2.1 AA violation fails the pull request and there is no allowlist of accepted violations.
- **`text-muted` is for `surface-card` and `surface-page` only.** DESIGN.md scopes it, and the arithmetic agrees: on `surface-sunken` it is 4.39:1, under AA. An `aria-disabled` control is live text, so the disabled button writes in `text-secondary` (6.9:1).
- **`/badges` is unlinked on purpose.** It renders every badge in the vocabulary plus one live instance of each component, so axe has something to scan and the dialog specs have a dialog to open. It is protected by default-deny like every other route, and everything on it below the vocabulary is labelled illustrative.
- **Any object lookup keyed by request input needs `Object.hasOwn`.** A plain `MAP[key]` inherits from `Object.prototype`, so `key = 'toString'` or `'constructor'` returns a function and the code carries on with it. This has now bitten three times: `ACTION_RULES[action]` in the gating policy (Story 1.3), and `SECTION_LABELS[segment]` in the breadcrumbs (Story 1.4, where the segment comes straight from the URL bar). Guard the lookup, or use a `Map`.
- **`decodeURIComponent` throws on a malformed escape.** `/runs/%E0%A4%A` is a URL anybody can type; unguarded, the URIError takes down every page under the shell. Wrap it and fall back to the raw text — `readableSegment` in `apps/web/src/shell/breadcrumb-rules.ts`.
- **Copy quoted from the UX contract lives in `apps/web/src/design/copy.ts`.** A sentence typed inline in a component is pinned against nothing: the component and its test get retyped together and both drift from DESIGN.md. `copy.test.ts` reads DESIGN.md and EXPERIENCE.md off disk and requires each string character for character, the way `tests/unit/denial-strings.test.ts` does for the refusal strings.
- **A variant name needs a rule that paints it.** `status.test.ts` proves the vocabulary matches the contract and `tokens.test.ts` proves the values do; neither notices a missing class. Delete `.ls-badge--danger-outline` and four states render as plain text with the suite green. `stylesheet.test.ts` reads `globals.css` and requires a rule for every badge treatment, banner tone, button variant and shell class.
- **`aria-disabled`, never `disabled`, on an action with a reason.** A `disabled` element cannot be focused, so its `aria-describedby` reason is unreachable by keyboard — the tooltip-only explanation DESIGN.md forbids. `Button` refuses activation in its handler; `shell.spec.ts` clicks one to prove it.
- **`aria-modal` stops nothing on its own.** `ConfirmDialog` portals to `<body>`, sets `inert` on `#ls-app`, locks body scroll, and binds its key handler to `document` — a handler on the scrim element stops firing the moment a backdrop click moves focus to `<body>`, which silently breaks Escape.
- **Playwright specs sign in twice, in `auth.setup.ts`, and reuse the state.** `/sign-in/email` is rate limited to ten attempts a minute and the limiter is real production behaviour; a suite that signs in per test spends the budget and then fails on its own load. `E2E_PASSWORD` has no default, deliberately.
- **The suite must use `localhost`, never `127.0.0.1`.** Next's dev server blocks cross-origin requests to its own dev resources and does not treat the two spellings as one host: the browser is refused `/_next/hmr`, the client runtime never boots, and every page renders server-side only with no button working.
- **`pnpm -r typecheck` skips the workspace root.** `playwright.config.ts`, `scripts/` and everything under `tests/` live there, so the root `pnpm typecheck` script runs `tsc -p tsconfig.root-tests.json` after it, and CI calls the root script. That config was `tsconfig.e2e.json` and covered `tests/e2e/` alone, so `tests/unit/` and `tests/integration/` were typechecked by nothing at all — the root also has to link every workspace package those suites import, or the import resolves to nothing and the file is silently unchecked.

### Managing users and roles (added with Story 1.5)

- **A Server Action needs its own authorization check.** Next exposes each Server Action as its own POST endpoint addressed by an id that appears in the client bundle, so reaching the page it was written beside is not a precondition for invoking it. `app/administration/page.tsx` protects the page and nothing else; `app/administration/actions.ts` calls `requireServerAction` FIRST, before it reads any input, and `actions.test.ts` asserts the refusal against the action rather than the page. A validate-then-authorize action also tells a caller who may not act what the input contract is.
- **A user is created by an audited command, never by a public endpoint.** `disableSignUp: true` stays on the mounted Better Auth instance; `createSeedAuth` is the only instance that can create an account, and `BetterAuthUserCreator` builds it server-side behind `administration.users.manage`. `tests/integration/manage-users.test.ts` re-asserts that the mounted handler still refuses `POST /api/auth/sign-up/email`, because the seed instance is what every other test constructs.
- **Better Auth 1.7.2 answers a duplicate-address sign-up with a fabricated user.** No row is written, no error is raised, and `created.user.id` is a fresh id that exists nowhere — deliberate user-enumeration protection on a public endpoint, and a trap for an administrative one. `BetterAuthUserCreator` therefore checks the address before and re-reads the returned id after, and only a row that is really there counts as created. Never trust `signUpEmail`'s answer on its own.
- **A state change and its audit event share one transaction, through `PostgresIdentityUnitOfWork`.** It hands the command an `IdentityUnitOfWorkContext` in which the audit appender, `DrizzleRoleWriter`, `BetterAuthUserCreator` and `DrizzleSessionWriter` are all bound to the same handle, so there is no reachable writer outside the transaction. Better Auth joins it because the Drizzle adapter uses whatever handle it is given: `createSeedAuth(tx as unknown as Database, config)` puts the account rows inside the transaction and a rollback removes them.
- **A refusal returned from inside a unit of work COMMITS.** Everything written before it survives. `manage-users.ts` throws a private `CommandRefused` instead and converts it to a refusal outside the callback — the only way to say "this did not happen" to PostgreSQL as well as to the caller.
- **The prior role an event records is read inside the write's transaction.** A read through the pool can be answered by a snapshot the write is about to invalidate, so the chain would name a transition that never happened. `RoleWriter` carries `findRole` for exactly this.
- **Role events carry both `priorRole` and `newRole`, and `null` is a value.** A first assignment records `priorRole: null`; a revocation records `newRole: null`. The subject is a user id — an email address cannot enter the chain, and `SAFE_ID_PATTERN` has no `@`.
- **`user_role.assigned_by` is a real foreign key from generation 4, `ON DELETE SET NULL`.** `CASCADE` there would delete a role when the administrator who granted it is deleted, which is a silent privilege revocation nothing audited.
- **`DataTable`'s first-cell `href` is optional.** EXPERIENCE.md's rule is "every row's first cell is a link; no row-level click handlers", and its purpose is that a row must never be a click target a keyboard cannot reach. A table with no detail surface — the user list — satisfies it by having no target; inventing an `href` to a page that does not exist would satisfy the letter and send people to a 404. The structural guarantee is unchanged: there is no `onRowClick` prop.
- **One surface, one Banner.** `UsersPanel` owns the banner and both controls report into it. A banner per control is several live regions racing to announce the same kind of thing.
- **Sign-out revokes the session row itself, in the audit transaction.** Better Auth's own `/sign-out` commits on its own connection, so it cannot be atomic with the event. `apps/web/src/sign-out-route.ts` intercepts `POST /api/auth/sign-out`, runs `signOut` through the identity unit of work, and clears the cookies itself. If the event cannot be appended the session stays live and the caller gets a 503 — the only fail-closed direction a sign-out has.
- **A control that ends a session or mutates state must not depend on hydration.** Sign-out shipped first as a `fetch` inside an `onClick`: a click before React hydrated was swallowed — no request, no navigation, no message — so a person at a shared workstation walked away believing the session ended, and the browser test caught it only when it happened to click inside that window. It is now a real `<form method="post" action="/api/auth/sign-out">` the browser submits itself, answering a **303** to `/sign-in`; the route is idempotent, so a double submit, a resubmitted form or a second tab meets the same redirect rather than a 500. The remaining JavaScript is a double-submit guard that never prevents the first submission. `tests/e2e/administration.spec.ts` runs the journey in a context with `javaScriptEnabled: false` — the assertion that fails every time rather than sometimes.
- **A `<form>` with no `method` submits as a GET.** Any credential in it then lands in the URL, in browser history and in every access log. `sign-in-form.tsx` and `admin/UserForm.tsx` both carry `method="post"` for exactly this, even though both prevent the native submission once hydrated: the guard is for the submission that beats hydration. A POST to a page route has no handler and answers 405, which discloses nothing.
- **Sign-in and the administration mutations still require JavaScript, deliberately.** Both fail SAFE and visibly — a sign-in that does nothing leaves you on the sign-in page, and an administration mutation that does nothing shows no Banner and no changed row — which is the opposite of the sign-out defect, where nothing happening looked like success. The administration controls cannot be made to work without script at all: EXPERIENCE.md requires a focus-trapping confirmation dialog on every administration mutation. Sign-in could be made to work server-side and is worth a later story; it would mean a POST route reproducing the non-disclosure and rate-limit rules `handleAuthRequest` owns.
- **`auth.setup.ts` clears `auth_rate_limit` before the browser suite runs.** `/sign-in/email` allows ten attempts a minute and a full run spends six. CI gets a fresh database each time, but two local runs inside a minute make the second inherit the first's budget and fail on a real production rule — which reads as flakiness and is not. The limiter stays fully enabled during the run and `sign-in.spec.ts` still exercises it; only the spend carried between runs is removed.
- **Telemetry messages are an allowlist.** `TELEMETRY_MESSAGES` in `packages/infrastructure/src/telemetry/sentry.ts` is a closed union; a new `telemetry.info`/`captureError` message must be added there or it will not typecheck.
- **The unit suite now includes `apps/**/app/**/*.test.ts`.** Route handlers and Server Actions live under `app/`, not `src/`, and each is its own endpoint.

### Story 1.5 review findings (applied 2026-09-02)

- **A surface that grants roles must not be able to remove the last holder of one.** `setUserRole` refuses a self-role-change, and refuses any change that would leave zero `poc-administrator` rows. Both are enforced in the command; the disabled buttons are courtesy. The count is taken INSIDE the transaction and AFTER the write, behind a `SELECT ... FOR UPDATE` over the holders taken BEFORE it — because under READ COMMITTED two administrators demoting each other each see their own uncommitted write and count one remaining, and both commit into a deployment nobody can administer. Recovery would be shell access and `pnpm seed:identity`.
- **A lock that serializes must be taken in a deterministic order.** `DrizzleRoleWriter.lockHolders` orders by `user_id`; two callers locking the same set in different orders deadlock instead of queueing.
- **A concurrency test that starts two calls at once proves nothing.** They finish quickly enough that one commits before the other reads, and the test passes with the guard removed. `tests/integration/manage-users.test.ts` wraps the unit of work so the first transaction is held OPEN after its work and before its commit, and runs the second inside that window. Verified by removing the lock and watching it fail.
- **Never build a redirect `Location` from `request.url` or `request.nextUrl`.** Behind a proxy the host comes from the client's `Host` header, so a forged one redirects the browser to an attacker's origin — worst of all on the sign-out and sign-in-redirect paths, where the person arrives looking for somewhere to type a password. A relative `Location` is valid (RFC 9110 §10.2.2) and browsers resolve it against the origin they connected to. `middleware.ts` therefore does not use `NextResponse.redirect`, which requires an absolute URL.
- **`/api/auth/**` is an allowlist of three endpoints.** Better Auth mounts many more, and probing the real handler found `revoke-session`, `revoke-sessions`, `revoke-other-sessions`, `update-user`, `change-password`, `change-email`, `delete-user` and `reset-password` all live on the one publicly allowlisted path family, none audited — each ending a session or changing an identity with nothing in the chain. `SERVED_AUTH_ENDPOINTS` in `apps/web/src/sign-in-route.ts` names `sign-in/email`, `sign-out` and `get-session`; everything else answers 404 before the runtime is touched. An allowlist, not a denylist, so a dependency upgrade cannot mount a new endpoint into production unnoticed.
- **A Server Action's argument is untrusted, whatever its TypeScript type says.** `CreateUserFields` is a comment as far as a hand-made POST is concerned: `null`, a number or a missing field reaches `.trim()` and answers a framework 500 to the caller most likely to be probing. `actions.ts` checks shape and bounds length at the boundary — email 254, name 200, password 128, the last because scrypt cost is paid by this process and an unbounded password is unbounded cost bought with one request.
- **A refusal returned from inside a unit of work commits; a refusal thrown rolls back.** Already true of `CommandRefused`; the last-administrator and stale-role guards use the same mechanism because both fire after a write.
- **`Object.hasOwn` for any lookup keyed by request input — fourth occurrence.** `roles.ts` `roleLabelOfValue` took a `<select>` value straight into `ROLE_LABELS[...]`, where `'constructor'` returns an inherited function instead of the fallback. Previous three: `ACTION_RULES`, `SECTION_LABELS`, `ICON_GLYPHS`.
- **A guard needs its own tests, and mutation testing is how you get them.** `form-method.test.ts` asserted `/\bmethod=/`, so `method="get"` passed — the exact defect it existed to prevent — and its `<form\b[^>]*>` pattern truncated at the `=>` of a JSX handler. It now requires `post`, parses the tag brace- and quote-aware, scans `.ts` as well as `.tsx` (a route handler can emit raw HTML, and `sign-out-route.ts` does), and wraps `statSync` so a broken symlink cannot fail the suite.
- **Never assert a response equals the function that produced it.** `sign-out-route.test.ts` compared its cookies with `clearedSessionCookies()`, which proves only that the function was called. The attributes are checked one by one, `Path=/` included: `Path=/api/auth` would leave the session cookie in place on every page with every other assertion green.
- **Better Auth's session-cookie check comes before the database.** `handleSignOut` answers a caller with no session cookie from memory. `/api/auth/**` is publicly allowlisted and this handler intercepts before Better Auth's rate limiter sees the path, so sign-out is not rate limited; without the check every anonymous POST would cost a connection. An authenticated flood limits itself, because the first call deletes the session.
- **Do the risky work inside the route's own `try`.** `handleSignOut` acquired the runtime and resolved the session outside it, so a database outage threw through the route and the caller got a framework 500 instead of the fail-closed page written for that case.
- **The integration suite creates session rows directly instead of signing in.** `/sign-in/email` allows ten attempts a minute and that limiter is real production behaviour stored in PostgreSQL; six sign-ins from one file plus eight from another exceed it and the second file fails on a limiter doing its job. Only the one case that needs a signed Better Auth cookie signs in. Files clean up their own rows — scoped by an address prefix and a correlation-id prefix — and never `DELETE FROM audit_events` wholesale, which would leave `audit_event_heads` pointing past the rows that remain.
- **A test that writes to a database must refuse a database it does not recognize.** `assertThrowawayDatabase` in `tests/e2e/accounts.ts` allows loopback, a container hostname or CI; anything else refuses rather than wiping a real deployment's rate-limit counters.
- **The administrator sets every initial password, and nothing forces a change — an accepted risk.** There are no invite emails and no reset flow because this deployment sends no mail, so a PoC Administrator holds a working credential for every account they create. "PoC Administrator cannot author Procedures" is therefore a policy boundary, not a cryptographic one. Recorded in the spec's Design Notes rather than solved: a forced first-sign-in change needs a password-change command, its own event, and a gate on every surface. What is guaranteed is narrower — the password is never stored, logged, audited, echoed or placed in a URL, and the field is cleared as soon as it is used.
- **Better Auth's `signUpEmail` is not a constraint, and neither is a pre-check.** Generation 4 adds `auth_user_email_lower_uidx` on `lower(email)`, because the column's own unique index is case-sensitive and two concurrent creates of `Dana@x` and `dana@x` both pass any check. `BetterAuthUserCreator` maps SQLSTATE 23505 anywhere in the error's `cause` chain to the same "already has an account" refusal.
- **Build a privileged object only where it is used.** `PostgresIdentityUnitOfWork` constructed `createSeedAuth` — the one sign-up-capable instance — on every identity transaction, including every sign-out and every `security.denied` append. It is built lazily, only when a command actually creates a user.
- **A migration that adds a foreign key validates every existing row.** One non-matching value fails the whole migration and with it the release, so generation 4 runs a `UPDATE ... SET assigned_by = NULL WHERE ... NOT IN (SELECT id FROM auth_user)` first. It clears nothing today; it is there so data written before the column had a meaning cannot stop a release.
- **A branch nothing exercises is a branch that can be inverted silently.** `DataTable`'s first cell became a link-or-text ternary for the user list; `shell.spec.ts` now asserts the link arm on `/badges`, or inverting the ternary would turn every first cell in the product into plain text with a green suite.
- **One Banner, cleared on the next mutation and keyed by a counter.** A stale success sitting through the next attempt describes a change that is no longer in front of the person, and a live region whose text does not change is not re-announced — so two identical failures would be silent after the first. `sign-in-form.tsx` uses the same attempt counter for the same reason.
- **A glob that cannot match is a promise of coverage that does not exist.** `vitest.config.ts` briefly included `apps/**/app/**/*.test.tsx` in a `node` environment with no DOM and no such file.

### Target System registrations (added with Story 1.6)

- **There is one RFC 8785 canonicalizer, and it is `packages/domain/src/canonical-json.ts`.** `canonicalJson` was private inside `audit-event.ts` until the registration digest needed the same bytes. Both digests import it. Two copies would agree on every value anybody thought to try and diverge on the first one nobody did — an escaped lone surrogate, a `-0`, an integer past 2^53 — and each would look correct because each would be checked only against itself.
- **`packages/domain/src/registrations/target-system.ts` is the only place the registration digest is computed (AD-2).** SHA-256 over the RFC 8785 canonical JSON of exactly six keys: `allowed_origins`, `attribute_label_patterns`, `credential_ref`, `kind`, `permitted_actions`, `secondary_key`. A `desktop` system's application identity occupies the `allowed_origins` slot, so the key set is the same for every kind. The projection is written key by key, never a spread: a spread would put the display name, the note and the id into a value a Procedure Version freezes. Nothing recomputes it on read — the adapter stores and returns the number the domain module produced.
- **Origins, label patterns and permitted actions are sets, not lists.** They are trimmed, deduplicated and sorted (UTF-16 code unit, which is what `Array.prototype.sort` does) before hashing, so retyping the same two origins in the other order does not move a digest and mint a platform-authored draft for every Procedure that references it.
- **`packages/domain` hand-rolls SHA-256 and UTF-8 (`sha256.ts`) because it has no `@types/node`.** That absence is the compiler-enforced half of AD-11 — `process.env` does not typecheck there — so `node:crypto` is unreachable and adding the types to get it would trade an invariant for a convenience. It is checked against two implementations that are not it: the Python-produced fixture, and `tests/unit/sha256.test.ts` against `node:crypto` at the block-boundary lengths (55, 56, 63, 64, 119, 120) where a padding mistake hides. `utf8Bytes` REFUSES a lone surrogate rather than substituting U+FFFD as `TextEncoder` does, because that substitution would make two different inputs hash the same.
- **`tests/fixtures/registration-digest-golden.json` is produced by `uv run scripts/make-registration-digest-golden.py`, not by TypeScript.** Python `rfc8785` + `hashlib`, the same precedent as `audit-chain-golden.json`. Its envelopes are written out by hand in the generator, so the projection is checked as well as the hash. The unit test asserts `producer` starts with `Python` — a fixture regenerated from the code under test would prove only that it equals itself.
- **A credential that cannot be proven read-only is refused exactly like one that reports write access**, with the verbatim `Audit credentials must be read-only.`, and the attempt is audited as `configuration.registration-refused`. A provider that throws is treated as `unknown` too: otherwise "the check was unavailable" becomes a path on which an unproven credential is stored.
- **The read-only refusal event is appended in its OWN unit of work, before the write transaction opens.** It must commit while nothing is stored, and those are opposite requirements for one transaction.
- **`CredentialCapabilityReport` has exactly two fields.** A reference and a verdict — there is nowhere a secret could travel, so no response, log or audit payload downstream can carry one by accident. The credential reference is deliberately absent from every audit payload as well: the chain is immutable, so anything credential-shaped that enters it can never be taken out.
- **`CREDENTIAL_CAPABILITIES` is a declaration, not a probe.** A JSON object mapping an opaque reference to `read-only` or `write-capable`, validated at boot. An absent value is an empty manifest, which refuses every registration rather than accepting every one. Reading the capability out of the reference's spelling would make the guarantee a naming convention anybody can satisfy by typing.
- **`configuration.registration-changed` (`RegistrationChanged`) is published only when one of the six moves; every other change is `configuration.registration-annotated`.** Epic 2 turns `RegistrationChanged` into a platform-authored draft, so a rename must not produce one. But the spec's first wording — a non-digest change "publishes nothing" — meant a rename, and worse a RETIREMENT, wrote a row with nothing at all in the chain, which FR-45 forbids. Two event types keep both properties: `registration-annotated` records the change and Epic 2 does not read it. A save that moves one of the six AND a display name carries both halves in the one event (`changedFields`, `annotatedFields`). A save that moves nothing appends nothing. The command asserts the converse too — if the digest moved with no field changed, it throws rather than committing.
- **`array_length(x, 1)` of an empty array is NULL, and a CHECK that evaluates to NULL PASSES.** `target_system_registration_actions_present` uses `cardinality`. Written the obvious way, the constraint accepted exactly the row it existed to refuse; the integration suite's raw-SQL insert is what caught it.
- **Generation 5's CHECK constraints are the layer nothing can route around.** `permitted_actions <@ ARRAY[...]` means no command, migration or psql session can store a write action; `digest ~ '^[0-9a-f]{64}$'` refuses anything that is not a digest. They are asserted with raw SQL in `tests/integration/registrations.test.ts`, because a constraint tested through the command proves nothing about the constraint.
- **The probe module is unreachable from `apps/` and that is a build failure, not a convention.** `packages/infrastructure/src/registrations/probe.ts` is outside every barrel, has its own `@intellifin/infrastructure/probe` subpath, and `no-target-system-probe-in-apps` fails `pnpm boundaries` on any import of it from `apps/` — the web because AD-10 forbids it an outbound call, the worker because Story 1.8 runs it as its own entry point the way the release migrator is invoked. `tests/unit/boundaries.test.ts` plants both violations. **A new subpath export needs a matching alias in `vitest.config.ts` AND `tests/integration/vitest.config.ts`**, or the import resolves to an unbuilt `dist`.
- **The connectivity column reads rows the worker writes and says "Never probed" in words.** A dash or an empty cell is something a reader takes for "fine". `target_system_probe` holds one row per registration — the present, not a history.
- **A registration is never deleted; retirement is a status.** A Run that froze a digest must still be able to resolve it.

### Story 1.6 review findings (applied 2026-09-02)

- **`JSON.stringify` escapes a lone surrogate, so a guard downstream of it can never fire.** `utf8Bytes` in `sha256.ts` refuses one and this file used to record that as the protection; on the registration path it was unreachable, because `canonicalJson` serialises strings with `JSON.stringify` first. What it cost was a row that permanently disagreed with its own digest: the digest covered the escaped form, while the driver encoded the same string for the wire with U+FFFD substitution and PostgreSQL stored that. **`canonicalJson` is now the refusal point** — for an unpaired surrogate and for a non-finite number, both of which Python `rfc8785` also refuses — and `validateRegistrationFields` turns the throw into a sentence, because it arrives through a Server Action anybody with the role can post to. A serializer that substitutes is the same defect as an encoder that substitutes.
- **What is hashed and what is stored must be the same value.** Origins and label patterns were stored trimmed but not deduplicated, while the digest hashed the deduplicated set. Removing a duplicated origin then changed the column without moving the digest, and the command published `RegistrationChanged` with `priorDigest === newDigest` — an immutable event asserting a transition that did not happen, from which Epic 2 mints a platform-authored draft for every Procedure Version. The command asserts BOTH directions now: six changed with no digest movement, and digest movement with none of the six changed.
- **An optimistic-concurrency token must cover every field the write replaces.** It was the digest, which covers six of the row's ten fields — so `displayName`, `note` and `status` were exactly the fields it could not protect. One administrator retires a registration (the digest does not move), a second saves a note from a tab opened before that, the guard passes, and the write silently sets `status` back to `active`. `registrationRowVersion` hashes all ten. Not `updated_at`: `now()` is a transaction timestamp and two concurrent transactions are not guaranteed to disagree about it.
- **A dependency-cruiser `exclude` disables every rule for the excluded path — including `dist`.** Both probe and migrator rules match `(src|dist)`, and the `dist` half was dead because built output sat in `exclude`, so an import spelled at `packages/infrastructure/dist/...` passed with a `no-orphans` warning as the only trace. Built output is now in `doNotFollow`, which keeps it in the graph. **The rule is broader than "never exclude `node_modules`": never `exclude` anything a rule's `to.path` mentions.** `tests/unit/boundaries.test.ts` plants the `dist` spelling for both rules, guarded on the file existing so a fresh clone skips rather than passes.
- **A port with no host types cannot own a timeout.** `packages/application` has no `setTimeout` — that absence is what stops `process.env` typechecking there (AD-11) — so the deadline on the credential capability check is a required `DeadlinePort` dependency: the command owns the policy, `TimerDeadline` in infrastructure owns the mechanism, and an implementer cannot leave it out.
- **A structural type does not contain anything.** `CredentialCapabilityReport` has two fields, but TypeScript's excess-property check fires only on a fresh literal assigned directly to an annotated type; a class declared `implements CredentialProvider` with an inferred return type can return a `secret` and compile. The containment is the CALL SITE destructuring the two fields it needs and never holding the report. The test that claimed otherwise built a two-key object and asserted it had two keys — a contract compared with a copy of itself. It is now a hostile provider that returns a secret anyway.
- **An answer about a different reference proves nothing.** The provider echoes the reference it was asked about and the command compares it. A real service that batches, caches by a normalized key or resolves an alias can otherwise prove a write-capable credential read-only.
- **An existence check in a separate statement prevents nothing.** `recordProbe` did `SELECT` then `INSERT`, which under a pool is not even one connection, so the row could vanish in between and raise the foreign-key error the check existed to prevent. One `INSERT ... SELECT ... WHERE EXISTS`. A raw statement has no column type to infer from, so the timestamp is sent as ISO text with an explicit `::timestamptz`.
- **`tests/unit/` and `tests/integration/` were outside every tsconfig.** `pnpm -r typecheck` covers workspace packages only, and the root's second half covered `tests/e2e/` alone. The config is now `tsconfig.root-tests.json` and covers `scripts/`, `tests/e2e/`, `tests/integration/` and `tests/unit/` — and the root has to link every workspace package those suites import, or an import resolves to nothing and the file is silently unchecked. Widening it caught four real errors immediately.
- **The constraint whose obvious spelling is wrong is the one that must be pinned.** `schema.test.ts` pinned the read-only and digest CHECKs to the migration and not the `cardinality` one — backwards, since that is where an edit that looks like a tidy-up silently removes the rule. The negative assertion strips comment lines first: the migration's own header names `array_length` to explain why it is not used.
- **A browser assertion against a page rendered before the action cannot fail.** "Nothing was stored" checked a table the server sent before the click. Every such assertion now reloads first — and a reload clears the form as well as the table, so what follows re-fills it. Likewise `'recorded in the audit chain'` matched both the published and the annotated message, so the origin-change test passed with the event never published; it asserts the sentence unique to the published path.
- **A `var(--x)` naming nothing falls back silently.** `.ls-definition dt` read `--font-size-sm`, defined nowhere, and lived on its fallback — the rule looked token-driven and was not. `stylesheet.test.ts` now requires every custom property `globals.css` reads to be defined in `tokens.css` or in `globals.css` itself.
- **A 64-character digest read aloud is unusable.** The visible text stays the full value, because that is what an auditor compares; `spokenDigest` supplies the `aria-label` — first four and last four characters, spaced — which is enough to tell two digests apart by ear.
- **`Object.hasOwn` for any lookup keyed by request input — fifth occurrence, and this time the guards got their own test.** `registrations.ts` had all four guards and nothing exercised them; inverting one now fails four cases.
- **Never `git add -A` while a reviewer subagent is planting and reverting violations.** One review's deliberate AD-10 plant was swept into a commit and pushed, and CI caught it. Stage explicit paths, or commit before the reviewers start.

### Population Source bindings (added with Story 1.7)

- **The binding digest is SHA-256 over the RFC 8785 canonical JSON of exactly `{declared_count_mechanism, declared_schema, kind, location, sensitive_fields}`**, computed by `packages/domain/src/sources/population-source.ts` and nowhere else. It uses the shared `canonical-json.ts` — the same one the audit chain and the registration digest use — and its vector, `tests/fixtures/binding-digest-golden.json`, is produced by `uv run scripts/make-binding-digest-golden.py` with Python `rfc8785` + `hashlib`, envelopes written out by hand. `tests/unit/binding-digest.test.ts` asserts `producer` starts with `Python`; a fixture regenerated from the code under test would prove only that it equals itself.
- **AD-2 names the registration digest and NOT this one.** The spine fixes the six-key registration envelope by name; for the Population Source it says only that approval freezes the binding. Story 1.7 therefore extends the mechanism by analogy — one domain function, an explicit key-by-key projection, an independently produced vector — and says so here so that a later story reconciles the two deliberately instead of discovering a second, differently shaped freezing mechanism by accident.
- **`declared_schema` is an ORDERED list; `sensitive_fields` is a SET.** They are the two opposite normalization rules in one envelope, and each has a golden vector that fails if they are swapped. A schema declares field POSITIONS — `[account, amount]` is not `[amount, account]`, and a parser told the second reads the wrong column — so reordering it moves the digest. Masking asks only whether a field is in the group, so reordering that does not, and a digest that moved would mint a platform-authored draft over nothing. Both are trimmed, blank-free and deduplicated; only the set is sorted.

The command refuses it and the database refuses it, and `tests/integration/sources.test.ts` asserts the constraint with raw SQL — a constraint tested through the command proves nothing about the constraint.
- **`cardinality`, never `array_length(x, 1)` — second occurrence.** `population_source_binding_schema_present` would otherwise accept exactly the row it forbids, because `array_length` of an empty array is NULL and a NULL CHECK PASSES.

The warning is EXPERIENCE.md's sentence — `DECLARED_COUNT_MISSING_SENTENCE` in `apps/web/src/design/copy.ts`, checked against the artifact on disk — and it appears on the form as the mechanism is chosen and in the list's Declared-count column. - **`bindingRowVersion` covers all nine stored fields and NOT the derived digest.** Same lesson as `registrationRowVersion`: the display name, the note and the status sit outside the digest, so they are exactly the fields a digest-shaped token cannot protect — a stale tab would silently un-retire a binding. The digest is omitted because it is derived from five of the nine, so including it adds nothing and re-couples the token to the digest function.

- **A stale-row test that starts two changes at once proves nothing.** They finish quickly enough that one commits before the other reads, and the test passes with `SELECT ... FOR UPDATE` removed. `tests/integration/sources.test.ts` holds the first transaction OPEN after its work and before its commit, and runs the second inside that window — the same shape `manage-users.test.ts` uses.

### Story 1.7 review findings (applied 2026-09-02)

- **`aria-label` on a `<span>` or a `<dd>` is never applied.** ARIA prohibits an accessible name on a generic element, so both digests' labels were silently dropped and the accessible name stayed the sixty-four hex characters — the exact thing the label was added to prevent. axe reports `aria-prohibited-attr` as **incomplete**, not as a violation, and the browser gate asserts only `results.violations`, so the accessibility check could not see it. `apps/web/src/design/Digest.tsx` is now the one way a digest is rendered: the full value with `aria-hidden`, beside a `.ls-visually-hidden` sentence. No ARIA role, so no role rule can drop it, and `Digest.test.ts` scans every `.tsx` under `apps/web` and refuses `aria-label` on any element that cannot carry one.
- **A NUL is valid JSON and unstorable.** `U+0000` canonicalizes and hashes cleanly, then PostgreSQL raises `22021 invalid byte sequence for encoding "UTF8": 0x00` at the driver and the caller meets a framework 500. `canonicalJson` refuses it, next to the lone-surrogate refusal, because a value with no storable form has no canonical form.
- **`cardinality(x) >= 1` counts ELEMENTS, not names.** `ARRAY[NULL]` and `ARRAY['']` both satisfy it, and a NULL element then leaves the repository typed `string[]`. The NULL test that works is `array_position(x, NULL) IS NULL`: `NULL <> ALL(x)` returns NULL, and a NULL CHECK PASSES — the same trap `array_length` sets, one operator along. `<@` is NULL for the same reason when its left array holds a NULL.
- **`SUPPORTED_SCHEMA_MIN` must be a range the build can actually serve, so it equals `SUPPORTED_SCHEMA_MAX`.** It read `1`, which claimed a generation-6 image could serve a generation-1 database; every generation since has added a table the build queries unconditionally, so the image passed the AD-15 guard and then failed per request on a missing relation. A range wider than the truth turns a startup guard into a delayed crash. The cost — a rollback to an older image refuses to start against a newer database — is the direction a fail-closed guard should fail.
- **A malformed id is absence, not a 500, and the guard belongs in the repository.** PostgreSQL raises `22P02` comparing a `uuid` column against text that is not one, and that id comes from a URL segment. `isUuidText` in `packages/infrastructure/src/db/identifier.ts` is checked by every lookup-by-id, because a guard each page must remember is one the next page forgets.
- **A save that changes nothing writes nothing.** The UPDATE was unconditional, so an idle submit moved `updated_at` and left a row whose "Last changed" said somebody changed it, with no event saying who or what.
- **A normalisation the digest performs must be pinned on the STORED column too.** With `setOf` no longer sorting, every unit test stayed green while retyping the same masked fields in another order rewrote the row, moved the row version and appended no event. The database CHECK is order-blind and is no backstop.
- **A form must not default to its most restricted option.** The kind vocabulary is ordered `manual-upload, versioned-file, read-only-api`, so `OPTIONS[0]` opened every create form on the restricted kind — showing a restriction banner to somebody who had chosen nothing, and making two browser assertions true before the selection they were testing.
- **Playwright restarts its worker after a test failure, which runs `afterAll` early.** A later test then sees a cleaned database and fails for a reason that has nothing to do with it. Read the FIRST failure in a run; the ones after it may be its shadow.
- **A story that repeats another's shape inherits its defects.** Four of Story 1.7's findings were Story 1.6 defects found only because the same code was written twice. Fix them in the story that finds them.
- **A manifest keyed by a NORMALIZED value must refuse duplicates, not take the last one.** `CREDENTIAL_CAPABILITIES` trimmed each key and then `Map.set` it, so `{"prod":"write-capable"," prod":"read-only"}` yielded `prod -> read-only` — a later entry silently replacing an explicit write-capable declaration, and registration input is trimmed too, so `prod` was then accepted as PROVEN read-only. Inclusion uses the separately persisted Run dates without rewriting approved plan bytes. Indeterminate values remain rows and prevent readiness even when another predicate would exclude the row.
- **Population Evidence requires private S3 deployment configuration.** Worker startup requires EVIDENCE_S3_ENDPOINT, EVIDENCE_S3_REGION, EVIDENCE_S3_BUCKET, EVIDENCE_S3_ACCESS_KEY_ID and EVIDENCE_S3_SECRET_ACCESS_KEY. Optional EVIDENCE_S3_FORCE_PATH_STYLE supports compatible stores. This story provisions no bucket or credentials; the file store is test-only.
- **Worker browser fixtures must supply every required backend.** `tests/fixtures/s3-server.ts` provides an isolated HTTP object store to the actual worker and AWS SDK. Keep this wiring in older worker journeys too; injecting a handler or file store alone does not verify the production composition root.
- **Scope notification assertions to their Procedure.** A reused throwaway database can contain valid notices from earlier journeys. Match the test's unique Procedure as well as the notification kind; never clear unrelated notices to satisfy a global inbox assertion.
- **Reconcile response metadata as well as independent declarations.** Schema version, representation and ordered schema must agree. Use a closed API envelope so alternate/nested continuation markers cannot accidentally become a complete extraction. A Northstar cover's published HMAC is a synthetic integrity convention, not production authentication.
- **Preserve a bounded bad response before reporting failed checks.** Unsupported media and malformed declaration strings must not turn useful source bytes into a retry-only error. Fetch exposes decoded bytes; compressed Content-Length describes different bytes. Primary data is bounded at 16 MiB and declaration HTTP bodies at 1 MiB. Chunk UTF-8/hex encoding and CSV parsing; per-byte arrays and per-character concatenation amplify memory at the documented limit.
- **Exercise actual recovery interleavings.** Hold an old attempt, take over its expired lease, then release both success and failure paths; check revision ownership and unchanged events. The browser restart test kills the actual worker after envelope storage, expires only its persisted lease, restarts the process and checks stable Evidence. Merely constructing a new repository does not prove worker restart behavior.
- **A ready checkpoint still verifies Evidence on job redelivery.** Check both registered digests without rewriting objects. Do not describe this as ongoing tamper monitoring. Recovery handles each Run's error independently and stops scheduling the rest of its selected batch on shutdown. Completion rechecks the original overall execution deadline; each audit check records its own outcome.
- **A stale-claim test must keep the replacement claim active.** Hold attempt two in acquisition while releasing attempt one's success or failure. If attempt two has already completed, the status guard alone rejects the old result and the test does not prove revision ownership. Assert unchanged checkpoint/events before releasing the replacement.

### Adapter extraction and Reference Sources (added with Story 3.3)

- **The classification reads bytes that were already frozen, and needs no contract change.** `makePlan` emits one `extract-adapter` Session Step per non-agent-driven Target in authored order, and `inputs.targets[].contract.kind` is frozen beside it. `classifyPlanTargets` in `packages/domain/src/runs/execution.ts` reads only those two, so no action kind is added, `semantics()` does not move, and every ACTIVE version stays executable. Recorded as interpreter semantics in `docs/contracts/executable-plan-v1.md` and in full in `docs/contracts/adapter-extraction-v1.md`.
- **The spec's kind names were the POPULATION SOURCE vocabulary; the frozen bytes are the TARGET SYSTEM one.** Story 3.3's Boundaries say `read-only-api` is adapter-acquired and `versioned-file`/`manual-upload` are Reference Sources. A Target System registration's `kind` is `web | desktop | api | versioned-file` (`TARGET_SYSTEM_KINDS`), and `manual-upload` is not one of them. The implemented rule therefore is: `api` → one Work Item, `versioned-file` → a Reference Source Session Step and no Work Item, `web`/`desktop` → the stage refuses the plan. Refused, never skipped: skipping would let a Run conclude about a system nothing read. In practice such a plan never arrives, because its first Session Step is `create-workspace` and population acquisition already refuses that.
- **A credential value must have nowhere to live.** `ResolvedCredential` has `reference` and `authorize(headers)` and NO field holding the token; `resolvedCredential` closes over it, so `JSON.stringify` yields the reference alone and no checkpoint, audit payload, Timeline event, queue job, log field, Evidence artifact or error message has anywhere to pick it up from. Containment by shape, not by discipline — the same lesson `CredentialCapabilityReport` learned, one layer along.
- **"Audited by reference" cannot mean putting the reference in the payload.** `FORBIDDEN_PAYLOAD_KEYS` in `audit-event.ts` refuses `credentialref`, `credentialreference` and `credref` outright, so a `credentialRef` payload key throws. The retrieval event names the Target System instead; its frozen `credentialReferences` entry is in the plan the Run already points at. Check that list before adding any payload key that sounds credential-shaped.
- **`CredentialResolver` is a NEW port, not a widened `CredentialProvider`.** `describe` proves a reference read-only at registration time and has exactly two fields so the web can hold its result. A resolver returns something usable and is composed only by the worker, through `@intellifin/infrastructure/credentials`; `no-credential-resolver-in-web` and `no-adapter-extraction-in-web` fail `pnpm boundaries` on any import from `apps/web`, in both the `src` and the `dist` spelling.
- **`CREDENTIAL_TOKENS` is the worker's alone, and an ambiguous manifest is refused whole.** Two keys that trim to one reference reject the entire manifest — the `parseCredentialCapabilities` rule, for the same fail-open reason. The shape parser lives in `config.ts`, not in the resolver, so validating it at boot does not drag the resolver into the barrel the web imports. In production a non-empty value on any process but the worker refuses to start; outside production it is allowed, because one environment file is routinely shared and the web has no code path that reads it.
- **An adapter-acquired Target System's frozen allowed origin IS its extraction location.** Either the collection itself, or the system's read-only service index (`{service, synthetic, access: "read-only", endpoints[]}` — a closed shape, so a collection response can never be mistaken for one), from which the adapter follows exactly ONE entry, only inside the same origin, matched on a path boundary. That is what makes the registrations `scripts/seed-northstar.mts` writes (`http://host/accessgate`) executable without a path being guessed.
- **The RoleMatrix CSV carries a leading `entry` ordinal, and it had to.** The dataset declares `AMBIGUOUS_DUAL` twice with different permissions; flattened to `role,permission` those four rows union to `{CREATE_PAYMENT, RELEASE_PAYMENT, VIEW_PAYMENT}`, which CONTAINS a prohibited pair — so the account the expectations require to be Unevaluated (`p-2-sod-conflicts.json` case D5-c) would have been reported as an Exception. A boundary an artifact never had cannot be recovered downstream. The ordinal is generated by `uv run fixtures/northstar/generate.py` from the dataset's entry positions and the cover sheet's digest is recomputed over the new served bytes; `apps/northstar/src/fixtures.test.ts` recomputes both independently in TypeScript.
- **A duplicate population key is ONE Observation.** `run_observation` is unique on `(work_item_id, population_record_key)`, so a second row would be silently dropped and the reported count would disagree with the stored one. `buildAdapterObservations` deduplicates and reports `duplicate-record-keys:N` as the Work Item's diagnostic; the duplicate stays an Evidence Quality Gate event for Story 3.4. A record with no usable key produces NO Observation and is counted as `unkeyed-records:N` — inventing a key would fabricate coverage, and fewer Observations than included records is the safe direction.
- **The Run deadline starts with the FIRST POPULATION CLAIM and this stage inherits it.** `run_execution.run_started_at` is copied from `population_execution.started_at` on the first claim and never restarted, so a second stage cannot buy a Run another hour. Exhausting it is INCONCLUSIVE, not RUN_FAILED.
- **A Session Step failure is RUN_FAILED; a Work Item failure never stops the Run.** Addendum §E. A Work Item gets its bounded cycle plus the owner's automatic second (2026-09-05), so eight attempts, and then FAILED with a diagnostic while the next Work Item still runs. An unresolvable credential fails its item on the FIRST attempt: retrying a reference nobody declared eight times against a live system proves nothing.
- **The extraction stage does not propagate its retry to the queue.** A redelivery makes `acquirePopulation` re-verify its Evidence and can consume one of that stage's four durable attempts, so a transient extraction failure would spend the population's budget. It writes a `RETRY` checkpoint and the extraction recovery sweep — its own read, `PostgresAdapterExecutionRepository.recoverableRunIds`, because the population sweep stops selecting a Run once it is `POPULATION_READY` — picks it up.
- **Evidence rows are written before the Step or Work Item that names them.** `run_session_step.evidence_id` and `run_work_item.evidence_id` are real foreign keys, and `run_session_step_acquired` additionally forbids an ACQUIRED step with a null one — which also means a test's cleanup must delete steps and items BEFORE the Evidence they name.
- **`packages/application` has `lib: ["ES2024"]` and no host types at all.** `Headers` and `TextDecoder` do not typecheck there — that absence is the compiler-enforced half of AD-11. `CredentialHeaderSink` is a structural `{set(name, value)}`, and a test that needs to read bytes uses the domain's `decodePopulationUtf8`.
- **A fake clock plus an inherited deadline is a trap.** Every test in `execute-adapter-steps.test.ts` initially terminated at the claim with `run-time-limit`, because the fixed clock was four days after the population `startedAt` the fake supplied. When a stage inherits a durable deadline, the fixture has to be inside it.

### Observation registration (added with Story 3.4)

- **`registerObservations` is the ONE write path to `run_observation`, and the seam has no bypass.** `AdapterExecutionContext` EXTENDS `ObservationRegistrationContext` rather than owning a `saveObservations` of its own, so there is no reachable write that skips the digest, the coverage rule, the per-Observation checks or the event that records them — the containment `PostgresIdentityUnitOfWork` gives the identity commands, one layer along. The whole contract is `docs/contracts/observation-registration-v1.md`.
- **The Observation digest is SHA-256 over the RFC 8785 canonical JSON of the thirteen §B.1 wire keys, through the shared `canonical-json.ts`.** Written key by key, never a spread. It covers NOTHING operational — no attempt counter, lease, revision, row version, coverage state or registration time — because those move for reasons that have nothing to do with what was observed, and a digest that moved with them would make an untouched row look tampered with. `tests/fixtures/observation-digest-golden.json` is produced by `uv run scripts/make-observation-digest-golden.py` with Python `rfc8785` + `hashlib`, envelopes written out by hand; the unit test asserts `producer` starts with `Python`.
- **`observationId` is DERIVED, never minted** — RFC 9562 §5.8 UUIDv8 over a SHA-256 of `[workItemId, populationRecordKey]`. `run_observation` is unique on that pair, so a minted UUIDv7 would make every redelivery produce a different record, a different digest and orphaned check/evaluation rows: idempotency and tamper-detection would be indistinguishable. Two parts, not concatenated, so `("a","bc")` and `("ab","c")` are different Observations.
- **A stored row and its digest column are two things, and both have to be read.** An edit to a row does NOT touch its digest column, so comparing a fresh batch against that column alone finds them in agreement and sees nothing. `readObservations` returns the record rebuilt from the columns; registration recomputes its digest (`observation-integrity` on a disagreement) and only then compares it with the batch's (`digest-mismatch`). The first integration attempt at this passed for the wrong reason and had to be rewritten.
- **A refusal is thrown, so the transaction rolls back — the Evidence row, the Work Item and the Step Execution with it.** Same lesson as Stories 1.5–1.7. `ObservationRegistrationError` maps to the `observation-registration-refused` diagnostic and is TERMINAL on the first attempt: the same bytes make the same batch, so retrying it eight times against a live system proves nothing (the `credential-unresolved` rule).
- **`item.observations` is set before the commit that stores them, so a failed attempt must restore it.** Otherwise a rolled-back batch leaves the Work Item reporting Observations that are not there.
- **Honest absence has three legs and the third is the extraction envelope.** `parseExtractionRows` now returns `complete`: the response declares itself `complete`, its `returned` count equals the rows it carries, and its envelope holds no key outside the closed set. An open envelope lets an alternate continuation marker (`next`, `cursor`, a name nobody thought of) pass unnoticed, turning "this record is not in the system" into "this record is not on the page I happened to read". An unknown key does not fail the parse — the bytes are still what the Target System answered and are still frozen as Evidence — it makes the extraction not provably complete, so every absence from it is `UNINSPECTED`.
- **There is ONE closed collection envelope, `COLLECTION_ENVELOPE_KEYS` in `packages/domain/src/runs/population.ts`.** Story 3.2's `complete-extraction` check had it first, inline; Story 3.4 needed the same list and wrote a second one — which diverged immediately, on `synthetic`, the NFR-13 marker EVERY Northstar response carries. Every unit and integration fixture agreed with the new copy because the fixtures were written beside it, so all three suites were green while the real served bytes were judged incomplete. Only `population.spec.ts`, which runs the real worker against the real synthetic system, could see it — four and a half minutes in. Two copies agree on every value anybody thinks to try, and a fixture for a served response must carry the keys the server really sends. `tests/unit/collection-envelope.test.ts` is that check in one second: it calls the real Northstar handler and asserts every key it emits is in the list, so a key added to `collection()` fails there and not in a Run.
- **The absence proof is compared against an EXPECTED list the caller builds from the population record.** `adapterSearchKeys` returns every declared lookup column, not just the first: P-1 declares `employee_id` AND `full_name`, so an adapter that indexed one of them has not proven a record absent and the record stays `UNINSPECTED`. A declared key the record does not carry as a non-empty string gets the empty string, which no derived query key can equal.
- **`coverage` is three-valued, and `AMBIGUOUS` is not `COVERED`.** §H's per-record coverage counts `found ∈ {true, false}` only, so calling an ambiguous match covered would be a lie in exactly the place the Gate reads.
- **"An uninspected record is never Compliant" is a foreign key, not a rule in a command.** `run_observation_evaluation` carries the coverage state, held to the Observation's by a composite FK over `(observation_id, coverage)` (which needs a unique index on those two columns), under `CHECK (value <> 'COMPLIANT' OR coverage = 'COVERED')`. Claiming `COVERED` in the evaluation row does not help: the pair has to exist in `run_observation`. The command refuses first so the caller gets a named refusal rather than a constraint violation.
- **`required-evidence` must not require an attribute another Target System supplies.** `plan.observations` is the UNION across every Target System of the Procedure: P-3 declares `amount` and `processed_time`, which live in the population and not in the approvals system, so a check requiring every declared attribute of one adapter Observation FAILS a correct Run. It was written that way first and every suite stayed green, because a failing check is recorded rather than refused — the P-3 integration test passed with `attribute-missing` stored on every Observation. The check judges what the Observation carries: linked Evidence `REGISTERED`, every grounding linked, every carried attribute grounded. Per-record coverage is the Run-level Gate's question (3.8), and it needs to know which system supplies which field, which the frozen plan does not say.
- **A `PASS` never carries a diagnostic and a `FAIL` always does**, in `observationChecks` and in the `run_observation_check` CHECK alike. A passing check with a reason attached reads as a finding to everything downstream; a failing one with none is a finding nobody can act on. The corroboration seam's verdict is normalized to that rule rather than trusted.
- **`Date.parse` ROLLS OVER an impossible calendar date instead of refusing it.** `Date.parse('2026-02-30T00:00:00Z')` is 2026-03-02 — a two-day shift by the one function whose whole promise is that it never shifts one. `normalizeObservedAt` does the arithmetic itself with `setUTCFullYear` (not `Date.UTC`, which maps a two-digit year into the 1900s) and re-renders the fields to compare them. `observed_at_source` keeps the source text verbatim; registration refuses a source that does not normalize to the record's `observedAt`.
- **The two seams are REQUIRED dependencies, not optional ones.** `NO_CORROBORATION` and `NO_EVALUATION` are the explicit "not yet judged" the worker composes. Optional seams defaulted in the command would let a composition root register every attribute as unjudged forever with nothing saying so. Corroboration runs BEFORE the digest, because §B.1 sets corroboration at registration and a value written afterwards would leave every row disagreeing with its own digest; it must therefore be deterministic over the stored snapshot, or a redelivery reads as an integrity failure.
- **An evaluation's `confidence` is a DECIMAL STRING.** It is compared against the frozen `agentJudgedThreshold`, which Story 2.4 stores as a decimal string; two representations of one quantity is one representation too many. `UNEVALUATED` is a VALUE and never an origin.
- **Generation 20 adds three NOT NULL columns to `run_observation` with no backfill, on purpose.** A digest is SHA-256 over RFC 8785 canonical JSON and SQL has no canonicalizer, so there is nothing honest to backfill one with. Generation 19 is unreleased, so the table is empty in CI and in production; in a developer database the ALTER fails loudly with "column contains null values" and the fix is `DELETE FROM run_observation`. **The statement ORDER in that migration is load-bearing** — drizzle-kit emits `CREATE UNIQUE INDEX` last, and the composite FK needs it first, so it is moved up by hand.
- **An assertion that reads a column the query never selected cannot fail.** `expect(String(item!.diagnostic ?? '')).not.toContain('extraction-incomplete')` read `undefined` from a `SELECT` that omitted `diagnostic`, so it stayed green against a build whose closed envelope did not name `synthetic` and judged every real extraction partial — the exact defect the assertion was written to catch. `?? ''` and `String(...)` are what turned a missing column into a passing test; assert the value, not a substring of a coalesced one.
- **A cleanup that does not know about a new table takes the whole file's cleanup with it.** `run_observation_check` and `run_observation_evaluation` name their Observation with a real foreign key, so `DELETE FROM run_observation` now throws unless they go first. `tests/e2e/population.spec.ts`'s `afterAll` did not, so every row that file created survived and `procedures.spec.ts`'s empty-list test failed for a reason that was not its own — the "read the FIRST failure, the ones after it may be its shadow" rule, once more.
- **A batch is one transaction whatever its size**; only the STATEMENTS are chunked (500 rows), in order. `OBSERVATION_LIMITS.batch` equals `POPULATION_LIMITS.rows` and is a refusal, not a truncation. The stated cost of the event carrying every digest is that a batch at the cap writes a large immutable payload.

### Sealed Evidence packages (added with Story 3.5)

- **An Evidence id is a NAME, not a mint.** `evidenceIdFor({runId, kind, scope})` in `packages/domain/src/runs/evidence.ts` is a UUIDv8 over the idempotency key `evidence-v1:<runId>:<kind>:<scope>`, and `evidenceObjectKeys` derives the object keys from the same three values — the object keys Stories 3.2 and 3.3 already wrote, spelled in one place at last. A retried production after a crash therefore re-derives its reservation instead of minting a second object beside the first, exactly as `observationIdFor` makes a redelivered Observation batch byte-identical. `scope` is the FROZEN Session Step id; the Run-level population uses `''`, and a scope on it is refused.
- **Reserve, upload, verify, register — one implementation, in `packages/application/src/runs/evidence-package.ts`.** Both producers wrote the sequence by hand and the two copies had already diverged: the acquisition envelope was uploaded and then compared against the copy still in memory, which proves the process has not corrupted itself and nothing about what the store holds. `freezeArtifact` verifies availability, size and SHA-256 against the bytes just sent AND against any digest a previous attempt registered; `verifyRegisteredArtifact` is the resume check.
- **`SealPackage` is the ONLY thing that abandons a reservation.** `PostgresPopulationRepository.save` derived `ABANDONED` from a TERMINAL checkpoint and the adapter Work Item abandoned its own row on exhaustion; both meant the seal found nothing open and the Result listed no abandonment — the exact defect the story exists to prevent. A failed Work Item now leaves its reservation OPEN while the Run continues, which is true.
- **Sealing abandons BEFORE it judges, and before it inserts.** Completeness is judged over the artifacts as they will be, or a package seals on a reservation the same transaction is about to abandon. The insert order is also what makes the "Evidence frozen after the seal" trigger safe as an immediate trigger.
- **`required` is a flag on a RESERVATION, not a checklist of kinds a Template could have.** A Run that failed before it ever reserved a Reference Source is not incomplete for an artifact nobody asked for. `population` and `reference-source` are required; `adapter-extraction` is NOT — a failed Work Item is already `INCONCLUSIVE` at the Run-level Gate, and saying it again as an incomplete package would mean no INCONCLUSIVE Run could ever hold a complete one.
- **Generation 21 is the first migration in this repository with triggers, and that is deliberate.** Three of its four rules span rows, which no CHECK can express: a Run may not reach a terminal state without a `run_evidence_package` row (a DEFERRED constraint trigger on `audit_run` — the forcing function behind "seal on EVERY terminal transition", so a branch that forgets fails to commit rather than shipping an unsealed Run); a `SEALED` package may not exist while a required artifact is unregistered; and a sealed package freezes its Run's Evidence rows and can never be UPDATEd. DELETE is still allowed, because removing a whole Run is what test teardown does and is a different question from rewriting an outcome.
- **A test that drives a Run to a terminal state by raw SQL must seal it first.** `tests/integration/runs.test.ts` and `tests/e2e/runs.spec.ts` each have a `terminate()` helper that inserts a `SEALED` package over zero artifacts and then updates the state. Two statements, because postgres.js autocommits each one and the deferred trigger fires at the end of the second.
- **A teardown that deletes `audit_run` must delete `run_evidence_package` and `run_evidence_integrity` first.** Both carry a real foreign key. A teardown that fails leaves ACTIVE `procedure_version` rows behind, and the next run of `immutable-versions.test.ts` then fails inside `listActiveVersions` on somebody else's leftovers — three integration failures that look like defects and are pollution.
- **A mismatch during the Run is `RUN_FAILED`; the same mismatch after it changes nothing.** `verifySealedPackage` refuses a Run that is not terminal, and the `SealedPackageContext` it is handed has no writer for a Run state, a seal or an Evidence row — so "changes no state" is a property of what it can reach rather than of what it remembers not to do. A store that cannot be READ is not proof of tampering and is reported to the caller, never written into the chain as an integrity event.
- **`S3EvidenceStore.putIfAbsent` now reads first.** An object already at the key is reconciled with no write sent at all, so immutability no longer rests entirely on the backend honouring `IfNoneMatch: '*'`; the header covers only the window between that read and the write, which a leased claim already makes rare. The residual race — two writers landing between one's read and its write, on a backend that ignores the header — is still there and is written down rather than claimed away.
- **The population reservation addresses TWO objects under ONE row.** The raw bytes and the acquisition envelope are fetched, verified and registered together and neither means anything without the other, so `evidenceObjectKeys` returns both in a fixed order (`[0]` raw, `[1]` envelope) and `population_evidence` stays one row. The envelope's SIZE was never stored, so a post-Run verification checks it by digest alone: `expectedSize` is nullable through the domain, the port and the column, because a fabricated size would put a number nobody measured into an immutable chain.
- **`integrity` is not an audit event family.** The nine families are closed; a post-Run mismatch is `failure.evidence-integrity` and the seal is `lifecycle.evidence-package-sealed`. Inventing a tenth family in a story that does not own the vocabulary would be a schema change smuggled in as a string.

### Corroboration against the stored Structural Snapshot (added with Story 3.6)

- **The corroboration seam is not a dependency any more, and that is the point.** Story 3.4 left `NO_CORROBORATION` as an injected `AdapterExecutionDependencies` field; `executeAdapterSteps` now builds a `snapshotCorroboration` over the bytes `freezeArtifact` just read back and proved identical to what was uploaded, at the ONE `registerObservations` call site. The stage that froze the artifact is the stage that re-reads it, so no composition root can register an adapter Observation as unjudged forever. `NO_CORROBORATION` stays for a producer with no snapshot; the worker no longer names it. The whole rule is `docs/contracts/structural-snapshot-v1.md`.
- **`packages/domain/src/runs/structural-snapshot.ts` is the ONE extractor, and it does no I/O at all.** Bytes in, verdict out. Corroboration runs INSIDE the registration transaction (so a fetch would hold PostgreSQL open across a network call) and BEFORE the digest (so a verdict that could move between two reads would make a redelivery read as an integrity failure). Its only reachable input is the `Uint8Array` it was handed.
- **`web_tree` and `desktop_tree` are unimplemented BY NAME.** `corroboration-unsupported`, and the check FAILS. A substrate that fell through to "matched" for a snapshot nobody read would be the exact defect this story exists to remove. The substrate comes from the media type registration recorded beside the digest, so it is a property of the frozen artifact rather than a guess about its content.
- **One locator grammar for both implemented substrates: `$.<collection>[<index>].<field>`** — the shape the adapter already writes. Neither name segment may contain `.`, `[` or `]`, so the parse is unique; the index carries no leading zero, because `[07]` and `[7]` would otherwise be two spellings of one cell; and a `sheet`'s collection segment is exactly `rows`, because a free name would let two defensible extractors disagree about whether `$.rows[0].role` or `$.role-matrix[0].role` addresses the one table a sheet has. A `sheet` is parsed by `parsePopulationCsv` — the same RFC 4180 parser the population uses, marker line and all — so a cell address means one thing in this product and not two.
- **`matched` has six conjuncts, not two.** The locator parses AND resolves, the re-read label is the declared one, the re-read value equals `originalValue` as RFC 8785 canonical bytes, `extractedText` is the text of that value, and `normalizedValue` is the value or its UTC normalization. Canonical bytes are what keep `"007"`, `"7"` and `7` three different things. An attribute with NO grounding is judged `null`, not `contradictory`: it was never captured, `required-evidence` already says so, and there is nothing to contradict.
- **"Nothing could read it" and "it read differently" are different words.** An unsupported substrate or an unavailable/unreadable snapshot leaves every verdict `null` and FAILS the check (`corroboration-unsupported` / `corroboration-unavailable`); only a real disagreement writes `contradictory`. Marking an unread attribute contradictory would accuse an Observation of something nobody checked.
- **`normalizeObservationValue` and `groundedText` moved into `packages/domain/src/runs/observation.ts`.** The capture writes them and the corroboration re-derives them, so two copies would accuse a correct capture of contradicting itself on the first value nobody tried. `normalizeObservationValue` now goes through `normalizeObservedAt` rather than `Date.parse`, which ROLLS OVER an impossible calendar date instead of refusing it — the same trap, in the value the digest freezes rather than in `observedAt`.
- **`ObservationCorroborationVerdict` carries the identity in its OWN slot.** §B.1 lets a declared attribute share the identity's name, and the two are grounded at different locators; the Story 3.4 name-keyed map would have given one of them the other's verdict. Latent then, reachable now.
- **Generation 22: the rollup IS the derivation, and the FK widens to carry it.** `run_observation.corroboration` (`MATCHED`/`CONTRADICTORY`/`UNJUDGED`) is pinned to its own `identity`/`attributes` jsonb by a CHECK built out of `jsonb_path_exists` (the two-argument form is IMMUTABLE, so it is legal in a CHECK), and a second CHECK pins the per-attribute verdict vocabulary inside the jsonb. `run_observation_evaluation` carries the rollup too and the composite foreign key becomes `(observation_id, coverage, corroboration)` with `CHECK (value <> 'COMPLIANT' OR corroboration <> 'CONTRADICTORY')` — so "a record its own snapshot contradicts is never Compliant" is a foreign key, the Story 3.4 shape one column along. **`CREATE UNIQUE INDEX` has to be moved above the `ADD CONSTRAINT ... FOREIGN KEY`** drizzle-kit emits after it, and both backfills have to run before it, since adding a foreign key validates every existing row.
- **Unlike generation 20's digest, this column HAS an honest backfill and gets one.** A digest is SHA-256 over canonical JSON and SQL has no canonicalizer; a rollup is derived from columns that are already there, so the migration computes exactly what the CHECK then requires. `UNJUDGED` for a row registered before anything corroborated is what it is.
- **`tests/fixtures/snapshot-extraction-golden.json` is produced by `uv run scripts/make-snapshot-extraction-golden.py`** with Python `csv`, `json`, `datetime` and PyPI `rfc8785` — an independent locator parser, an independent CSV and JSON read, and an independent UTC normalization. The unit test asserts `producer` starts with `Python`. Its `sheet` vectors are the REAL `fixtures/northstar/generated/role-matrix.csv`, and the test requires the fixture to still hold that file's bytes, `entry` ordinal included.
- **An integration test for a hand-built batch needs population keys DISJOINT from the extraction.** `run_observation` is unique on `(work_item_id, population_record_key)`, so the adapter's own Observations take every key its population names; `DISJOINT_POPULATION` leaves the extraction rows free for a batch that grounds into them deliberately.
- **A value contradiction hides an identity mismatch.** `corroborateObservation` runs the identity-key comparison only when the identity attribute itself re-read faithfully, so a case meant to prove `identity-mismatch` must ground a real cell and bind it to the wrong population record — not record the wrong value at the right locator, which fails earlier as `value-contradicted`.

### Deterministic evaluation and Exceptions (added with Story 3.7)

- **There is one rules engine and Story 3.7 did not write it.** `evaluateComplianceRecord` in `packages/domain/src/procedures/plan-compiler.ts` already implements the approval and permission-pair rules, the closed applicability grammar, the exact decimal comparisons and the conservative evidence handling, over the conditions the Version FROZE. `packages/domain/src/runs/evaluation.ts` wires an Observation into it and maps the answer onto §B.1's shape; the reduction is the same `reduceComplianceEvaluations`. The whole rule is `docs/contracts/deterministic-evaluation-v1.md`.
- **The evaluation seam is built by the stage, not injected into it — the Story 3.6 lesson, one story along.** `ruleEvaluation` needs the frozen plan, the frozen included population and the Reference Source bytes this Run's own Session Steps froze; a composition root holds none of the three, so a seam it supplied could only ever be `NO_EVALUATION`. `AdapterExecutionDependencies` therefore lost `evaluation` and gained `exceptions`, the fingerprint key as a port.
- **A rule may read only the Template's DECLARED Observation fields.** P-2's `username` and P-3's `memo` are the seeded prompt-like strings; a value no rule can read is a value no rule can be steered by. The population supplies the base (P-3's `amount`, `currency` and `processed_time` live there and not in the approvals system) and the Observation's grounded attributes win. An `ambiguous` match gets NO boolean reading of `found`, so a condition naming it is `missing or invalid Observation field found` rather than quietly false.
- **A record key the included population carries TWICE resolves to `null`, never to one of the rows.** P-3's TX-500008 is 210,000.00 in one row and 215,000.00 in the other, and first-wins, last-wins and a union each answer a question the population cannot answer. `null` makes the record ambiguous, which is Unevaluated. P-2's AG-1007 is the same trap seen from the other side: the extraction carries it twice too, so the match is `ambiguous` as well.
- **A role expansion is a LIST of entries and the `entry` ordinal is the boundary.** The RoleMatrix declares `AMBIGUOUS_DUAL` twice with different permissions; merging them yields `CREATE_PAYMENT + RELEASE_PAYMENT`, a prohibited pair, and a confident Control Failure where the contract requires Unevaluated. Every read failure is `NO_ROLE_EXPANSION` (`incomplete role expansion`, therefore Unevaluated): a role expanded from half a file is indistinguishable from a role with fewer permissions, and the second reads as Compliant. Exactly one artifact must be readable as one — zero is incomplete and so is two.
- **The per-record Gate outcome outranks the rule verdict, through the evidence facts and not a second rule.** `observationEvidenceFacts` sets `complete: false` when ANY per-Observation check failed, and `evaluateComplianceRecord` then records every condition `UNEVALUATED` — including one the rule would have called an Exception. An Exception raised on a record whose identity did not corroborate is a finding about a record nobody has established the identity of.
- **`UNSUPPORTABLE_COMPLIANT` is a second lock on a door the evidence facts already close, and it never turns.** A COMPLIANT on a record that is not `COVERED`, or one its own snapshot contradicts, is REFUSED by `registerObservations` and by the composite foreign key — which rolls the whole batch, the Work Item and the Step Execution back. Degrading an outcome is the right failure; destroying a Run is not. Because the branch is unreachable while the two agree, `evaluation.test.ts` asserts the AGREEMENT over every coverage x corroboration rather than the branch.
- **Every row this evaluator writes carries origin `RULE` and no `rationale`.** Including one that records an Agent-Judged condition as Unevaluated: the origin says which evaluator wrote the row, and the deterministic one did. A free-text rationale is where retrieved content gets quoted back as the reason for an outcome — exactly what the seeded memos exist to catch. A rule's reason is its diagnostics.
- **A non-applicable condition stores COMPLIANT and says why.** Compiler 1 gives it that value and the record's evaluation is the compiler's fixed reduction over these values, so a second reduction here would be a second engine. `CONDITION_NOT_APPLICABLE` in the diagnostic is what lets Story 3.8's count of APPLICABLE conditions exclude it: a row saying only `COMPLIANT` is indistinguishable from a rule that was evaluated and passed.
- **The Exception is created by the FIRST `EXCEPTION` evaluation, in that transaction.** `exceptionIdFor(runId, observationId)` is a derived UUIDv8, never minted, so a redelivery reaches the row it already wrote; a unique index on `observation_id` and `ON CONFLICT DO NOTHING` say the same thing below the command. The fingerprint is HMAC-SHA-256 over the canonical JSON of five keys and the RUN IS DELIBERATELY ABSENT: a fingerprint identifies the FINDING, so the same control failure recurring next month is recognisable as the same one.
- **`EXCEPTION_FINGERPRINT_KEY` is the worker's alone, and without it adapter execution is DISABLED by name.** The `CREDENTIAL_TOKENS` trade, one line along: refusing to boot would stop plan derivation, notification delivery and the liveness row for a stage that could not run anyway, and an Exception with no fingerprint is a permanent row nobody can later check. The key reaches the evaluator as an `ExceptionFingerprinter` port with NO field holding it — `JSON.stringify` yields `{"keyId":"..."}` — the `ResolvedCredential` containment.
- **`sha256HexOfBytes` is now a rendering of `sha256Bytes`, and `hmacSha256Hex` chains the same function.** One implementation, so the hex form and the keyed form cannot disagree about what SHA-256 is. `tests/unit/sha256.test.ts` checks the HMAC against `node:crypto` at the three key lengths where RFC 2104 padding hides (shorter than a block, exactly a block, longer) and against the published RFC 4231 vectors.
- **Generation 23's two rules are triggers because neither is a CHECK: an Exception can never be UPDATEd, and never DELETEd while its Observation stands.** Removing a whole Observation is a different act — it takes the record and its digest with it, and the registration event still names both — so `run_exception.observation_id` cascades and the DEFERRED constraint trigger passes at commit. That is also why no teardown needed changing: `DELETE FROM run_observation` already carries the Exceptions away.
- **`verifyRegisteredArtifact` is now the verdict of `readRegisteredArtifact`.** A resumed Run needs both that the stored Reference Source is what it froze and what it SAYS; two functions that each read and compared would be two answers to one question.
- **P-3's TX-500007 has no per-record evaluation, and that is correct.** It carries no `processed_time`, so the frozen inclusion rule cannot place it in or out of the Period: Story 3.2 marks the row INDETERMINATE, it never reaches an Observation, and the `complete-inclusion` population Gate is what makes the Run Inconclusive. `tests/unit/golden-evaluation.test.ts` pins that this is the ONLY expectation case reached that way, and asserts the row's disposition and reason, so the branch cannot quietly absorb a record that simply went missing.
- **The golden expectations are asserted twice: in one second and in a real Run.** `tests/unit/golden-evaluation.test.ts` drives both populations through the production pipeline (inclusion rule, `buildAdapterObservations`, `snapshotCorroboration`, `ruleEvaluation`, `registerObservations`) and `tests/e2e/population.spec.ts` asserts every P-2 case again against the real worker, the real Northstar service and a real database. Both read the expectation files OFF DISK; runtime code never imports them (AD-12). Verified by mutation: first-wins on a duplicate population key fails P-3 D5, and merging RoleMatrix entries by role fails P-2 D5-c.

### The Run-level Evidence Quality Gate and limit mapping (added with Story 3.8)

- **`GATE_CHECKS` is a TRANSCRIPTION of addendum §H, and something compares it with the addendum.** Twenty rows, in the addendum's own order; `tests/unit/gate-vocabulary.test.ts` reads the §H table off disk and asserts the row set, the order, and — per row — whether `GATE_DIAGNOSTIC_STATE` can produce each state that row's "Failure outcome" cell names. A list asserted against a copy of itself proves only that it equals itself, and this one decides whether an audit Run may conclude. The whole rule is `docs/contracts/run-level-gate-v1.md`.
- **A row's failure outcome belongs to its DIAGNOSTIC, not to the row.** §H gives population acquisition and pagination/extraction completeness BOTH outcomes, so a table keyed by row loses half the addendum. `GATE_DIAGNOSTIC_STATE` is keyed by diagnostic and exhaustive by type. One failure genuinely lands on two rows: a Session Step whose `extract-adapter` acquisition failed is both `session-step-failed` (workspace access) and `acquisition-unavailable` (extraction completeness), and §H says so twice.
- **The Gate CONSUMES what earlier stories recorded; it never re-judges it.** Six rows roll up `run_observation_check` (Stories 3.4 and 3.6) and seven route `population_snapshot.checks` (Story 3.2) onto their §H row. `POPULATION_CHECK_DIAGNOSTIC` is `Record<PopulationCheckName, …>` and the observation table is `Record<ObservationCheckName, …>`, so a check added upstream without a §H row does not compile. That is why `POPULATION_CHECK_NAMES` became a closed union the reconciler is typed against.
- **`AdapterExecutionContext` EXTENDS `RunGateContext`, so there is no injection point.** The stage that finishes the last Work Item already holds everything the Gate needs; a composition root cannot omit or switch it off. Stories 3.6 and 3.7 both REMOVED such a seam rather than leave one, and a Gate that could be left out is a Run that concludes without one.
- **The Gate rows, every Timeline event, the terminal Run state and the Evidence package seal commit in ONE transaction.** `sealIfTerminal` runs inside it, and generation 21's deferred trigger refuses a Run reaching a terminal state without a package row — so a branch that forgot would fail to commit rather than ship an unsealed Run.
- **A Gate failure is never repaired by re-running a check, and the ROWS alone do not prove it.** `saveGateChecks` uses `ON CONFLICT DO NOTHING`, so removing the `readGateChecks` early return leaves the rows identical and appends a SECOND full set of Timeline events. The idempotency test asserts the event count as well; generation 24 refuses an `UPDATE` to `run_gate_check` in a trigger. `DELETE` stays permitted — removing a Run takes its Gate rows with it, which is a different act from rewriting one row's outcome.
- **`population_snapshot.generated_at` (generation 24) exists because §H's freshness row has to name WHICH way a snapshot is unfit.** Stale, future-dated and unknown are three different statements and an auditor acts differently on each; the stored pass/failed boolean beside it can say none of them. It is nullable, NOT backfilled and never defaulted to `now()`: a row an earlier build wrote reads as "unknown", which §H makes `INCONCLUSIVE` — the fail-closed direction — and a fabricated generation time would put a fact nobody measured into an audit conclusion.
- **`run_gate_check` keeps an EXACT `total` beside a bounded sample of at most 32 identities.** A Run over a hundred thousand records has to be able to commit its own conclusion, and the rows go onto the Result and into an immutable event. `tallyGateFindings` takes an ITERABLE so a producer walking the population never holds a hundred thousand findings.
- **The closed diagnostic vocabulary is pinned inside the jsonb by CONTAINMENT.** `diagnostics <@ '[...]'::jsonb` refuses a number, an object and an undeclared spelling alike, in one expression rather than thirty-three `jsonb_path_exists` clauses. The integration test asserts BOTH directions: an invented diagnostic is refused, and every diagnostic the domain has is storable — a CHECK that quietly refused a finding the Gate can produce would be found by nothing else.
- **`CANCELED` is never produced by a timeout or a limit.** `RUN_STOP_STATES` is `['INCONCLUSIVE','RUN_FAILED']` and a test walks every cause. `CANCELED` is reserved for a person cancelling (Story 3.10), and the §E.1 outcome rules read that state to decide what a human may do next.
- **The frozen limits are READ from the plan, never restated.** `exhaustedRunLimit(usage, plan.limits)` checks Step Executions, elapsed time and tokens in §E.1's order. Step Executions count ATTEMPTS — `startStepExecution` increments the counter where a Step Execution actually starts, so no branch can start one without spending the limit for it — and the count on the claim comes from `run_step_execution`, so attempts an earlier claim made before a restart still count. Tokens are 0 for every Run of this epic because the adapter path calls no model; the counter is passed anyway so the agent epic fills it rather than adding a limit that was never mapped.
- **`adapterAttemptBudget` is `(retriesPerStep + 1) x 2` and `sessionStepAttemptBudget` is `x 1`.** The owner's 2026-09-05 second cycle exists to let a Run CONTINUE past a failed unit; §E maps a Run-level Session Step's failure to `RUN_FAILED`, so a second cycle there buys nothing. Both are derived from the plan's own `retriesPerStep`.
- **A 401 or a 403 is `denied`, not `transport` — and a redirect is `scope`.** They used to land in `!response.ok`, so a Work Item was retried three times against a system that would go on refusing and the only durable record that the platform had been told no was a transport count. `PopulationAcquisitionError` gained `'denied'` and `'scope'`; both are terminal for the unit AND for the Run, and `stopRun` appends the `security.action-denied` event from `runStopFor(cause).securityEvent` rather than at each call site.
- **Duplicate Source primary keys are counted over EVERY parsed row, not only the included ones.** §H says "No duplicate Source primary key", and a duplicate inclusion happened to filter out is still two Source rows claiming one identity.
- **The required evaluation fields are the Template's declared Observation fields INTERSECTED with the binding's declared schema.** `COMPLIANCE_OBSERVATION_FIELDS` is the union across the population and every Target System — P-3 declares `decision`, which lives in the approvals system — so requiring all of them of a population row would fail a correct Run. The `required-evidence` trap of observation registration v1, one layer along.
- **The §H unnamed-value row matches §B's OWN sentence, `rule does not name value <v>`, and not the missing-field one.** `RULE_DOES_NOT_NAME_VALUE` is exported from `plan-compiler.ts` beside `MISSING_OBSERVATION_FIELD` and matched by the repository, because a retyped copy of either inside a SQL `LIKE` drifts silently the first time the wording changes. They are two DIFFERENT defects: a value the condition met and does not name, versus a value it names and could not read. Read the FIRST failure, and check the teardown when an unrelated suite starts failing on counts.

Every Story 3.5 test that mutates `run_evidence` after `executeAdapterSteps` therefore needs `unseal()` first — generation 21 freezes a sealed Run's Evidence — and every resume test needs `audit_run.state` set back to `RUNNING` beside `run_execution.status='RETRY'`, because the stage refuses to claim a Run that is not RUNNING and the two commit together in real life.

### What a Run concludes: three repairs (2026-09-05)

- **§H's per-record coverage rule is per TEMPLATE, and it is now machine-readable.** The row says coverage is "computed over Observations per the Template's coverage rule (§C)", and the four §C rules genuinely differ: P-3 says "found or proven absent" in as many words and P-1's C1 makes a proven absence the Compliant finding, while P-2 requires every account to "appear in the extraction with a grounded role list" and P-4 requires each parameter grounded in the page. The generic `found ∈ {true, false}` reading was applied to all four, and under P-2 that made an account absent from its own Target System `COVERED` → its `found = true` applicability NOT APPLICABLE → compiler 1's COMPLIANT for a non-applicable condition. **An account whose permissions nothing could read passed its own control**, and `p-2-sod-conflicts.json` case D6 names that state Inconclusive. `TEMPLATE_COVERAGE_RULES` in `templates.ts` is `must-appear` / `found-or-proven-absent`, `observationCoverage` takes it as a REQUIRED input, and `must-appear` + `found = 'false'` is `UNINSPECTED` — which the generation-20 composite foreign key already makes impossible to call Compliant, so nothing downstream needed changing and no migration was needed.
- **It is a coverage rule, not a new check.** `search-completeness` still says whether the ADAPTER LOOKED and still PASSES for an honest P-2 absence; whether this Template accepts an absence as coverage is a different question. A new check name would have meant a new `run_observation_check` CHECK and a migration for nothing.
- **`templateCoverageRule` fails closed to `must-appear`.** The id comes from a frozen plan, so it is arbitrary text; `must-appear` can only DEGRADE coverage. It uses `Array.prototype.find`, not an object index — the `Object.hasOwn` trap, sixth occurrence.
- **A test of the honest-absence legs must run under a `found-or-proven-absent` Template.** Under `must-appear` every absence is `UNINSPECTED` whatever it proves, so the three legs decide nothing and the test would pass against an implementation that had none of them. `register-observations.test.ts` and the integration honest/dishonest test both moved to P-3; the P-2 case is a separate test that names the rule it exercises.
- **An unaccounted population row no longer ends the Run at acquisition.** `POPULATION_CHECKS_DECIDED_AT_THE_GATE` in `population.ts` holds exactly `complete-inclusion`, and `ready` excludes it. §H's early-stop row is "Population acquisition", which is about acquisition FAILING; an indeterminate row is not that, and §E decides the Gate rows "after the last Work Item". The OUTCOME is unchanged — the failing check is on the checkpoint summary, reaches the Run-level Gate and makes the Run `INCONCLUSIVE` on `count-reconciliation-inclusion` — only WHEN it is decided, and what exists by then. Every other check still stops the Run where it did: those are about whether the BYTES are what they claim to be, and a Run that cannot trust its bytes has nothing to execute over. Before this, twelve of P-3's thirteen named golden cases could not be produced by a Run at all: `TX-500007` has no `processed_time`, so one indeterminate row ended every P-3 Run before its first Work Item, and only a hand-built unit test that called `includePopulation` itself and filtered to `included` ever saw them. `tests/e2e/population.spec.ts` now runs the P-3 journey against the real worker and the real synthetic ApproveNow service.
- **`complete-inclusion` is RECOMPUTED at the Gate, not routed.** `runGateChecks` already derives `rows-unaccounted` from the counts — deliberately, because the stored boolean is what a defect in the counting would have written — so routing the boolean as well reported ONE unaccounted row as two. `RECOMPUTED_POPULATION_CHECKS` in `gate.ts` skips it in the routing loop; `total` is exact and is what the Result shows. Unreachable before, because a failing `complete-inclusion` never reached the Gate.
- **An evaluation port answers about EVERY Observation it was given, exactly once.** `registerObservations` refuses anything else as `evaluation-shape`. A short answer leaves those Observations with no evaluation row, which downstream is indistinguishable from a frozen plan whose Compliance Rule this build cannot recompile — §H's condition-completeness row reports both as `condition-evaluation-missing` and nothing says which happened. "Nothing judged this" is therefore a result carrying NO evaluations, never an omitted result: `NO_EVALUATION` and `ruleEvaluation`'s unknown-Template branch both map every subject. Returning `[]` there would now REFUSE the batch, and a refusal rolls the Work Item and its Step Execution back — destroying a Run where §H only wanted to degrade it.
- **A §H row must never PASS for want of a fact.** `condition-completeness` counted gaps against `plan?.inputs.complianceConditions.length ?? 0`, so a Run whose plan could not be read compared every Observation against zero conditions, found no gaps and PASSED. `runRunLevelGate` fails that row outright when `plan === null`. The adapter stage refuses such a plan as `unsupported-frozen-plan` before its first Work Item, so this is the second lock on that door — and `run-gate.test.ts` exists because that makes the branch unreachable from the composed stage, and a branch nothing exercises is a branch that can be inverted silently.
- **An unqualified `LIMIT 1` over "the rows in this state" picks a row a later change can add to.** `adapter-execution.test.ts` selected `WHERE coverage='UNINSPECTED' LIMIT 1` to get the row it had just inserted by raw SQL; the P-2 coverage rule made a real Observation UNINSPECTED too, and the test's next raw insert collided with that Observation's real check outcomes. Scope such a select to the key the test itself wrote, and order it.

### Evidence integrity repairs (2026-09-06)

- **An adapter extraction's Evidence scope carries the ATTEMPT; a Reference Source's does not.** A Work Item freezes its response BEFORE it parses it and keeps failed bytes registered — both deliberate, because a response that is not a declared collection is still what the Target System answered. What follows is that a second attempt has different bytes to freeze, and `putIfAbsent` reconciles rather than overwrites: with a key derived from the step id alone, every retry read back attempt 1's object, found a digest that did not match, and died with `extraction-integrity-failed` against a system that was answering perfectly well. One gateway maintenance page therefore spent all eight attempts and cost the Run that system's coverage, and **the owner's two bounded retry cycles were decorative for exactly the transient failure they exist for.** `adapterExtractionScope(stepId, attempt)` puts the attempt in the name. A crash does not advance the attempt counter, so a resumed attempt still derives its own key and reconciles with its own bytes — Story 3.5's idempotency is unchanged. The number is durable before any upload: the reservation commit persists `item.attempts` before `extract` is called. `item.evidenceId` is deliberately NOT carried in as the prior id — it names the previous attempt's row, and adopting it would give that row this attempt's object key and lose the earlier artifact. A Session Step is acquired without being parsed, so its retries only run when nothing was frozen at all, and it keeps a scope with no attempt in it.
- **A failed Work Item therefore leaves EIGHT abandoned reservations, not one.** That is the truthful record of eight attempts, and `adapter-extraction` is not `required`, so the package still seals. The test asserts they are DISTINCT: eight entries naming one artifact would mean the key never varied.
- **A Reference Source is refused at acquisition unless its media type is one the extractor can actually read.** `acquireReference` accepted any 2xx body, so an HTML proxy error page became a REGISTERED required artifact and the package sealed while the Run page printed "Sealed. Every artifact this Run required is registered and verified" over it — the one claim Story 3.5 exists to make true, wrong. The list is `isReferenceSourceMediaType` in the DOMAIN, the same list the snapshot extractor reads, so acquisition refuses exactly what nothing could read rather than a second list that drifts. The Session Step then fails, §E makes that `RUN_FAILED`, and the abandoned reservation makes the package INCOMPLETE, which is true. A cover-sheet path is NOT guessed from the artifact's name: reading a guarantee out of a URL's spelling makes it a naming convention anybody can satisfy by typing.
- **`observed_at_source` is re-derived at the integrity recomputation.** It sits outside the thirteen hashed wire keys and has no CHECK, so an `UPDATE` rewriting it left the digest matching and a redelivered batch reported the row as already registered. `readObservations` selects it and registration requires `normalizeObservedAt(stored.observedAtSource).observedAt === stored.record.observedAt`. It is NOT added to the digest: that envelope is §B.1's and is pinned by an independently produced Python vector.
- **`verifySealedPackage` finally has a caller.** `startEvidenceIntegritySweep` is a bounded page per tick over terminal Runs with its own keyset read, the shape `startPopulationRecovery` and the probe runner use. It is inside the `evidence.enabled` branch, so an unprovisioned bucket disables it rather than crashing the worker (the PR 23 lesson), and it imports NOTHING — it takes its ports — so adding it to the barrel the web reads does not drag the storage client into the web bundle.
- **Never edit a shell script while it is executing.** bash reads a script by BYTE OFFSET as it goes, so inserting text mid-run leaves the running shell resuming at an offset that is now the middle of a different line. The gate script was edited during a run and every step after that point executed garbage — printing a `command not found`, then a stream of `FAIL` lines that were fragments of the edit rather than results. The steps BEFORE the edit are still real; everything after it must be discarded and the run repeated. Same class as editing source during a browser run, which crashes Turbopack and produces failures that are not product defects.
- **A verification script must exit non-zero when any step fails.** `gates.sh` echoed `FAIL` per step and then exited 0 regardless, so a background completion notice read as an all-clear over a failing gate. It tracks a flag and ends with `GATE PASSED` or `GATE FAILED`. An absent signal that looks like "fine" is the defect shape this project keeps finding; a harness is not exempt from it.
- **A test that waits on a queue row and then reads an in-process counter has a race.** `plan-recovery.test.ts` waited for the delivery row to reach `completed` and then asserted both handler invocations had been observed; the row goes final slightly before the last invocation is visible here, so it read `[1]` about one run in three. Wait on BOTH facts. A regression where the retry never happens still fails, on the timeout message rather than on a bare count mismatch.

### The sealed Result and the System Outcome (added with Story 3.9)

- **`OUTCOME_ROWS` is a TRANSCRIPTION of addendum §E.1 and something compares it with the addendum.** Seven rows, in the addendum's own order, with the first, second and fourth cells verbatim; `tests/unit/outcome-rules.test.ts` reads §E.1 off disk and compares them cell by cell. The rows apply IN ORDER and the FIRST match wins, which is why they are an array of predicates walked with `Array.prototype.find` rather than a chain of conditionals anybody can reorder without noticing — and why there is no lookup keyed by anything a caller supplies. The whole rule is `docs/contracts/run-result-v1.md`.
- **A passed Gate is NECESSARY and never sufficient for Pass.** The Gate asks whether the Evidence supports a conclusion; the outcome asks what that conclusion is, and deriving either from the other is the mistake this story exists to prevent. `gatePassed` is read from the twenty `run_gate_check` rows Story 3.8 wrote and the evaluation facts from the `run_observation_evaluation` rows Story 3.7 wrote. FEWER than twenty rows is not a pass either: a Run stopped by a limit or a denial never reached the Gate, and an unrun Gate is not a passed Gate — the `snapshot-generation-unknown` reading. `run_result_pass_requires_gate` says the necessary half where nothing can route around it.
- **Rows 4 to 7 do not repeat "Gate passes" in their predicates, because row 3 already did.** By the time the walk reaches row 4 the Gate passed; writing the precondition into each of the four as well would be four copies of one fact, and the copies are what drift. The consequence is that the ORDER carries the precondition, which `outcome-rules.test.ts` asserts by driving a Run whose Gate failed and every evaluation fact is set.
- **Row 5's "(by human rejection)" is PROVENANCE, not a predicate.** Made one, an `UNEVALUATED` of any other origin would match no row at all and fall through to Pass, whose own cell requires "every condition on every record Compliant". Read as provenance the table is TOTAL — rows 1 to 3 cover every terminal state but COMPLETED, rows 4 to 7 partition (pending) × (Exception) × (Unevaluated) — and `systemOutcome` THROWS rather than defaulting, because a default would quietly become the eighth row.
- **All seven rows ship even though this epic can reach five.** Epic 3 produces evaluations of origin `RULE` only, so nothing is ever `pending` and row 4 cannot fire; row 5 fires by human rejection, which is Epic 6. Both are tested with a constructed state, in `complete-run.test.ts` and against PostgreSQL — the whole §E vocabulary landing at once, exactly as `procedure_version.state` and `GATE_CHECKS` did.
- **`sealed` means FINAL, and only `PENDING_CONFIRMATION` is not.** §E's "a Result seals when the Gate has passed and no evaluation is pending" describes the COMPLETED path, the only one where sealing is a decision rather than a consequence; a Canceled, Run Failed or Gate-failed Run has nothing left to decide and its outcome can never change either, so calling those unsealed would say the opposite. `version` is 1 on write, and generation 25's trigger permits exactly ONE update — the sealing of a pending Result, which must seal and must raise the version by one — and refuses every other, including a re-statement of what is already there.
- **`completeRun` replaces `sealIfTerminal` at every terminal transition, in both producers.** `RunResultContext` is extended by `RunGateContext` and by `PopulationExecutionContext`, so there is no seam a composition root could omit — the Stories 3.6/3.7/3.8 discipline. `audit_run_requires_result` is a DEFERRED constraint trigger beside generation 21's: a branch that reaches a terminal state without a Result fails to commit rather than shipping a Run nobody can read.
- **The order inside the transaction is load-bearing: decide, move the Run state, seal the package, publish, write.** Row 5 is §E's `COMPLETED → INCONCLUSIVE` "only at Result sealing", so the state is taken BEFORE the package is sealed — otherwise `run_evidence_package.run_state` records a state the Run left in the same transaction.
- **`requiredTargetSystems` and `includedRecordKeys` moved into `gate.ts`.** The Result's coverage counts and the §H per-record coverage row are the SAME matrix, decided by the same `coverageFindings`; two derivations of its axes would be two answers to one question, and here the divergence would be a Result that disagrees with the Gate it reports. `OBSERVATION_CHECK_DIAGNOSTIC` is exported from `run-gate.ts` for the same reason — the golden reconciliation rolls the per-Observation checks up through the command's own table rather than a retyped copy.
- **`TEMPLATE_RESULT_FIELDS` is transcribed from each §C block and only names fields the Template DECLARES.** A Result that published every attribute would print the seeded prompt-like strings beside the outcome they must never influence; P-2's prohibited pairs come from the compiled rules' own diagnostics rather than from a second role expansion. `outcome-rules.test.ts` reads §C off disk for each of the four.
- **A test whose Gate failure and Exception land on the SAME record proves nothing about the order.** Duplicating the conflicted account made its population row ambiguous, so the evaluator recorded UNEVALUATED and the Exception the ordering test needed had never existed. The duplicate has to be a different account: the Run then really produces both, and row 3 winning over row 6 is observable.
- **The `gatePassed` fact is redundant with the Run state for every producer that exists, and is kept anyway.** `runRunLevelGate` sets INCONCLUSIVE/RUN_FAILED before completing, so hard-coding `gatePassed: true` passed every integration test; only `complete-run.test.ts`'s constructed nineteen-row Gate caught it. It is the second lock on the door `run_result_pass_requires_gate` holds, and it is tested where it is reachable.
- **The Result's coverage COUNTS are over included rows; its named sample is deduplicated.** A population that carries one key twice is two included rows and one record, and `coverageFindings` produces a finding per row — so `inspected + uninspected` equals `population.included` and an auditor can check the arithmetic, while naming the record twice would read as two records. The Gate's own `affected` lists dedup for the same reason.
- **A file that raises real Exceptions cannot `DELETE FROM run_exception` in its teardown.** Generation 23 refuses to delete an Exception while its Observation exists, and `run_exception` cascades from `run_observation` — so removing the Observation is what carries it away. `run-gate.test.ts` deletes it first and never notices, because nothing there raises one.
- **Every test file that writes Run rows must now delete `run_result` before `audit_run`** — the fourth table to join that list after `run_gate_check`, `run_evidence_package` and `run_evidence_integrity`. A teardown that does not know about a new table takes the whole file's cleanup with it, and the next run of an unrelated suite then fails on somebody else's leftovers: 162 Runs and 1097 queue jobs survived one failed run here and pushed two Evidence packages off the first page of a keyset read.

### Cancelling a Run and starting a linked rerun (added with Story 3.10)

- **Who performs the `CANCELED` transition depends on who owns the Run, and the domain owns the table.** `RUN_CANCEL_TRANSITIONS` in `packages/domain/src/runs/run.ts` maps each of the four ACTIVE states to `command` or `worker`. A `QUEUED`, `PAUSED` or `AWAITING_AUDITOR` Run has no process holding it, so `CancelRun` transitions it AND removes its dispatch job in one transaction — leaving a "cancel requested" marker on a queued Run would mean it is cancelled only if a worker eventually collects it, which is exactly backwards. A `RUNNING` Run is held under a lease by a worker mid-transaction, so the request is recorded and honoured at the boundary that worker already commits at. All four states are in the table although this epic produces two, for the same reason the whole §E state vocabulary and the whole §E.1 outcome table landed at once.
- **A cancellation IS a terminal transition, so it goes through `completeRun` like every other one.** `performCancellation` in `packages/application/src/runs/cancel-run.ts` is the ONE place a Run becomes `CANCELED` — the web command and both worker stages reach it — and it writes the state, the Timeline event and the Result together. Generation 25's deferred trigger refuses a Run reaching a terminal state without a Result, so a bare state update fails to commit rather than shipping a Run nobody can read.
- **`CANCELED` is the one §E.1 outcome that does not require the Gate to have run.** A Run cancelled while queued has no Gate rows, no Observations and no Evidence beyond what it had already frozen; its Result records `gatePassed: false` with `checks: 0`, and the `canceled` row is first in the table and matches on the state alone. Do not fabricate a Gate result to make it look like the others.
- **Cancel-meets-claim is decided by the Run's own row lock, not by the configuration advisory lock.** `PostgresRunCancellationRepository` takes `SELECT … FOR UPDATE` on `audit_run`, exactly as the two worker-stage repositories do, and deliberately does NOT take `pg_advisory_xact_lock(20428, 1)`: cancelling reads no Active version set, and serializing every cancellation against every configuration write buys nothing. Removing the `FOR UPDATE` makes the held-open race test fail.
- **A held-open race test must close its transaction in the `finally`.** The first version released the claim in a `finally` and awaited it AFTER the try/finally, so a failed poll left the transaction dangling; the file's own cleanup then raced a commit still in flight and left a Run, a Procedure and five versions behind for a later suite to trip over. `release()` and `await claim` both go inside the finally.
- **A rerun is a new Run, and its Procedure and period come from the PREDECESSOR.** `rerunRun` shares `createRun` with `initiateRun`, so there is ONE creation path: the request-token idempotency check, the active-Run check, the period owner resolved AFRESH, the insert under the partial unique index, the dispatch and the first Timeline event. Resolving the owner afresh is what makes a rerun after a handover run the version that NOW owns the period, and is why a period with no `ACTIVE` owner is refused with initiation's own `NO_RUN_OWNER` sentence. A caller that could supply the Procedure could point a "rerun" at a different one entirely.
- **There is deliberately NO `run.rerun` gated action.** A rerun starts a Run, so it is gated by `run.initiate`. `roles.test.ts` asserts all 24 actions against all 3 roles, so a synonym would break a completeness claim about a table transcribed from EXPERIENCE.md character for character.
- **The rerun link is on the NEW Run's row and its own chain, and nowhere else.** No event is appended to the predecessor's aggregate, which turns "the predecessor is unchanged" from a promise into a check: `tests/integration/cancel-run.test.ts` compares the whole `audit_run` row, the whole `run_result` row and `audit_event_heads` before and after.
- **The cancellation marker is four columns written whole or not at all, and the FIRST request wins.** `(a IS NULL) = (b IS NULL)` is boolean = boolean and is never NULL, so unlike a comparison of the values a NULL CHECK cannot pass here. `DrizzleRunRepository.requestCancellation` guards on the marker still being absent, so a second person cannot overwrite the requester, the time or the reason the Canceled Run Detail then reports; the command refuses the duplicate above it and appends nothing.
- **Neither surface collects a reason, and the domain supplies the sentence.** EXPERIENCE.md's confirmation table puts cancel AND rerun under the ROUTINE weight, which restates the consequence and has no rationale field — unlike the "routine with rationale" weight a Result rejection gets. The commands accept an optional bounded reason for a caller that has one; the web passes none, and `RUN_CANCELED_DEFAULT_REASON` / `RUN_RERUN_DEFAULT_REASON` are what is recorded. A blank reason would read as a missing fact rather than as an absent note.
- **A cancellation observed at a boundary beats a limit observed at the same boundary.** The check runs before the limit and attempt computation in both stages, so a Run whose deadline had passed and whose cancellation had been requested records `CANCELED`. That is not a limit producing `CANCELED` — a person did, while the Run was still `RUNNING` and nothing had yet recorded the limit — and it is the only ordering that keeps a named actor on the outcome. The reserved-state rule is unchanged: `RUN_STOP_STATES` still holds `INCONCLUSIVE` and `RUN_FAILED` only, and a test walks every stop cause.
- **A unit already running finishes and commits; only the NEXT one is refused.** `canceledAtBoundary()` runs before each Session Step and each Work Item, inside the same guarded transaction that writes, so the Evidence, Step Execution and Observations of the unit in flight all survive. The Run-level Gate is deliberately NOT gated by it: a Run that has finished its last Work Item should conclude rather than be cancelled.
- **A partial reservation is left OPEN and named by the seal.** Nothing on the cancellation path touches an Evidence row or an artifact; `SealPackage` is the one thing that abandons a reservation, so a Run cancelled mid-acquisition seals INCOMPLETE and lists the reservation as abandoned rather than dropping it.
- **`predecessor_run_id` is a self-referencing foreign key, so a teardown deletes successors first.** `DELETE FROM audit_run WHERE procedure_id=… AND predecessor_run_id IS NOT NULL` before the unqualified delete, in `tests/integration/cancel-run.test.ts` and `tests/e2e/runs.spec.ts` alike.
- **Never `DELETE FROM audit_events WHERE actor_id = …` in a teardown.** A `security.denied` event has no aggregate and is chained under `platform`, so removing one takes a row out of the MIDDLE of that chain and `procedures.test.ts`'s "the platform chain is verifiable" test then fails for a reason that is not its own. Leave the denial where it is; `audit_events` has no key to the user anyway.
- **The Cancel and Rerun controls require JavaScript, deliberately, and say when they are ready.** EXPERIENCE.md requires a focus-trapping confirmation dialog on every mutating action, which cannot exist without script — the same trade the administration mutations record — and both fail SAFE: a click before hydration does nothing and the Run is visibly unchanged. `RunLifecycleActions` carries `data-client-ready` on `#run-lifecycle` and the browser journey asserts it before every click. Without that, the click after the full-document navigation to the successor Run passed standalone and hung for the whole 120-second timeout inside the full suite.

Inventing a sentence there would put the platform's words where the contract already has some.

A stale `dist` showed up as the exact defect the new code had just fixed.

#### What Story 3.11 found with no data behind it

Both are stated on the surface in words rather than shown as a dash, and both are named here so a later story fixes the WRITE rather than the read:

- **No Evidence table records a capture time.** FR-31 requires "Work Item, Target System, Step, capture method, capture time in UTC, and integrity digest" on every Evidence item, and neither `run_evidence` nor `population_evidence` has a column for one. For a Reference Source and an adapter extraction the instant is recovered from the `run_step_execution` that uploaded, verified and registered the bytes; for the POPULATION artifact nothing recorded one at all and the card says `Capture time was not recorded.` The capture METHOD is derived from the kind, which is a stored value and not a guess.
- **The independently declared record count is never persisted.** `reconcilePopulation` checks `d['count']` and stores only the `declared-count` pass/fail boolean; the declaration itself is frozen inside the acquisition envelope in object storage, which this surface may not read (`no-evidence-store-in-web`). The Population reconciliation states the §H verdict and says where the declaration is, rather than printing a number nobody stored.
- **The Review tab and the Review column have no data by DESIGN, not by omission.** Epic 3 creates no Auditor Review; Story 6.3 submits one. The column shows the contract's absent marker with a spoken sentence beside it, and the tab says what would appear — never a "Draft" badge for a review nobody started, which is Story 2.1's "Active version: Draft" defect in a new place.
- **An accessibility scan that runs while a navigation is committing reads the wrong document.** `executable-plan.spec.ts` failed once in a full-suite run with a `document-title` violation of `serious` impact, and passed alone immediately afterwards — the shape of a race, not of a missing title, and the page does set one. The preview POLLS, so a refresh can be in flight when the scan starts, and a navigation that has begun committing briefly has no `<title>`. Assert the title BEFORE scanning: it removes the race and asserts something true, since WCAG 2.4.2 requires that title and the page has it. Do not re-run an intermittent accessibility failure until it is green — the gate has no allowlist precisely so that a violation cannot be waved through, and an intermittent one is the kind that ships.

### Signing in, and the gate every Tool Action passes (added with Story 4.2)

- **The action gate is at the port's CALL SITE, in `packages/application`, and never in the provider adapter.** `performToolAction` in `execute-agent-steps.ts` is the ONLY path from a stage to `BrowserExecution.perform`, and it calls `authorizeToolAction` first. An adapter that enforced its own allowlist would make the guarantee a property of that adapter, and the whole point of the port is that the provider can be replaced — the containment shape this codebase uses everywhere: the correct path is the only reachable one. The workspace's request interception is the SECOND boundary, not the first, and `tests/integration/agent-execution.test.ts` calls the port DIRECTLY with the gate bypassed to prove the second one exists. The whole rule is `docs/contracts/tool-action-v1.md`.
- **The gate reads the VERSION's frozen bytes and nothing else**, in a fixed order: the action against `permitted_actions`, then the destination against `allowed_origins`, then every parameter VALUE against the Run's frozen population. First refusal wins, so one action gives one reason rather than a list a reader has to rank. A write action is not expressible — `PermittedReadAction` is eight literals and every member observes — and the membership test is `includes` over the frozen array, never an object index, because the action is request input (`Object.hasOwn`, seventh occurrence).
- **An empty `scopeValues` denies every parameter.** Fail-closed: a stage that has not put the frozen population in front of the gate has not proved a value is inside it, and "no scope" must never read as "no rule". Story 4.2's sign-in carries no parameters, so the first PRODUCTION caller of the parameter rule is the story that searches (4.5); it is exercised by unit, application and integration tests today rather than left as a branch nothing runs.
- **`withinFrozenOrigin` in `packages/domain/src/runs/tool-action.ts` is now the ONE home of "stay inside the frozen origins".** It is written over STRINGS because `packages/domain` and `packages/application` have no host types at all — the compiler-enforced half of AD-11 — so there is no `URL` there and a gate that could not ask the question would have needed a second copy of the answer. `packages/infrastructure/src/runs/origin-policy.ts` became a `URL`-shaped door onto it (`withinOrigin(o, c) => withinFrozenOrigin(o.href, c.href)`), which is safe because `URL` has already normalized the spellings a browser produces. It REFUSES a dot segment rather than resolving one: normalizing would be doing the browser's job with the browser's rules, and the two only have to disagree once.
- **`sanitizeDestination` STRIPS where `parseFrozenLocation` REFUSES, and the difference is the point.** A destination denied FOR carrying `user:pass@` must still be recorded, and recorded without them. `safeDestination` in `browser-execution.ts` is now a rendering of it, so the log and the gate cannot disagree about what a destination is.
- **`run_tool_action` is ONE table and ONE shape for both surfaces** (generation 28), because AD-6 says it in as many words: "every lookup or extraction is an Adapter Action on the Timeline with the same sanitized-action schema". `surface` is the only field that distinguishes the producers. Story 4.2 writes the `agent` rows; **the adapter path writes none yet**, and that is named rather than counted — the SHAPE is here so it is not invented twice.
- **A 401 from a Target System is `performed` with `status: 401`, not `denied`.** The action HAPPENED and the system said no, which is a different fact from a gate refusal that never left. Both are terminal, both carry `security.action-denied`, and neither is ever a transport failure: Epic 3 paid for that once. `run_tool_action_denied` is ONE CHECK — `(outcome='denied') = (denial IS NOT NULL)` — because either half alone permits a row that reads as the other.
- **`run_session_step` gained an `action` column, and the ACQUIRED constraint had to read it.** `run_session_step_acquired` required Evidence on every ACQUIRED step, which is right for a Reference Source acquisition and refuses exactly the row a successful sign-in writes: a sign-in establishes a session and freezes nothing. The constraint now says what it always meant — an ACQUIRED ACQUISITION has Evidence. The migration adds the column with a DEFAULT, backfills, and DROPs the default, because `ADD COLUMN ... NOT NULL` fails on a table that already holds rows.
- **`acquirePopulation` read `sessionSteps[0]` literally, so every agent Run was refused before anything could sign in.** The compiler emits `create-workspace` FIRST whenever a Target is agent-driven, so the population step is at index 1 in an agent plan. `populationSessionStep(plan)` is where the compiler's own ordering now lives, and it is a POSITION check rather than a search: a plan that puts the population step somewhere else is a plan this build did not compile. It also refuses a `create-workspace` step on a plan with no agent-driven Target, which is the case `classifyPlanTargets` used to catch by accident.
- **The agent phase has its OWN checkpoint (`run_agent_execution`) and its own recovery sweep**, and it does NOT propagate a retry to the queue — the Story 3.3 rule, one phase along: a redelivery re-verifies the population Evidence and spends one of that stage's four durable attempts, so a transient sign-in failure would cost a Run the budget of a stage that had already finished. The adapter sweep's read now excludes a Run whose agent phase is unfinished, or it would end a Run whose workspace and Target System were both healthy.
- **The sign-in destination is the FROZEN origin, and no path is guessed.** `allowed_origins` is a normalized set and is SORTED, so "the first" is deterministic for one frozen contract — the same rule `targetOrigin` applies on the adapter path, and a registration with several origins signs in at whichever sorts first. An integration test that added a second origin called `/elsewhere` therefore signed in THERE rather than at `/loancore`, silently; it names the second one to sort after.
- **The credential is attached by the INTERCEPTION, not by `setExtraHTTPHeaders`.** The header would otherwise ride every request the page makes until it is cleared — and the workspace's egress allowlist is the UNION of every web Target's frozen origins, so the moment a plan names two web systems the first one's credential would reach the second. It is attached only to requests inside the DESTINATION's own frozen origin, and dropped in the `finally`. Proven by mutation: removing the origin check makes the cross-origin sub-resource arrive with the header.
- **A denied SUB-RESOURCE must not fail the Tool Action.** `perform` compared the workspace's denial COUNT before and after a successful navigation and threw `scope` if it had moved — which is right for a navigation that was aborted and wrong for a page that merely referenced a font, a beacon or an image off-origin. It reported `scope` for something the platform never attempted, and one test-server change that added an `<img>` to the served page turned three passing tests red. What is checked after a SUCCESSFUL goto is where the main document ended, against the workspace's own allowlist; the denial count still distinguishes a refusal from an outage on the FAILURE path, because Chromium reports both as an aborted navigation.
- **A spent lease is not an unresolvable credential.** `unit.budget()` throws when the lease, the frozen Step timeout or the Run deadline runs out, and it is called inside the credential block — reporting that as `credential-unresolved` would name the wrong thing AND be terminal, because a reference nobody declared is not worth retrying and a deadline is a different fact.
- **The authoring warning and the execution denial are still two mechanisms.** FR-8 flags and never refuses; the gate refuses and never flags. `tests/unit/scope-widening.test.ts` proves both halves against the same fixture and builds each execution action out of the value the ADVISORY check named, so the thing the Builder flagged is provably the thing the gate refuses — without the two sharing an implementation, which is what would make a false positive block a save.
- **A Playwright spec that reads module state after another test failed reads an empty string.** Playwright restarts its worker after a failure, so `agent-sign-in.spec.ts` re-reads its Run id from the database rather than trusting a module variable — otherwise a later test fails on `''` instead of failing for its own reason.
- **The workspace row's STATUS is not assertable after the Run ends.** The worker releases the workspace in its `finally`, so a browser test that read `status = 'OPEN'` after a terminal transition was asserting a race. What is assertable is that the Run HAD one and which guarantee it was.
- **`[NAMED, NOT BUILT]` The Timeline does not render Tool Actions yet.** Story 3.11 anticipated the fourth level ("Epic 4's agent Runs and the fourth Tool Action level slot in without a rewrite") and this story writes the rows without rendering them: a surface showing agent Tool Actions beside no Adapter Actions would be worse than none, and the tab has its own accessibility gate. The data is complete; the read is a later story's.

And §E.1 row 3 sits ABOVE row 6, so a Run with three real Exceptions is still Inconclusive. ### The isolated Agent Workspace (added with Story 4.1)

- **Solari and Playwright were never alternatives, and there is ONE implementation.** Solari is a managed remote browser you drive WITH the Playwright client API: `sessions.create()` hands back a wire-protocol endpoint and `chromium.connect()` connects to it. So `PlaywrightBrowserExecution` is the only implementation of the port and where the browser runs is a composition-root choice. It uses `sessions.create()` + `chromium.connect()` rather than `solari.launch()`, because `launch()` returns a `BrowserSession` typed against the SDK's bundled **`patchright-core`** — a different package from `playwright-core`, with separately declared types that do not assign to each other. Two modes would then hold two `Browser` types, and the only ways out are a second code path or an `as`. `Session` is four strings, so nothing typed against the fork crosses the module. The whole rule is `docs/contracts/agent-workspace-v1.md`.
- **The weaker guarantee is written wherever the guarantee is claimed, and `run_workspace.mode` records which one a Run had.** `solari` is a separate managed browser with provider-side egress; `local` isolates browser STATE per Run — cookies, storage, cache, session — and does **not** isolate the worker process at all, with egress policed inside the browser rather than at the network. The acceptance text says nothing crosses between Runs: that is true of browser state and false of process memory, and a column that says which is what stops the stronger sentence covering both.
- **"Does this Run need a workspace" is a pure function of the frozen plan.** `workspaceRequirement` in `packages/domain/src/runs/execution.ts`, beside `classifyPlanTargets`: the compiler emits `create-workspace` FIRST exactly when a selected Target is web or desktop. No stored flag, because a flag could disagree with the plan the Run is executing and the plan is what an auditor reads.
- **The egress allowlist is the `web` Targets' frozen origins and NOTHING else.** A `desktop` registration's application identity (`com.northstar.ledgerdesk`) occupies the `allowed_origins` slot of the six-key envelope and is not a URL; putting it in a browser allowlist would be inert at best. A desktop-only plan therefore gets an EMPTY allowlist, under which every destination is denied — the truth about a browser with no web system to visit, and fail-closed.
- **`withinOrigin` has one home now, `packages/infrastructure/src/runs/origin-policy.ts`.** It was private to `adapter-extraction-http.ts` until the workspace interception needed the same judgement; both import it and the extraction module re-exports it so its own test keeps working. Two copies would agree on every value anybody thought to try and diverge on the first one nobody did.
- **A fragment is stripped before the comparison and a request carrying one is not denied.** `withinOrigin` refuses a non-empty hash, which is right for a location this platform CHOSE to fetch and wrong for a URL a browser handed back — a fragment never goes on the wire.
- **A WebSocket handshake is not a `route()` request.** Without `context.routeWebSocket` a page could open one to any host and the allowlist would never see it. `serviceWorkers: 'block'` for the same reason: a service worker's own fetches are invisible to `context.route`.
- **A frozen origin this build cannot parse refuses the WHOLE workspace (`policy`), never a partial allowlist.** A silently narrower allowlist is a workspace confined to less than the Version said, and it looks exactly like a Target System that was simply down.
- **A denial is a security event with the destination and no query string.** `security.action-denied`, `cause: scope-violation`, diagnostic `workspace-egress-denied`. The recorded destination is scheme, authority and path only: the chain is immutable and a query string is where a token or a signed URL lives. `denied()` keeps the exact total beside a bounded sample of 100 — the `run_gate_check` shape, because the enforcement is never bounded even when the record is. The lifecycle event's field is `deniedTotal` and not `denials`: it never resets, so a second boundary reports every refusal the workspace has had rather than the ones since the last one, and a number that reads as a delta and is a total is a number somebody will add up.
- **`SOLARI_API_KEY` absent is not a disabled duty.** Unlike `populationExecution` and `adapterExtraction`, `agentWorkspace` is never disabled: the local mode is the same code path against a locally launched Chromium, so the question is only WHICH guarantee, said once at boot by name. Provisioning still lives inside the storage branch because that is where the job handler is; the REAPER is outside it, because a deployment that lost its bucket still has workspaces to give back.
- **`await solari.close()` is REQUIRED in Node and `browser.close()` is not enough.** The client keeps a loopback proxy server open for its connection-retry path and that handle keeps the event loop alive, so a worker that closes only its browsers never exits. Same defect class as an unread `fetch` body holding a socket (Story 1.8) and a deadline's `dispose` that cleared the timer without aborting (PR 23), so it is a shutdown step in `main.ts`, not a happy-path call.
- **`Session.expiresAt` is a HARD provider deadline, not an idle window.** The SDK's `timeoutMs` is the CLIENT's HTTP timeout and has nothing to do with the browser; what ends a session is `expiresAt`, at which Solari auto-releases it, and nothing a Run does resets it. It is stored on the row, and a resumed claim past it treats the identity as GONE (`workspace-expired`) rather than as an outage. The frozen Run limits stay the authority for ending the RUN.
- **`recording: true` must be passed at session creation or the replay 404s forever**, and there is no way to enable it later. That decision is taken in Story 4.1's code and Epic 5 is what reads a replay, so the flag is threaded through now (`SOLARI_RECORDING`) even though nothing reads one yet. It is OFF by default, matching the provider: recording is metered, and turning one on is a cost decision this build must not take for a deployment. The consequence is written down rather than discovered — **a Run made before it is switched on has no replay, permanently**, so Epic 5 turns it on before the Runs whose replay it wants and cannot recover the ones behind it.
- **`proxy`, `stealth`, `captcha`, `webBotAuth` and profiles are OFF and named rather than defaulted.** `proxy: "smart"` runs an escalation ladder and swaps the egress in place when it detects a block page — the opposite of confining a Run to its frozen origins. Naming no profile is what makes every session start clean, which is exactly what per-Run isolation wants; a later "resume where the agent left off" story would be choosing to weaken it.
- **`SolariErrorCode` is five codes and they are not one class**, and it is widened with `| string`. `ConcurrencyLimitExceeded` → `capacity` (retried), `BrowserUnhealthy` → `unavailable` (retried), `FeatureRequiresPlan`/`PlanLimitExceeded` → `entitlement` (terminal), and **an unrecognised code → `refused`, terminal**: calling an unknown reason transient would retry it four times on the strength of not knowing what it is. Folding a refusal into `unavailable` would leave the only durable record saying something was unreachable — the `credential-unresolved` rule from Story 3.3.
- **`attach` returning `null` is expected, not exceptional, and the stale identity is RELEASED before a replacement is made.** A browser does not survive the process that connected to it: Solari's `wsEndpoint` is loopback-wrapped by the client, so it means nothing outside the process that created it, and the SDK has no `sessions.get`. So reattach across a worker RESTART is impossible with `@solarisdk/browser@0.1.3` and the I/O matrix's "reattach impossible" row is the honest path — release, recreate, record `workspace-reattach-failed`. Within one process a lost claim really does reattach.
- **The provider identity may be stored and named in a Timeline event; the endpoint and the key may not.** `workspace_id` is `browser.id`, opaque and NOT a capability — releasing a Solari session still needs the deployment's API key — and it is what makes a provider-side session correlatable with a Run. `WorkspaceRef` has no field for a key, a token or an endpoint, so no checkpoint, payload, log field or error message can pick one up.
- **`run_workspace` cascades from `audit_run`, unlike the four tables every teardown deletes by name.** `run_gate_check`, `run_result`, `run_evidence_package` and `run_evidence_integrity` record an OUTCOME and should not be silently removable; a workspace row is operational state, and removing a whole Run takes it along — the reading that already makes `run_exception` cascade from `run_observation`. Ten existing teardowns delete `audit_run` without knowing this table exists, and a foreign key nobody knew about does not fail its own suite: it leaves rows behind and fails an unrelated one later on a count.
- **The reaper is the third sweep of an existing shape.** Its own read (`reapableRunIds`, a keyset page ordered by Run id), ten Runs per tick, a cursor that resets on a short page, and a stop that lets the active release finish and starts none of the rest. A release is network I/O, so it cannot be a step inside the transaction that ends the Run; the worker releases in a `finally` and the reaper is the backstop for a worker that died before reaching it.
- **The one leak that cannot be closed is written down rather than claimed away.** A provider session created and the process dying before the identity is committed cannot be released by anything here: there is no name for it and the SDK offers no listing. It is bounded by the provider's own grace timer.
- **A `create-workspace` Step Execution needs a row on the Timeline to render it.** `run_step_execution` rows with `work_item_id = null` are keyed by plan step, and nothing rendered `session-1`, so the attempt would have been an invisible row. `RunTimelineRead.workspace` and the row above it in `Timeline.tsx` are what make it visible, and the mode is shown in words because `local` and `solari` are not the same guarantee.
- **A retry counter must not count a SUCCESS.** `attempts` bounded provisioning failures, but the claim incremented it on every delivery — including one that only REATTACHED to a workspace that was fine. `acquirePopulation` asks for a redelivery on any transient transport failure and has four attempts of its own, so a Run that retried its population three times arrived here four times, and the fifth delivery failed a Run whose workspace had been healthy every single time. An `OPEN` row now carries its count forward unchanged and is exempt from the limit; a failure moves it to `RETRY`, and the next claim does count. Found by reading rather than by a test, and the test that catches it drives six redeliveries.
- **A browser spec that hard-codes an address the suite parameterises asserts the wrong row.** `administration.spec.ts` located the signed-in administrator's own row by the literal `administrator@example.test` while `ACCOUNTS.administrator.email` reads `E2E_ADMIN_EMAIL`. Pointed at a differently-named administrator the locator resolved to somebody ELSE's row, whose select is correctly enabled — so the failure read as a broken self-demotion guard rather than as a wrong locator. Locate by the configured value, never by a copy of its default.
- **`pkill -f <pattern>` matches your own shell.** `pkill -f northstar` inside a command line containing the word `northstar` killed the shell running it (exit 144). The environment's own rule, met in practice.
- **`git checkout -- <file>` reverting an uncommitted fix, a second time.** Restoring `labels.ts` after a mutation test silently deleted the `workspaceModeWord` the story had just added, and the suite went green because the test file had been reverted with it. Copy the file aside and restore from the copy — the rule Story 2.1 recorded, learned again.

### The verification harness is not exempt (2026-09-06)

Four failures in one session were in the HARNESS rather than in the code under test, and every
one of them looked like a result. An absent or miscounted signal that reads as success is the
same defect class this project keeps finding in the product; the thing that checks the work has
to be held to the rule the work is.

- **A status check that greps a nested JSON body counts the wrong things.** A monitor on the
  GitHub jobs API grepped `"status": *"completed"` and reported ALL FOUR GREEN while two of the
  four jobs were still running: each job embeds a `steps[]` array whose entries carry their own
  `status`, so completed STEPS were counted as completed JOBS. Parse the job-level fields, treat
  any non-`success` conclusion as a failure, and require every job `completed` before reporting
  green. It was caught only because the answer was checked against the authoritative API before
  being acted on — the same "verify the reported figure" that catches an agent's numbers.
- **A verification script must exit non-zero when a step fails.** `gates.sh` echoed `FAIL` per
  step and then exited 0 regardless, so a background completion notice read as an all-clear over
  a failing gate. It tracks a flag now and ends `GATE PASSED` or `GATE FAILED`.
- **`pgrep -f <pattern>` matches your own shell**, so `until ! pgrep -f ...` can never exit. It
  deadlocked one agent for hours. Check once, wait a bounded time, check again, and proceed
  saying so — never an unbounded loop. Same root as the `pkill -f northstar` that killed its own
  shell.
- **A gate script needs every environment variable the app validates at STARTUP, not only the
  ones its tests read.** A browser gate that set `DATABASE_URL` but neither `SERVICE_NAME` nor
  `BETTER_AUTH_SECRET` failed with the web process printing `"Refusing to start"` and naming the
  missing key — the AD-15 startup guard working exactly as designed, read at first glance as a
  defect in the story under test.
- **`pnpm seed:identity` takes ONE account per invocation**, `--email` and `--role`, and only
  re-assigns a role for an address that already exists; it never resets a password. There is no
  bulk seed, and `SEED_PASSWORD` alone does nothing.
- **Two branches at the same schema generation are two different schemas.** While Epic 3's repair
  and Epic 4's Story 4.1 both sat at generation 27, running one branch's suite against the
  other's database would have migrated nothing and tested the wrong shape while looking fine.
  A worktree gating a different branch needs its OWN database, not just its own checkout.

### Credentials just in time, and capture suppressed while one is on the wire (added with Story 4.3)

- **"Entry" is credential USE, not typing, and that is the STRONGER guarantee.** LoanCore authenticates a GET with an `Authorization` header and has no form — every synthetic system refuses a POST above routing, and a `method="get"` form would put the credential in the URL — so there is nothing being typed to photograph. What must have nowhere to land is the request header and every artifact that could carry it: a network artifact, a Structural Snapshot, a screenshot, a frame. Settled in `epic-4-loancore-authentication-decision.md`; if a later story adds a Target System that really does have a form, the typing case JOINS this one rather than replacing it. The whole rule is `docs/contracts/credential-containment-v1.md`.
- **`ResolvedCredential` gained two METHODS and still has no field.** `redact(text)` removes every whole-value spelling; `discloses(bytes)` says whether bytes carry it. Neither returns the value and neither widens what a holder can learn — `authorize` already writes it into any sink it is handed — so `JSON.stringify` of a resolved credential is still `{"reference":"..."}` and there is nowhere for a checkpoint, payload, queue job, log field or error message to pick one up. Fifth time this codebase has made the containment-by-shape move.
- **The needle is encoded, not the haystack decoded, and the scan is over BYTES.** A screenshot is not text and `decodePopulationUtf8` throws on the first malformed sequence; a byte search reads a PNG, a PDF and a Structural Snapshot with one rule. Percent-, HTML- and JSON-escaping are the identity on `[A-Za-z0-9._~-]`, so the raw form covers them for an ordinary token; **base64 is the one that transforms everything**, and it is searched for at all three byte alignments because that is how a value sits inside a `data:` URL, an `Authorization: Basic` header or a HAR. What it does NOT catch — compressed, encrypted, re-cased, split across a line break — is written down in the module rather than claimed away: detection is a wall against the paths a capture mechanism produces, never a proof of absence.
- **A credential this build cannot scan for is never resolved at all.** `compileSecret` refuses a value under `MIN_SCANNED_SECRET` (12): a four-character "secret" matches ordinary text, so scanning for it would refuse almost every artifact, and lowering the bar would fail OPEN in the one guarantee the module exists to give. It surfaces as `credential-unresolved` — terminal, because a manifest entry does not get longer by being asked for again — and NOT at boot, so a deployment with an unscannable token still runs plan derivation, notification delivery and its heartbeat (the PR 23 lesson).
- **The guard is fed by WRAPPING the resolver, never by remembering.** `guardedCredentials(resolver)` returns a resolver whose every answer is held by a `CredentialGuard`; each stage wraps once at the top and never keeps the unwrapped one, so there is no "register this credential" step for a branch to skip. `freezeArtifact` takes the guard as a REQUIRED argument and `NO_CREDENTIALS` is the explicit "this stage has presented none" — the `NO_CORROBORATION` shape, because an optional seam defaulted inside the function would let a composition root register every artifact unscanned for ever with nothing saying so. Proven by mutation: either stage keeping its unwrapped resolver fails a named test.
- **The population stage passes `NO_CREDENTIALS` and that is the TRUTH, not a convenience.** Population acquisition runs before the sign-in and before any adapter extraction, so at the moment its bytes are frozen the Run has resolved nothing to scan for. Holding the plan's credentials there to scan for them would mean resolving a secret in a stage that must never have one.
- **The scan runs BEFORE the upload, so "nothing is stored" is literal rather than nearly true.** The object store is immutable by design and an artifact that reached it could not be taken back out. And it is a REFUSAL, never a redaction: bytes a Target System served are Evidence, and rewriting them to make them acceptable would falsify what a system answered. A platform-produced capture is redacted by its producer, through the same guard, before it gets here; one that still discloses afterwards is a redaction defect and must fail loudly rather than be quietly re-redacted.
- **`AcquisitionFailureCode` gained `credential`, and it is neither `integrity` nor `contract`.** Nothing is damaged and the system honoured its contract; what happened is that the platform may not keep what it answered with. `extraction-credential-disclosed` / `reference-credential-disclosed` are TERMINAL for the unit on the first attempt — the same bytes disclose the same credential every time (the `credential-unresolved` rule). A Work Item failure still never stops a Run: the reservation stays open, the seal abandons it, and the Gate concludes on the coverage that item never produced.
- **`BrowserToolAction` is a UNION, and that is the suppression.** The arm carrying a credential has no `capture` field at all, so a Structural Snapshot, a screenshot or a frame cannot be asked for while a credential is on the wire — it does not compile. A structural type does not CONTAIN anything, so `perform` refuses such a request at runtime too, FIRST, before the workspace is looked up: it is a fact about the REQUEST, and reporting it as `unavailable` because the browser happened to be gone would name the wrong thing. **`[NAMED, NOT BUILT]` nothing in this build captures**; `BROWSER_CAPTURE_KINDS` is the vocabulary and Story 4.4 owns the mechanism.
- **A suppression that showed as a gap would be the sign-out defect's shape.** `run_tool_action` records `capture` on EVERY row and `capture_suppression` when there is one (generation 29), pinned by ONE CHECK — `(capture='SUPPRESSED') = (capture_suppression IS NOT NULL)` — because either half alone permits a row that reads as the other. The value is DERIVED by the platform from its own request (`captureStateFor`), never reported by a provider: a fact a provider reported is a fact a provider could get wrong.
- **Generation 29 HAS an honest backfill, unlike generation 20's digest, so it gets one.** A Tool Action inside a `sign-in` Step Execution presented a credential, and that is a stored column rather than an assumption about what the code did when the migration was written: `UPDATE ... FROM run_step_execution`, then `SET NOT NULL`, then the CHECKs. Exercised against real rows in a scratch schema before it was trusted, because `ADD COLUMN ... NOT NULL` fails on a table that already holds any.
- **`sanitizeDestination` keeps the PATH, so a destination is redacted before it is recorded.** A system that puts a token in a path segment — or a redirect that does — would otherwise put a working credential into the immutable action log. Both the requested destination and the location the navigation ENDED on go through `guard.redact`. Same doctrine one step along as stripping `user:pass@`: a destination denied FOR carrying a credential must still be recorded, and recorded without it.
- **The Timeline's fourth level is rendered now, which overturns Story 4.2's deferral, deliberately.** 4.2 left Tool Actions as data because "a surface showing agent Tool Actions beside no Adapter Actions would be worse than none". 4.3's acceptance text requires the action to be VISIBLE and to say its capture was suppressed, and a data-only guarantee is not that. The adapter path still writes no rows, which is a gap already named rather than a new one. Rows collapse under the Step Executions `<details>` by default — EXPERIENCE.md's "collapsed to Work Item rows by default" — so a browser assertion has to open it, exactly as a reader does.
- **A Session Step's Timeline row said "Reference Source" for every Session Step**, which stopped being true the moment Story 4.2 wrote the first `sign-in` row. A label stating something untrue is worse than one stating nothing; `RunTimelineSessionStep` now carries the frozen `action` and `planActionWord` names it. `RunTimelineWorkItem` omits it: a Work Item's action is the plan step it belongs to, which is already `stepId`.
- **The seeded negative test is a deliberately hostile synthetic surface.** `/accessgate/credential-echo` echoes the presented `Authorization` header into its own response body — the path nobody predicts, and the one that matters — inside the same closed collection envelope every other endpoint serves, so the ONLY thing wrong with it is the disclosure. It is bound by no Procedure this repository seeds, named in no expectation file and registered by no seed script; `tests/e2e/credential-containment.spec.ts` is the only thing that points a Run at it. It invents no credential — it repeats what the caller sent — so this environment still holds none (Story 1.8's rule, unchanged).
- **Test credentials are built by the REAL factory or by the domain's own functions, never hand-stubbed.** A `{reference, authorize}` literal whose `redact` is the identity would let every containment assertion in three suites pass against a build that redacts nothing. The unit vectors go the other way: they are encoded by Node's `Buffer`, `encodeURIComponent` and `JSON.stringify` rather than by asking the module for its own forms and then looking for them.
### PR 23 review findings, second pass (applied 2026-09-06)

**The shape four of the ten share: a rule stated correctly in prose and implemented incompletely.** Two are a LIMIT applied to a read whose cardinality is not what the limit bounds; two are a capability disabled by name without disabling what depends on it. A doc comment is not an implementation, and in this codebase the comment is usually right — so when one is found, read the code beneath it as a claim to be checked rather than as an explanation of it.

- **A limit belongs to the cardinality of the READ, not to the table it starts from.** `readGateObservations` was capped at `POPULATION_LIMITS.rows`, which is exactly right one function above it — acquisition caps `population_row` at that number, so it can never bind — and wrong here, because the per-record coverage matrix is RECORDS × REQUIRED TARGET SYSTEMS. Sixty thousand records over two systems is a hundred and twenty thousand Observations and twenty thousand were dropped; a dropped `COVERED` cell reads as MISSING coverage, so a fully covered Run sealed `INCONCLUSIVE` and published coverage counts that were wrong. `GATE_OBSERVATION_LIMIT` is now `POPULATION_LIMITS.rows * TARGET_DRAFT_LIMITS.targets` and provably cannot bind, and the read is ordered on the unique index so a bound that somehow did bind would drop the same rows every time. `result-repository.test.ts` checks it against `OBSERVATION_LIMITS.batch` and the `<= 32` read out of generation 9's own CHECK on disk — never against a copy of its own definition.
- **An exact total and a bounded sample are two questions, and `LIMIT` answers only the second.** `readConditionGaps` took `rows.length` after a `LIMIT`, so a §H row's `total` was not a count at all. It is two statements now — a `count(*)` and a `LIMIT GATE_AFFECTED_LIMIT` sample — which is what `readFailedObservationChecks` and `readUnnamedValues` in the same file already did, and what `readResultFindings` does one file along. **Copy the working sibling rather than inventing a third shape.** The original defect needed more than a hundred thousand Observations to show, so the integration test pins the shape at thirty-three gaps instead: it fails against the re-merge a later edit would produce, and could not have failed against the code it replaced.
- **A capability disabled by name must also stop the work that depends on it.** The whole Run block sat inside `if (evidence.enabled)`, so with no `EVIDENCE_S3_*` the worker registered NO consumer for the `runs` queue while the web's Initiate Run action stayed enabled and went on enqueueing: every Run sat `QUEUED` for ever, with no diagnostic and no Result. One stage along was worse — `if (acquired.retry || adapter === null) return acquired;` acknowledged the job after acquisition, leaving the Run `RUNNING` at `POPULATION_READY` with its Evidence frozen and neither sweep able to select it again. The worker now ALWAYS consumes the queue and `stopUnexecutableRun` ends such a Run `RUN_FAILED` through `completeRun`, with a closed diagnostic naming the missing capability. **The web cannot make this decision** — `EVIDENCE_S3_*` and `CREDENTIAL_TOKENS` are the worker's environment — so refusing at initiation was never available; and a Run that failed for a stated reason can be acted on and rerun, while a Run that never moved cannot. The trade is that a MIXED worker pool, one process configured and one not, would let the unconfigured one fail Runs the other could run. That is not a shape `.railway/railway.ts` declares; if it ever is, the capability belongs in the queue's job routing and not in whether a consumer exists.
- **`stopUnexecutableRun` fabricates nothing.** No checkpoint is written and no Evidence reserved: for a queued Run nothing was ever attempted, and an invented reservation would make the seal list an abandonment for an artifact nobody asked for. For the `POPULATION_READY` case the checkpoint is left exactly as acquisition wrote it, because the population really was ready — what failed is the stage after it. A cancellation still wins there, because a Run that never ran earned no outcome to keep.
- **A bucket that is not there is not an object that is not there.** `isMissing` in `s3-evidence-store.ts` counted `NoSuchBucket` as absence, and S3 answers it with HTTP **404**, so removing the name alone would not have been enough — the status test had to be reached second. `read` answering `null` is what `verifySealedPackage` records as `object-missing`, so one deleted or misnamed bucket would have written a PERMANENT tamper finding, and its immutable `failure.evidence-integrity` event, against every registered artifact of every terminal Run the sweep reached. The rule was already written down one file along: *a store that cannot be READ is not proof of tampering.* Only OBJECT-level absence may answer `null`.
- **A keyset cursor naming no row must resolve to NO cursor, and the comparison must not lose precision.** The cursor was compared against a scalar subquery inline, so a valid UUID naming nothing made `(initiated_at, run_id) < NULL` — NULL for every row — and the page came back EMPTY, which is neither the first page nor an error. It is resolved in its own statement now and treated as absent when it finds nothing. **The resolved timestamp travels as TEXT and returns as `::timestamptz`**: `timestamptz` keeps microseconds and a JavaScript `Date` keeps milliseconds, so a round trip through one would truncate the cursor downward and silently skip every Run sharing that millisecond — a row on no page at all, which is the failure the total order exists to prevent. The existing test ASSERTED the empty page, three lines under a comment saying a person who edits a URL should meet page one.
- **Generation 21's DELETE exemption was right and one case too wide.** Removing a WHOLE Run is test teardown and stays permitted; deleting a `run_evidence` or `population_evidence` row while its `run_evidence_package` SURVIVES is not that — the package goes on naming an artifact whose metadata is gone, and the post-Run sweep verifies only what `readRegisteredArtifacts` returns, so nothing is read, nothing fails, no finding is recorded, and the Run page keeps printing "registered and verified". Generation 27 refuses that delete while the package row exists, and stands down once it is gone. **So the SEAL is deleted before what it sealed**, and two teardowns that had the two lines the other way round were reordered. `TG_OP` chooses `OLD` or `NEW`: a function reading `NEW.run_id` on a DELETE dereferences NULL and fails every delete, teardown included.
- **The outcome a Run EARNED beats a cancellation observed at the final boundary, and the request is never silent.** A person can ask for a Run to stop while its last Work Item runs, or while its acquisition is already failing. Honouring it at the adapter stage would throw away a complete, sealed conclusion one transaction from being written — §E.1's `canceled` row matches on the STATE alone, so twenty Gate rows would become `gatePassed: false, checks: 0` — and at the population stage it would hide WHY the Run could not conclude behind a state that says only "somebody asked". What was missing is that the committed marker was then answered by NOTHING: the person clicked Cancel, got a confirmation, and the Run said Completed. `completeRun` now appends `lifecycle.cancellation-superseded` naming the requester, the time, the reason and what happened instead. It lives THERE and not at the two call sites because every terminal transition already goes through it — which is why Story 3.10 put `performCancellation` there — so one check covers both worker stages, the web command and every path Epic 4 adds. `readCancellation` is a port on `RunResultContext` and reads on the TRANSACTION's connection: the `RunRecord` a stage carries was read at its claim, and the case this exists for is a request committed after it. The UI half already existed — `CancellationBanners` says "The Run ended before the cancellation was performed, so its own outcome stands."

It does NOT refuse a second rerun: nothing in the contract says a terminal Run has at most one successor, and inventing that rule inside a bug fix would be a product decision taken sideways.
